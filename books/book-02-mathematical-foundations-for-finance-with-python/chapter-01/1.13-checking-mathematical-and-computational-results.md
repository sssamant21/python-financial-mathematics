## 1.13.1 Learning Objectives

After this section, you should be able to check a result against its mathematical specification, distinguish exact equality from an approximate comparison, construct independent reference calculations, use boundary cases and invariants, and report the scope of computational evidence. You should also be able to diagnose a failed check without immediately changing the expected answer or relaxing its tolerance.

Section 1.12 translated formulas into Python. Here we ask what would justify trusting the result. A successful execution establishes that the interpreter completed the selected operations. It does not establish that those operations answer the intended question.

We revisit the small compound-growth model and use both correct and deliberately incorrect candidate results. The goal is to produce evidence that a check can detect a meaningful mistake, rather than merely demonstrate a passing run.

## 1.13.2 Check the Specification Before the Number

Begin with the stated model:

\[
A=P(1+r)^n,\qquad P\geq0,\quad r>-1,\quad n\in\{0,1,2,\ldots\}.
\]

Here \(r\) is the effective decimal rate per period and \(n\) counts matching periods. The principal and final balance share one currency and scale. There are no contributions, withdrawals, fees, or rounding steps inside this hypothetical model.

A reported balance can disagree with this expression for several reasons: a mathematical derivation error, a code translation error, a wrong input convention, or an external data problem. Checking only the final digits cannot distinguish them.

For example, treating `5` as a decimal rate means 500%, while treating it as a percent quotation means 5%. Both calculations may be internally consistent. Before inspecting arithmetic, confirm the period, rate representation, timing, and quantity being requested. The conventions in Section 1.10 are part of the specification, not optional metadata.

## 1.13.3 Build a Hand-Solvable Reference Case

Choose inputs with a transparent result. With \(P=100\), \(r=0.10\), and \(n=2\), the first period ends at 110 and the second at 121. This can be checked without a large dataset or a specialized library.

Now inspect a candidate \(\widehat A=110\). It is nonnegative and greater than principal, so it looks plausible for a positive rate. Yet it accounts for only one period. Its signed discrepancy from the correct reference is

\[
\widehat A-A=110-121=-11.
\]

A plausibility check alone would miss the error. An explicit expected value detects it immediately.

Choose examples that exercise the feature you want to check. A zero principal produces zero under many incorrect growth expressions. A zero rate cannot reveal a missing power. Such cases remain important boundaries, but they should accompany a nonzero principal, nonzero rate, and multiple periods rather than replace them.

## 1.13.4 Use an Independent Calculation Path

A useful reference calculation expresses the same model through different operations. For compound growth, start at \(B_0=P\) and repeatedly apply

\[
B_{j+1}=B_j+rB_j,\qquad j=0,\ldots,n-1.
\]

For the declared model, \(B_n=P(1+r)^n\). One implementation evaluates a power; the reference repeatedly updates the balance. Agreement across selected cases is stronger evidence than comparing two copies of the same power expression.

Independence is limited, not absolute. Both implementations can share a wrong interpretation of the rate, and both rely on the arithmetic library. Therefore agreement does not establish that the financial model or input data are appropriate.

A second useful check discounts a candidate back to time zero:

\[
\frac{\widehat A}{(1+r)^n}=P.
\]

For 110, the recovered principal is \(110/1.21=1000/11\), not 100. This catches the candidate's inconsistency. However, the round trip uses the same growth factor, so it is related to the formula check and should not be counted as wholly independent mathematical evidence.

## 1.13.5 Residuals and Error Measures

A **residual** measures how closely a candidate satisfies a stated equation. If the equation is \(f(x)=0\), its residual at candidate \(\widehat x\) is \(f(\widehat x)\). For a direct output equation, a signed discrepancy is candidate minus reference; its absolute value gives an absolute error when the reference is accepted as correct.

For \(\widehat A=110\) and reference 121, absolute error is 11. Relative error measured against this reference is

\[
\frac{|110-121|}{|121|}=\frac1{11}\approx9.09\%.
\]

Relative error needs a nonzero denominator. Near a zero reference, an absolute comparison is often more meaningful. Always state the reference and scale used; “the error is small” is incomplete without them.

Residual size alone can mislead. Equations \(x-1=0\) and \(10^{-12}(x-1)=0\) have the same solution, but their residuals have different scales. At \(x=2\), the latter residual is only \(10^{-12}\) even though the candidate is one unit from the solution. A tolerance must relate to the specification, not merely to the apparent number of small digits.

## 1.13.6 Exact Equality and Approximate Equality

For the exact rational computations in this chapter, equality is appropriate. Two `Fraction` results either represent the same rational number or do not. There is no need to permit a discrepancy simply because the calculation concerns money.

Binary floating-point arithmetic is different. For example, `0.1 + 0.2 == 0.3` is false in ordinary Python floating-point evaluation because the represented binary values and their rounded sum differ. This does not justify accepting any convenient discrepancy.

A numerical comparison should specify its rule before interpreting the result. Python's `math.isclose` uses a combination of relative and absolute tolerances. In the finite-input lab we use the criterion

\[
|a-b|\leq\max\left(\tau_{\mathrm{rel}}\max(|a|,|b|),
\tau_{\mathrm{abs}}\right).
\]

The relative tolerance is dimensionless. The absolute tolerance has the same units as the compared quantities. A tolerance suitable for balances measured in USD cannot be carried unchanged into balances measured in millions of USD.

Near zero, relative tolerance alone may reject a tiny discrepancy; an explicit absolute tolerance supplies a scale there. Conversely, a large absolute tolerance can conceal an important error in a small value. This section demonstrates chosen tolerances for small synthetic examples, not a universal finance acceptance policy.

## 1.13.7 Separate Numerical Tolerance from Business Rules

A tolerance for comparing approximate computations does not automatically change a contractual inequality. If a reserve requirement is \(S'\geq R\), a computed shortfall should not be silently accepted merely because two balance values are numerically close.

Where finite precision affects a decision boundary, specify the arithmetic, rounding, and decision policy together. Section 1.11 used exact rational values, so a reserve shortfall was an exact violation. Adding `isclose` would change that behavior without authorization from the model.

Nonfinite values also need an explicit policy. NaN is not a real number satisfying the model's order relations, and infinities are outside the lab's finite comparison interface. The comparison helper rejects them before asking whether values are close.

The helper also rejects strings, Boolean values, and numbers that cannot be converted to a finite built-in float. This defines a supported software interface. It does not establish that very large mathematical integers are invalid quantities in every model.

## 1.13.8 Boundaries, Invariants, and Relations Between Cases

Boundary cases clarify what a formula promises:

- Zero periods give \(A=P\).
- Zero rate gives \(A=P\) for every allowed horizon.
- Zero principal gives \(A=0\).
- A rate just above −1 is allowed; −1 itself is excluded by the shared interface.

An **invariant** is a relationship expected to hold throughout the relevant calculation. In the growth model, nonnegative principal and positive growth factor imply nonnegative balances. In the transfer model, the two-account total falls by the fee. Such relationships detect some classes of error without requiring a precomputed answer for every input.

Relations between cases provide additional checks. For fixed rate and horizon,

\[
A(cP,r,n)=cA(P,r,n),\qquad c\geq0.
\]

For two nonnegative integer horizons,

\[
A(P,r,m+n)=A(A(P,r,m),r,n).
\]

These statements follow from the formula and give testable properties. They do not uniquely identify the implementation: a function that always returns zero satisfies some scaling relationships. Combine properties with concrete nonzero references and domain checks.

## 1.13.9 Confirm That Checks Detect Mistakes

A passing test is more informative when a plausible incorrect result fails it. Deliberately try a candidate with a missing period, a misplaced parenthesis, or the wrong rate representation. This is a small manual form of checking the effectiveness of the tests.

For the reference case, 110 is a missing-period result. The expression \((100\times1.1)^2\) produces 12,100 by applying the power to principal as well. Using decimal rate 10 instead of 0.10 produces another distinct answer. A useful exact audit rejects each candidate.

Not every check needs to fail. The candidate 110 passes nonnegativity and the weak positive-rate lower bound. The named result report should show that these conditions are insufficient, rather than imply that every check independently establishes correctness.

Avoid inflating confidence by repeating the same assertion many times. More cases help only when they cover meaningful boundaries, input classes, relationships, or failure modes. Preserve the failing inputs and the named check so the discrepancy is reproducible.

## 1.13.10 Diagnose and Record a Failure

When a check fails, keep the observed result. Revisit the specification and input interpretation, reproduce the smallest failing case, inspect intermediate values, and compare with an independent calculation. Determine whether the implementation, the expected result, or the specification needs correction.

Do not relax a tolerance until the output passes without explaining why the new tolerance is justified. Likewise, changing an expected answer to match the current program removes evidence unless the revised answer has independent support.

A useful execution record contains the inputs or case description, commands, runtime version, observed output, check results, and the exact files tested. A file hash helps identify the artifact associated with the record; it does not certify the mathematics or prevent every environmental difference.

Distinguish runtime evidence from editorial review and model validation. Finite checks support the implementation on their stated cases. A proof supports a mathematical claim under assumptions. External data verification and economic model assessment address different questions again. The book's Draft status remains separate from a passing test command.

## 1.13.11 Worked Python Lab — An Exact Audit and a Finite Comparison

Save as [code/section_1_13.py](code/section_1_13.py). The lab imports the published [Section 1.12 implementation](code/section_1_12.py); keep both files in the chapter's `code` directory. The exact audit accepts rational candidates, including negative candidates that should fail its checks. Unsupported inputs raise exceptions.

```python
"""Check exact growth candidates and explicitly bounded float comparisons."""
import math
from section_1_12 import compound_balance, periodic_rate, rational


def audit_growth(*, principal, period_rate, periods, candidate):
    formula = compound_balance(principal=principal, period_rate=period_rate,
                               periods=periods)
    p = rational(principal)
    rate = periodic_rate(period_rate)
    observed = rational(candidate)
    reference = p
    for _ in range(periods):
        reference = reference + reference * rate
    recovered = observed / (1 + rate) ** periods
    direction_ok = observed >= p if rate >= 0 else observed <= p
    checks = {
        "formula_agreement": observed == formula,
        "recurrence_agreement": observed == reference,
        "round_trip": recovered == p,
        "nonnegative": observed >= 0,
        "direction_bound": direction_ok,
    }
    return {"candidate": observed, "reference": reference,
            "discrepancy": observed - reference, "checks": checks,
            "passed": all(checks.values())}


def finite_float(value):
    if type(value) not in (int, float):
        raise TypeError("use built-in int or float, excluding bool")
    try:
        number = float(value)
    except OverflowError as exc:
        raise ValueError("value exceeds the float interface") from exc
    if not math.isfinite(number):
        raise ValueError("comparison requires finite values")
    return number


def compare_finite(actual, reference, *, rel_tol, abs_tol):
    a, b = finite_float(actual), finite_float(reference)
    relative, absolute = finite_float(rel_tol), finite_float(abs_tol)
    if not 0 <= relative < 1 or absolute < 0:
        raise ValueError("require 0 <= rel_tol < 1 and abs_tol >= 0")
    return math.isclose(a, b, rel_tol=relative, abs_tol=absolute)


def main():
    inputs = dict(principal=100, period_rate="0.10", periods=2)
    good = audit_growth(candidate=121, **inputs)
    bad = audit_growth(candidate=110, **inputs)
    print(f"Correct candidate passed: {good['passed']}")
    print(f"Missing-period candidate passed: {bad['passed']}")
    print(f"Missing-period discrepancy: {bad['discrepancy']}")
    print(f"Weak bounds passed: {bad['checks']['nonnegative']} and "
          f"{bad['checks']['direction_bound']}")
    print("Float equality:", 0.1 + 0.2 == 0.3)
    print("Explicit close comparison:", compare_finite(
        0.1 + 0.2, 0.3, rel_tol=1e-12, abs_tol=0))
    print("Near zero, relative only:", compare_finite(
        1e-12, 0, rel_tol=1e-9, abs_tol=0))
    print("Near zero, absolute tolerance:", compare_finite(
        1e-12, 0, rel_tol=1e-9, abs_tol=1e-12))


if __name__ == "__main__":
    main()
```

Expected output:

```text
Correct candidate passed: True
Missing-period candidate passed: False
Missing-period discrepancy: -11
Weak bounds passed: True and True
Float equality: False
Explicit close comparison: True
Near zero, relative only: False
Near zero, absolute tolerance: True
```

## 1.13.12 Practice Problems

1. For principal 200, rate 5% per period, and two periods, compute the exact balance and the signed discrepancy of candidate 210. Which simple plausibility checks would still pass?
2. Why is comparing a function with a copied version of the same expression weaker than comparing it with a recurrence? What shared error could survive either comparison?
3. A reference value is zero and an observed value is \(10^{-8}\). With relative tolerance \(10^{-6}\) and absolute tolerance zero, does the stated closeness rule pass? What happens with absolute tolerance \(10^{-8}\)?
4. A reserve condition is violated by 0.001 USD. May a numerical comparison tolerance of 0.01 USD automatically make the transfer feasible?
5. A function always returns zero. Give one property it passes and a concrete test that detects its error for the growth model.
6. A check fails after an implementation change. List the evidence to preserve and explain why increasing the tolerance is not automatically a fix.

## 1.13.13 Worked Answers

1. \(200(1.05)^2=220.5\). The signed discrepancy is \(210-220.5=-10.5\). Candidate 210 is nonnegative and at least the initial principal, so those weak bounds pass despite the missing period.
2. A copied expression can repeat the same parentheses, exponent, or index mistake. A recurrence uses a different calculation structure. Both can still interpret an annual rate as a monthly rate, so the input conventions need separate review.
3. Relative allowance is \(10^{-6}\times10^{-8}=10^{-14}\), less than discrepancy \(10^{-8}\), so it fails. Absolute tolerance \(10^{-8}\) makes it pass at the included boundary. Whether that tolerance is appropriate depends on the quantity and required accuracy.
4. No. Numerical closeness and contractual feasibility are separate rules. A rounding or boundary policy must be explicitly specified; it cannot be inferred from a convenient test tolerance.
5. It passes nonnegativity and scaling of principal, since scaling zero still gives zero. The reference case \(P=100,r=0.10,n=2\) must return 121, which detects the error. Zero-period equality at positive principal also detects it.
6. Preserve the failing inputs, expected and observed values, named check, commands, environment, and exact code version. Reproduce and investigate the discrepancy. A tolerance change is justified only by a documented accuracy requirement or numerical analysis, not by the desire to remove a failure.

## 1.13.14 Common Mistakes, Summary, and Sources

Common mistakes include treating a completed run as correctness, using only zero-valued examples, accepting weak bounds as sufficient, comparing two copies of the same bug, rounding before comparison, and widening tolerance until a failure disappears. Another is claiming universal or canonical validation from a finite test suite.

Check the specification first, then a hand-solvable case, an alternative calculation, boundaries, invariants, and relationships between cases. Use exact equality where the arithmetic is exact. For approximate values, state the finite-input policy, tolerance rule, units, and reason for the chosen tolerances. Keep numerical acceptance separate from business constraints.

Report what was tested and what remains outside scope. The lab checks fixed-rate rational growth and a small finite-float comparison interface. It does not supply production accuracy requirements, contractual rounding rules, or independent economic model validation. Canonical editorial review remains pending.
