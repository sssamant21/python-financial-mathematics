Section 1.1 established that a model needs meaningful inputs and a valid domain. We now examine what those inputs are and how Python represents them.

## 1.2.2 Mathematical Objects Have Structure

A mathematical object is something whose properties and relationships can be studied. A number is one example, but finance also uses ordered collections, functions, and systems of equations.

Consider an account with a balance of 1000, an annual effective rate of 0.05, and a two-year horizon. These are three scalar inputs. The schedule [(0,-1000),(1,50),(2,1050)] is a different kind of object: a collection of dated, signed payments. Replacing that schedule with the scalar 100 would lose the timing information needed for valuation.

| Object | Meaning | Financial example |
|---|---|---|
| Scalar | One numerical value | A balance or rate |
| Ordered pair | Two components with defined roles | (time, payment amount) |
| Vector | An ordered collection with vector operations | Holdings for several assets |
| Matrix | A rectangular collection representing a linear map or related structure | Instrument-to-factor exposures |
| Function | A rule assigning one output to each admissible input | Value as a function of rate |
| Set | A collection considered through membership | Admissible rate values |

A Python tuple or list can store these components, but storage alone does not supply the mathematical operations. For example, adding two Python lists concatenates them; it does not perform vector addition. The later linear-algebra chapters will develop the corresponding mathematical structures explicitly.

## 1.2.3 Natural Numbers and Whole-Number Counts

For this book, define:

$$\mathbb{N}=\{1,2,3,\ldots\},\qquad \mathbb{N}_0=\{0,1,2,3,\ldots\}.$$

Some texts include zero in the natural numbers. Neither convention is universal, so we state ours and use $\mathbb{N}_0$ when zero is included. Reference 1 uses the names natural numbers and whole numbers to make this distinction.

Payment counts and recurrence indexes often belong to $\mathbb{N}_0$. A zero-payment schedule is possible; a schedule with -3 payments is not. An annual recurrence requiring complete periods can accept n=3 while rejecting n=3.5.

This restriction belongs to the model. A different model may accept a horizon of 3.5 years and use a specified fractional-time convention. Do not confuse “this function requires an integer period count” with “financial time must always be an integer.”

Python int represents whole-number values exactly for supported arithmetic, with size limited by available resources rather than a fixed 32-bit or 64-bit integer range. Converting a very large int to float can still lose precision or fail because the target representation is different.

## 1.2.4 Integers and Signed Quantities

The integers are:

$$\mathbb{Z}=\{\ldots,-2,-1,0,1,2,\ldots\}.$$

They add negative values to whole-number counts. Signed monetary minor units, position changes, and discrete inventory movements can naturally be integers.

If one currency unit is defined as 100 minor units, an amount of -12.34 can be stored as -1234 minor units. Its sign might represent an outflow under the model's chosen convention. That convention is separate from the fact that -1234 is an integer.

Integers are closed under addition, subtraction, and multiplication: these operations on integer inputs produce integers. Division does not preserve that property. Splitting 105 minor units equally between two recipients gives 52.5 minor units per recipient, outside an integer-minor-unit domain.

A valid allocation therefore needs a rule. One possible rule gives the first recipient 53 and the second 52. The rule preserves the total but does not give identical amounts. Record who receives the remainder, especially when repeatedly allocating many payments.

## 1.2.5 Rational Numbers and Exact Ratios

A rational number can be written as:

$$\frac{p}{q},\qquad p,q\in\mathbb{Z},\qquad q\neq0.$$

The rational numbers form $\mathbb{Q}$. Every integer is rational because $k=k/1$. Terminating decimal quantities are rational too: 0.035 equals 35/1000, which reduces to 7/200.

A decimal can repeat forever and still be rational. One third is the exact ratio 1/3 even though its base-ten expansion is repeating. The finite decimal 0.333333 is a different rational number, 333333/1000000.

Python's Fraction stores a rational value as an exact numerator and denominator. For example, Fraction(1,3) multiplied by three gives exactly one. Constructing Fraction("0.035") preserves the quoted finite decimal as 7/200.

Exactness depends on construction. Fraction(0.1) captures the exact rational value of the already-stored binary float 0.1; Fraction("0.1") captures the exact decimal tenth. These are different inputs. Converting a previously approximated value into a rational container does not recover an unstated original intention. Reference 2 documents these construction behaviors.

## 1.2.6 Irrational and Real Numbers

An irrational number is real but cannot be written as a ratio of integers with a nonzero denominator. Examples include $\sqrt{2}$, $\pi$, and $e$. Their decimal expansions neither terminate nor eventually repeat.

One familiar reason $\sqrt{2}$ is irrational is a parity contradiction. Suppose it were p/q in lowest terms. Squaring gives $p^2=2q^2$, so p is even. Writing p=2k gives $q^2=2k^2$, so q is even too. That contradicts the assumption that the fraction was in lowest terms.

The real numbers $\mathbb{R}$ include rational and irrational values. We have the nested inclusions:

$$\mathbb{N}\subset\mathbb{N}_0\subset\mathbb{Z}\subset\mathbb{Q}\subset\mathbb{R}.$$

An ideal mathematical value and a computer's stored approximation are different objects. The result of math.sqrt(2) is a finite float approximation; it is not the exact irrational number. Every finite binary floating-point value can itself be expressed as an integer divided by a power of two, so the stored approximation is rational.

Testing whether a float has an integer ratio cannot distinguish whether the intended mathematical quantity was rational or irrational. In this book, irrational constants are described mathematically and their numerical approximations are evaluated with suitable error checks.

## 1.2.7 What Binary Floating Point Represents

Python float normally uses binary floating-point arithmetic. A finite value combines a sign, a significand, and a power of two. This is efficient for numerical work, but most finite decimal fractions have no exact finite binary representation.

The decimal fraction 0.125 equals 1/8 and is exactly representable in binary. The fraction 0.1 equals 1/10 and is not. A rational has a terminating base-b expansion when, after reduction, its denominator divides a power of b. Powers of two therefore suit binary representation; a denominator containing a factor of five, as in 1/10, does not.

This explains why ordinary binary-float arithmetic can make 0.1+0.2 compare unequal to 0.3. It does not mean Python adds arbitrary errors. It means input representation and arithmetic rounding must be considered alongside the mathematical expression.

A float may print as 0.1 because the display is a short decimal representation of the stored value. A display that looks exact is not proof of exact internal decimal storage. Reference 5 explains this distinction in more detail.

For approximate calculations, math.isclose can test whether a discrepancy is acceptably small under specified relative and absolute tolerances. Approximate equality is not a substitute for a contract's exact settlement or rounding rules.

## 1.2.8 Decimal Representation and Arithmetic Context

Decimal provides decimal floating-point arithmetic with an explicit arithmetic context. Constructing Decimal("0.1") preserves an exact decimal tenth. Constructing Decimal(0.1) instead preserves the exact value of the binary float argument, including the difference from a tenth.

Decimal arithmetic still has finite precision unless a calculation happens to be exactly representable within the context. Decimal(1)/Decimal(3) requires rounding. Increasing context precision can retain more digits, but no finite decimal expansion becomes the exact rational third.

A context defines working precision, rounding behavior, and signals. Use localcontext for an isolated calculation so its settings do not silently alter unrelated code. For the examples below, the context precision is 28 significant digits. This is not a rule that every monetary value has 28 decimal places.

To round a value to a decimal quantum, use quantize and name the rounding mode. Under ROUND_HALF_EVEN, exact decimal 2.685 rounded to 0.01 becomes 2.68; under ROUND_HALF_UP it becomes 2.69. The choice affects the result and must be specified rather than inferred from an amount's display.

The code below uses original examples with these APIs; Reference 3 supplies the authoritative API and context definitions.

## 1.2.9 Choose Representation and Operations Together

| Requirement in a stated model | Possible representation | Limitation to address |
|---|---|---|
| Whole payment count | int | Enforce nonnegative count; reject unintended booleans |
| Exact finite decimal quote | Decimal constructed from text | Choose arithmetic precision and rounding |
| Exact allocation ratio | Fraction | Numerators/denominators can grow with computation |
| Large numerical arrays and approximate analysis | float-based numerical types | Rounding, scale, conditioning, and tolerances |
| Settled amounts in one fixed minor unit | int minor units | Multiplication/division may require allocation or rounding |

This is a mapping between requirements and representations, not a universal preference order. A model can use decimal amounts at an accounting boundary and approximate floating-point calculations inside a numerical routine, provided conversions and error policies are explicit.

Different representations do not generally mix automatically. Decimal plus float, for example, raises TypeError in ordinary arithmetic. Prefer an intentional conversion at a documented boundary over ad hoc coercion inside the formula.

Currency and unit information also matter. The integer 1000 could mean dollars, cents, shares, or milliseconds. Its type establishes none of those meanings. Later sections make units and input conventions part of the mathematical specification.

## 1.2.10 Finiteness, Booleans, and Missing Values

A float type check does not establish a valid real-valued model input. NaN and positive or negative infinity are floating-point values but are not finite real numbers.

NaN also has unusual comparisons: it does not compare equal to itself, and comparisons such as NaN<0 are false. A check that rejects only negative values can therefore accidentally accept NaN. Use an explicit finiteness check for a model requiring finite real inputs. Decimal has its own is_finite method.

Python bool is a subclass of int. Thus isinstance(True,int) is true, even though True usually does not represent an intended payment count. A public numeric interface should state whether booleans are accepted. The example below rejects them by requiring built-in int for integer counts.

A missing observation is another concept. None is not zero, and a missing price must not be replaced by zero without a stated policy. A zero price, an unknown price, and an invalid nonfinite price describe different inputs and can lead to different decisions about whether valuation is possible.

## 1.2.11 Executable Representation Lab

The following complete program demonstrates exact ratios, decimal construction, rounding policy, finite-real checks, and an integer allocation. It uses only the Python standard library.

Save it as [code/section_1_02.py](code/section_1_02.py).

```python
from decimal import Decimal, ROUND_HALF_EVEN, ROUND_HALF_UP, localcontext
from fractions import Fraction
from math import isclose, isfinite


def payment_count(value):
    """Whole count only; bool and 3.0 are outside this interface."""
    if type(value) is not int:
        raise TypeError("count must be a built-in int, excluding bool")
    if value < 0:
        raise ValueError("count must be nonnegative")
    return value


def split_minor_units(total, recipients):
    """Nonnegative total; positive recipient count; earliest positions get remainder."""
    total = payment_count(total)
    recipients = payment_count(recipients)
    if recipients == 0:
        raise ValueError("at least one recipient required")
    base, remainder = divmod(total, recipients)
    return [base + (index < remainder) for index in range(recipients)]


def main():
    exact_third = Fraction(1, 3)
    assert 3 * exact_third == 1
    quoted_rate = Fraction("0.035")
    assert quoted_rate == Fraction(7, 200)
    rational_balance = Fraction(1000) * (1 + quoted_rate)
    assert rational_balance == 1035
    assert Fraction(0.1) != Fraction("0.1")
    assert isclose(0.1 + 0.2, 0.3, rel_tol=1e-12)
    assert isfinite(0.05) and not isfinite(float("nan"))
    assert isinstance(True, int)  # explains the explicit count policy
    with localcontext() as context:
        context.prec = 28
        context.rounding = ROUND_HALF_EVEN
        decimal_total = Decimal("0.1") + Decimal("0.2")
        assert decimal_total == Decimal("0.3")
        assert Decimal(0.1) != Decimal("0.1")
        rounded_third = Decimal(1) / Decimal(3)
        half_even = Decimal("2.685").quantize(Decimal("0.01"), rounding=ROUND_HALF_EVEN)
        half_up = Decimal("2.685").quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
        assert half_even == Decimal("2.68")
        assert half_up == Decimal("2.69")
    allocation = split_minor_units(105, 2)
    assert allocation == [53, 52] and sum(allocation) == 105
    print(f"Exact rational third: {exact_third}")
    print(f"Quoted rate as fraction: {quoted_rate}")
    print(f"One-period rational balance: {rational_balance}")
    print(f"Decimal sum: {decimal_total}")
    print(f"Decimal third at precision 28: {rounded_third}")
    print(f"Half-even / half-up: {half_even} / {half_up}")
    print(f"Minor-unit allocation: {allocation}")


if __name__ == "__main__":
    main()
```

Expected output:

```text
Exact rational third: 1/3
Quoted rate as fraction: 7/200
One-period rational balance: 1035
Decimal sum: 0.3
Decimal third at precision 28: 0.3333333333333333333333333333
Half-even / half-up: 2.68 / 2.69
Minor-unit allocation: [53, 52]
```

The remainder-allocation rule assigns extra units by list position. It preserves the total and keeps allocations at most one minor unit apart. It does not establish fairness across repeated allocation cycles. The function returns a list and is intended for small instructional recipient counts; a large-scale service would need an appropriate resource policy.

## 1.2.13 Practice Problems and Worked Answers

**Problem 1 — Number systems.** Classify 0,-3,7/20,$\sqrt{2}$, and 0.125 using the sets defined in this section. A value can belong to more than one set.

**Answer.** Zero belongs to $\mathbb{N}_0,\mathbb{Z},\mathbb{Q},\mathbb{R}$ but not our $\mathbb{N}$. Negative three is integer, rational, and real. The ratio 7/20 is rational and real. The exact $\sqrt{2}$ is irrational and real. The decimal 0.125 equals 1/8, so it is rational and real. A float approximation of $\sqrt{2}$ is itself rational and must not be classified as the exact irrational constant.

**Problem 2 — Exact finite decimals.** Express a quoted rate of 1.25% as an exact fraction and calculate its one-period effect on a principal of 800.

**Answer.** Decimal rate 0.0125 equals 125/10000=1/80. Interest is $800/80=10$, so the ending amount is 810. A compatible exact-rational implementation is Fraction(800)*(1+Fraction("0.0125")).

**Problem 3 — Decimal precision.** Does setting Decimal working precision to 50 make 1/3 exact? Explain the distinction between constructing Decimal("0.1") and computing Decimal(1)/Decimal(3).

**Answer.** No. A rational third has no terminating decimal expansion, so finite-precision division still rounds. Decimal("0.1") directly represents an exact finite decimal; 1/3 requires a repeating expansion. The context controls arithmetic rounding, not a transformation of a repeating expansion into a finite exact one.

**Problem 4 — Allocation.** Split 101 minor units between four recipients using the published rule. Explain why equal integer amounts cannot preserve the total.

**Answer.** Dividing gives quotient 25 and remainder 1, hence [26,25,25,25]. The total is 101. Four identical integers would sum to a multiple of four, and 101 is not divisible by four.

**Problem 5 — Converting after approximation.** A float price was created from 0.1 and later converted into Decimal. Has the original exact decimal tenth necessarily been recovered?

**Answer.** No. Decimal(0.1) preserves the exact value of the float argument, including its binary approximation. If the intended source was exact decimal text, construct from that validated text at the input boundary. Inferring and rounding to the presumed quote precision is a separate policy and should not be hidden.

**Problem 6 — Object structure.** A portfolio stores prices [10,20] and holdings [2,3]. What additional information is required before computing value? What goes wrong if ordinary list addition is used as vector addition?

**Answer.** Confirm matching asset labels and order, units/currency, compatible valuation times, and equal dimensions. Under those assumptions, value is $2(10)+3(20)=80$. Ordinary list addition concatenates components instead of adding them coordinate by coordinate. A matching shape does not itself prove semantic alignment.

These exercises prepare the reader for the larger problem set in Section 1.15; they do not replace it.

## 1.2.14 Common Mistakes

| Mistake | Why it fails | Better specification |
|---|---|---|
| Treating 3.0 and 3 as interchangeable in every API | Mathematical equality does not settle interface types | Define whether integral floats are accepted |
| Calling every infinite decimal irrational | Rational decimals can repeat forever | Use the ratio definition and repetition criterion |
| Calling a stored sqrt(2) float irrational | Finite binary storage is a rational approximation | Distinguish intended constant from representation |
| Constructing Decimal from a float to recover decimal text | The float approximation already exists | Construct from validated source text where appropriate |
| Assuming Decimal arithmetic never rounds | Arithmetic depends on context precision | State precision, rounding, and traps |
| Splitting integer cents without an allocation rule | Equal division may leave fractional minor units | Define remainder handling |
| Accepting all int instances as counts | bool subclasses int | State a boolean policy explicitly |
| Conflating zero, None, NaN, and infinity | They have different meanings and behavior | Separate missingness, domain, and finiteness checks |

## 1.2.15 Summary and Next Section

A model specifies mathematical quantities; an implementation selects representations and operations for them. Natural numbers and integers support counting and discrete amounts, rational numbers support exact ratios, and real-number models also include irrational values. Python numeric types represent particular values and behaviors rather than entire abstract number systems.

Exactness, numerical approximation, and business rounding are distinct questions. A deliberate input policy preserves the meaning of source data, while explicit arithmetic and allocation rules make results reviewable.
