## 1.5.1 Learning Objectives

After completing this section, you should be able to:

- Read subscripts, superscripts, function arguments, and elementary summation notation without confusing their roles.
- State an index set and distinguish an item's label, storage position, and financial time.
- Translate one-based and zero-based mathematical conventions into Python explicitly.
- Represent irregular schedules and repeated payment dates without losing records.
- Recognize the meaning of multiple indexes and preserve asset alignment.
- Detect missing or mismatched data instead of silently truncating a calculation.

Mathematical notation compresses relationships. It is useful only when the reader knows what each symbol labels and which values its indexes can take.

## 1.5.2 Symbols Need a Notation Key

The same letter can mean different things in different models. A short notation key prevents readers from assuming a convention that was never stated.

| Symbol in this section | Meaning | Units or index convention |
|---|---|---|
| $C_t$ | Signed payment at integer period t, when the schedule has one aggregate payment per period | Currency units |
| $C_j$ | Payment record j in an explicitly dated list | Currency units; j is a record label |
| $t_j$ | Payment time associated with record j | Periods from valuation time zero |
| $r$ | Constant effective rate per modeled period | Decimal rate |
| $h_i$ | Holding in instrument i | Instrument units |
| $p_i$ | Price per unit of instrument i | Currency per instrument unit |
| $V_0$ | Value measured at the chosen time-zero date | Currency units |

The symbols $C_t$ and $C_j$ use different indexing conventions. In a period-indexed schedule, the subscript itself is time. In a record-indexed schedule, a separate $t_j$ stores the financial time. Neither convention can be inferred safely from the letter C alone.

The valuation date and period length belong to the notation key too. Time zero means the chosen reference date, not necessarily the current calendar date.

## 1.5.3 Subscripts Are Labels, Not Multiplication

The notation $C_2$ means the C quantity labeled by index 2. It does not mean C times 2. Likewise, $p_i$ is an instrument's price, while $pi$ without an explicit notation convention could be read as a product or a different symbol.

For example:

$$C_1=100,\qquad C_2=120.$$

These are two separately specified payments. Knowing $C_1$ does not determine $C_2$ unless the model supplies an additional rule. A schedule may be a list of inputs, a sequence generated by a formula, or an aggregation of records. State which interpretation applies.

Python represents these quantities through a container or lookup, such as amounts[0] or payments_by_period[2]. The mathematical subscript need not equal the Python storage index. Reference 1 develops sequence notation and distinguishes explicitly listed terms from formula-defined sequences.

## 1.5.4 Superscripts, Powers, and Function Arguments

In $(1+r)^2$, the superscript 2 is an exponent. In a report, a deliberately defined notation such as $V^{(stress)}$ can instead label a stress scenario. Parenthesized superscripts are not automatically powers; their role must be declared.

Similarly, $V(r)$ ordinarily denotes a function evaluated at input r when V has been defined as a function. It does not mean V multiplied by r. Context and definitions determine the interpretation.

For this book, use explicit multiplication signs or unambiguous products in derivations and descriptive names in code. Translate powers using **. Avoid copying a mathematical scenario superscript into Python exponent syntax: stress_value is a label, while value**2 squares a quantity.

A superscript T will later denote transpose in linear algebra, after that convention is introduced. Encountering a new symbol should prompt a check of the local notation key rather than a guess based on typography.

## 1.5.5 Define the Index Set and Count Its Terms

An index set states the admissible labels:

$$t\in\{0,1,\ldots,n\}\quad\text{or}\quad j\in\{1,2,\ldots,m\}.$$

The first contains n+1 labels; the second contains m labels. Zero-based and one-based conventions can describe the same number of records, but their upper bounds differ.

For three payments, a one-based list can use $C_1,C_2,C_3$. A zero-based list can use $A_0,A_1,A_2$. If these represent the same records in order, then:

$$A_k=C_{k+1},\qquad k=0,1,2.$$

This relationship changes record labels, not financial payment times by itself. To change timing, the time associated with each record must change explicitly.

Python range(3) generates 0,1,2, while range(1,4) generates 1,2,3. Its stopping value is excluded. The mathematical expression “t=0 through n” therefore corresponds to range(n+1), not range(n).

## 1.5.6 Translate Payment Timing Deliberately

Suppose a list [100,120] stores payments at the ends of periods one and two.

| Python position | Mathematical label | Payment time | Amount |
|---:|---|---:|---:|
| 0 | $C_1$ | 1 | 100 |
| 1 | $C_2$ | 2 | 120 |

Enumerating the amounts with start=1 supplies the correct time labels for this schedule. Default enumeration starts at zero and would move the financial interpretation one period earlier if used directly as a discount exponent. Reference 2 documents enumerate's start argument.

At effective period rate r=0.10, the end-period schedule has value:

$$V_0=\frac{100}{1.1}+\frac{120}{1.1^2}=190.0826446281\ldots.$$

If the amounts actually occur at times zero and one, their value is:

$$\widetilde{V}_0=100+\frac{120}{1.1}=209.0909090909\ldots.$$

Both calculations are mathematically consistent with their timelines. They answer different timing questions. The earlier schedule's value is 1.1 times the later schedule's value because each payment moves one period earlier.

## 1.5.7 Read a Finite Sum Before Coding It

The compact expression:

$$V_0=\sum_{t=1}^{n}\frac{C_t}{(1+r)^t}$$

means: calculate one discounted term for each integer t from one through n, then add those terms. The upper and lower limits are inclusive.

For n=2, expanding the notation gives exactly the two-payment calculation above. A time-zero payment, if present, must be added explicitly or included by changing the lower bound to zero. Its discount exponent is zero, so its factor is one.

A summation index is local to that sum. Renaming t to k gives the same expression if every occurrence belonging to the sum is renamed consistently. It does not change the payment dates or create a new economic model. An index still appearing outside an aggregation is not automatically summed.

We use sums here to read and translate schedules. Chapter 06 develops summation identities, series, and related cash-flow derivations in detail.

## 1.5.8 Record Index and Financial Time Can Differ

A general finite schedule is better written as records:

$$(t_j,C_j),\qquad j=1,\ldots,m,$$

with value:

$$V_0=\sum_{j=1}^{m}\frac{C_j}{(1+r)^{t_j}}.$$

Here j identifies a record, while $t_j$ states when it is paid. A record number of two does not imply payment at period two.

For example, the schedule [(0,-100),(1,5),(3,120)] has three records at times zero, one, and three. No record is stored for period two. In this illustration the schedule is declared complete, so the omitted period has no payment. In a raw data feed, an absent record might instead indicate missing data. Completeness is an input assumption, not something a summation symbol can establish.

The code in this section accepts nonnegative integer periods only. Fractional years and actual dates need separate time-conversion conventions. Storing a calendar timestamp does not automatically establish the exponent for an effective annual rate.

## 1.5.9 Repeated Dates and Record Identity

Two payment records can have the same time. For [(1,100),(1,-5),(2,120)], the second record is a fee at the same date as the first inflow. Both must be retained unless the model explicitly aggregates them.

Under this linear discounting model, aggregating the two period-one records into a payment of 95 preserves present value:

$$\frac{100}{1+r}-\frac{5}{1+r}=\frac{95}{1+r}.$$

This identity assumes the same currency, valuation rule, and discount convention. A calculation that charges a separate per-record fee or applies nonlinear rules may not preserve value after aggregation.

Converting payment records directly into a dictionary keyed only by time can overwrite repeated dates. An unordered set can also remove repeated identical records, even if they represent distinct contractual payments. Preserve record identity before choosing an aggregation or deduplication policy.

## 1.5.10 Multiple Indexes and Asset Alignment

The notation $C_{i,t}$ can describe the cash flow for instrument i at time t. Define the instrument set, time set, and whether each pair has an explicit value. For the small table below, every displayed entry is supplied:

| Instrument | Period 1 | Period 2 |
|---|---:|---:|
| A | 10 | 110 |
| B | 20 | 220 |

If holdings are $h_A=2$ and $h_B=1$, aggregate cash flow at period one is 2(10)+1(20)=40; at period two it is 2(110)+1(220)=440. We summed over the instrument index while retaining the time index.

Similarly, portfolio value can be written:

$$V=\sum_{i\in I}h_i p_i.$$

The same label i must refer to the same instrument in both quantities. Holdings [2,3] for [A,B] and prices [20,10] for [B,A] have matching lengths but incompatible order. Multiplying by position gives 70. Matching by label gives 2(10)+3(20)=80.

Matching dimensions are necessary but not sufficient. Review labels, currencies, valuation times, and units. Before converting source data into a dictionary, also detect duplicate labels that could otherwise overwrite one another.

## 1.5.11 Executable Schedule-Translation Lab

The following complete example pairs explicit periods with amounts, detects unequal lengths, and keeps duplicate dates. It is independent of earlier code files and uses Python 3.10 or later for zip(strict=True).

Save it as [code/section_1_05.py](code/section_1_05.py).

```python
from math import fsum, isclose, isfinite


def finite_amount(value, name):
    if type(value) not in (int, float):
        raise TypeError(f"{name} must be a built-in int or float, excluding bool")
    try:
        result = float(value)
    except OverflowError as exc:
        raise ValueError(f"{name} exceeds supported range") from exc
    if not isfinite(result):
        raise ValueError(f"{name} must be finite")
    return result


def dated_payments(*, periods, amounts):
    """Finite iterables; nonnegative integer dates; signed, single-currency amounts."""
    records = []
    for period, amount in zip(periods, amounts, strict=True):
        if type(period) is not int:
            raise TypeError("period labels must be built-in integers, excluding bool")
        if period < 0:
            raise ValueError("period labels must be nonnegative")
        records.append((period, finite_amount(amount, "amount")))
    return tuple(records)


def periodic_payments(amounts, *, first_period=1):
    """Consecutive whole periods; preserve amount order and repeated amounts."""
    if type(first_period) is not int:
        raise TypeError("first_period must be a built-in integer, excluding bool")
    if first_period < 0:
        raise ValueError("first_period must be nonnegative")
    records = tuple(enumerate(amounts, start=first_period))
    return dated_payments(periods=(t for t, _ in records),
                          amounts=(c for _, c in records))


def present_value(*, periods, amounts, period_rate):
    """Constant effective period rate; empty schedule has value zero."""
    rate = finite_amount(period_rate, "period_rate")
    if rate <= -1:
        raise ValueError("period_rate must be greater than -1")
    records = dated_payments(periods=periods, amounts=amounts)
    terms = []
    for t, cash in records:
        if cash == 0:
            terms.append(0.0)
            continue
        try:
            factor = (1 + rate)**t
            if not isfinite(factor) or factor == 0:
                raise ArithmeticError("discount denominator outside supported range")
            value = cash / factor
        except OverflowError as exc:
            raise ArithmeticError("discount calculation exceeds supported range") from exc
        if not isfinite(value) or value == 0:
            raise ArithmeticError("nonzero payment overflowed or underflowed")
        terms.append(value)
    try:
        total = fsum(terms)
    except OverflowError as exc:
        raise ArithmeticError("schedule total exceeds supported range") from exc
    if not isfinite(total):
        raise ArithmeticError("schedule total must be finite")
    return total


def main():
    records = periodic_payments([100, 120], first_period=1)
    for position, (time, amount) in enumerate(records):
        print(f"Position {position} -> period {time}: {amount:.2f}")
    end_value = present_value(periods=[1, 2], amounts=[100, 120], period_rate=0.1)
    early_value = present_value(periods=[0, 1], amounts=[100, 120], period_rate=0.1)
    assert isclose(early_value, 1.1 * end_value, rel_tol=1e-12)
    print(f"End-period PV: {end_value:.6f}")
    print(f"One-period-earlier PV: {early_value:.6f}")
    repeated = dated_payments(periods=[1, 1, 2], amounts=[100, -5, 120])
    assert len(repeated) == 3
    print(f"Repeated-date records retained: {len(repeated)}")
    holdings, prices = {"A": 2, "B": 3}, {"B": 20, "A": 10}
    if holdings.keys() != prices.keys():
        raise ValueError("instrument labels do not match")
    labelled_value = fsum(holdings[label] * prices[label] for label in holdings)
    assert labelled_value == 80
    print(f"Value matched by instrument label: {labelled_value:.2f}")


if __name__ == "__main__":
    main()
```

Expected output:

```text
Position 0 -> period 1: 100.00
Position 1 -> period 2: 120.00
End-period PV: 190.082645
One-period-earlier PV: 209.090909
Repeated-date records retained: 3
Value matched by instrument label: 80.00
```

Ordinary zip stops when its shortest input is exhausted. The strict form raises ValueError if the inputs have different lengths. This check occurs as the iterator is consumed; it is not an eager inspection at zip construction. Our functions consume the inputs and return no partial report on failure. Input iterators may already have advanced when an error occurs. Reference 2 documents both behaviors.

The implementation materializes small finite schedules and is intended for teaching, not unbounded streams. It validates the rate even when the schedule is empty. Unsorted dates are permitted and preserved; this model values each dated record independently rather than using a rolling balance that requires chronological order.

All values use one currency and one effective period rate. No calendar conversion, currency conversion, contractual rounding, record deduplication, or completeness inference occurs automatically. The direct power evaluation has the same introductory precision limits discussed earlier; later chapters develop stable numerical methods for difficult scales.

## 1.5.13 Practice Problems and Worked Answers

**Problem 1 — Translate indexes.** A one-based schedule has C_1=20,C_2=30,C_3=40. List the equivalent zero-based values A_0,A_1,A_2. Does relabeling alone change payment times?

**Answer.** A_0=20,A_1=30,A_2=40 with A_k=C_(k+1). Relabeling record positions does not itself change times. If the original times are 1,2,3, retain those times explicitly after relabeling.

**Problem 2 — Count terms.** How many terms are in the sum over t=0 through 4? Which Python range represents these labels?

**Answer.** Five terms. Use range(5), which generates 0,1,2,3,4. The mathematical upper bound is included; Python's stop argument is excluded.

**Problem 3 — Record time.** Record j=2 has payment time t_2=5 and amount C_2=100. At an effective period rate r, what is its discounted contribution?

**Answer.** 100/(1+r)^5. The record label two identifies the payment; the exponent five measures its time from the valuation date. The domain requires the chosen discount-rate convention and a supported numerical evaluation.

**Problem 4 — Aggregate a repeated date.** At periods 0,1,1,2, the amounts are -100,20,-5,110. Write the expanded PV and a date-aggregated equivalent.

**Answer.** PV=-100+20/(1+r)-5/(1+r)+110/(1+r)^2. Under the stated linear single-currency rule, this equals -100+15/(1+r)+110/(1+r)^2. Aggregating by date must add amounts, not overwrite one record with another.

**Problem 5 — Multiple indexes.** Using the table in Section 1.5.10 and holdings (2,1), calculate both aggregate dated cash flows and their present value at zero rate.

**Answer.** Period-one flow is 40 and period-two flow is 440. At r=0 their present value is 480. Summing across instruments retains the time label; summing across times then produces one total value.

**Problem 6 — Silent data loss.** A calculation combines periods [1,2,3] and amounts [50,60] with ordinary zip. What can it detect, and what can it not infer?

**Answer.** Ordinary zip emits only (1,50) and (2,60), silently ignoring the extra time label. Using strict=True detects unequal lengths and raises during consumption. It cannot infer whether the missing amount was zero, an unrecorded payment, or an erroneous extra date. Correcting the data requires a stated source and completeness policy.

## 1.5.14 Common Mistakes and Summary

| Mistake | Consequence | Correction |
|---|---|---|
| Treating a subscript as multiplication | Labels become arithmetic factors | Define each indexed quantity |
| Using a record number as a payment time | Discount exponents are wrong | Store explicit times when labels differ |
| Forgetting the zero-based offset | Every payment moves one period | Map mathematical and Python indexes explicitly |
| Omitting a time-zero term | Initial contributions disappear | Define inclusive summation bounds |
| Using ordinary zip for required pairs | Extra records are silently omitted | Enforce equal lengths or explicit strict pairing |
| Converting repeated dates into a plain dictionary | A later record overwrites an earlier one | Preserve records or aggregate deliberately |
| Aligning assets only by array length | Prices match the wrong holdings | Validate and align labels, units, and dates |
| Treating absent records as zero without evidence | Missing data becomes a financial assumption | Establish schedule completeness separately |

Notation should make relationships shorter without hiding meaning. State each symbol's role, its index set, the mapping to storage, and the associated financial time. Preserve repeated records and align multiple indexed quantities before aggregating them.
