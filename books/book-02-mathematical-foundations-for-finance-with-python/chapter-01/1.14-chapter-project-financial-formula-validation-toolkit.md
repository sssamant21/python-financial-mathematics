## 1.14.1 Project Goal and Learning Outcomes

Build a small command-line toolkit that checks reported financial results against explicit mathematical specifications. It should explain whether a result agrees with its formula, whether required constraints hold, and whether the supplied record can be interpreted at all.

The project integrates the chapter's main ideas: objects and domains, parameters and decisions, indexed inputs, equations and inequalities, logical conjunction, assumptions, units, conventions, and executable evidence. Its main deliverable is an inspectable report, not a single unexplained Boolean.

The complete [reference implementation](code/section_1_14.py), [sample batch](data/section-1.14-cases.json), [acceptance checks](code/check_section_1_14.py), and [companion walkthrough](solutions/1.14-project-walkthrough.md) accompany this section. You can implement the requirements first, then compare your work with the reference. No paid data, network service, external package, or cloud account is required.

## 1.14.2 The Problem Statement

A reviewer receives small records containing a formula name, inputs, currency label, and reported result. Some records are correct, some contain arithmetic mistakes, and some are missing the information needed to interpret them. The toolkit should retain each record and attach a clear outcome.

Its three registered model names are `growth`, `simple_accrual`, and `transfer`. They use the already published functions from Sections 1.10–1.13. This is an integration project: it does not introduce a new financial model or silently broaden the domains of those functions.

For growth and accrual, the observation is a scalar reported balance or interest amount. For a transfer, the observation contains reported fee and final account balances, while the proposed transfer itself is an input. The transfer record must satisfy the destination target and source reserve as well as agree with the accounting equations.

The toolkit checks a proposed transfer; it does not select the minimum transfer from Section 1.11. Preserving that distinction prevents a formula validator from unexpectedly becoming an optimizer.

## 1.14.3 Mathematical Specifications

The growth calculation is

\[
A=P(1+r)^n,\qquad P\geq0,\quad r>-1,\quad n\in\{0,\ldots,120\}.
\]

The project adds a teaching limit of 120 periods. It normalizes an explicit rate representation before using the exact growth audit from Section 1.13. That audit includes the power formula, repeated-period reference, round trip, and weak bounds. Related checks are not claimed to be independent proofs.

Simple annual accrual uses

\[
I=Pr\alpha,
\qquad
\alpha=d/360\ \text{or}\ d/365,
\]

under the exact names `ACT/360` and `ACT/365F`. Dates use the half-open interval and constant-principal assumptions from Section 1.10. Negative rates are allowed; principal must be nonnegative.

For a proposed transfer \(x\geq0\), use the Section 1.11 fee definition

\[
g(0)=0,\qquad g(x)=F+kx\quad(x>0),
\]

and equations \(S'=S-x-g(x)\), \(D'=D+x\). Require \(S'\geq R\) and \(D'\geq T\). Inputs and fee parameters are nonnegative; the fee is paid extra by the source. The transfer fee rate is already a decimal fraction, not a quotation to be inferred.

All records use exact rational arithmetic and one declared currency and scale within each record. There is no exchange conversion, contractual rounding, or cent-increment restriction.

## 1.14.4 Define the Outcomes Before Writing Code

| Outcome | Meaning | Example |
|---|---|---|
| PASS | Interpretable record; every registered check passes | Growth observation 121 for 100 at 10% over two periods |
| FAIL | Interpretable record; at least one check fails | Growth observation 110, or a transfer below its reserve |
| INVALID | Record violates its schema or supported input domain | Missing rate, unsupported day count, Boolean period count |

An incorrect numeric observation is usually FAIL, not INVALID. It is legitimate data to investigate. A missing observation or an unsupported object is INVALID because the comparison cannot be performed under the interface.

A transfer can have perfectly correct reported arithmetic and still FAIL because it breaches a constraint. The report retains the individual checks so that an arithmetic mismatch and an infeasible proposal remain distinguishable.

Batch-envelope errors are handled separately. An empty batch, unsupported schema version, missing case identifier, or duplicate identifier prevents a trustworthy batch report and ends the command with exit code 2. Individual records with valid identifiers can be INVALID without stopping their neighboring records.

## 1.14.5 Specify the Input Schema

A document contains exactly `schema_version` and `cases`. The version is integer 1, excluding Boolean values; `cases` is a list of 1–100 records. Identifiers must be unique nonempty strings. Each record contains exactly `id`, `formula`, `currency`, `inputs`, and `observed`.

| Formula | Exact input fields | Observation |
|---|---|---|
| `growth` | `principal`, `rate`, `representation`, `periods` | Reported final balance |
| `simple_accrual` | `principal`, `rate`, `representation`, `start`, `end`, `convention` | Reported interest |
| `transfer` | `source`, `destination`, `reserve`, `target`, `fixed_fee`, `fee_rate`, `transfer` | Object with `fee`, `source_after`, `destination_after` |

Growth and accrual accept rate representations `decimal`, `percent`, and `basis_points`, using the conversion from Section 1.10. Dates must be canonical `YYYY-MM-DD` strings. The currency label must contain three uppercase ASCII letters. This is a syntax check, not membership validation against a currency registry.

Use JSON integers or rational strings such as `"0.01"` and `"3600/73"` for financial values. JSON fractional numeric literals become Python floats and are rejected by the exact arithmetic interface. Boolean values and null are not substitutes for missing numbers.

For example, a complete growth record is:

```json
{
  "id": "growth-correct",
  "formula": "growth",
  "currency": "USD",
  "inputs": {
    "principal": 100,
    "rate": 10,
    "representation": "percent",
    "periods": 2
  },
  "observed": 121
}
```

This record belongs inside the document's `cases` list. Exact keys reject spelling mistakes and unexpected fields rather than discarding them. The JSON loader also rejects duplicate object keys and nonstandard NaN/Infinity tokens, avoiding silent overwriting or nonfinite values at the file boundary.

## 1.14.6 Organize the Implementation

The project adds one executable module and reuses four existing modules in the chapter's `code` directory:

| Module | Responsibility |
|---|---|
| `section_1_10.py` | Rate normalization and simple accrual |
| `section_1_11.py` | Proposed-transfer accounting and constraints |
| `section_1_12.py` | Shared exact rational conversion; growth implementation used by the audit |
| `section_1_13.py` | Exact growth result audit |
| `section_1_14.py` | Record schemas, dispatch, reports, JSON loading, and CLI |

Keep all five modules together. Running the project from the full repository supplies these dependencies; copying only its newest file will not.

The reference separates `load_document`, `run_batch`, and `evaluate_case`. Loading handles JSON syntax; batch validation handles identity and envelope rules; case evaluation handles the selected model and observation. `json_ready` converts fractions to exact strings for serialization. It does not round or silently convert them to floats.

The dispatcher uses explicit branches for the registered names. It does not execute a formula string, import a module supplied by a record, or guess a model from input shape. Adding a model requires adding its specification, schema, implementation branch, and checks deliberately.

## 1.14.7 Build the Report Contract

A report contains schema version, comparison policy, scope, status counts, overall success, and the ordered case results. Each result retains the submitted record and includes its status, named checks, details, and any expected input error.

For a valid growth observation of 110, the report includes reference 121 and discrepancy −11. For an invalid record, checks are empty and details are null; an error identifies why evaluation could not proceed. Empty checks do not produce a PASS because INVALID is assigned explicitly rather than inferred through `all([])`.

Fractions are serialized as exact strings, so the accrual value \(3600/73\) remains `"3600/73"`. Integers used as control fields and Boolean check outcomes retain their JSON types. A consumer must understand this report schema rather than assume every numeric-looking string is a float.

Overall success requires every supplied case to be PASS. It is not a majority vote. The report's scope says that it covers only the declared cases and registered models; it does not claim that a passing record represents a suitable real transaction or verified external data.

## 1.14.8 Work Through the Sample Batch

The supplied batch has eight records with expected outcomes:

| Identifier | Outcome | Reason |
|---|---|---|
| `growth-correct` | PASS | Exact growth result 121 |
| `growth-missing-period` | FAIL | Observation 110 omits one period |
| `growth-missing-rate` | INVALID | Required input absent |
| `accrual-act360` | PASS | 10,000 at 6% for 30/360 gives 50 |
| `accrual-unsupported` | INVALID | `ACT/365` is not an accepted exact convention name |
| `transfer-feasible` | PASS | Fee and balances agree; both constraints hold |
| `transfer-reserve-breach` | FAIL | Arithmetic agrees but final source 288 is below reserve 300 |
| `growth-zero-periods` | PASS | Zero periods preserve principal |

For the failing transfer, fee is \(5+0.01(700)=12\). Source balance is \(1000-700-12=288\); destination balance is \(200+700=900\). The fee and both reported balances are correct. Only the source-reserve condition fails. This is a useful test of whether the toolkit preserves distinct meanings instead of calling every failure a formula error.

Expected totals are four PASS, two FAIL, and two INVALID. Deliberate negative examples remain in the fixture; do not change their observations just to make the default batch return overall success.

## 1.14.9 Run the Project

From the chapter directory:

```text
python code/section_1_14.py
python code/section_1_14.py data/section-1.14-cases.json --output validation/local-section-1.14-report.json
python code/check_section_1_14.py
```

On Windows, `py` may replace `python`. In PowerShell, inspect the immediately preceding command's exit code with `$LASTEXITCODE`; in a POSIX shell, use `echo $?`. Inspect the code after the command of interest, before another command replaces it.

The first two commands intentionally return exit code 1 because the demonstration batch contains FAIL and INVALID records. They print:

```text
growth-correct: PASS
growth-missing-period: FAIL
growth-missing-rate: INVALID
accrual-act360: PASS
accrual-unsupported: INVALID
transfer-feasible: PASS
transfer-reserve-breach: FAIL
growth-zero-periods: PASS
PASS=4 FAIL=2 INVALID=2
```

The second command also writes the JSON report to the explicitly supplied path. Without `--output`, it writes no report file. A requested output path must differ from the input path. Use a new output filename when you want to retain an earlier local run.

| Exit code | Meaning |
|---:|---|
| 0 | Every supplied case passes |
| 1 | Batch evaluated; at least one case is FAIL or INVALID |
| 2 | CLI, file, JSON, or batch-envelope error |

The acceptance-check command should return zero. Its job is to verify all expected outcomes, including the demonstration command's nonzero result.

## 1.14.10 Complete the Build in Milestones

1. Write the three mathematical contracts and record domains before implementing dispatch.
2. Implement exact-key and identity validation. Verify missing and unexpected fields explicitly.
3. Normalize rate representations and dates, then call the published functions. Keep the submitted observations unchanged.
4. Build named result checks, preserve details, and assign PASS, FAIL, or INVALID according to the contract.
5. Serialize rational results without rounding and add the command-line exit behavior.
6. Run the mixed fixture, all-pass subsets, malformed inputs, and acceptance checks. Record evidence and explain limitations.

Do not replace a missing value with zero or catch every possible exception as INVALID. The reference catches expected conversion and domain errors per case. An unexpected programming exception should remain visible so it can be repaired instead of disguised as an ordinary data issue.

The project limits input files to 1,000,000 bytes and batches to 100 records for a small teaching workload. These are interface limits, not a general service-hardening claim. It runs trusted local exercises and does not implement a production workload or security boundary.

## 1.14.11 Acceptance Tests and Evidence

The [acceptance script](code/check_section_1_14.py) verifies more than the displayed totals. It inspects the named failure checks, exact serialized values, zero-action fee behavior, rate-representation equivalence, malformed schemas, invalid dates, duplicate identities, strict JSON loading, and input immutability.

It also runs the command as a subprocess to verify exit codes 0, 1, and 2, report writing, and input-path protection. Temporary files are removed after the checks. The reference check script refuses optimized execution because its assertions must remain active.

The [validation record](validation/section-1.14.json) contains the tested runtime, commands, outputs, acceptance counts, and hashes of the project artifacts and imported modules. Its PASS means the acceptance checks behaved as expected, not that every sample record passed. Linux execution is recorded; Windows execution is not claimed.

No test can confirm that an external source labeled its rate or currency correctly. The project verifies the declared convention and supplied inputs. Independent source review, economic model assessment, and canonical editorial review remain separate work.

## 1.14.12 Six Project Challenges

1. Correct the missing-period observation in a copied batch and predict the new counts. Does the whole batch now pass?
2. Replace the unsupported accrual convention with `ACT/365F`. What exact observation makes that record pass?
3. Make the reserve-breach transfer meet a target of 700 while preserving the original reserve. Update every affected input and observed value.
4. Add a zero-transfer case with source equal to reserve and destination equal to target. What fee must the report expect despite a positive fixed-fee parameter?
5. Express the same 10% growth rate as decimal, percent, and basis points. Verify equal references without relaxing exact comparison.
6. Produce one invalid case and one malformed batch. Explain why their command-line handling differs and preserve evidence for both.

Keep these changes in separate local copies so the shipped fixture remains a reproducible demonstration. The [companion walkthrough](solutions/1.14-project-walkthrough.md) gives exact answers and explains the acceptance criteria.

## 1.14.13 Review and Extension Boundaries

A complete submission includes the specification, runnable code, fixture, report, acceptance results, and explanation of at least one valid-but-failing record and one invalid record. A reviewer should be able to explain a status from named checks without reading hidden assumptions into the record.

Potential extensions include an explicit transfer-fee quotation field, additional day-count conventions, irregular cash-flow dates, or contractual rounding. Each extension requires a changed specification and tests. Adding a string to an accepted-name list without implementing its actual rules is not support for a new convention.

## 1.14.14 Summary and Sources

The toolkit combines mathematical specifications with explicit schemas and reproducible reports. It keeps invalid data separate from a valid calculation that fails a comparison or constraint. Exact rational values, named checks, deliberate negative examples, and tested exit codes make its behavior inspectable.

The reference supports three registered small models, one currency per record, the stated domains, and exact comparison. It does not implement live data ingestion, currency conversion, contractual rounding, extra day-count variants, optimization, or production accuracy policies.
