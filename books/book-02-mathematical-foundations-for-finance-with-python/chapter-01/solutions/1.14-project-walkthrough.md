## Challenge 1 — Correct One Observation

Change `growth-missing-period` observed value from 110 to 121. Its two-period calculation is 100 × 1.1 × 1.1 = 121. Counts become PASS=5, FAIL=1, INVALID=2. Exit code remains 1; correcting one case does not eliminate the remaining failure or missing information.

The original observation was interpretable but wrong, so its original status was FAIL. It was not a schema error.

## Challenge 2 — Change the Accrual Convention

With `ACT/365F`, 30 actual days, principal 10,000, and simple annual rate 6%, interest is 10,000 × 0.06 × 30/365 = 3600/73. Supply observed value `"3600/73"` as a JSON string. That preserves the exact rational amount. A rounded decimal is a different value and does not pass this exact-comparison interface.

Changing only the convention while leaving observed value 50 makes the record valid but FAIL. The previously unsupported convention produced INVALID. This distinction shows why a schema repair and a formula correction are separate steps.

## Challenge 3 — Repair the Transfer Scenario

Set destination target to 700 and proposed transfer to 500. Keep source 1000, destination 200, reserve 300, fixed fee 5, and decimal fee rate `"0.01"`. Report fee 10, final source 490, and final destination 700.

The source reserve and destination target both pass. The combined account total falls from 1200 to 1190, exactly the fee of 10. Changing only the target to 700 while retaining transfer 700 still fails the source reserve: the smaller target does not reverse the source debit.

This is a proposed-transfer validator. It does not automatically search for or replace the submitted transfer with 500.

## Challenge 4 — Do Nothing Without a Fee

For example, use source 300, reserve 300, destination 200, target 200, fixed fee 5, decimal fee rate `"0.01"`, and transfer 0. Observed fee must be 0, source after must be 300, and destination after must be 200. All checks pass.

A positive fixed-fee parameter does not trigger a fee when no transfer is made under this model. Charging five at zero would change the piecewise fee definition. Changing the data to hide that discrepancy would not be a valid repair of the implementation.

## Challenge 5 — Equivalent Rate Quotations

For growth with principal 100 and periods 2, these input pairs all produce reference 121:

| `rate` | `representation` |
|---|---|
| `"0.10"` | `"decimal"` |
| `10` | `"percent"` |
| `1000` | `"basis_points"` |

The normalized rate is exactly 1/10. Observed value 121 passes in each case. Decimal numeric literal `0.10` becomes a Python float under the loader and is rejected by the exact-input interface; use the string shown above.

## Challenge 6 — Invalid Case and Malformed Batch

A growth record with `periods: true` has a stable identifier but violates the project domain. It becomes INVALID, neighboring records still evaluate, and the command exits 1.

A document with duplicate case identifiers cannot provide unambiguous batch identity. It ends the command with exit code 2 before producing a report. An empty list of cases also receives exit code 2; it cannot produce success through an empty conjunction.

Duplicate JSON object keys and NaN/Infinity tokens are rejected during loading. A missing rate inside an otherwise identifiable record is instead a per-case INVALID result. Preserve the submitted file, command, observed exit code, and error or result details when diagnosing either outcome.

## Reference Design Decisions

Exact key matching catches misspellings and unimplemented metadata. The shared currency label is syntactically checked but not converted or validated against a registry. Every record already uses one currency and scale. Rate representation is mandatory for growth and accrual; transfer fee rate is explicitly decimal.

The exact growth audit includes related checks as well as a repeated-period reference. Their agreement does not constitute an independent economic validation. Accrual uses the published two-convention implementation. Transfers compare every observed accounting field and evaluate both constraints, so a correct accounting observation can still fail feasibility.

Expected input errors become INVALID. Unexpected programming exceptions remain visible. The CLI uses code 1 for evaluated failures and code 2 for file, JSON, envelope, or argument problems. A successful acceptance run checks those behaviors, rather than expecting every demonstration record to pass.
