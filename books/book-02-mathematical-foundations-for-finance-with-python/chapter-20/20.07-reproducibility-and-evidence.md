# 20.7 — Reproducibility and Evidence

## Learning objectives

Distinguish repeatability from independent reproducibility; identify the inputs, software, assumptions and execution environment needed to reconstruct a financial calculation; create an evidence manifest; and report validation status without overstating what was checked.

## 1. Why evidence matters

A number without its inputs and assumptions is hard to investigate. A validation record connects the calculation and its expected behavior to a particular source version, data set, environment, command, output and reviewer. This supports debugging and review; it does not itself prove that the model is suitable.

**Repeatability** means obtaining consistent results when the same procedure is repeated under the same conditions. **Reproducibility**, in this section, means another person can reconstruct and assess the result using recorded materials and a comparable environment. Different disciplines use these words differently, so state the intended meaning.

## 2. What to capture

| Evidence | Examples | Purpose |
|---|---|---|
| Model specification | Formula, units, rate convention, domain | Defines what is being tested |
| Source identity | Repository, commit, dirty-tree state | Identifies code actually used |
| Inputs | Synthetic data, input hash, as-of date | Identifies the scenario |
| Execution | Command, timestamp, exit code, environment | Describes what ran and where |
| Expected and actual | Independent reference, result, tolerance | Supports assessment |
| Review | Reviewer, scope, findings, decision | Separates execution from approval |

Do not place credentials, sensitive customer data, or unredacted financial records in a manifest or public repository. A hash identifies bytes for comparison; it does not anonymize low-entropy or guessable data. Store sensitive evidence according to the applicable access and retention policy.

## 3. Seeds and determinism

For generated tests, record the random generator, seed, parameters, test count and software version. A seed makes a sequence reproducible only under the generator and environment's stated guarantees; algorithms, library versions, parallel execution and hardware can affect results. A fixed seed does not make a test representative or statistically valid.

For parallel computations, ordering can change floating-point results because addition is not associative. Specify tolerances and compare against an appropriate reference. If exact replay is required, record the execution settings and test that replay in the intended environment.

## 4. Hashes, provenance and limitations

A SHA-256 digest of a file detects a byte change when compared with a trusted previously recorded digest. It does not establish authorship, correctness, authenticity, or that the file was actually used. Protect the manifest and obtain independent provenance where required. A commit ID alone does not capture uncommitted changes, external inputs, dependencies or runtime configuration.

Record the source commit and dirty status; identify dependency versions and input files; retain the exact command and result. A lock file can constrain dependencies, but platform-specific libraries and system settings may still matter.

## 5. Evidence states

Use distinct states:

1. **Authored:** source exists; execution is not implied.
2. **Executed:** command ran in a recorded environment; record its result.
3. **Reviewed:** an identified reviewer assessed a defined scope and findings.
4. **Approved:** an authorized decision was recorded for a stated use.

An executed test can fail; a passing test can have incomplete coverage. Neither execution nor review implies production approval. Never populate a pass status simply because code or a manifest exists.

## 6. Small reproducibility example

For \(PV=100e^{-rT}\), fix \(r=0\) and \(T=2\). The independently derived expected value is 100. Record units, inputs, formula, version, command, actual output, tolerance and result. With zero rate, an exact reference exists; other cases may need a documented numerical tolerance.

The companion lab writes a local JSON manifest for synthetic inputs. Its default status is **not run**, and it does not execute a test or assert approval. Populate execution fields only after real execution and review.

## 7. Twenty worked exercises

1. A source file alone is evidence of authorship, not execution.
2. A recorded exit code describes an execution outcome, not model suitability.
3. A passing test does not imply independent review.
4. A seed without the generator and version may be insufficient for replay.
5. A fixed seed does not prove representative coverage.
6. A changed input file normally changes its cryptographic digest.
7. A digest does not establish that the source is trustworthy.
8. A public hash of a guessable secret can leak information.
9. A commit ID omits uncommitted changes.
10. A dependency lock file does not completely specify hardware and system libraries.
11. An expected value should be independently justified.
12. A tolerance should state scale and units.
13. A reviewer should identify scope and unresolved findings.
14. Approval should name the intended use and authority.
15. An execution can be recorded as failed.
16. A manifest should not label unexecuted checks as passed.
17. Synthetic test data avoids publishing real customer records.
18. An input as-of date is material when data changes over time.
19. Parallel summation order can change floating-point output.
20. Evidence supports review but does not automatically certify a model.

## 8. Twelve-step hands-on lab

1. Define a synthetic valuation scenario and its units.
2. Record the formula and admissible input domain.
3. Identify source repository and exact commit.
4. Record whether the working tree contains uncommitted changes.
5. Record Python and dependency versions.
6. Hash the exact synthetic input bytes.
7. Record the command and chosen tolerances.
8. Derive the expected result independently.
9. Execute the command in a suitable environment when validation is scheduled.
10. Capture actual output, exit status and execution time.
11. Record discrepancies and independent review findings.
12. Protect and retain evidence according to the applicable policy.
