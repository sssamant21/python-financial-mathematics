## Learning objectives

Distinguish mathematical derivation, software verification, numerical validation, and financial model validation; design independent reference calculations; define traceable requirements and acceptance gates; classify test evidence; and communicate the limitations of unexecuted checks.

## 1. Why a correct calculation can still be wrong

A program can evaluate a formula exactly while the formula represents the wrong financial question. For example, a program that discounts a cash flow by \((1+r)^T\) may be correctly implemented, but inappropriate if \(r\) is a continuously compounded rate. Conversely, a financially appropriate model may be implemented with an incorrect sign or cash-flow date.

A defensible workflow distinguishes **four layers**:

1. **Mathematical formulation:** Is the equation derived correctly from stated assumptions?
2. **Software verification:** Does the implementation conform to the mathematical specification?
3. **Numerical validation:** Does the algorithm deliver sufficiently accurate numerical approximations for the intended domain?
4. **Model validation:** Do the assumptions, inputs, calibration, and boundaries represent the intended real-world financial use?

The term *validation* is used differently across industries; always define the scope of a claim.

## 2. A testable financial specification

Consider the present value of a future cash flow \(F\), paid after \(T\) years, discounted at a continuously compounded rate \(r\):

\[
\boxed{PV(F,r,T)=Fe^{-rT}}.
\]

State explicitly that \(F\) and \(PV\) are currency, \(r\) is inverse years, and \(T\ge0\) is years. Negative rates may be allowed. The formula assumes deterministic cash flows, a constant continuous discount rate, and no default or liquidity adjustments.

A specification should identify valid input domains, units, expected outputs, exceptional conditions, and numerical precision requirements. The function must reject nonfinite values rather than return them as apparently valid financial results.

## 3. Verification with independent references

A known-value benchmark for \(r=0\) is \(PV=F\). At \(T=0\), \(PV=F\) for any finite \(r\). A reference for \(F=1000,r=0.05,T=2\) is \(1000e^{-0.1}\).

An independent test should derive its expected value from mathematics, not simply call the function under test with the same inputs and compare the output to itself.

An important verification strategy is to compare two mathematically equivalent implementations, such as continuous discounting and a nominal-compounding conversion, while ensuring they do not share the same faulty conversion helper.

## 4. Mathematical properties

The formula has useful properties:

\[
PV(F_1+F_2,r,T)=PV(F_1,r,T)+PV(F_2,r,T)
\]

and, for \(F>0\) and \(T>0\),

\[
\frac{\partial PV}{\partial r}=-TFe^{-rT}<0.
\]

These give linearity and monotonicity tests. A test must state the conditions under which a property applies: negative cash flows reverse the sign of the monotonicity claim.

A property-based check complements, rather than replaces, independent known-value benchmarks.

## 5. Numerical validation

For small \(|rT|\), the exponential discount factor is close to one; direct \`math.exp(-r*T)\` is usually appropriate for a simple present value. For differences of nearby exponential values, \`math.expm1\` can reduce cancellation. For rate conversion, \`math.log1p\` can improve accuracy near zero.

Overflow and underflow require explicit policies. Underflow to zero may be an acceptable representational limit in some contexts, but must not be confused with a financially exact zero. Rejecting nonfinite outputs is a reasonable educational default.

Use a documented absolute/relative tolerance pair:

\[
|a-b|\le \mathrm{atol}+\mathrm{rtol}|b|.
\]

This numerical criterion is not an estimate of model uncertainty.

## 6. Model validation and intended use

A continuously discounted present value may be appropriate for a deterministic benchmark, but insufficient for a security exposed to default, uncertain cash flows, taxes, liquidity effects, or a term structure of interest rates. A valid model review asks whether the rate convention, day count, currency, timing, and risk assumptions match the decision.

Model validation evidence may include sensitivity analysis, comparison against external data, independent review, and documented limitations. It cannot be established solely through unit tests.

## 7. Requirements-to-evidence traceability

| Requirement | Evidence | Claim allowed |
|---|---|---|
| Correct formula | Independent symbolic derivation | Mathematical derivation documented |
| Zero-rate and zero-horizon behavior | Reference test source and recorded execution | Behavior checked only if executed |
| Finite input and output policy | Boundary tests | Guardrails verified only if executed |
| Floating-point accuracy | Benchmark comparisons and tolerance record | Numerical behavior measured for tested domain |
| Appropriate financial assumptions | Domain review and approved intended use | Model validation only after review |
| Reproducibility | Code revision, environment, and outputs | Reproduction possible when evidence retained |

Writing a check script is not the same as executing it. A successful local run is not the same as independent review or production approval.

## 8. Validation lifecycle

A practical staged workflow is: document the specification; derive reference values; author unit, property, and boundary tests; execute tests in a controlled environment; review failures; independently review the mathematics and financial assumptions; record versioned evidence; and approve or reject the release against explicit gates.

For this book, **the current phase is manuscript and companion-source publication**. Comprehensive runtime validation, independent mathematical review, and canonical approval are intentionally deferred until the Book 02 manuscript is complete.

## 10. Twenty worked exercises

**1.** Define software verification.  
*Solution:* Checking that software implements the stated mathematical specification.

**2.** Define numerical validation.  
*Solution:* Checking the accuracy and stability of numerical approximations in a stated domain.

**3.** Define model validation.  
*Solution:* Assessing whether assumptions and inputs are suitable for the intended use.

**4.** Write the continuous-discounting formula.  
*Solution:* \(PV=Fe^{-rT}\).

**5.** What are the units of \(r\)?  
*Solution:* Inverse years when \(T\) is years.

**6.** What is \(PV\) at \(r=0\)?  
*Solution:* \(F\).

**7.** What is \(PV\) at \(T=0\)?  
*Solution:* \(F\).

**8.** Find \(PV\) for \(F=1000,r=0.05,T=2\).  
*Solution:* \(1000e^{-0.1}\).

**9.** What is the sign of \(\partial PV/\partial r\) for \(F,T>0\)?  
*Solution:* Negative.

**10.** State additivity.  
*Solution:* \(PV(F_1+F_2,r,T)=PV(F_1,r,T)+PV(F_2,r,T)\).

**11.** Can negative rates be handled mathematically?  
*Solution:* Yes, if allowed by the specification.

**12.** Why reject nonfinite inputs?  
*Solution:* To avoid silently propagating invalid numeric states.

**13.** What is an independent oracle?  
*Solution:* A separately derived expected result used to assess the implementation.

**14.** Is calling the function twice an independent test?  
*Solution:* No.

**15.** What is a boundary test?  
*Solution:* A test at or near a valid-domain boundary.

**16.** State a mixed tolerance rule.  
*Solution:* \(|a-b|\le\mathrm{atol}+\mathrm{rtol}|b|\).

**17.** Does numerical tolerance measure financial forecast uncertainty?  
*Solution:* No.

**18.** What distinguishes a drafted check from an executed test?  
*Solution:* Recorded execution evidence and observed results.

**19.** Can passing unit tests alone validate a financial model's assumptions?  
*Solution:* No.

## 11. Applied problems

**A. Rate conventions:** Compare continuous discounting against nominal monthly discounting after converting rates correctly.

**B. Negative cash flows:** Revisit rate monotonicity for \(F<0\) and explain the reversed derivative sign.

**C. Numerical limits:** Specify expected behavior for an extremely large positive discount exponent and an underflowing discount factor.

**D. Traceability:** Map each mathematical requirement to a reference, a check, an execution record, and a reviewer.

**E. Release decision:** Explain why a passing local script is insufficient for canonical publication without mathematical and editorial review.

## 12. Acceptance criteria

The source must enforce finite inputs, nonnegative horizons, consistent units, and explicit nonfinite-output handling. Reference checks must be derived independently and must not claim execution or certification before evidence exists. The manuscript must separate implementation verification from financial model validation.
