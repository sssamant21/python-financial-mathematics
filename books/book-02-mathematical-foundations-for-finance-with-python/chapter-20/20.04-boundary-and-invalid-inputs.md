## Learning objectives

Specify input contracts; distinguish valid boundaries from invalid values; derive limiting cases; design tests at, inside, and outside domains; and interpret numerical failures.

## 1. Why boundaries matter

A model can work for typical inputs but fail at zero, an endpoint, or a nearly singular denominator. A boundary is a point at or near the edge of an explicitly defined domain. Invalid inputs violate the contract; exceptional but valid inputs deserve a meaningful result or a documented numerical failure.

State units, types, admissible ranges, missing-value policy, output behavior, and financial conventions. Passing tests does not establish that a contract fits a business use case.

## 2. Present-value contract

For annual effective rate \(r\), integer horizon \(n\ge0\), and finite signed cash flow \(F\), define

\[
PV(F,r,n)=\frac{F}{(1+r)^n},\qquad r>-1.
\]

This contract requires a positive accumulation factor even at \(n=0\). Negative rates above \(-1\) are valid and can produce a discount factor greater than one. Rates are decimals per year, not percentages. Signed amounts represent receipts or payments. Other models may use different domains.

At \(n=0\), \(PV=F\); at \(r=0\), \(PV=F\). At \(r=-1\), the denominator vanishes for positive \(n\), so reject it consistently. As \(r\to-1^+\), PV for a positive cash flow and positive horizon grows without bound; admissible inputs may overflow floating-point representation.

## 3. Removable singularity: ordinary annuity

For payment \(C\) at the end of each of \(n\) periods,

\[
A(C,r,n)=C\sum_{k=1}^n(1+r)^{-k}
=C\frac{1-(1+r)^{-n}}{r},\quad r\ne0.
\]

At \(r=0\), the sum gives \(A(C,0,n)=Cn\), including \(n=0\). Division by zero in the closed form is removable; rejecting zero would exclude a meaningful case. Near zero use numerically stable log1p and expm1 functions, while recognizing that conditioning and floating-point range still limit accuracy. A tiny nonzero rate is not automatically zero.

## 4. Classes of inputs

| Class | Example | Behavior under this lab's contract |
|---|---|---|
| Typical valid | \(r=0.05,n=3\) | Calculate if representable |
| Boundary valid | \(n=0\), \(r=0\) | Return the defined result |
| Near boundary valid | \(r=-0.999\) | Calculate if representable or report overflow |
| Outside domain | \(r=-1\), \(n=-1\) | Raise ValueError |
| Wrong type | string, Boolean, fractional period | Raise TypeError |
| Missing or non-finite | None, NaN, infinity | Reject; never silently replace |
| Numerically extreme | enormous valid horizon | Detect overflow; underflow may yield zero |

A finite result does not establish economic validity. Underflow may erase a small positive value; applications requiring detection need a stronger policy, log-domain output, or higher precision. The lab is illustrative, not production-ready.

## 5. Test design

For each boundary, test the endpoint and values on each admissible side. For floating-point inputs, use representable neighbors such as math.nextafter(-1.0, math.inf), rather than assuming a decimal perturbation survives rounding. Also cover invalid types, empty inputs, mismatched lengths, and non-finite elements where applicable.

Record test ID, contract, input, independent expected result or exception, tolerance, actual result, environment, and review status. Check error types; avoid fragile full-message assertions unless messages are part of the public API.

## 6. Other financial and mathematical domains

- **Log return:** \(\log(P_1/P_0)\) requires strictly positive prices under the usual real-valued convention. Zero and negative prices require a different model, not silent clipping.
- **Weights:** an empty vector is not a portfolio; equal lengths, finite entries and explicit leverage or short-sale rules are necessary. A sum of one is a constraint, not proof of optimality.
- **Matrices:** a linear system requires compatible dimensions; a singular matrix can have no solution or multiple solutions. An ill-conditioned matrix can produce unstable results even if invertible.
- **Solvers:** define endpoints, convergence limits, tolerances and failure policy. Check endpoints separately. A sign change supports existence only under continuity; it does not guarantee uniqueness.
- **Dates:** specify day-count convention, relevant time zone, ordering, and whether same-day cash flows are allowed.

## 7. Exceptions and safeguards

Validate before computing. Distinguish type errors, domain errors, and numerical overflow. Do not clamp a negative rate to zero, replace NaN with zero, or catch every exception and return a plausible price. Record rejected input safely without exposing sensitive data. Validation rules should be consistent across interfaces.

The accompanying functions use Python floats and the standard library. Python's bool is a subclass of int, so it is explicitly rejected. These examples accept finite real inputs convertible to float and nonnegative integer periods. Other numeric types need a separate contract.

## 8. Twenty worked exercises

1. **Zero horizon:** \(PV(100,0.05,0)=100\).
2. **Zero rate:** \(PV(100,0,2)=100\).
3. **Positive rate:** \(PV(125,0.25,1)=100\).
4. **Negative rate:** \(PV(100,-0.1,2)=100/0.81\approx123.45679\).
5. **Rate -1:** rejected by the chosen contract.
6. **Rate below -1:** rejected even if integer powers may be defined algebraically.
7. **Zero payment:** an annuity with \(C=0\) has value zero mathematically.
8. **Zero periods:** the empty annuity sum is zero.
9. **Zero rate annuity:** \(C=100,n=3\) gives 300.
10. **One-period annuity:** \(C=100,r=0.25\) gives 80.
11. **Signed cash flow:** \(PV(-100,0.25,1)=-80\).
12. **Fractional period:** 1.5 is rejected by this integer-period contract.
13. **Boolean period:** True is rejected despite being an integer subclass.
14. **NaN amount:** rejected because it is not finite.
15. **Infinite rate:** rejected because it is not finite.
16. **Near-zero rate:** compare with 300 using justified tolerance, not exact equality.
17. **Near -1:** a mathematically valid rate can lead to overflow; report it.
18. **Logarithm:** \(\log(0)\) is outside the real log domain.
19. **Root at endpoint:** evaluate the endpoint before requiring opposite signs.
20. **Singular system:** a zero determinant alone does not distinguish no solutions from infinitely many.
