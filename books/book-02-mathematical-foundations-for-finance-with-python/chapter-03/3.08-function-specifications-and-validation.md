# 3.8 — Function Specifications and Validation

**Status:** Draft; runtime validation and editorial review pending.

A formula is not a complete software specification. Financial software must describe valid inputs, output units, boundary conventions, assumptions, and how invalid requests are handled. A mathematically correct expression can still produce an incorrect business result if its software contract is ambiguous.

## Learning objectives

Define a mathematical function's domain and range; write explicit preconditions and postconditions; distinguish exact rational arithmetic from approximate floating-point arithmetic; test boundary values, invariants, and round-trip identities; and separate mathematical validation from business-model validation.

## 1. Mathematical contract versus implementation contract

For a one-period present-value function,

$$PV(C,r)=\frac{C}{1+r},$$

a mathematical contract might state $C\ge0$ and $r>-1$, with output in the same currency as $C$. The function is defined for every input in that domain. An implementation contract adds accepted Python types, exception behavior, and representation of results.

For example, our reference implementation accepts integers, rational strings, and \`fractions.Fraction\`, returning an exact \`Fraction\`. It rejects Python floats (including values such as \`0.1\`) to avoid accidental binary rounding. It also rejects booleans, even though Python considers \`bool\` a subclass of \`int\`.

A contract should say whether zero cash flow is permitted, whether negative rates greater than -1 are permitted, and whether currency conversion or rounding is performed. In this lab, zero cash flow is allowed and no currency rounding occurs.

## 2. Preconditions, postconditions, and invariants

A **precondition** is a condition required before a function is evaluated; a **postcondition** is a property guaranteed for a valid result.

For the present-value function, preconditions are $C\ge0$ and $r>-1$. A postcondition is

$$PV(C,r)(1+r)=C.$$

This is a useful exact-arithmetic invariant. It checks consistency without relying on one hard-coded expected value.

For the linear profit model

$$\Pi(q)=(p-v)q-F,$$

the reference contract requires $q\in\mathbb Z_{\ge0}$ and $p,v,F\ge0$. It returns an exact rational profit, which may be negative. A valid profit result must satisfy

$$\Pi(q)+F=(p-v)q.$$

Notice that **profit itself need not be nonnegative**. Requiring nonnegative outputs would be a bug.

## 3. Units and dimensional consistency

Suppose $p$ and $v$ are measured in currency per item, $q$ in items, and $F$ in currency. Then

$$(p-v)q-F$$

has units of currency. A discount rate is dimensionless over the specified period. A rate entered as 10 (meaning 10%) rather than 0.10 (meaning 10%) changes the result dramatically; a clear interface must specify the convention.

Exact fractions are not a replacement for unit checking: the numeric expression $10+3$ is valid Python even when one operand means dollars and the other means items.

## 4. Boundaries and partitions

A good test suite includes:

| Situation | Example | Expected behavior |
|---|---|---|
| Ordinary valid input | $PV(110,1/10)$ | 100 |
| Boundary valid input | $PV(0,0)$ | 0 |
| Negative cash flow | $PV(-1,0)$ | Reject under this contract |
| Singular rate | $PV(100,-1)$ | Reject |
| Rate below singularity | $PV(100,-2)$ | Reject |
| Negative but valid rate | $PV(100,-1/2)$ | 200 |
| Wrong representation | Float \`0.1\` | Reject |
| Wrong semantic type | Boolean \`True\` | Reject |

For piecewise functions, test values below, at, and above each threshold. For whole-unit quantities, test zero, a positive integer, a negative integer, and a noninteger.

## 5. Mathematical properties as tests

Example-based tests verify particular outputs. **Property-based reasoning** checks relationships that should hold for many inputs:

- **Identity:** $PV(C,r)(1+r)=C$ for valid $C,r$.
- **Linearity in cash flow:** $PV(C_1+C_2,r)=PV(C_1,r)+PV(C_2,r)$ for nonnegative $C_1,C_2$.
- **Profit differences:** $\Pi(q+1)-\Pi(q)=p-v$.
- **Zero-rate identity:** $PV(C,0)=C$.
- **Monotonicity:** For fixed $C>0$, present value decreases as $r$ increases over $r>-1$.

Finite tests provide evidence of correctness; they do not constitute a proof for every possible input. The algebraic identities establish the underlying mathematical properties.

## 7. Model validation versus code validation

Passing tests shows that software behaves consistently with its **specified model**. It does not prove the model represents reality. A fixed unit price may be an invalid assumption for a market with volume discounts; a constant variable cost may fail after capacity expansion. Business-model validation requires independent evidence, documented assumptions, and review by appropriate domain owners.

For production financial systems, also consider currency minor units, rounding policy, transaction dates, timezone conventions, auditability, exception handling, versioned assumptions, and reproducible test evidence. This introductory lab intentionally leaves those features out.

## 8. Exercises

**1.** State the preconditions and output units of $PV(C,r)$ under the lab contract.

**2.** Explain why the profit function should permit negative outputs while rejecting negative fixed costs.

**3.** Write a test that verifies $PV(110,1/10)=100$ without using a float.

**4.** Give three tests for the whole-unit quantity boundary.

**5.** Derive an invariant for $\Pi(q)=(p-v)q-F$.

**6.** Explain why passing every software test does not prove that a financial forecast is accurate.

**7.** A caller supplies rate \`10\` intending 10%. What value does the formula interpret it as, and what contract clarification prevents the error?

### Worked answers

1. $C\ge0$, $r>-1$; output is in the same currency as $C$.
2. Losses are valid profit outputs, whereas the model defines fixed cost as nonnegative.
3. \`assert present_value(110, "1/10") == 100\`.
4. Quantity 0 should succeed, quantity -1 should fail, and quantity "1/2" should fail; also test a positive integer.
5. $\Pi(q)+F=(p-v)q$, by rearrangement.
6. Tests check implementation against assumptions, not whether the assumptions predict actual outcomes.
7. Rate 10 means 1000%, not 10%; document that rates are decimal fractions (0.10 for 10%).
