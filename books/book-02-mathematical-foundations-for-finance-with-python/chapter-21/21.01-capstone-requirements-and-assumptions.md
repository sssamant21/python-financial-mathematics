# 21.1 — Capstone Requirements and Assumptions

**Status:** Draft — comprehensive runtime validation and independent mathematical/editorial review pending.

[Book 02](../README.md) · [Master table of contents](../MASTER-TOC.md)

## Learning objectives

Translate an educational financial question into a testable specification; document scope, units, assumptions and limitations; define module interfaces and acceptance evidence; and distinguish a draft toolkit from a production-approved model.

## 1. Capstone purpose

The capstone integrates deterministic financial mathematics from Book 02 into a small, reproducible Python toolkit. Given synthetic inputs, it should calculate cash-flow values, explore sensitivities, solve selected linear and optimization problems, and describe continuous-time account scenarios. Each calculation must expose its assumptions and limitations.

The intended use is **education and model-validation practice**, not investment advice or production valuation. The capstone does not claim that its assumptions fit a particular institution or instrument.

## 2. Scope and boundaries

| Area | Intended capability | Key restriction |
|---|---|---|
| Cash flows and rates | Present value under a documented rate convention | Constant deterministic rate in the initial example |
| Sensitivity | Analytic and numerical derivatives and approximation | Explicit step size and tolerance |
| Linear algebra | Small linear systems and replication examples | Dimension, rank and conditioning checks |
| Optimization | Small deterministic allocation examples | Separate feasibility and optimality evidence |
| Continuous time | Account growth and flows | Explicit time units and boundary policy |
| Evidence | Benchmarks, tests, assumptions and review records | Pending evidence is never called passed |

Probability, stochastic processes, taxes, transaction costs, default, market impact, and live market data are outside this initial scope unless a later specification explicitly adds them. A result is meaningful only for its stated inputs and model.

## 3. A reference valuation contract

For signed cash flows \(C_i\) at times \(t_i\ge0\), in a common currency, with a constant continuous annual rate \(r\),

\[
V=\sum_{i=1}^{m}C_i e^{-rt_i}.
\]

The rate is a decimal per year and time is measured in years. Inputs must be finite real values; negative cash flows and negative rates are allowed. An empty sequence has value zero. Negative times and non-finite values are rejected. Mathematically valid inputs can exceed finite floating-point range, so numerical failure must be reported explicitly.

**Known values:** At \(r=0\), flows \((100,1)\) and \((200,2)\) have value 300. At \(r=\ln2\), a payment of 100 at year one has value 50. These examples are independent analytic anchors for the later implementation.

This simplified formula does not choose a market discount curve or determine whether a cash flow is collectible.

## 4. Functional requirements

- **F1:** Accept explicitly paired cash-flow amounts and dates; validate types, dimensions, finite values and domain before calculation.
- **F2:** State each rate convention and time unit; reject unsupported conventions rather than silently converting.
- **F3:** Provide known-value, boundary and property checks for each implemented module.
- **F4:** Report numerical tolerances and diagnostic information with their units and rationale.
- **F5:** Identify source version, inputs and environment in a reproducibility record.
- **F6:** Report invalid input, numerical failure and missing evidence distinctly.
- **F7:** Produce a synthetic scenario report with assumptions, outputs, limitations and review status.
- **F8:** Keep evidence, independent review and authorized approval as separate states.

Later sections refine these requirements; a requirement is not implemented or validated merely because it is listed here.

## 5. Nonfunctional requirements

The reference exercises should run on a CPU with small synthetic data and without paid data or cloud accounts. Document Python and dependency versions. Provide clear exceptions and deterministic behavior where practical; record seeds and generator versions for generated cases. Never store credentials or sensitive customer data in examples.

For an actual production system, additional security, access, observability, performance, governance and recovery requirements would be determined by its owner. This draft does not establish those controls.

## 6. Interfaces and diagnostics

An interface should specify input types, units, shapes, accepted ranges, output units, failure modes and numerical limitations. A valuation interface might accept a sequence of amount-time pairs and a rate, returning a currency value. The API must decide whether empty input is permitted and what errors represent invalid input versus overflow.

A solver should return more than a number: include convergence state, iterations or evaluations, residual, tolerances, and assumptions. Feasibility of a candidate does not prove optimality. A small residual does not guarantee small solution error in an ill-conditioned problem.

## 7. Acceptance matrix

| ID | Evidence to collect | Expected criterion |
|---|---|---|
| A1 | Specification review | Units, domain, assumptions and exclusions documented |
| A2 | Known-value checks | Independent expected results match within justified tolerances |
| A3 | Boundary and invalid-input checks | Behavior matches the stated contract |
| A4 | Property checks | Relations hold under their stated hypotheses |
| A5 | Reproducibility record | Source, inputs, environment, command and results identifiable |
| A6 | Independent mathematical and software review | Findings and scope recorded |
| A7 | Decision record | Authorized decision for a stated use and version |

A1–A7 are requirements, not completed results. A passing test does not establish suitability or approval. Comprehensive validation and independent review remain pending.

## 8. Twenty worked exercises

1. **Purpose:** The toolkit is for education and validation practice.
2. **Unit:** A rate of 0.05 means 5% per year under the stated convention.
3. **Time:** A horizon of 2 means two years.
4. **Zero rate:** The PV of 100 after two years is 100.
5. **Zero time:** The PV of 100 is 100 for any finite rate.
6. **Known value:** \(100e^{-\ln2}=50\).
7. **Signed amount:** -100 represents an outflow under the chosen sign convention.
8. **Negative rate:** Permitted mathematically; suitability depends on context.
9. **Negative time:** Rejected by the contract.
10. **Empty portfolio:** Value is zero by the chosen convention.
11. **Non-finite input:** Rejected before computation.
12. **Overflow:** Report a numerical failure, even if the mathematical input is valid.
13. **Feasibility:** Meeting constraints does not prove optimality.
14. **Residual:** A small residual does not alone establish accurate solution values.
15. **Tolerance:** State the scale, units and reason for the threshold.
16. **Reproducibility:** Record source, inputs, environment and command.
17. **Seed:** Record the generator and version as well as the seed.
18. **Privacy:** Use synthetic inputs in the public examples.
19. **Review:** Independent mathematical review is distinct from code execution.
20. **Approval:** A passing checklist is not itself an authorized release decision.

## 9. Twelve-step hands-on lab

1. Write the intended use and audience.
2. List the model's financial assumptions and exclusions.
3. Define cash-flow, rate and time units.
4. Define valid types, ranges and empty-input behavior.
5. Specify how non-finite values and overflow are handled.
6. Derive two independent known values.
7. Design boundary and invalid-input checks.
8. Specify a metamorphic relation and its assumptions.
9. Choose a tolerance and document its rationale.
10. Define reproducibility fields and a synthetic input.
11. List review owners, evidence and unresolved findings.
12. Record an acceptance decision only when authorized evidence exists.

## 10. Applied problems

1. Write a contract for an effective annual rate model and compare its domain to the continuous-rate contract.
2. Develop an acceptance case for negative cash flows and explain how rate monotonicity changes.
3. Identify missing assumptions in a request for “the value of a portfolio.”
4. Propose a reproducibility record for a synthetic optimization case.
5. Explain what additional approvals and controls would be needed before a real production use.
