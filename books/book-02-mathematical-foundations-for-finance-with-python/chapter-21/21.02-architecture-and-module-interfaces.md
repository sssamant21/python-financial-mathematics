## Learning objectives

Design cohesive modules with explicit contracts, describe dependency direction, define input and output semantics, separate calculation from reporting, and connect interface requirements to validation evidence.

## 1. Architecture and purpose

The capstone is an educational deterministic financial mathematics toolkit. Its architecture organizes related calculations into modules with explicit assumptions. An interface describes what a caller may supply, what is returned, and how errors are reported. An architecture diagram is a plan, not proof that every component exists or works.

## 2. Proposed modules

| Module | Responsibility | Illustrative output |
|---|---|---|
| Cash flow and rates | Discount and aggregate paired cash flows | Value in one currency |
| Sensitivity | Analytic and numerical derivatives | Derivative with units and step diagnostics |
| Linear algebra | Linear systems and replication | Solution, residual and conditioning information |
| Optimization | Constrained allocation | Candidate, feasibility and solver diagnostics |
| Continuous time | Account transitions and scenarios | State trajectory and event information |
| Evidence and reporting | Record assumptions, results and validation status | Structured scenario report |

Modules exchange explicit values and metadata. A reporting layer consumes results; calculations should not require a report writer, network connection, or user interface. The precise package layout is a proposal to be refined in later sections.

## 3. Dependency direction

Model functions should depend on small, documented numerical primitives rather than a scenario report. A scenario layer orchestrates model calculations and passes results to reporting. Checks exercise contracts independently and use analytic reference values where possible.

Avoid circular dependencies: if a cash-flow module imports reporting while reporting imports cash flow, neither has a clear responsibility. Shared definitions can be placed in a small contracts module when they are truly common.

## 4. Cash-flow interface

For signed cash flows \(C_i\) and nonnegative times \(t_i\) in years under constant continuous annual rate \(r\),

\[
V=\sum_i C_i e^{-rt_i}.
\]

An illustrative contract accepts a finite sequence of paired amounts and times plus a finite rate. The output is a value in the same currency. Negative amounts and rates are allowed; negative times and non-finite inputs are rejected. The empty sum is zero. The implementation must report numerical overflow and document potential underflow.

A scalar output is adequate for a simple calculation, but a scenario report should also identify the convention, units and assumptions. Avoid returning a bare value when callers need those details to interpret it.

## 5. Sensitivity interface

For one cash flow, \(P=Fe^{-rT}\), so

\[
\frac{\partial P}{\partial r}=-TF e^{-rT}.
\]

If \(r\) is expressed as a decimal annual rate, the derivative is currency units per unit change in that rate. For a one-basis-point change, the first-order approximation multiplies the derivative by \(0.0001\); this approximation is not an exact revaluation.

A numerical derivative interface must specify its scheme, step, input domain and diagnostic behavior. Central differences require admissible inputs on both sides. Compare against an independent analytic derivative and document tolerance.

## 6. Linear algebra and optimization interfaces

A linear solver must state matrix and vector shapes, units, supported rank conditions, numerical method and failure behavior. A residual \(Ax-b\) is useful evidence; a small residual alone does not guarantee a small solution error for an ill-conditioned matrix.

An optimizer should report candidate weights, objective value, termination status, feasibility violations and tolerances. A solver's success flag is not proof of feasibility or global optimality. State short-sale, leverage and full-investment constraints explicitly.

## 7. Continuous-time interface

For a simple model \(A'(t)=rA(t)+u\), define initial balance, rate, contribution rate, time horizon, units and any depletion policy. The interface must distinguish a mathematical trajectory from a policy such as stopping withdrawals at zero. Numerical solvers need method, step or tolerances, and event diagnostics.

## 8. Error and evidence contracts

Distinguish malformed types, domain violations, numerical failures, nonconvergence and missing evidence. Never silently replace a failed calculation with zero. A structured evidence record should identify source, inputs, environment, command, result, tolerance and review scope. The presence of a field does not establish that the evidence is authentic.

Avoid hard-coding approval into computational code. Execution, independent review and authorized release are separate states.

## 9. Twenty worked exercises

1. A module groups related responsibilities behind an interface.
2. A contract specifies inputs, outputs, assumptions and failure modes.
3. Reporting consumes results; the valuation formula does not need to import reporting.
4. A circular dependency complicates maintenance and testing.
5. Cash-flow amounts and times must stay paired.
6. A negative cash flow is an outflow under the chosen sign convention.
7. A negative continuous rate is mathematically allowed by the stated contract.
8. A negative horizon is rejected.
9. The empty cash-flow sum is zero by convention.
10. \(P(100,\ln2,1)=50\).
11. \(\partial P/\partial r=-TF e^{-rT}\).
12. At \(F=100,T=1,r=0\), the rate derivative is -100.
13. A one-basis-point first-order change in exercise 12 is approximately -0.01 currency units.
14. A finite-difference method needs a documented step.
15. A matrix interface must specify compatible dimensions.
16. A small residual is not proof of small solution error.
17. Feasible weights are not necessarily optimal.
18. A trajectory and a depletion policy are distinct concepts.
19. A recorded source version helps trace evidence.
20. A completed report is not itself approval.

2. List each proposed module and responsibility.
3. Draw dependencies from scenario orchestration to model modules.
4. Specify the cash-flow interface and units.
5. Define invalid-input and numerical-failure behavior.
6. Specify derivative units and approximation method.
7. Specify linear-system shape and residual diagnostics.
8. Define optimization constraints and feasibility reporting.
9. Describe continuous-time event policy.
10. Define a structured result and evidence fields.
11. Add independent contract checks.
