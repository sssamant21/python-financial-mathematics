## Learning objectives

Design a layered test strategy for the capstone, document model contracts and evidence, distinguish execution from independent review, and explain the transition from deterministic models to probability and stochastic modeling.

## 1. Testing the integrated toolkit

The capstone combines cash-flow valuation, rate conversions, sensitivity, replication, optimization and continuous-time scenarios. Each module needs its own contract and independent checks. Integration tests then verify that data and units pass correctly between modules. A successful integration test does not replace mathematical review or validate every assumption.

Use synthetic inputs with known expected results. Record the source version, environment, inputs, command, actual output, tolerance and exit status. The existence of a test file is not evidence that it ran.

## 2. Layers of checks

| Layer | Purpose | Example |
|---|---|---|
| Known value | Compare with an independent analytic result | \(100e^{-\ln2}=50\) |
| Boundary and invalid input | Check explicit domain and errors | Zero time; negative time rejected |
| Property | Verify a conditional relation | Same-date cash-flow splitting |
| Numerical | Assess error and diagnostics | Derivative against analytic benchmark |
| Integration | Check contracts across modules | Rate conversion followed by valuation |
| Review | Assess assumptions and intended use | Independent mathematical review |

Property checks must state their assumptions; a function that always returns zero can satisfy scaling while being incorrect. Use multiple forms of evidence.

## 3. Capstone validation examples

For a constant continuous annual rate, a one-year payment of 100 at \(r=\ln2\) has PV 50. The equivalent annual effective rate is 1, since \(e^{\ln2}-1=1\); under the stated annual-effective power convention the factor is also \(1/2\).

For a continuous account with \(r=0\), initial 1000, annual flow 200 and horizon 3, the balance is 1600. For the allocation example with targets \(a=0.7,b=0.2\), the optimal weights are \((0.75,0.25)\) for the specific squared-distance objective and long-only full-investment constraints. These values are analytic anchors, not evidence of an executed test.

## 4. Tolerances and failures

A tolerance should follow the quantity's units, numerical scale, algorithmic error and intended use. Near zero, use a justified absolute tolerance. A tolerance selected for an educational synthetic example is not automatically suitable for real valuation.

Distinguish invalid input, numerical overflow, solver nonconvergence, failed checks and missing evidence. Do not turn exceptions into plausible values. Capture failures with their inputs and environment; investigate before changing thresholds.

## 5. Documentation contract

Each module should document:

- Purpose, formula, units, conventions, assumptions and exclusions.
- Input types, domain, output meaning, exceptions and numerical limits.
- Small reproducible examples and independent expected results.
- Dependencies, commands and environment needed to run checks.
- Evidence status, known limitations, findings and review scope.

A scenario report should associate each result with its specific input and assumptions. Sensitive data and credentials do not belong in public examples.

## 6. Evidence and release status

Keep **authored**, **executed**, **reviewed** and **approved** distinct. A failed test is an execution result; pending means no result has been established. An independent reviewer assesses a stated scope; an authorized owner decides whether a specific use is acceptable. Approval cannot be inferred from a generated report or a green unit-test suite.

The [validation tracker](../validation/PROGRESS.md) records executed checks at named revisions. Independent mathematical and editorial review, supported-platform validation, and approval remain pending. The following lab builds a test plan; it does not run or certify the listed checks.

## 7. Transition to Book 03

Book 02 emphasizes deterministic relationships: the same model inputs determine the same output. Probability introduces uncertainty through random variables, distributions and expectations; stochastic processes describe random evolution over time. A deterministic formula can be used as a building block or conditional model, but adding randomness requires new assumptions, calibration, validation and interpretation.

For example, treating a future cash flow as a random variable raises questions about its distribution, dependence, information and risk treatment. Discounting its expectation under a chosen measure is not automatically a market price. Later models must state their probability measure and assumptions.

The transition also changes validation: simulation requires attention to sampling error, random generators, seeds, convergence, dependence and reproducibility. A fixed seed supports replay under documented conditions but does not establish statistical validity.

## CF-04: mathematical identity and floating-point acceptance

At a common date, discounting is mathematically linear. The numerical check requires that the exact sum of the normalized split float amounts equals the merged float amount, and that every discounted term and both returned portfolio values are finite. The implementation rounds each discounted monetary term before summing the represented terms; it does not combine same-date amounts before discounting.

CF-04 therefore compares an absolute rounding bound, not unconditional float equality. In the selected checks, independently evaluated terms are rounded to float and the allowance is one-half ULP for every split discounted term, the merged discounted term, and the split final value. The triangle inequality supplies this allowance when those term values are correctly rounded. The checks verify the selected outputs against high-precision references; this is not a proof that every finite input is correctly rounded.

Subnormal splits may return zero while a merged payment returns the least positive float. Signed cancellation can also exceed an ordinary fixed relative/absolute tolerance while remaining inside the rounding bound. Individual-term overflow excludes the comparison even when a pre-combined payment would be finite. The aggregation policy is unchanged. See the [CF-04 boundary evidence](../validation/chapter-21-splitting-property-followup.md), including the retained initial test assumption and corrected fixture.

## INT-01: equivalent-rate factors after conversion

Let `c = log1p(i)` be the mathematical continuous rate for the represented effective rate `i`, and let `c_hat` be the returned float conversion. At horizon `T`, the factor ratio before final rounding is `exp(-(c_hat-c)*T)`. INT-01 therefore allows the effective factor multiplied by `abs(expm1(-(c_hat-c)*T))`, plus one-half ULP for each returned factor. The comparison domain requires a finite converted rate and finite positive factors.

The selected checker independently evaluates the conversion and each convention with high-precision logarithms and exponentials, and then checks that propagation allowance. It separately checks the conversion against its oracle; a wrong conversion is not accepted merely because its error makes the allowance larger. Underflow to zero, overflow and invalid effective-rate endpoints are boundaries, not successful equivalence comparisons. This adds no financial-suitability or universal correctly-rounded-library claim. [INT-01 evidence](../validation/chapter-21-equivalent-factor-property-followup.md) retains the baseline policy gap and runnable checks; the valuation and conversion helpers are unchanged.
