# 20.5 — Testing Floating-Point Results

## Learning objectives

Explain floating-point comparison risks; distinguish absolute and relative tolerances; use `math.isclose` and explicit reference-based criteria; test nonfinite values and financial boundaries; and validate numerical results against independent benchmarks.

## 1. Why floating-point tests need care

Many decimal fractions cannot be represented exactly in binary floating-point. The familiar expression `0.1 + 0.2 == 0.3` is typically false with Python's binary64 floats. Rounding can accumulate across calculations, and algebraically equivalent expressions may behave differently numerically.

Tests should identify unacceptable errors without failing on irrelevant last-digit differences. A tolerance is part of the test specification, not a universal property of money or floating-point values.

## 2. Absolute error

For actual a and reference b, absolute error is **|a−b|**. A test can require it to be at most atol, expressed in the output's units.

For price 100.02 against reference 100.00, absolute error is .02 currency units. Whether that is acceptable depends on the instrument, position size and use. Across one million units, .01 per unit represents 10,000 currency units.

## 3. Relative error

When the reference is nonzero, relative error is **|a−b|/|b|**. For 100.02 versus 100, relative error is .0002, or .02%.

Relative error alone is undefined at zero and unstable when the reference is very small. An appropriate absolute scale is needed for near-zero quantities.

## 4. Mixed criteria

A commonly used reference-based criterion is:

**|a−b| ≤ atol + rtol |b|.**

It is asymmetric because b is the reference. With a=100.02, b=100, atol=.01 and rtol=.00005, the threshold is .015; the .02 error fails.

Python's `math.isclose(a,b,rel_tol=...,abs_tol=...)` uses a **symmetric** criterion based on the larger magnitude and the maximum of the relative and absolute limits, not the sum above. Select and document the intended rule rather than assuming all comparison helpers behave identically.

## 5. Choosing tolerances

Set tolerances before examining the result, using financial units, algorithmic error, input precision and intended use. A price tolerance in currency cannot be reused as a yield tolerance in decimal rates. A one-basis-point yield difference is .0001 in decimal rate units.

Do not enlarge a tolerance solely to suppress a failure. Investigate model assumptions, timing, units, conditioning and numerical stability first.

## 6. Known-value benchmarks

Use independently derived cases:

- 110 paid in one period discounted at 10% annual effective rate has PV 100.
- [−100,110] at 10% has NPV 0 in exact arithmetic.
- 100→101.50 has simple return .015.
- A zero-rate payment of 100 has PV 100.

The reference and implementation must share timing, currency, compounding and rounding conventions. A small residual does not prove the model or input data are correct.

## 7. NaN and infinity

NaN is not equal to itself and ordinarily fails closeness comparisons. Infinity can compare as close to the same signed infinity in `math.isclose`; whether that is acceptable is a separate contract decision.

The reference comparator below rejects all nonfinite inputs and nonfinite tolerances. It raises an exception rather than interpreting NaN or infinity as acceptable results.

## 8. Numerical stability

A test can compare stable and naive approaches against an independent reference, including small inputs. For tiny x, `math.log1p(x)` and `math.expm1(x)` are designed to retain accuracy where direct `log(1+x)` or `exp(x)-1` can lose significant digits.

Conditioning is distinct from algorithmic stability. A small residual in an ill-conditioned root or linear system can coexist with a large solution error. Test sensitivity and use appropriate benchmarks.

## 9. Invariants and boundary cases

Test known results, domains and relationships: scaling cash flows scales NPV; a positive future payment has lower PV at a higher valid rate; zero rate has a known limit. Record assumptions and compare at the correct scale.

Do not assume a passing test proves all extreme inputs safe. Overflow, underflow, cancellation and platform-dependent reduction order may require separate checks.

## 10. Reference implementation

Save as `floating_point_tests.py`. It provides an explicit reference-based mixed comparison, a simplified annual effective NPV calculation and reference tests.

~~~python
import math
import unittest

def finite_number(x):
    return type(x) in (int,float) and math.isfinite(x)

def close_to_reference(actual,reference,atol,rtol):
    if not all(finite_number(x) for x in (actual,reference,atol,rtol)):
        raise ValueError("finite numeric values required")
    if atol<0 or rtol<0:
        raise ValueError("nonnegative tolerances required")
    return abs(actual-reference) <= atol+rtol*abs(reference)

def npv(cashflows,rate):
    flows=list(cashflows)
    if not flows or not finite_number(rate) or rate<=-1:
        raise ValueError("nonempty flows and finite rate > -1 required")
    if not all(finite_number(x) for x in flows):
        raise ValueError("finite numeric cash flows required")
    try:
        result=math.fsum(c*math.exp(-t*math.log1p(rate))
                         for t,c in enumerate(flows))
    except OverflowError as exc:
        raise ValueError("discount calculation overflow") from exc
    if not math.isfinite(result):
        raise ValueError("nonfinite NPV")
    return result

class FloatingPointTests(unittest.TestCase):
    def test_absolute_pass(self):
        self.assertTrue(close_to_reference(100.01,100,.02,0))
    def test_absolute_fail(self):
        self.assertFalse(close_to_reference(100.02,100,.01,0))
    def test_mixed_fail(self):
        self.assertFalse(close_to_reference(100.02,100,.01,.00005))
    def test_near_zero(self):
        self.assertTrue(close_to_reference(1e-12,0,1e-10,0))
    def test_exact_equal(self):
        self.assertTrue(close_to_reference(100,100,0,0))
    def test_nonfinite_actual(self):
        with self.assertRaises(ValueError): close_to_reference(float("nan"),0,1,0)
    def test_nonfinite_tolerance(self):
        with self.assertRaises(ValueError): close_to_reference(1,1,float("inf"),0)
    def test_negative_tolerance(self):
        with self.assertRaises(ValueError): close_to_reference(1,1,-1,0)
    def test_known_npv(self):
        self.assertTrue(close_to_reference(npv([-100,110],.1),0,1e-10,0))
    def test_zero_rate(self):
        self.assertEqual(npv([0,100],0),100)
    def test_scaling(self):
        self.assertTrue(close_to_reference(npv([-200,220],.05),
                                          2*npv([-100,110],.05),1e-10,1e-12))
    def test_invalid_rate(self):
        with self.assertRaises(ValueError): npv([100],-1)
    def test_log1p(self):
        self.assertTrue(math.isclose(math.log1p(1e-12),1e-12,
                                     rel_tol=1e-11,abs_tol=0))
    def test_nonfinite_flow(self):
        with self.assertRaises(ValueError): npv([100,float("inf")],.05)

if __name__ == "__main__":
    unittest.main(verbosity=2)
~~~

This comparator's tolerance arithmetic can itself overflow for extreme finite magnitudes; production code should define and test its supported numeric range. The NPV example uses binary floats, positional periods and no dated cash-flow conventions; underflow is possible.

## 13. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Last-digit mismatch | Floating-point rounding or reduction order | Review justified tolerance |
| Test passes despite large discrepancy | Tolerance too broad or wrong units | Revisit specification and scale |
| NaN propagates | Missing finiteness checks | Validate input and output |
| Zero-reference comparison fails | Relative-only criterion | Add a justified absolute threshold |
| Small residual but inaccurate solution | Ill-conditioning | Inspect sensitivity and benchmark |
| Different helpers disagree | Different comparison definitions | Align criteria and reference scale |
