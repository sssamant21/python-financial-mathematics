## Learning objectives

Design a small financial library with a documented contract, predictable exceptions, financial invariants, reference tests and a reproducible release process. Separate a production-quality engineering goal from evidence that a particular library is ready for production.

## 1. Project brief and scope

Build `finlib`, a small, dependency-free educational library that discounts a sequence of equally spaced cash flows. The first element is at time zero; subsequent elements occur at the end of consecutive periods. One constant effective rate applies per period. Amounts share one currency and unit; signs indicate inflows and outflows from the same perspective. The function returns an unrounded binary floating-point amount.

For cash flows \(C_0,\ldots,C_n\) and effective per-period rate \(r>-1\):

\[
NPV=\sum_{t=0}^{n}\frac{C_t}{(1+r)^t}.
\]

Example: `[-100.0, 110.0]` at 10% has NPV zero in exact arithmetic. `[-100.0, 60.0, 60.0]` at 10% has NPV approximately 4.1322314050. These are synthetic examples, not investment recommendations.

The model assumes deterministic cash flows and a flat periodic rate. It excludes actual dates, day counts, taxes, fees, credit, inflation, liquidity, currency conversion and cash-flow uncertainty. It does not calculate IRR. Rate period and cash-flow interval must match. Model suitability requires independent review even if software tests pass.

## 2. Contract and design decisions

| Concern | Contract |
|---|---|
| Inputs | A nonempty `list` or `tuple` of built-in `float` values and a built-in `float` rate. Booleans, integers and other numeric types are rejected. |
| Domain | Inputs must be finite; rate must be greater than −1. Negative cash flows and negative rates above −1 are permitted. |
| Result | Finite `float`, in the same units as the cash flows; no automatic currency rounding. |
| Failures | Invalid input or nonfinite intermediate/result raises `ValueError`; callers handle failure explicitly. |
| Numerics | Floating-point rounding, cancellation and underflow may occur; overflow is rejected. Extreme cases can be unsuitable. |
| Side effects | Calculation is deterministic and does not read files, configure logging, fetch data or mutate the input. |

This strict teaching interface is intentionally narrower than Python's general numeric ecosystem. The annotations do not enforce it at runtime, and some static checkers allow an `int` where `float` is annotated. Decimal accounting, rounding policies, currency metadata and input-size limits need explicit requirements before real use.

### `finlib/valuation.py`

```python
"""Educational periodic cash-flow valuation; see the documented scope."""
import math


def npv(cashflows: list[float] | tuple[float, ...], rate: float) -> float:
    """Return periodic NPV in cash-flow units, without currency rounding.

    The first cash flow is at t=0; the rate is effective per period.
    Only finite built-in floats are accepted, with rate > -1.
    Invalid inputs or nonfinite intermediates raise ValueError.
    Floating-point rounding, cancellation and underflow are possible.
    """
    if type(rate) is not float or not math.isfinite(rate) or rate <= -1.0:
        raise ValueError("rate must be a finite float greater than -1")
    if type(cashflows) not in (list, tuple) or not cashflows:
        raise ValueError("cashflows must be a nonempty list or tuple")
    if any(type(c) is not float or not math.isfinite(c) for c in cashflows):
        raise ValueError("cashflows must contain finite floats")

    # Discount backwards using Horner's method. Check each intermediate:
    # finite inputs can still produce an infinite intermediate.
    value = 0.0
    denominator = 1.0 + rate
    for cashflow in reversed(cashflows):
        value = cashflow + value / denominator
        if not math.isfinite(value):
            raise ValueError("nonfinite valuation intermediate")
    return value
```

Horner's method evaluates \(C_0+(C_1+(C_2+\cdots)/(1+r))/(1+r)\). The reverse traversal gives time zero its correct weight. It does not eliminate rounding or overflow, and intermediate overflow may reject cases whose exact final answer is finite. The strict contract makes the outcome explicit rather than silently returning infinity.

### Example use

From the project root, after saving the files:

```python
from finlib import npv

value = npv([-100.0, 60.0, 60.0], 0.10)
print(f"NPV: {value:.6f}")  # approximately 4.132231
```

The display rounds to six decimal places; the function itself does not. Do not interpret the displayed value as a guarantee of six accurate decimals for all inputs.

## 4. Reference tests

Save the following as `tests/test_valuation.py`. Expected values are derived from the stated formula; invariants complement, rather than replace, independent benchmarks. Tolerances are illustrative in cash-flow units and must be chosen for the intended application.

```python
import math
import unittest

from finlib import npv


class ValuationTests(unittest.TestCase):
    def test_one_period_break_even(self):
        self.assertTrue(math.isclose(npv([-100.0, 110.0], 0.1), 0.0,
                                     rel_tol=0.0, abs_tol=1e-10))

    def test_two_period_benchmark(self):
        self.assertTrue(math.isclose(npv([-100.0, 60.0, 60.0], 0.1),
                                     4.13223140495868, rel_tol=0.0,
                                     abs_tol=1e-10))

    def test_zero_rate(self):
        self.assertEqual(npv([-100.0, 60.0, 60.0], 0.0), 20.0)

    def test_time_zero_only(self):
        self.assertEqual(npv((25.0,), 0.1), 25.0)

    def test_negative_rate(self):
        self.assertTrue(math.isclose(npv([0.0, 95.0], -0.05), 100.0,
                                     rel_tol=0.0, abs_tol=1e-10))

    def test_scaling(self):
        self.assertTrue(math.isclose(npv([-200.0, 120.0, 120.0], 0.1),
                                     2.0 * npv([-100.0, 60.0, 60.0], 0.1),
                                     rel_tol=1e-12, abs_tol=1e-10))

    def test_rate_monotonicity_positive_future_flow(self):
        self.assertGreater(npv([0.0, 100.0], 0.05), npv([0.0, 100.0], 0.10))

    def test_empty(self):
        with self.assertRaises(ValueError):
            npv([], 0.1)

    def test_invalid_rate_boundary(self):
        with self.assertRaises(ValueError):
            npv([1.0], -1.0)

    def test_nonfinite_inputs(self):
        for flows, rate in [([float("nan")], 0.1), ([1.0], float("inf"))]:
            with self.subTest(flows=flows, rate=rate):
                with self.assertRaises(ValueError):
                    npv(flows, rate)

    def test_wrong_types(self):
        for flows, rate in [([1], 0.1), ([1.0], True), ("1", 0.1)]:
            with self.subTest(flows=flows, rate=rate):
                with self.assertRaises(ValueError):
                    npv(flows, rate)

    def test_nonfinite_intermediate(self):
        with self.assertRaises(ValueError):
            npv([0.0, 1e308], -0.5)


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

## 5. Engineering and release workflow

1. Write requirements and a traceable specification: timing, rate convention, units, input domain and error policy.
2. Review the design and derive benchmarks independently. Include cancellation and extreme-value cases appropriate to the use.
3. Implement small, side-effect-free functions and preserve clear boundaries between calculation and input/output.
4. Review source and run unit, integration, property and regression tests appropriate to risk. Use financial invariants with their assumptions stated.
5. Check types, formatting, dependencies and security as applicable; pin and record the build environment and dependency provenance.
6. Perform independent mathematical, numerical and model review; reconcile differences with appropriate benchmarks.
7. Package and install in a clean environment; test the installed artifact, documentation examples and supported platforms.
8. Version the artifact, document changes and known limitations, obtain required approvals, and retain review and test evidence.
9. Monitor usage, errors and model performance; define ownership, rollback and change control.

Library code should not configure application-wide logging. Applications may log operation identifiers and sanitized failure categories; avoid sensitive cash flows, secrets and uncontrolled exception details. A release gate must be based on observed evidence, not merely on the presence of a checklist.

## 7. Forty worked exercises

1. **Time zero:** NPV of `[50.0]` at 10%? **Answer:** 50; it is not discounted.
2. **Break-even:** NPV of `[-100.0, 110.0]` at 10%? **Answer:** 0 in exact arithmetic.
3. **Two periods:** NPV of `[-100.0, 60.0, 60.0]` at 10%? **Answer:** Approximately 4.132231405.
4. **Zero rate:** NPV of `[-100.0, 60.0, 60.0]` at 0%? **Answer:** 20.
5. **Negative rate:** PV of 95 one period ahead at −5%? **Answer:** 100 in exact arithmetic.
6. **Rate boundary:** Why reject −1? **Answer:** The discount denominator is zero.
7. **Units:** What unit does NPV use? **Answer:** The common cash-flow unit.
8. **Signs:** Can a cash flow be negative? **Answer:** Yes; signs must follow a consistent perspective.
9. **Frequency:** Can an annual rate directly discount monthly periods? **Answer:** No; first convert to a consistent effective monthly rate.
10. **Timing:** Where is the first flow? **Answer:** At time zero.
11. **Scale:** Double every cash flow. What happens in exact arithmetic? **Answer:** NPV doubles.
12. **Additivity:** What happens if corresponding flows of two equal-length schedules are added? **Answer:** Their NPV is the sum of individual NPVs in exact arithmetic, at the same rate.
13. **Rate sensitivity:** What happens to a positive future payment's PV when rate rises? **Answer:** It falls, all else equal.
14. **Mixed signs:** Is total NPV always decreasing with rate? **Answer:** No; cash-flow signs and timing matter.
15. **Empty schedule:** What is the specified behavior? **Answer:** Raise `ValueError`.
16. **Integer input:** Does `[100]` satisfy this contract? **Answer:** No; use built-in floats.
17. **Boolean rate:** Is `True` accepted? **Answer:** No.
18. **NaN:** Is NaN a valid amount? **Answer:** No; nonfinite inputs are rejected.
19. **Infinity:** Is an infinite rate accepted? **Answer:** No.
20. **Mutation:** Does the function modify the input list? **Answer:** No.
21. **Underflow:** Can a small contribution become zero? **Answer:** Yes, with floating-point underflow or rounding.
22. **Overflow:** Can finite inputs yield a nonfinite intermediate? **Answer:** Yes; the function raises `ValueError`.
23. **Cancellation:** Why can close positive and negative terms be difficult? **Answer:** Significant digits can be lost in subtraction.
24. **Tolerance:** Why use an absolute tolerance around zero? **Answer:** Relative tolerance alone is ineffective against a zero benchmark.
25. **Rounding:** Does formatted output change the stored result? **Answer:** No.
26. **Currency:** Does the function round to cents? **Answer:** No.
27. **Decimal:** Can `Decimal` be passed directly? **Answer:** No; this contract accepts built-in floats only.
28. **Type hints:** Do annotations alone enforce the contract? **Answer:** No; runtime checks do that.
29. **Exceptions:** Why avoid returning zero on invalid input? **Answer:** Zero could be mistaken for a valid valuation.
30. **Horner:** Why traverse in reverse? **Answer:** It builds the nested discount expression from the last payment to time zero.
31. **Tests:** Does a passing test prove all inputs correct? **Answer:** No; it checks specified examples and properties.
32. **Independence:** Why derive a benchmark separately? **Answer:** To reduce the chance of reproducing the same error.
33. **Model:** Do software tests establish suitability for a risky bond? **Answer:** No; credit and other omitted risks need review.
34. **Regression:** What does a regression test protect? **Answer:** A documented expected behavior against unintended changes.
35. **Logging:** Should the library configure the root logger? **Answer:** No; leave application logging configuration to the caller.
36. **Sensitive data:** Should all cash flows be logged by default? **Answer:** No; minimize sensitive data in logs.
37. **Reproducibility:** Which evidence identifies a test run? **Answer:** Revision, environment, command and actual results.
38. **Installation:** Is importing from the project root an installed-package test? **Answer:** No.
39. **Release:** Does the title imply production approval? **Answer:** No; actual readiness requires appropriate evidence and authorization.

## 8. Troubleshooting

| Symptom | Possible cause | Action |
|---|---|---|
| `ModuleNotFoundError` | Command run outside project root or files misplaced | Check layout and run discovery from project root |
| `ValueError` | Wrong type, invalid rate, nonfinite input or intermediate | Inspect sanitized inputs and contract; do not substitute zero |
| Small benchmark discrepancy | Binary floating-point rounding | Reconcile convention and use a justified tolerance |
| Large discrepancy | Rate frequency, timing, sign or units differ | Reconcile assumptions before changing tolerances |
| Tests pass but use is unsuitable | Model assumptions omit material risk | Perform independent model review |

## 9. Key takeaways

A financial library requires a precise contract, tested implementation, numerical policy, documented limitations and reproducible evidence. The project demonstrates a small foundation; a production release also needs context-specific validation, controls and operational ownership.
