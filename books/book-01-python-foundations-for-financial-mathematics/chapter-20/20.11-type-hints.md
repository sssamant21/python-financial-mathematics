# 20.11 — Type Hints

**Book:** Book 1 — Python Foundations for Financial Mathematics  
**Chapter:** 20 — Testing and Engineering Financial Python  
**Status:** Published draft; comprehensive runtime, mathematical, and editorial QA deferred until Book 1 manuscript completion.

## Learning objectives

Read and write Python type hints; annotate financial functions and collections; distinguish static checking from runtime validation; represent optional values; and document units and financial domains that types alone cannot express.

## 1. Why type hints?

Type hints describe expected interfaces. They help readers, editors and static analysis tools identify incompatible uses before execution. They do not automatically enforce types at runtime or prove that financial values, units or models are correct.

A function accepting a `float` rate still needs a convention: decimal or percent, period, compounding and allowed domain. A typed price still needs currency, price type and time semantics.

## 2. Annotating functions

~~~python
def simple_return(start: float, end: float) -> float:
    return end / start - 1.0
~~~

The annotations describe the interface; ordinary Python does not automatically reject a zero starting price or a string passed at runtime. Add explicit validation and tests.

## 3. Collections and optional values

Modern Python supports annotations such as `list[float]`, `tuple[float, ...]` and `dict[str, float]`. A value that can be absent can be annotated `float | None` on Python 3.10 or later. These examples target Python 3.10+.

A missing price is not the same as zero. A type hint can show that `None` is possible, but the function contract must say whether to reject, propagate or handle it.

## 4. Decimal and financial units

`Decimal` can be annotated directly for decimal-based calculations. Constructing Decimal from text, defining precision and rounding, and validating finiteness remain separate responsibilities.

A type such as `Decimal` does not distinguish USD from EUR or percent from decimal rate. Use meaningful names, documentation and, where appropriate, domain types or validated structures.

## 5. Static checking and runtime validation

A static type checker examines annotated code without executing every path. It can find mismatched interfaces, but it cannot generally establish market-data freshness, a positive price, a valid rate domain or absence of look-ahead.

Runtime checks should raise documented exceptions for invalid inputs. Tests should verify both supported behavior and failure cases. Python can omit `assert` statements under optimization, so do not rely on them as the only input validation.

## 6. Type aliases and domain types

A type alias can improve readability but does not automatically enforce a business rule. `typing.NewType` can help a static checker distinguish concepts such as a decimal rate from a price; it does not perform runtime validation or conversion.

Data classes can group fields such as amount and currency, but their annotations alone do not guarantee a valid currency, timestamp or value. Define and test construction rules.

## 7. Iterables and contracts

An `Iterable[float]` can accept a list, tuple or generator. If a function consumes an iterable, document that behavior. Validate emptiness, supported numeric types and finite values according to its contract.

Do not promise broader support in annotations or documentation than the implementation provides. Python treats `bool` as a subclass of `int`, but an application may choose to reject booleans as financial inputs.

## 8. Reference implementation

Save as `type_hints_finance.py`. This example targets Python 3.10+ and uses a narrowly defined float contract. It uses type hints and explicit runtime checks.

~~~python
import math
from collections.abc import Iterable
from decimal import Decimal, localcontext, ROUND_HALF_EVEN
from typing import NewType
import unittest

DecimalRate = NewType("DecimalRate", float)

def finite_float(value: object) -> bool:
    return type(value) is float and math.isfinite(value)

def npv(cashflows: Iterable[float], rate: float) -> float:
    flows = list(cashflows)
    if not flows or not all(finite_float(x) for x in flows):
        raise ValueError("nonempty finite float cash flows required")
    if not finite_float(rate) or rate <= -1:
        raise ValueError("finite float rate > -1 required")
    try:
        result = math.fsum(c * math.exp(-t * math.log1p(rate))
                           for t, c in enumerate(flows))
    except OverflowError as exc:
        raise ValueError("discount calculation overflow") from exc
    if not math.isfinite(result):
        raise ValueError("nonfinite NPV")
    return result

def decimal_return(start: Decimal, end: Decimal) -> Decimal:
    if not isinstance(start, Decimal) or not isinstance(end, Decimal):
        raise ValueError("Decimal prices required")
    if not start.is_finite() or not end.is_finite() or start <= 0 or end < 0:
        raise ValueError("positive start and nonnegative end required")
    with localcontext() as ctx:
        ctx.prec = 28
        ctx.rounding = ROUND_HALF_EVEN
        return end/start-Decimal("1")

def require_price(value: float | None) -> float:
    if value is None or not finite_float(value) or value <= 0:
        raise ValueError("positive finite float price required")
    return value

class TypeHintTests(unittest.TestCase):
    def test_known_npv(self) -> None:
        self.assertTrue(math.isclose(npv([-100.0,110.0],.1),0.0,
                                     rel_tol=0,abs_tol=1e-10))
    def test_generator(self) -> None:
        self.assertEqual(npv((x for x in [0.0,100.0]),0.0),100.0)
    def test_negative_rate(self) -> None:
        self.assertTrue(math.isclose(npv([0.0,95.0],-.05),100.0,
                                     rel_tol=0,abs_tol=1e-10))
    def test_decimal_return(self) -> None:
        self.assertEqual(decimal_return(Decimal("100"),Decimal("101.50")),Decimal(".015"))
    def test_optional_price(self) -> None:
        self.assertEqual(require_price(100.0),100.0)
    def test_missing_price(self) -> None:
        with self.assertRaises(ValueError): require_price(None)
    def test_zero_price(self) -> None:
        with self.assertRaises(ValueError): require_price(0.0)
    def test_invalid_rate(self) -> None:
        with self.assertRaises(ValueError): npv([100.0],-1.0)
    def test_empty(self) -> None:
        with self.assertRaises(ValueError): npv([],0.0)
    def test_nonfinite(self) -> None:
        with self.assertRaises(ValueError): npv([float("nan")],0.0)
    def test_boolean_runtime(self) -> None:
        with self.assertRaises(ValueError): npv([True],0.0)
    def test_integer_runtime(self) -> None:
        with self.assertRaises(ValueError): npv([100],0.0)

if __name__ == "__main__":
    unittest.main(verbosity=2)
~~~

The example deliberately accepts only built-in float values in `npv` and `require_price`; integers, booleans and other numeric types are rejected at runtime. Some static type checkers allow an integer where a float is annotated, so a `float` annotation alone does not express this stricter runtime rule. Document and test that difference.

`DecimalRate` illustrates a static distinction but is not used as a runtime validator in the example. The NPV model uses annual effective rates and positional periods; it does not validate currency, dates or financial suitability. Underflow and extreme inputs remain limitations.

## 12. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Static check passes but runtime rejects an integer | Narrower runtime float-only policy | Align and document interface expectations |
| Annotated rate has wrong unit | Unit not represented by type | Use explicit naming and contract |
| None causes a runtime error | Missing handling | Define and validate optional values |
| Generator is unexpectedly empty | It was already consumed | Document consumption or materialize once |
| Checker reports unsupported syntax | Python target version differs | Align project configuration |
| Types look correct but valuation is wrong | Model or data semantics incorrect | Independently validate assumptions |
