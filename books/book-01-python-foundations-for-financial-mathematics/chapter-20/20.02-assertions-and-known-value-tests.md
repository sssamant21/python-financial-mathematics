## Learning objectives

Use assertions to express expected behavior; derive independent financial benchmarks; choose exact or tolerance-based comparisons; test boundaries and exceptions; and interpret the limits of a passing test.

## 1. What is an assertion?

An assertion checks a condition that is expected to hold. In Python, `assert condition` raises `AssertionError` when the condition is false in a normal run. A descriptive message helps identify a failure.

~~~python
assert 2 + 2 == 4, "arithmetic benchmark failed"
~~~

Python can omit assert statements when run with optimization, such as `python -O`. Do not use `assert` as the sole validation of production inputs or security requirements. Raise explicit exceptions for invalid inputs.

## 2. Known-value tests

A known-value test compares an implementation with an independently derived result under documented assumptions. For a one-year payment of 110 discounted at 10% annual effective rate:

**PV = 110/(1+.10) = 100.**

The expected result should not be generated by calling the same function under test. Record the rate convention, timing, units and rounding assumptions so the benchmark is meaningful.

## 3. Cash-flow benchmark

For [−100,110] with the second cash flow one year later and a 10% annual effective rate:

**NPV = −100+110/1.1 = 0.**

A test that forgets the time-zero investment or discounts it as if it occurs in year one checks a different problem. Sign and timing conventions are part of the test.

## 4. Exact and approximate comparisons

Exact equality is appropriate for some integers, strings, dates and deliberately specified decimal calculations. Binary floating-point arithmetic can produce small representation differences. For numerical results, choose a justified tolerance.

One asymmetric comparison to a reference b is **|a−b|≤atol+rtol|b|**. Absolute tolerance has the output's units; relative tolerance is dimensionless. Near zero, use an appropriate absolute tolerance. Python's `math.isclose` uses its own documented symmetric rule based on the larger magnitude, so understand the comparison being used.

Avoid exact equality for a float solely because a single example happens to pass. Conversely, an excessively broad tolerance can hide a real defect.

## 5. Decimal checks

`Decimal("101.50")` represents the supplied decimal value directly. With a stated context and rounding policy, exact comparisons can be appropriate for specified decimal outcomes. Decimal arithmetic can still round, overflow or signal errors under its context; financial conventions and inputs still need validation.

For 100.00→101.50, simple return is **.015**, or 1.5%, under a defined decimal calculation.

## 6. Exceptions and boundaries

A test can verify that invalid input raises a specific exception. The annual effective rate model used here requires r>−1. A rate of −.05 can be valid; −1 is invalid because the discount base is zero.

Test nonfinite values, missing inputs, zero denominators and domain boundaries. Avoid swallowing exceptions and returning a plausible default that masks failure.

## 7. Invariants and independent references

Known-value tests cover selected cases. Add relationship checks where assumptions support them: doubling all cash flows doubles NPV, and a positive future payment has lower PV at a higher rate.

An inserted zero cash flow can shift later payments in a positional schedule. An appended zero does not. State timing assumptions in both code and tests.

## 8. Test structure

A readable test has an **arrange** stage defining inputs, an **act** stage running the operation, and an **assert** stage comparing the result or exception. Name tests for the behavior, not merely the implementation.

Python's `unittest` offers `assertEqual`, `assertAlmostEqual`, `assertRaises` and other methods. `assertAlmostEqual` with `places` uses decimal-place rounding; it is not a general mixed absolute-relative tolerance. Choose a method suitable for the quantity and document the threshold.

## 9. Reproducibility and evidence

Record the actual test command, inputs, code revision, Python and dependency versions, and result. A test included in a manuscript is not evidence that it has run. A passing test checks the specified example, not all market conditions or model assumptions.

Independent model review, integration tests and source-data checks remain necessary for a real system.

## 10. Reference implementation

Save as `known_value_tests.py`. It implements a small periodic NPV function, a decimal simple-return function and reference tests. It does not implement dated cash flows, bond conventions or production accounting policy.

~~~python
import math
from decimal import Decimal, localcontext, ROUND_HALF_EVEN
import unittest

def finite_number(value):
    return type(value) in (int,float) and math.isfinite(value)

def npv(cashflows,rate):
    flows=list(cashflows)
    if not flows or not finite_number(rate) or rate<=-1:
        raise ValueError("nonempty flows and finite rate > -1 required")
    if any(not finite_number(x) for x in flows):
        raise ValueError("finite numeric cash flows required")
    try:
        value=math.fsum(c*math.exp(-t*math.log1p(rate))
                        for t,c in enumerate(flows))
    except OverflowError as exc:
        raise ValueError("discount calculation overflow") from exc
    if not math.isfinite(value):
        raise ValueError("nonfinite NPV")
    return value

def decimal_return(start,end):
    if not isinstance(start,Decimal) or not isinstance(end,Decimal):
        raise ValueError("Decimal prices required")
    if not start.is_finite() or not end.is_finite() or start<=0 or end<0:
        raise ValueError("positive start and nonnegative end required")
    with localcontext() as ctx:
        ctx.prec=28
        ctx.rounding=ROUND_HALF_EVEN
        return end/start-Decimal("1")

class KnownValueTests(unittest.TestCase):
    def test_one_period_pv(self):
        self.assertTrue(math.isclose(npv([0,110],.1),100,rel_tol=0,abs_tol=1e-10))
    def test_zero_npv(self):
        self.assertTrue(math.isclose(npv([-100,110],.1),0,rel_tol=0,abs_tol=1e-10))
    def test_zero_rate(self):
        self.assertEqual(npv([0,100],0),100)
    def test_negative_rate(self):
        self.assertTrue(math.isclose(npv([0,95],-.05),100,rel_tol=0,abs_tol=1e-10))
    def test_decimal_return(self):
        self.assertEqual(decimal_return(Decimal("100"),Decimal("101.50")),Decimal(".015"))
    def test_zero_end(self):
        self.assertEqual(decimal_return(Decimal("100"),Decimal("0")),Decimal("-1"))
    def test_scaling(self):
        self.assertTrue(math.isclose(npv([-200,220],.05),2*npv([-100,110],.05),
                                     rel_tol=1e-12,abs_tol=1e-10))
    def test_append_zero(self):
        self.assertTrue(math.isclose(npv([-100,110],.05),npv([-100,110,0],.05),
                                     rel_tol=0,abs_tol=1e-10))
    def test_invalid_rate(self):
        with self.assertRaises(ValueError): npv([1],-1)
    def test_empty(self):
        with self.assertRaises(ValueError): npv([],.05)
    def test_nonfinite(self):
        with self.assertRaises(ValueError): npv([1,float("nan")],.05)
    def test_invalid_start(self):
        with self.assertRaises(ValueError): decimal_return(Decimal("0"),Decimal("1"))

if __name__ == "__main__":
    unittest.main(verbosity=2)
~~~

The float examples use explicit tolerances where appropriate. The decimal calculation uses precision 28 and half-even rounding, but its inputs and results may still be unsuitable for a particular accounting standard. Extreme inputs can overflow or underflow.

## 13. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Assertion disappears under optimization | Python -O removes asserts | Use explicit input validation and test framework |
| Float comparison fails in last digits | Representation or operation order | Review an appropriate tolerance |
| Known value differs | Timing, sign or unit mismatch | Re-derive the benchmark |
| Test passes despite a defect | Case or expectation too weak | Add an independent, discriminating test |
| Decimal result differs | Context or rounding policy differs | Record and compare context |
| Unit tests pass but workflow fails | Data or integration issue | Test interfaces and conventions |
