## Learning objectives

Define financial input contracts; distinguish type, domain and cross-field checks; handle missing and nonfinite values; validate units and timing; raise explicit errors; and test boundaries without claiming that validation proves data or model accuracy.

## 1. Why validate inputs?

Financial calculations are only meaningful when inputs fit the model and its conventions. A price, rate or cash flow may be numerically valid but have the wrong unit, currency, timestamp or sign.

Input validation checks a documented contract before computation. It cannot by itself establish that a market price is current, a source is trustworthy or a model is appropriate.

## 2. Contract layers

| Layer | Example |
|---|---|
| Presence and shape | Required fields exist; cash-flow list is not empty |
| Type | Rate is a supported finite numeric value |
| Domain | Annual effective rate r>−1 |
| Cross-field | Starting and ending prices refer to compatible units |
| Temporal | Data was available by decision time |
| Business | Currency, instrument and price type match the use |

Choose rules for each specific model. A negative interest rate can be valid; a blanket “all rates positive” check is often wrong.

## 3. Cash-flow example

For periodic cash flows Cₜ and annual effective rate r:

**NPV=Σ Cₜ/(1+r)ᵗ**, with r>−1.

The input list must identify time-zero and subsequent periods. Under this section's contract, it must be nonempty and contain finite built-in numeric values. Negative cash flows are valid; r=−.05 is valid and r=−1 is invalid.

For [−100,110] at 10%, NPV is zero in exact arithmetic. A validation rule does not verify that these cash flows, dates or rate are appropriate for an actual transaction.

## 4. Return example

For simple return R=(P₁−P₀)/P₀, this section requires P₀>0 and P₁≥0. A zero starting price is invalid because it is a denominator; a zero ending price gives −100%.

This is a contract for an asset-price example. Other financial quantities may legitimately be negative and need different rules.

## 5. Missing, null and zero

A missing input, `None`, an empty list and numeric zero are distinct. Do not silently replace unknown prices with zero. Define whether each case is rejected, quarantined or accepted and record an error category without leaking sensitive values.

Python's `bool` is a subclass of `int`. If booleans are not meaningful financial quantities, reject them explicitly.

## 6. Finite values and numerical limits

NaN and infinity can propagate and make comparisons misleading. Reject them where finite values are required. A mathematically valid input can still exceed floating-point range or underflow; define supported ranges and behavior separately from the mathematical domain.

The example catches exponential overflow and rejects nonfinite results, but it cannot detect every underflow or cancellation case.

## 7. Units, currency and time

Five percent is .05 as a decimal; 100 basis points is .01. Record currency, price type, rate convention, payment timing and units. An observation date is not a publication timestamp. In backtests, check whether data was available by the decision time and preserve revisions where available.

A generic numeric validator cannot infer whether 5 means 5%, 500% or five basis points. Require explicit units in the surrounding contract.

## 8. Explicit exceptions

Raise a documented exception for invalid input. Do not rely solely on `assert`, since Python can omit assert statements under optimization. Do not catch every error and return zero: zero may be a valid NPV or return and would hide the failure.

Error messages should be useful without exposing credentials, account data or confidential input. Decide whether processing is fail-fast or whether invalid records are quarantined and reported.

## 9. Reference implementation

Save as `financial_input_validation.py`. The code validates a narrow periodic NPV and simple-return contract. It does not validate financial data sources, dates or currencies.

~~~python
import math
import unittest

def finite_number(value):
    return type(value) in (int,float) and math.isfinite(value)

def validate_cashflows(cashflows):
    if cashflows is None:
        raise ValueError("cash flows required")
    try:
        flows=list(cashflows)
    except TypeError as exc:
        raise ValueError("cash flows must be iterable") from exc
    if not flows or not all(finite_number(x) for x in flows):
        raise ValueError("nonempty finite numeric cash flows required")
    return flows

def npv(cashflows,rate):
    flows=validate_cashflows(cashflows)
    if not finite_number(rate) or rate<=-1:
        raise ValueError("finite rate greater than -1 required")
    try:
        result=math.fsum(c*math.exp(-t*math.log1p(rate))
                         for t,c in enumerate(flows))
    except OverflowError as exc:
        raise ValueError("discount calculation overflow") from exc
    if not math.isfinite(result):
        raise ValueError("nonfinite NPV")
    return result

def simple_return(start,end):
    if not all(finite_number(x) for x in (start,end)):
        raise ValueError("finite numeric prices required")
    if start<=0 or end<0:
        raise ValueError("positive start and nonnegative end required")
    return end/start-1

class InputValidationTests(unittest.TestCase):
    def test_known_npv(self):
        self.assertTrue(math.isclose(npv([-100,110],.1),0,rel_tol=0,abs_tol=1e-10))
    def test_valid_negative_rate(self):
        self.assertTrue(math.isclose(npv([0,95],-.05),100,rel_tol=0,abs_tol=1e-10))
    def test_negative_cashflow(self):
        self.assertTrue(math.isclose(npv([0,-110],.1),-100,rel_tol=0,abs_tol=1e-10))
    def test_zero_end(self):
        self.assertEqual(simple_return(100,0),-1)
    def test_zero_start(self):
        with self.assertRaises(ValueError): simple_return(0,100)
    def test_negative_end(self):
        with self.assertRaises(ValueError): simple_return(100,-1)
    def test_rate_boundary(self):
        with self.assertRaises(ValueError): npv([100],-1)
    def test_empty_flows(self):
        with self.assertRaises(ValueError): npv([],.05)
    def test_missing_flows(self):
        with self.assertRaises(ValueError): npv(None,.05)
    def test_nan(self):
        with self.assertRaises(ValueError): npv([float("nan")],.05)
    def test_infinity(self):
        with self.assertRaises(ValueError): simple_return(100,float("inf"))
    def test_boolean(self):
        with self.assertRaises(ValueError): npv([True],.05)
    def test_string(self):
        with self.assertRaises(ValueError): npv(["100"],.05)
    def test_noniterable(self):
        with self.assertRaises(ValueError): validate_cashflows(100)

if __name__ == "__main__":
    unittest.main(verbosity=2)
~~~

The contract intentionally accepts only built-in integers and floats, rejects booleans and Decimal values, and treats the input sequence as positional periods. A string is iterable but its elements fail the numeric check. Decimal, arrays or dated cash flows require a separate explicit contract and tests.

## 12. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Valid negative rate rejected | Overly broad domain rule | Check the model's stated boundary |
| Missing price becomes zero | Implicit coercion | Apply explicit missing-data policy |
| NaN reaches calculation | Missing finiteness check | Validate inputs and outputs |
| Correct number but wrong result | Units or timing mismatch | Review the surrounding contract |
| Valid input overflows | Numerical range exceeded | Define supported range and stable method |
| Error message exposes data | Logging or exception policy | Redact sensitive information |
