# 20.14 — Model Validation vs. Software Validation

**Book:** Book 1 — Python Foundations for Financial Mathematics  
**Chapter:** 20 — Testing and Engineering Financial Python

## Learning objectives

Distinguish software verification from financial model validation; specify intended use and limitations; design independent benchmarks, sensitivities and outcome analysis; record findings and review evidence; and identify why passing tests cannot establish model suitability.

## 1. Two related questions

Software validation asks whether a particular implementation satisfies its specified behavior: for example, whether it handles a zero rate, rejects invalid values and returns the expected discounted cash flow. Model validation asks whether the conceptual framework, assumptions, implementation and outputs are appropriate for the intended use. Terminology and governance requirements vary by organization; model validation commonly includes implementation review as well as conceptual and outcome analysis.

These activities overlap but are not interchangeable. Correctly implementing a simplified model does not establish that its assumptions fit a real instrument. Likewise, a sound formula implemented incorrectly can produce misleading outputs.

## 2. A simple present-value model

For a certain payment \(C\) one period from now and an effective rate \(r>-1\), define:

\[
PV=\frac{C}{1+r}.
\]

For \(C=100\) and \(r=0.10\), the exact expression is \(100/1.1\), approximately 90.9091. At zero rate the value is 100; at −5%, a payment of 95 has present value 100 in exact arithmetic.

Software checks can verify those examples, the rate boundary and the behavior of invalid inputs. Model review asks whether the payment is truly certain, whether the selected rate is appropriate, whether the period matches the payment date and whether omitted credit, liquidity, tax or currency effects matter. If the payment can default, this simple formula alone does not model that risk.

## 3. A practical validation framework

| Area | Questions and evidence |
|---|---|
| Intended use | What decision will the model support, for which instruments and users? |
| Conceptual soundness | Are the formula, assumptions, simplifications and limitations justified for that use? |
| Data | Are sources, units, quality, timing, revisions and missing-data rules appropriate? |
| Implementation | Does the code implement the specification, handle errors and meet numerical requirements? |
| Outcomes | How do results compare with independent benchmarks, alternative methods and observed outcomes where meaningful? |
| Governance | Who owns the model and review, what findings remain open, and when will it be reassessed? |

For a real organization, apply the applicable internal policies and external requirements. A validator should have sufficient expertise and independence for the model's risk and context.

## 4. Evidence from software checks

Use independently derived known values, boundary cases, invalid-input tests, regression tests and financial invariants. Specify tolerances in output units and distinguish numerical error from a material pricing difference. For a zero benchmark, use a suitable absolute tolerance.

Tests sample specified behavior; they do not cover every input or prove that a specification is financially appropriate. Coverage measures execution of code paths, not the quality of the financial model. Preserve the actual commands, versions and results separately from test definitions.

## 5. Evidence from model review

Review assumptions and intended use before inspecting results. For the example, compare the periodic result with an independently calculated benchmark. Examine sensitivities to rates, timing and payment amounts; stress plausible extremes and document numerical limitations. Compare with a richer model when relevant, explaining why differences arise.

Outcome analysis may compare forecasts with subsequently observed results, subject to adequate data, appropriate performance metrics and data availability. A close fit on historical observations is not a guarantee of future performance. Investigate discrepancies, uncertainty, regime changes and selection bias.

A useful counterexample: the software may return 90.9091 for a promised payment of 100 at 10%, yet be inappropriate for a risky bond if default and recovery materially affect the decision. That is a model-scope finding even when the arithmetic is correct.

## 6. Findings and lifecycle

Document the model identifier, owner, purpose, assumptions, input sources, implementation version, review methods, actual evidence, limitations, findings and decisions. Assign each finding an owner, impact, severity, due date and disposition under applicable policy. Do not describe a model as approved merely because tests exist.

Reassess after material changes to code, data, assumptions or use, and monitor performance and conditions over time. Record outstanding limitations and avoid use outside the reviewed scope without appropriate review.

## 7. Reference implementation

Save as `validation_example.py`. This synthetic example provides software checks and a simple sensitivity demonstration; it does not automate independent model validation.

~~~python
import math
import unittest


def present_value(payment: float, rate: float) -> float:
    """Discount one finite float payment by one effective period.

    The rate must be a finite built-in float greater than -1. The returned
    amount has the payment's units. Dates, default, fees, taxes, and currency
    conversion are outside this example. Overflow raises ValueError;
    underflow and floating-point rounding can occur.
    """
    if type(payment) is not float or not math.isfinite(payment):
        raise ValueError("payment must be a finite float")
    if type(rate) is not float or not math.isfinite(rate) or rate <= -1:
        raise ValueError("rate must be a finite float greater than -1")
    value = payment / (1.0 + rate)
    if not math.isfinite(value):
        raise ValueError("nonfinite present value")
    return value


class PresentValueTests(unittest.TestCase):
    def test_known_value(self):
        self.assertTrue(math.isclose(present_value(100.0, .1), 100 / 1.1,
                                     rel_tol=1e-12, abs_tol=1e-10))
    def test_zero_rate(self):
        self.assertEqual(present_value(100.0, 0.0), 100.0)
    def test_negative_rate(self):
        self.assertTrue(math.isclose(present_value(95.0, -.05), 100.0,
                                     rel_tol=0, abs_tol=1e-10))
    def test_zero_payment(self):
        self.assertEqual(present_value(0.0, .1), 0.0)
    def test_negative_payment(self):
        self.assertTrue(math.isclose(present_value(-110.0, .1), -100.0,
                                     rel_tol=0, abs_tol=1e-10))
    def test_scaling(self):
        self.assertTrue(math.isclose(present_value(200.0, .1),
                                     2 * present_value(100.0, .1),
                                     rel_tol=1e-12, abs_tol=1e-10))
    def test_rate_monotonicity(self):
        self.assertGreater(present_value(100.0, .05),
                           present_value(100.0, .10))
    def test_rate_boundary(self):
        with self.assertRaises(ValueError): present_value(100.0, -1.0)
    def test_nonfinite_rate(self):
        with self.assertRaises(ValueError): present_value(100.0, float("nan"))
    def test_nonfinite_payment(self):
        with self.assertRaises(ValueError): present_value(float("inf"), .1)
    def test_integer_rejected(self):
        with self.assertRaises(ValueError): present_value(100, .1)
    def test_boolean_rejected(self):
        with self.assertRaises(ValueError): present_value(100.0, True)


if __name__ == "__main__":
    for rate in (0.0, .05, .10):
        print(f"rate={rate:.2%}; PV={present_value(100.0, rate):.6f}")
    unittest.main(verbosity=2)
~~~

The test benchmark reflects the same formula and is useful for checking implementation behavior, but the expression alone does not independently validate model suitability. The implementation deliberately accepts only built-in floats, even though some static type checkers accept integers for float annotations. Extreme finite inputs can overflow or underflow; the model does not address actual dates or risk.

## 9. Forty worked exercises

1. **Software:** Does a correct implementation guarantee a suitable model? **Answer:** No; assumptions and intended use also require assessment.
2. **Model:** What is model validation? **Answer:** Assessment of conceptual soundness, implementation and outcomes for intended use.
3. **Testing:** Does a passing unit test prove a financial assumption? **Answer:** No.
4. **Discounting:** What is 100 due in one period at 10%? **Answer:** 100/1.1, approximately 90.9091.
5. **Zero rate:** Present value of 100 at zero rate? **Answer:** 100.
6. **Negative rate:** Present value of 95 at −5% for one period? **Answer:** 100.
7. **Rate boundary:** Is −1 valid for the periodic formula? **Answer:** No; its denominator is zero.
8. **Rate unit:** Is 5 equal to 5% in decimal units? **Answer:** No; 5% is 0.05.
9. **Tenor:** What happens to present value when a positive rate rises for a positive future cash flow? **Answer:** It decreases, holding other inputs fixed.
10. **Scale:** Double a fixed cash flow: what happens to present value? **Answer:** It doubles in exact arithmetic.
11. **Timing:** Can a correct formula misprice a dated payment? **Answer:** Yes, if its periods do not match the payment date convention.
12. **Liquidity:** Does a risk-free discount example model liquidity risk? **Answer:** No.
13. **Credit:** Does the example model default? **Answer:** No; promised payment is assumed certain.
14. **Currency:** Does the implementation convert currency? **Answer:** No.
15. **Data:** Why examine source and timestamp? **Answer:** Inputs must be relevant and available at the valuation time.
16. **Historical data:** Can revised data cause look-ahead? **Answer:** Yes, if unavailable revisions are used historically.
17. **Benchmark:** Why independently derive a benchmark? **Answer:** It reduces the risk of repeating the same implementation error.
18. **Alternative model:** Why compare against one? **Answer:** It can reveal sensitivity to assumptions or implementation choices.
19. **Backtesting:** Do good past results ensure future accuracy? **Answer:** No.
20. **Outcomes:** What should a validator investigate when realized outcomes differ? **Answer:** Data, assumptions, implementation and changing conditions.
21. **Stress:** What is a stress scenario? **Answer:** A specified severe or unusual input scenario used to explore behavior.
22. **Sensitivity:** What does sensitivity analysis vary? **Answer:** One or more assumptions or inputs to examine their effect.
23. **Range:** Does an input accepted by code necessarily fit model scope? **Answer:** No.
24. **Independence:** Why have an independent reviewer? **Answer:** To challenge assumptions and reduce conflicts of interest.
25. **Documentation:** What should a model inventory record? **Answer:** Purpose, owner, version, use, limitations and validation status.
26. **Governance:** What should a validation finding contain? **Answer:** Evidence, impact, severity, owner and remediation or acceptance.
27. **Change:** Can a data-source change require renewed review? **Answer:** Yes; its materiality determines review scope.
28. **Monitoring:** Why monitor after approval? **Answer:** Inputs, usage and market conditions can change.
29. **Tolerance:** Why specify units? **Answer:** A price tolerance differs from a rate tolerance.
30. **Zero benchmark:** Why use an absolute tolerance? **Answer:** Relative tolerance alone cannot accommodate nonzero error against zero.
31. **Overflow:** Can finite inputs still overflow? **Answer:** Yes.
32. **Underflow:** Can a discount factor underflow? **Answer:** Yes, at extreme values.
33. **Precision:** Does rounding a display prove computational accuracy? **Answer:** No.
34. **Regression:** What does a regression test compare? **Answer:** Current behavior against an established expected behavior.
35. **Reproducibility:** Can a repeatable result still be wrong? **Answer:** Yes.
36. **Boundary:** What does rejecting NaN address? **Answer:** Input integrity, not financial suitability.
37. **Code coverage:** Does complete coverage validate all possible inputs? **Answer:** No.
38. **Exceptions:** Should a failed calculation silently return zero? **Answer:** No; it should communicate failure.
39. **Approval:** Do these reference tests confer approval? **Answer:** No.

## 10. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Tests pass but valuation is unsuitable | Assumptions do not match intended use | Review model scope, data and limitations |
| Benchmark differs | Convention, units or formula differ | Reconcile timing and rate definitions |
| Historical performance appears unusually strong | Data leakage or selection bias | Check availability times and sample construction |
| Results change after deployment | Inputs, environment or implementation changed | Compare versions, data and configuration |
| Model behaves poorly under stress | Extrapolation or numerical limits | Investigate limitations and define controls |
| Review status is unclear | Evidence and ownership are missing | Record findings, decisions and responsible owners |
