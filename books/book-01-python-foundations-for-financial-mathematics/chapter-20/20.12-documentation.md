## Learning objectives

Document financial functions, units, assumptions, errors and numerical policies; write examples and docstrings; distinguish software documentation from model validation; and retain information needed to reproduce a calculation.

## 1. Why documentation matters

Financial code can produce a plausible number under the wrong convention. Documentation makes its contract reviewable: what the function calculates, accepted inputs, units, timing and limitations. Update documentation with the code and review both.

Documentation does not prove that the implementation or model is correct. Tests, data checks and independent model validation remain necessary.

## 2. A financial function contract

State purpose, formula, input types and domains, units, timing, compounding, output, rounding, exceptions and limitations. For a periodic NPV function, identify the time-zero flow and the effective rate per period. A value of 5 is ambiguous unless its unit is specified; 5% is .05 in decimal units.

For [−100,110] with the second flow one year later and a 10% annual effective rate, **NPV=−100+110/1.1=0** in exact arithmetic. State assumptions so readers can independently reproduce the benchmark.

## 3. Docstrings and comments

A docstring describes a function's contract and can be accessed through Python's help function. Comments explain non-obvious choices near code. Avoid stale comments and descriptions that contradict implementation.

Type hints and docstrings do not automatically validate inputs. Runtime checks and tests should agree with the documented interface.

## 4. Errors and boundaries

Document invalid inputs and exceptions. For the annual effective discount model, r>−1: −.05 is valid while −1 is not. State behavior for empty flows, nonfinite values and numerical overflow.

Do not turn every failure into a plausible result such as zero. Error messages and logs should not expose credentials or confidential financial input.

## 5. Numerical and rounding policies

Specify float versus Decimal, precision, rounding and tolerances. A currency price tolerance is not a yield tolerance. A displayed two-decimal result does not imply that intermediate values were rounded. Currency minor units and settlement policies differ.

Document any supported numerical range and known underflow or cancellation risks. Passing a few tests does not establish accuracy over every magnitude.

## 6. Data, timing and provenance

Record source, instrument identifier, currency, price type, observation and availability time, revisions and corporate-action treatment where relevant. A date is not automatically an instant or publication time.

A current corrected dataset may not reconstruct what was known historically. State such gaps instead of claiming a backtest is free of look-ahead.

## 7. Examples and evidence

Use synthetic inputs where possible. Derive benchmark values independently and state dependencies and commands. An example or test included in documentation is not evidence that it has run.

Record actual test command, output, code revision, Python and dependency versions, and a safe input identity. Distinguish a draft, a tested implementation and an independently validated model.

## 8. Reference implementation

Save as `documented_finance.py`. It includes a documented periodic NPV function and a reference test suite.

~~~python
import math
import unittest
from collections.abc import Iterable

def npv(cashflows: Iterable[float], rate: float) -> float:
    """Calculate NPV for equally spaced periodic cash flows.

    The first flow is at time zero and subsequent flows are one period apart.
    Rate is a finite decimal effective rate per period greater than -1.
    Cash flows must be a nonempty iterable of finite built-in floats.

    Return a float in the same monetary unit, without display rounding.
    Raise ValueError for invalid input or detected numerical overflow.
    Underflow and cancellation remain possible. Dates, currencies, fees,
    taxes and day-count conventions are not modeled.

    Example: [-100.0, 110.0] at 0.10 has NPV zero in exact arithmetic.
    """
    flows=list(cashflows)
    if not flows or any(type(x) is not float or not math.isfinite(x) for x in flows):
        raise ValueError("nonempty finite float cash flows required")
    if type(rate) is not float or not math.isfinite(rate) or rate<=-1:
        raise ValueError("finite float rate > -1 required")
    try:
        result=math.fsum(c*math.exp(-t*math.log1p(rate))
                         for t,c in enumerate(flows))
    except OverflowError as exc:
        raise ValueError("discount calculation overflow") from exc
    if not math.isfinite(result):
        raise ValueError("nonfinite NPV")
    return result

class DocumentationTests(unittest.TestCase):
    def test_known_value(self):
        self.assertTrue(math.isclose(npv([-100.0,110.0],.1),0,
                                     rel_tol=0,abs_tol=1e-10))
    def test_zero_rate(self):
        self.assertEqual(npv([0.0,100.0],0.0),100.0)
    def test_negative_rate(self):
        self.assertTrue(math.isclose(npv([0.0,95.0],-.05),100,
                                     rel_tol=0,abs_tol=1e-10))
    def test_generator(self):
        self.assertEqual(npv((x for x in [0.0,100.0]),0.0),100.0)
    def test_invalid_rate(self):
        with self.assertRaises(ValueError): npv([100.0],-1.0)
    def test_empty(self):
        with self.assertRaises(ValueError): npv([],0.0)
    def test_integer_rejected(self):
        with self.assertRaises(ValueError): npv([100],0.0)
    def test_boolean_rejected(self):
        with self.assertRaises(ValueError): npv([True],0.0)
    def test_nonfinite_flow(self):
        with self.assertRaises(ValueError): npv([float("nan")],0.0)
    def test_nonfinite_rate(self):
        with self.assertRaises(ValueError): npv([100.0],float("inf"))
    def test_docstring_exists(self):
        self.assertIsNotNone(npv.__doc__)
    def test_scaling(self):
        self.assertTrue(math.isclose(npv([-200.0,220.0],.05),
                                     2*npv([-100.0,110.0],.05),
                                     rel_tol=1e-12,abs_tol=1e-10))

if __name__ == "__main__":
    print(npv.__doc__)
    unittest.main(verbosity=2)
~~~

The example deliberately rejects integers at runtime even though many static type checkers accept integers for a float annotation. It consumes the iterable and does not support dated payments or Decimal values. The presence of a docstring does not prove that its contents are accurate.

## 9. Twelve-step hands-on lab

1. Write the formula, cash-flow timing and rate convention.
2. Independently calculate the example NPV.
3. Save the code and record Python version.
4. Inspect the docstring using help after importing the function.
5. Identify supported runtime types and the invalid rate boundary.
6. Describe output units and rounding.
7. List unsupported dates, currency, fees and tax.
8. Compare the type hint with the stricter runtime float-only rule.
9. Propose a change note for a modified rate convention.
10. Identify safe input and environment metadata needed for replay.
11. Run the reference tests and retain actual output.
12. Record documentation gaps for later Book 1 QA.

## 11. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Rate interpreted incorrectly | Unit or convention omitted | Clarify contract and examples |
| Code and docstring disagree | Change not documented | Reconcile implementation and tests |
| Example fails elsewhere | Version or dependency omitted | Record environment |
| Correct NPV but wrong financial result | Timing or model assumptions differ | Review conventions independently |
| Error exposes sensitive input | Unsafe exception or logging policy | Redact and restrict detail |
| Test status unclear | Reference tests confused with execution | Retain actual command and output |
