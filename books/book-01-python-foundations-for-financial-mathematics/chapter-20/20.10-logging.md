## Learning objectives

Use Python logging for financial calculations; select levels and safe event fields; preserve diagnostic context without exposing sensitive inputs; test emitted events; and distinguish operational logs from authoritative audit records.

## 1. Why log?

Logs help explain what a process did, when it failed and which safe run identifier or component was involved. For a financial calculation, useful events can include a start, successful completion or an error category.

Logs are not a substitute for input validation, exception handling, durable transaction records or independent model review. They can be missing, delayed or altered unless the surrounding system provides appropriate controls.

## 2. Logging versus printing

Python's `logging` module supports named loggers, levels, handlers and formatting. Applications configure destinations and levels; reusable libraries should generally avoid configuring the root logger on import.

A library can emit a named event while the application decides whether it goes to a console, file or centralized platform. Avoid adding handlers repeatedly, which can duplicate messages.

## 3. Levels

| Level | Typical meaning |
|---|---|
| DEBUG | Detailed diagnostics, enabled selectively |
| INFO | Normal operational milestones |
| WARNING | Unexpected but potentially recoverable condition |
| ERROR | An operation failed |
| CRITICAL | A severe condition requiring urgent attention |

Level choice is a policy decision. A WARNING or ERROR does not automatically notify anyone; routing and alerting must be configured separately.

## 4. Safe context

Useful fields may include event name, component, a non-sensitive run identifier, outcome category, schema or code version, and timestamps. Define which identifiers are permitted and prevent untrusted text from injecting misleading log lines.

Do not log credentials, tokens, account numbers, raw confidential payloads or full market positions merely for convenience. Redaction and access controls are defense in depth; the strongest approach is to avoid collecting unnecessary sensitive data.

## 5. Exceptions and tracebacks

Raise explicit exceptions for invalid inputs and numerical failures. Log at a boundary that knows the operational context, and avoid logging the same exception repeatedly at every layer.

Tracebacks and exception messages can contain sensitive values or paths. Choose safe error categories for broadly accessible logs and restrict detailed diagnostics according to policy. Do not swallow an error and return zero: zero can be a valid financial result.

## 6. Structured events

Structured logging uses named fields, often serialized as JSON, so systems can filter and correlate events. Define field types, timestamp semantics, schema version and cardinality. A run ID is useful for correlation but does not prove data integrity.

A hash can identify bytes, but it does not prove data accuracy, authenticity or confidentiality. Do not assume hashing a sensitive low-entropy identifier anonymizes it.

## 7. Audit and reproducibility

An operational log is not automatically an immutable audit trail. Audit requirements may include access control, retention, integrity, clock synchronization and independent review. Record code and configuration versions, source identity and actual outcomes where appropriate, while following data-handling rules.

A reproducible run can still use incorrect inputs or a wrong financial model. Logs support investigation; they do not validate the model.

## 8. Reference implementation

Save as `financial_logging.py`. It logs fixed event names and controlled run IDs for a simplified periodic NPV calculation. The caller configures the logger. It does not log raw cash flows, rates, exception messages or tracebacks.

~~~python
import io
import logging
import math
import re
import unittest

LOGGER=logging.getLogger("financial_example")
RUN_ID=re.compile(r"^[A-Za-z0-9_-]{1,32}$")

def finite_number(value):
    return type(value) in (int,float) and math.isfinite(value)

def calculate_npv(cashflows,rate):
    flows=list(cashflows)
    if not flows or not finite_number(rate) or rate<=-1:
        raise ValueError("invalid calculation input")
    if not all(finite_number(x) for x in flows):
        raise ValueError("invalid calculation input")
    try:
        result=math.fsum(c*math.exp(-t*math.log1p(rate))
                         for t,c in enumerate(flows))
    except OverflowError as exc:
        raise ArithmeticError("numerical calculation failed") from exc
    if not math.isfinite(result):
        raise ArithmeticError("numerical calculation failed")
    return result

def run_calculation(run_id,cashflows,rate):
    if not isinstance(run_id,str) or not RUN_ID.fullmatch(run_id):
        raise ValueError("invalid run identifier")
    LOGGER.info("calculation_started run_id=%s",run_id)
    try:
        result=calculate_npv(cashflows,rate)
    except ValueError:
        LOGGER.warning("calculation_rejected run_id=%s category=invalid_input",run_id)
        raise
    except ArithmeticError:
        LOGGER.error("calculation_failed run_id=%s category=numerical",run_id)
        raise
    LOGGER.info("calculation_completed run_id=%s",run_id)
    return result

class LoggingTests(unittest.TestCase):
    def test_valid_result(self):
        self.assertTrue(math.isclose(run_calculation("run_1",[-100,110],.1),
                                     0,rel_tol=0,abs_tol=1e-10))
    def test_start_and_completion(self):
        with self.assertLogs(LOGGER,level="INFO") as captured:
            run_calculation("run_1",[0,100],0)
        self.assertEqual(len(captured.output),2)
        self.assertIn("calculation_started",captured.output[0])
        self.assertIn("calculation_completed",captured.output[1])
    def test_invalid_input_event(self):
        with self.assertLogs(LOGGER,level="WARNING") as captured:
            with self.assertRaises(ValueError): run_calculation("run_1",[100],-1)
        self.assertIn("category=invalid_input",captured.output[0])
    def test_no_raw_cashflow(self):
        with self.assertLogs(LOGGER,level="INFO") as captured:
            run_calculation("run_1",[123456789],0)
        self.assertNotIn("123456789"," ".join(captured.output))
    def test_invalid_run_id(self):
        with self.assertRaises(ValueError): run_calculation("bad\nline",[100],0)
    def test_empty_flows(self):
        with self.assertRaises(ValueError): calculate_npv([],.05)
    def test_nan(self):
        with self.assertRaises(ValueError): calculate_npv([float("nan")],.05)
    def test_invalid_rate(self):
        with self.assertRaises(ValueError): calculate_npv([100],-1)
    def test_valid_negative_rate(self):
        self.assertTrue(math.isclose(calculate_npv([0,95],-.05),100,
                                     rel_tol=0,abs_tol=1e-10))
    def test_numerical_event(self):
        with self.assertLogs(LOGGER,level="ERROR") as captured:
            with self.assertRaises(ArithmeticError):
                run_calculation("run_1",[0]*1000+[1],-.9)
        self.assertIn("category=numerical",captured.output[0])
    def test_no_result_logged(self):
        with self.assertLogs(LOGGER,level="INFO") as captured:
            run_calculation("run_1",[987654321],0)
        self.assertNotIn("987654321"," ".join(captured.output))
    def test_boolean_input(self):
        with self.assertRaises(ValueError): calculate_npv([True],0)

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO,format="%(levelname)s %(name)s %(message)s")
    run_calculation("demo_1",[-100,110],.1)
    unittest.main(verbosity=2)
~~~

This example uses plain text with fixed fields, not a JSON formatter. The restricted run ID reduces newline injection for this field; it does not replace a full organization-wide logging or privacy policy. Unexpected exceptions are not caught by `run_calculation`; the application boundary must define their handling. The example does not implement persistence, retention, access control, audit integrity, dates or currency.

## 11. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Duplicate events | Multiple handlers or propagation | Inspect logger configuration |
| Missing INFO events | Level or routing filters | Check application logging configuration |
| Secret appears in log | Unsafe field or exception text | Restrict access, redact and review the source |
| Error count exceeds failures | Same error logged at multiple layers | Define a single logging boundary |
| No alert despite ERROR | No routing or alert rule | Check operational configuration |
| Logs cannot reproduce a result | Missing code, input or configuration identity | Review safe evidence requirements |
