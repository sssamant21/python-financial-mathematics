## Learning objectives

Explain why financial software needs tests; distinguish software verification from model validation; design known-value, boundary and invariant checks; use appropriate numerical tolerances; identify testing limitations; and document reproducible evidence.

## 1. The cost of a small error

Financial software can process many positions, transactions or scenarios. A one-cent error per unit becomes 10,000 currency units across one million units. An incorrect rate unit, timing convention or sign can produce a result that looks plausible but materially changes a decision.

Testing helps detect defects before use and supports safer changes. A passing test suite is evidence about the tested cases, not proof that every calculation or financial model is correct.

## 2. Verification and validation

**Software verification** asks whether the implementation follows its specification. **Model validation** asks whether the mathematical model and assumptions are appropriate for the intended use.

For a present-value calculation, a test may verify that code implements an annual effective discount formula. Separate review must establish whether that formula, payment timing, currency and convention are appropriate for the actual instrument.

Correct software can accurately calculate an inappropriate model; a sound model can also be implemented incorrectly.

## 3. Known-value tests

Use independently derived examples with explicit assumptions:

- A cash flow of 110 received after one year at 10% annual effective rate has PV=100.
- Cash flows [−100,110] at 10% have NPV=0.
- A price rising from 100 to 101.50 has simple return .015, or 1.5%.
- At zero rate, an un-discounted payment of 100 in one year has PV=100.

Avoid deriving the expected value by calling the same implementation under test. Record units and rounding so another reviewer can reproduce the benchmark.

## 4. Boundary and invalid inputs

Test zero rates, valid negative rates, empty inputs, zero denominators, nonfinite values, invalid dates and values at domain boundaries. Define whether each case should return a value or raise a specific exception.

For the annual effective model (1+r)⁻ᵗ used here, r>−1. A rate of −.05 is in the domain; r=−1 is invalid. Different compounding conventions have different domains.

## 5. Financial invariants

An invariant or metamorphic test checks a relationship under stated assumptions:

- Doubling all cash flows doubles NPV at the same rate and schedule.
- Adding a zero cash flow at the end does not change NPV.
- Increasing the rate lowers PV of a positive future cash flow.
- Converting all cash flows consistently from one currency unit to another scales monetary results.

Inserting a zero cash flow in the middle shifts later payments in a positional schedule and can change NPV. A negative future cash flow reverses the monotonicity direction.

## 6. Numerical comparisons

Binary floating-point values may differ by small rounding amounts. A common comparison against reference b is **|a−b|≤atol+rtol|b|**. Absolute tolerance has output units; relative tolerance is dimensionless. Near zero, a justified absolute tolerance is important.

Choose tolerances from the calculation, scale and intended use, not simply to make a failure pass. A price tolerance in dollars is not a yield tolerance in decimal rates. Reject or handle nonfinite values explicitly.

For accounting-style decimal requirements, `Decimal` and a documented precision and rounding policy may be appropriate. Decimal arithmetic still requires tests of inputs, context, domain and financial semantics.

## 7. Test layers

| Layer | Example |
|---|---|
| Unit | NPV calculation for a known cash-flow sequence |
| Integration | Data parser feeding the calculation |
| Regression | A known corrected defect remains fixed |
| Property / invariant | Scaling cash flows scales NPV |
| System | A complete workflow with controlled inputs |
| Independent model review | Appropriateness of assumptions and conventions |

The exact layers and controls depend on the application. Tests should have clear expected results and should fail when behavior is incorrect, rather than duplicating implementation logic.

## 8. Testing errors and exceptions

Invalid inputs should produce a documented result or exception. Avoid swallowing exceptions and returning a plausible number such as zero. Tests should verify the intended exception type and, where relevant, a stable error category.

Python's `assert` is useful in tests and debugging, but assertions can be removed when Python runs with optimization. Do not rely on `assert` as the only production input validation.

## 9. Reproducibility and data

Record the code revision, Python and library versions, inputs, units, configuration, seed when randomness is involved, test command and actual results. Synthetic fixtures can reduce dependency on live data; they should still represent important boundary and failure cases.

Preserve source and availability information for historical datasets. A reproducible backtest can still contain look-ahead bias or survivorship bias.

## 10. Integration and independent checks

A unit test for a pricing function does not verify that a data pipeline supplies the correct currency, payment date or adjusted price. Test interfaces and reconcile representative outputs against independent benchmarks under identical conventions.

Use controlled fixtures for deterministic regression tests. For simulations, record the generator and seed for replay and use analytical or statistical checks appropriate to the estimator; a single fixed seed does not establish distributional validity.

## 11. Reference implementation

Save as `financial_testing_basics.py`. It implements a small annual effective NPV function and reference tests. Cash flows are positional: element zero is at time zero. This example is not a production valuation library.

~~~python
import math
import unittest

def finite_number(value):
    return type(value) in (int,float) and math.isfinite(value)

def npv(cashflows, rate):
    flows=list(cashflows)
    if not flows or not finite_number(rate) or rate<=-1:
        raise ValueError("nonempty cash flows and finite rate > -1 required")
    if not all(finite_number(value) for value in flows):
        raise ValueError("finite numeric cash flows required")
    try:
        value=math.fsum(flow*math.exp(-period*math.log1p(rate))
                        for period,flow in enumerate(flows))
    except OverflowError as exc:
        raise ValueError("discount calculation overflow") from exc
    if not math.isfinite(value):
        raise ValueError("nonfinite NPV")
    return value

def simple_return(start,end):
    if not all(finite_number(x) for x in (start,end)) or start<=0 or end<0:
        raise ValueError("positive start and nonnegative end required")
    return end/start-1

class FinancialTests(unittest.TestCase):
    def test_known_npv(self):
        self.assertAlmostEqual(npv([-100,110],.1),0,places=10)
    def test_zero_rate(self):
        self.assertEqual(npv([0,100],0),100)
    def test_negative_valid_rate(self):
        self.assertAlmostEqual(npv([0,95],-.05),100)
    def test_scaling(self):
        self.assertAlmostEqual(npv([-200,220],.05),2*npv([-100,110],.05))
    def test_append_zero(self):
        self.assertAlmostEqual(npv([-100,110],.05),npv([-100,110,0],.05))
    def test_positive_flow_monotonicity(self):
        self.assertGreater(npv([0,100],.05),npv([0,100],.06))
    def test_known_return(self):
        self.assertAlmostEqual(simple_return(100,101.5),.015)
    def test_zero_end(self):
        self.assertEqual(simple_return(100,0),-1)
    def test_bad_rate(self):
        with self.assertRaises(ValueError): npv([1],-1)
    def test_empty(self):
        with self.assertRaises(ValueError): npv([],.05)
    def test_nonfinite(self):
        with self.assertRaises(ValueError): npv([1,float("nan")],.05)
    def test_zero_start(self):
        with self.assertRaises(ValueError): simple_return(0,1)

if __name__ == "__main__":
    print("NPV example:",npv([-100,110],.1))
    unittest.main(verbosity=2)
~~~

The example uses binary floating-point and does not implement dated cash flows, tax, fees, day-count rules, corporate actions or a production precision policy. Extreme inputs can still create numerical issues, including underflow.

## 14. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Correct-looking price differs from benchmark | Units, timing or convention mismatch | Compare assumptions and inputs |
| Test fails only in last digits | Floating-point differences | Review a justified tolerance |
| Invalid input returns zero | Exception swallowed or validation missing | Check error policy and tests |
| Unit tests pass but workflow fails | Integration or data contract issue | Test interfaces and representative data |
| Historical results look too good | Look-ahead or leakage | Audit availability, splits and revisions |
| Same simulation seed differs | Generator, version or draw order changed | Compare run metadata |
