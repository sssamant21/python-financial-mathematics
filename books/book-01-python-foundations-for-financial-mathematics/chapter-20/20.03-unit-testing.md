## Learning objectives

Design focused unit tests for financial functions; use Python's `unittest`; derive independent expected values; test valid, boundary and invalid inputs; choose numerical comparisons; isolate dependencies; and distinguish unit-test evidence from model validation.

## 1. What is a unit test?

A unit test checks a small, specified behavior, usually a function or method, using controlled inputs. For financial code, the specification must include units, timing, rate conventions and expected error handling.

A test should fail when the behavior it protects is broken. A suite of focused tests provides useful regression evidence, but it does not prove correctness for every input or establish that the financial model is appropriate.

## 2. Arrange, act and assert

A clear test defines inputs and expectations (**arrange**), invokes the function (**act**), and checks the result (**assert**). Name the test after the behavior. Avoid constructing an expected result by repeating the same implementation logic; use an independently derived benchmark or invariant.

For example, 110 paid in one year at 10% annual effective rate has PV=100. The independent arithmetic is 110/1.1=100.

## 3. A small financial unit

For a payment C after n periods at effective per-period rate r:

**PV=C/(1+r)ⁿ**, with r>−1 and integer n≥0.

At n=0, PV=C. A valid negative rate such as −.05 produces a larger PV for a positive future payment. This simplified model omits calendars, fees, tax and instrument-specific conventions.

## 4. Known values and boundaries

Test 110 at 10% for one period, 95 at −5%, zero rate and zero periods. Test invalid rate −1, negative periods, nonfinite inputs and wrong types according to the function contract.

A good boundary test distinguishes adjacent cases: r=−.05 is valid while r=−1 is invalid. Do not assume negative financial rates are universally invalid.

## 5. Assertions and numerical precision

Use exact equality when the representation and expected result justify it. Binary floats often require a tolerance. A mixed comparison may use **|a−b|≤atol+rtol|b|** against reference b, while `math.isclose` has its own documented symmetric rule.

Set tolerances in meaningful units and keep them narrow enough to reveal an error. Near zero, absolute tolerance is essential. `unittest.assertAlmostEqual` with `places` tests decimal-place rounding, not a general mixed tolerance.

## 6. Error tests

Use `assertRaises` to verify that invalid inputs raise the documented exception. Do not swallow errors and return zero: zero can be a valid financial value and mask a defect.

Production input checks should use explicit exceptions. Python can remove `assert` statements under optimization, so `assert` should not be the sole input-validation mechanism.

## 7. Invariants

Known-value examples can be complemented by relationships that hold under explicit assumptions:

- PV is linear in cash flow at fixed rate and time.
- For a positive future payment, PV decreases when the rate rises.
- At zero periods, PV equals the cash flow.

A negative cash flow reverses the monotonicity direction. A test should describe its domain rather than assert an overbroad rule.

## 8. Fixtures and isolation

Fixtures prepare repeatable test inputs. Avoid tests that depend on a live market API, current date, shared mutable global state or a developer's credentials. Inject or mock external dependencies when appropriate, and separately test real integration boundaries in a controlled environment.

Mocks can hide incorrect assumptions about an external service. Unit tests do not replace integration tests, source reconciliation or independent financial model review.

## 9. Reference implementation

Save as `unit_testing_finance.py`. This standard-library example contains a simple present-value function and a focused test suite. It is not a production bond or settlement model.

~~~python
import math
import unittest

def finite_number(value):
    return type(value) in (int,float) and math.isfinite(value)

def present_value(cashflow,rate,periods):
    if not finite_number(cashflow) or not finite_number(rate) or rate<=-1:
        raise ValueError("finite cash flow and rate > -1 required")
    if type(periods) is not int or periods<0:
        raise ValueError("nonnegative integer periods required")
    try:
        result=cashflow*math.exp(-periods*math.log1p(rate))
    except OverflowError as exc:
        raise ValueError("discount calculation overflow") from exc
    if not math.isfinite(result):
        raise ValueError("nonfinite present value")
    return result

class PresentValueTests(unittest.TestCase):
    def test_one_period_known_value(self):
        self.assertTrue(math.isclose(present_value(110,.1,1),100,
                                     rel_tol=0,abs_tol=1e-10))
    def test_zero_rate(self):
        self.assertEqual(present_value(100,0,1),100)
    def test_zero_periods(self):
        self.assertEqual(present_value(100,.05,0),100)
    def test_valid_negative_rate(self):
        self.assertTrue(math.isclose(present_value(95,-.05,1),100,
                                     rel_tol=0,abs_tol=1e-10))
    def test_negative_cashflow(self):
        self.assertTrue(math.isclose(present_value(-110,.1,1),-100,
                                     rel_tol=0,abs_tol=1e-10))
    def test_linearity(self):
        self.assertTrue(math.isclose(present_value(220,.1,1),
                                     2*present_value(110,.1,1),
                                     rel_tol=1e-12,abs_tol=1e-10))
    def test_positive_cashflow_rate_monotonicity(self):
        self.assertGreater(present_value(100,.05,1),present_value(100,.06,1))
    def test_rate_boundary(self):
        with self.assertRaises(ValueError): present_value(100,-1,1)
    def test_negative_periods(self):
        with self.assertRaises(ValueError): present_value(100,.05,-1)
    def test_fractional_periods(self):
        with self.assertRaises(ValueError): present_value(100,.05,1.5)
    def test_nonfinite(self):
        with self.assertRaises(ValueError): present_value(float("nan"),.05,1)
    def test_boolean_periods(self):
        with self.assertRaises(ValueError): present_value(100,.05,True)

if __name__ == "__main__":
    unittest.main(verbosity=2)
~~~

The implementation uses binary floats and positional periods. It does not handle dates, day-count conventions, taxes, fees, currencies or every extreme numerical input. Underflow can occur. Explicit type checks intentionally reject booleans even though Python treats `bool` as a subclass of `int`.

## 10. Running and interpreting tests

During deferred QA:

~~~bash
python unit_testing_finance.py
python -m unittest -v unit_testing_finance
python -m compileall -q unit_testing_finance.py
~~~

For this standalone file, either of the first two commands runs its `unittest` suite; compilation checks syntax, not financial correctness. Record the command, Python version and actual output. The 12 reference tests have not been executed during publication.

A test failure is a signal to investigate the implementation, expected result, assumptions and environment. Do not simply relax tolerances to make it pass.

## 13. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Test fails in last digits | Floating-point rounding | Review a justified tolerance |
| Known value differs | Timing, rate or sign convention mismatch | Re-derive independently |
| Exception test fails | Wrong validation or exception type | Check the documented contract |
| Tests pass locally but fail elsewhere | Environment or hidden dependency | Record versions and isolate state |
| Mocked test passes but integration fails | Mock differs from service contract | Test the integration boundary |
| Suite passes but model result is unsuitable | Model assumptions not validated | Perform independent financial review |
