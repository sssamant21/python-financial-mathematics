## Learning objectives

Identify the information needed to replay a financial calculation; distinguish exact from tolerance-based agreement; preserve input provenance and environment details; manage random streams; and design a minimal, safe run manifest.

## 1. What reproducibility means

A reproducible calculation can be rerun with recorded code, inputs, configuration and environment, and the result compared against retained evidence. Agreement can mean identical bytes or agreement within a justified numerical tolerance. State the target explicitly. Reproducing an incorrect calculation does not make its financial assumptions correct.

For equally spaced cash flows, the effective rate applies per period and the first flow occurs at time zero:

\[
\operatorname{NPV}=\sum_{t=0}^{n}\frac{C_t}{(1+r)^t}.
\]

For −100 now and 110 one period later at 10%, the exact NPV is zero. A binary floating-point implementation may return a tiny nonzero value. Compare with an absolute tolerance in the cash-flow currency; relative tolerance alone is unhelpful for a zero benchmark.

## 2. Identify the calculation

Record the repository and commit, any uncommitted changes, command or entry point, relevant configuration, valuation date, financial conventions and output identity. A branch name can move. A commit does not identify an uncommitted modification, external data, environment variables or runtime dependencies.

State currency, units, timing, day count, compounding, price type, rounding and treatment of fees or missing observations where they matter. Make assumptions explicit enough for another person to reconstruct the calculation.

## 3. Preserve data and provenance

Retain an immutable input snapshot where rights and controls permit. Record its source, retrieval time, as-of and availability times, revision, schema, transformations and content digest. A digest verifies candidate bytes; it does not recover missing data, establish correctness or guarantee that data were available at the valuation time.

Historical market data may be revised. Use the dataset actually available at the simulated decision time when evaluating a backtest, and disclose any missing provenance. A digest of predictable sensitive data may itself leak information through guessing; restrict it appropriately.

## 4. Capture the environment

Record Python and dependency versions, lockfiles and package artifact hashes when available, operating system, architecture, relevant numerical libraries and non-secret settings. Retain installation instructions and, where appropriate, container images or artifacts. Pinning versions alone cannot guarantee that packages remain available or behave identically across platforms.

Floating-point summation order, processor instructions, parallel libraries and solver settings can change results. Define financially meaningful absolute and relative tolerances and investigate differences rather than silently accepting every deviation.

## 5. Randomness and parallel work

For simulations record the generator implementation, version, seed or initial state, number and order of draws, distribution parameters and stream allocation. An explicit local generator avoids accidental interference from unrelated code. A seed alone is not a universal cross-version or cross-library guarantee. Parallel scheduling and worker count can change stream consumption; define deterministic independent streams and retain their allocation.

A reproducible simulation is still subject to sampling error and model risk. Record sample size and uncertainty alongside the estimate.

## 6. Evidence and safe manifests

Retain the command, actual output, test results, run time and code/data identities. Separate a declared test from one that actually ran. Do not store passwords, access tokens or confidential raw data in a public manifest; apply access controls and retention rules to sensitive artifacts. A hash is an identity check, not an anonymization technique.

The following example hashes deterministic JSON bytes for a small synthetic NPV input. It records a supplied revision label and Python version. It does not capture a full environment, verify the revision, retain external data or guarantee replay on another machine.

## 7. Reference implementation

Save as reproducible_npv.py. All inputs are synthetic; this code and its tests are publication drafts.

~~~python
import hashlib
import json
import math
import platform
import unittest


def input_bytes(flows, rate):
    """Canonical UTF-8 JSON for nonempty finite built-in float inputs."""
    values = list(flows)
    if not values or any(type(x) is not float or not math.isfinite(x)
                         for x in values):
        raise ValueError("nonempty finite float cash flows required")
    if type(rate) is not float or not math.isfinite(rate) or rate <= -1:
        raise ValueError("finite float rate > -1 required")
    payload = {"cashflows": values, "rate": rate}
    return json.dumps(payload, sort_keys=True, separators=(",", ":"),
                      allow_nan=False).encode("utf-8")


def run(flows, rate, revision):
    """Return NPV and a minimal manifest; revision is an unverified label."""
    if not isinstance(revision, str) or not revision.strip():
        raise ValueError("nonempty revision required")
    values = list(flows)
    raw = input_bytes(values, rate)
    try:
        result = math.fsum(c * math.exp(-t * math.log1p(rate))
                           for t, c in enumerate(values))
    except OverflowError as exc:
        raise ValueError("calculation overflow") from exc
    if not math.isfinite(result):
        raise ValueError("nonfinite result")
    return {
        "npv": result,
        "manifest": {
            "input_sha256": hashlib.sha256(raw).hexdigest(),
            "revision": revision,
            "python": platform.python_version(),
            "model": "periodic-npv-v1",
            "convention": "first flow at time zero; effective rate per period",
        },
    }


class ReproducibilityTests(unittest.TestCase):
    def test_known_value(self):
        self.assertTrue(math.isclose(run([-100.0, 110.0], .1, "demo")["npv"],
                                     0.0, rel_tol=0, abs_tol=1e-10))
    def test_repeat_digest(self):
        self.assertEqual(input_bytes([1.0, 2.0], .1),
                         input_bytes([1.0, 2.0], .1))
    def test_digest_changes(self):
        a = run([1.0, 2.0], .1, "x")["manifest"]["input_sha256"]
        b = run([1.0, 3.0], .1, "x")["manifest"]["input_sha256"]
        self.assertNotEqual(a, b)
    def test_order_matters(self):
        self.assertNotEqual(input_bytes([1.0, 2.0], .1),
                            input_bytes([2.0, 1.0], .1))
    def test_zero_rate(self):
        self.assertEqual(run([1.0, 2.0], 0.0, "x")["npv"], 3.0)
    def test_negative_rate(self):
        self.assertTrue(math.isclose(run([0.0, 95.0], -.05, "x")["npv"],
                                     100.0, rel_tol=0, abs_tol=1e-10))
    def test_generator(self):
        self.assertEqual(run(iter([1.0, 2.0]), 0.0, "x")["npv"], 3.0)
    def test_empty_flows(self):
        with self.assertRaises(ValueError): run([], .1, "x")
    def test_invalid_rate(self):
        with self.assertRaises(ValueError): run([1.0], -1.0, "x")
    def test_nonfinite(self):
        with self.assertRaises(ValueError): run([float("nan")], .1, "x")
    def test_integer_rejected(self):
        with self.assertRaises(ValueError): run([1], .1, "x")
    def test_revision_required(self):
        with self.assertRaises(ValueError): run([1.0], .1, " ")


if __name__ == "__main__":
    print(run([-100.0, 110.0], .1, "synthetic-demo"))
    unittest.main(verbosity=2)
~~~

The input digest identifies this example's serialized bytes, not the complete run. Identical decimal values may have distinct representations, such as negative zero; the serialization is specific to this implementation and its environment, not a universal JSON canonicalization standard. The calculation uses floats, rejects integers and booleans, and does not model dates, currencies, fees or taxes. Underflow and cancellation remain possible.

## 8. Twelve-step hands-on lab

1. Define a synthetic periodic cash-flow scenario and its units.
2. Calculate an independent NPV benchmark.
3. Save the example and identify the code revision and local changes.
4. Record Python version and relevant platform details.
5. Record the period rate, time-zero convention and valuation date.
6. Serialize the inputs and retain the exact bytes.
7. Calculate and record their SHA-256 digest.
8. Run the calculation and preserve the actual output and command.
9. Replay with the same inputs and compare using a justified tolerance.
10. Change one flow and compare the input digest.
11. Identify missing dependencies, provenance, access controls and assumptions.
12. Run the tests during QA, preserve their actual output and record any discrepancies.

## 9. Forty worked exercises

1. **Replay:** What must accompany code? **Answer:** Inputs, configuration, environment and conventions.
2. **Revision:** Is a branch name enough? **Answer:** No; a commit identifies the revision more precisely.
3. **Dirty tree:** Why record uncommitted changes? **Answer:** The commit alone does not identify the executed code.
4. **Dependencies:** Why record versions? **Answer:** Changes may alter behavior or availability.
5. **Platform:** Why record architecture? **Answer:** Numerical behavior can depend on hardware and libraries.
6. **Input hash:** What does a SHA-256 digest identify? **Answer:** The exact bytes hashed, subject to collision assumptions.
7. **Hash:** Does a digest recover missing data? **Answer:** No.
8. **Data:** Why keep a snapshot? **Answer:** A source may change or be revised.
9. **Time:** Why record availability time? **Answer:** It helps prevent future information leaking into a historical analysis.
10. **Calendar:** Can a calendar revision change results? **Answer:** Yes, payment dates and schedules may change.
11. **Rate:** What does 0.05 mean here? **Answer:** A 5% effective rate per period.
12. **Cash flows:** When is the first flow? **Answer:** At time zero.
13. **NPV:** What is the exact NPV of −100 then 110 at 10%? **Answer:** Zero.
14. **Seed:** Does a seed prove a model is valid? **Answer:** No.
15. **Generator:** Why name the algorithm and version? **Answer:** A seed alone may not specify a stream across implementations.
16. **Parallel simulation:** Why allocate independent streams deliberately? **Answer:** Scheduling can change which worker consumes which draws.
17. **Rounding:** Why record the rounding policy? **Answer:** Different policies can change reported or settled amounts.
18. **Float:** Must replay be bitwise identical everywhere? **Answer:** No; use justified numerical tolerances where appropriate.
19. **Summation:** Can order matter? **Answer:** Yes, floating-point addition is not associative.
20. **Configuration:** Why include valuation date? **Answer:** It determines which data and assumptions apply.
21. **Currency:** Why include currency? **Answer:** A bare monetary value has ambiguous meaning.
22. **Tolerance:** Should one tolerance fit every quantity? **Answer:** No; units and scale matter.
23. **Secrets:** Should credentials be in a manifest? **Answer:** No; record a safe reference if needed.
24. **Privacy:** Can a hash be sensitive? **Answer:** Yes; low-entropy inputs can be guessed and checked.
25. **Snapshot:** Is an external URL a permanent snapshot? **Answer:** No; its content can change or disappear.
26. **Serialization:** Why define canonical bytes? **Answer:** Equivalent objects can otherwise serialize differently.
27. **NaN:** Why reject nonfinite JSON values in this example? **Answer:** They are unsuitable for the stated finite input contract.
28. **Hash change:** What if one input byte changes? **Answer:** The digest will normally change.
29. **Input order:** Does cash-flow order matter? **Answer:** Yes; it defines timing.
30. **Tests:** Does the presence of tests establish execution? **Answer:** No; preserve actual results separately.
31. **Logs:** Do logs replace input data? **Answer:** No; they may omit essential values and conventions.
32. **Model:** Does deterministic output prove correctness? **Answer:** No; a repeatable error remains an error.
33. **Version:** Does pinning packages guarantee future installation? **Answer:** No; artifacts and platform compatibility also matter.
34. **Lockfile:** Why retain package hashes? **Answer:** They help identify and verify downloaded artifacts.
35. **Output:** Why preserve an output digest? **Answer:** It helps compare exact output bytes.
36. **Revision history:** Can corrected market data alter an old result? **Answer:** Yes; retain the as-of dataset and revision.
37. **Dates:** Is a date a time zone? **Answer:** No; record the relevant time and zone when needed.
38. **Environment variable:** Can an unrecorded setting change a run? **Answer:** Yes, so capture relevant non-secret configuration.
39. **Replay failure:** What should be investigated first? **Answer:** Differences in code, data, configuration and environment.
40. **Independent review:** Does reproducibility replace model validation? **Answer:** No; the financial assumptions still need review.

## 10. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Input digest differs | Changed bytes or serialization | Compare snapshots and serialization rules |
| Same input, different NPV | Code, environment or configuration changed | Compare revision, runtime and numerical settings |
| Same seed, different simulation | Generator or draw order changed | Check implementation, versions and stream allocation |
| Historical backtest changes | Data revised | Restore the as-of snapshot and provenance |
| Identical outputs but wrong decision | Incorrect convention or model | Independently review financial assumptions |
| Test status unclear | Reference code confused with executed tests | Retain actual command and output |
