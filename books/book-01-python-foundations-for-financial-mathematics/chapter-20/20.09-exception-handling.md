## Learning objectives

Distinguish invalid inputs from numerical and external failures; raise and catch specific exceptions; preserve causal information; avoid misleading fallback values; test failure behavior; and report errors without exposing sensitive data.

## 1. Why exceptions matter

A calculation can fail because an input is invalid, a numerical range is exceeded, a required file is missing or a service is unavailable. Returning a plausible value such as zero for every failure can silently contaminate financial reports. Zero is a legitimate NPV, return or balance in many contexts.

Define the function's valid inputs, results and failure behavior. A caller can then decide whether to stop, quarantine an item or take a documented recovery action.

## 2. Validation versus exceptions

Validation checks a contract before or during calculation. An exception reports that an operation cannot proceed as specified. For annual effective discounting, r>−1 is required; r=−.05 is valid but r=−1 is not.

Use explicit checks for external input. Python may remove `assert` statements under optimization, so assertions must not be the sole production validation.

## 3. Catch specific failures

Catch the exceptions that a boundary can meaningfully handle. For example, translate an `OverflowError` from an exponential calculation into a documented domain-specific numerical error. Avoid broad `except Exception` blocks that hide programming defects or return a default.

When translating an exception, `raise NewError(...) from exc` preserves the cause for debugging. At a user-facing boundary, choose what details can be shown or logged without exposing credentials, account data or confidential inputs.

## 4. Error categories

A small library may distinguish:

- Invalid input: wrong type, missing value or domain violation.
- Numerical failure: overflow or nonfinite output.
- External failure: unavailable file or service.
- Business or model failure: unsupported convention or inconsistent state.

Categories and recovery must be documented. A transient network failure may justify a bounded retry under an appropriate policy; invalid data normally requires correction, not repeated identical retries.

## 5. Retry and idempotence

Retry only operations for which repetition is safe and permitted. A timeout does not prove a remote write failed; it may have succeeded before the response was lost. Define idempotency keys, transaction boundaries and reconciliation where applicable.

For a read, use explicit timeouts and bounded backoff under the provider's policy. This section's reference code makes no network calls and implements no retry behavior.

## 6. Fail-fast and quarantine

A batch can fail entirely or quarantine invalid records, depending on the contract. A partial batch must not be reported as complete. Preserve counts and error categories with appropriate access controls and avoid indiscriminate logging of raw financial data.

An exception message should identify the problem category without embedding secrets. Operational logs need their own retention and redaction policies.

## 7. Numerical examples

A simplified periodic NPV is ΣCₜ/(1+r)ᵗ for r>−1. For [−100,110] at .10, NPV is zero in exact arithmetic and is a valid result. An empty list, NaN or r=−1 is invalid under this example's contract.

A valid mathematical input can still exceed floating-point range. A numerical exception is not the same as invalid financial data, and a test should distinguish them where the interface promises that distinction.

## 8. Reference implementation

Save as `financial_exceptions.py`. It defines specific exception types and a simplified NPV function. It contains no external service or database operations.

~~~python
import math
import unittest

class FinancialInputError(ValueError):
    """Input violates the documented calculation contract."""

class FinancialNumericalError(ArithmeticError):
    """A numerical calculation cannot produce a finite result."""

def finite_number(value):
    return type(value) in (int,float) and math.isfinite(value)

def npv(cashflows,rate):
    if cashflows is None:
        raise FinancialInputError("cash flows required")
    try:
        flows=list(cashflows)
    except TypeError as exc:
        raise FinancialInputError("cash flows must be iterable") from exc
    if not flows or not all(finite_number(c) for c in flows):
        raise FinancialInputError("nonempty finite numeric cash flows required")
    if not finite_number(rate) or rate<=-1:
        raise FinancialInputError("finite rate greater than -1 required")
    try:
        result=math.fsum(c*math.exp(-t*math.log1p(rate))
                         for t,c in enumerate(flows))
    except OverflowError as exc:
        raise FinancialNumericalError("discount calculation overflow") from exc
    if not math.isfinite(result):
        raise FinancialNumericalError("nonfinite NPV")
    return result

class ExceptionTests(unittest.TestCase):
    def test_valid_zero_npv(self):
        self.assertTrue(math.isclose(npv([-100,110],.1),0,rel_tol=0,abs_tol=1e-10))
    def test_valid_negative_rate(self):
        self.assertTrue(math.isclose(npv([0,95],-.05),100,rel_tol=0,abs_tol=1e-10))
    def test_invalid_rate(self):
        with self.assertRaises(FinancialInputError): npv([100],-1)
    def test_empty(self):
        with self.assertRaises(FinancialInputError): npv([],.05)
    def test_missing(self):
        with self.assertRaises(FinancialInputError): npv(None,.05)
    def test_noniterable_cause(self):
        with self.assertRaises(FinancialInputError) as caught: npv(100,.05)
        self.assertIsInstance(caught.exception.__cause__,TypeError)
    def test_nan(self):
        with self.assertRaises(FinancialInputError): npv([float("nan")],.05)
    def test_infinity(self):
        with self.assertRaises(FinancialInputError): npv([100],float("inf"))
    def test_boolean(self):
        with self.assertRaises(FinancialInputError): npv([True],.05)
    def test_wrong_type(self):
        with self.assertRaises(FinancialInputError): npv(["100"],.05)
    def test_overflow(self):
        with self.assertRaises(FinancialNumericalError) as caught:
            npv([0]*1000+[1],-.9)
        self.assertIsInstance(caught.exception.__cause__,OverflowError)
    def test_negative_cashflow(self):
        self.assertTrue(math.isclose(npv([0,-110],.1),-100,rel_tol=0,abs_tol=1e-10))
    def test_zero_rate(self):
        self.assertEqual(npv([0,100],0),100)
    def test_error_category(self):
        self.assertTrue(issubclass(FinancialInputError,ValueError))

if __name__ == "__main__":
    unittest.main(verbosity=2)
~~~

The example uses binary floats and positional cash flows. It catches exponential overflow but does not promise detection of all underflow, cancellation, memory exhaustion or exceptional iterator behavior. It omits currencies, dates, external operations and production logging.

## 11. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Invalid input yields zero | Error swallowed or fallback used | Review validation and exception policy |
| Numerical error reported as input error | Categories conflated | Inspect cause and contract |
| Repeated writes after timeout | Unsafe retry | Reconcile remote state and idempotency policy |
| Sensitive data in traceback | Raw input included in message | Redact and review logging boundaries |
| Partial batch appears complete | Failure not surfaced | Report counts and batch status |
| Test expects wrong exception | Contract and implementation differ | Review both before changing the test |
