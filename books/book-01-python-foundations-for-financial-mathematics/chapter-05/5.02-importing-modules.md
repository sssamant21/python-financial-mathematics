## 5.2.1 Purpose

Import statements connect a caller to definitions owned by another module. The spelling controls which names appear in the caller; it does not copy a financial implementation or validate its assumptions.

This section compares qualified imports, aliases, and explicit from-imports. The lab demonstrates their bindings in fresh interpreters and uses all three styles against the same validated quantity function. It also distinguishes missing modules, missing imported names, and missing attributes.

## 5.2.2 Learning Objectives

You should be able to:

1. State which local name each import form binds.
2. Use aliases to resolve naming collisions clearly.
3. Explain why from-import is not a live attribute link.
4. Distinguish name rebinding from mutation of a shared object.
5. Diagnose import failures without masking dependency errors.
6. Inspect the actual source file used by a local import.
7. Test equivalent financial behavior across import forms.

## 5.2.3 Import Forms and Call Sites

| Statement | Name bound in caller | Example use |
|---|---|---|
| import quantity_rules | quantity_rules | quantity_rules.checked_quantity(value) |
| import quantity_rules as qr | qr | qr.checked_quantity(value) |
| from quantity_rules import checked_quantity | checked_quantity | checked_quantity(value) |
| from quantity_rules import checked_quantity as validate_units | validate_units | validate_units(value) |

These forms initialize or locate the same named module through the import system. A from-import binds the requested attribute in the caller; it does not bind quantity_rules there as an additional convenience. Ordinary aliases do not create independent module copies.

Qualified names make ownership visible in longer financial programs. Explicit from-imports can be convenient for a small, clear API. Choose a readable convention and avoid reusing an imported function's name for an unrelated variable.

The table is a syntax guide. The complete files below are the runnable examples.

## 5.2.4 Rebinding Is Not a Live Link

Suppose a caller binds a module attribute using from-import. Later assigning a new object to that module attribute does not automatically rebind the caller's existing name. Conversely, a qualified lookup obtains the attribute currently stored on the module.

If both names refer to one mutable object, mutating that object may be visible through both references. Importing a list does not copy it. This is the same ownership principle developed in Chapter 4, now applied to module attributes.

The tests demonstrate these rules using a harmless string label and list inside a disposable child process. They do not modify financial validation functions or retain modified module state between tests.

## 5.2.5 Avoid Wildcard Imports in Application Code

A wildcard import makes the origins and possible collisions of names harder to inspect. Its selected names are governed by __all__ when defined, or the module's public-name convention otherwise. It is not a mechanism for importing every dependency safely, and __all__ is not access control.

This lab uses only explicit imports. It does not rely on __all__. A leading underscore may indicate an internal helper, but Python does not enforce that convention as a privacy boundary.

## 5.2.6 Imports Execute Initialization

Normal imports reuse a cached module for the same name in an interpreter. The first initialization can execute arbitrary top-level statements, including imports of dependencies. A name imported with from-import does not bypass initialization.

Keep required dependencies visible near the top of a module. Moving an import into a function can defer it, but it does not repair a circular design or install a dependency. Circular imports may expose a partially initialized module before the requested name exists. Move shared low-level logic to a separate module when that resolves the dependency relationship; do not broadly suppress the error.

Packages and relative imports are developed in Section 5.5. The current lab uses three sibling source files and absolute module names.

## 5.2.7 Recognize the Failure Boundary

| Operation | Typical failure | Meaning to investigate |
|---|---|---|
| import missing_name | ModuleNotFoundError | Requested module or one of its dependencies cannot be found |
| from existing_module import missing_name | ImportError | Requested name cannot be imported in this case |
| existing_module.missing_name | AttributeError | Module object lacks the requested attribute |
| Imported module initializes | Other exceptions possible | Top-level module or dependency code failed |

ModuleNotFoundError is a subclass of ImportError. Catching ImportError broadly can therefore hide a missing transitive dependency or a broken module. Inspect the exception and traceback before deciding whether a dependency is optional. Do not replace an import failure with zero prices or an empty portfolio.

The lab deliberately exercises predictable missing-name cases using existing modules. It does not assume every ImportError has the same cause.

## 5.2.9 File 1 — Quantity Policy

Save as quantity_rules.py:

```python
"""Shared teaching policy for nonnegative instrument units."""

from decimal import Decimal

POLICY_LABEL = "nonnegative-units-v1"


def checked_quantity(value: object) -> Decimal:
    """Accept an exact finite nonnegative Decimal; perform no arithmetic."""
    if type(value) is not Decimal:
        raise TypeError("quantity must be an exact Decimal")
    if not value.is_finite() or value < 0:
        raise ValueError("quantity must be finite and nonnegative")
    return value
```

The label documents this teaching policy; it is not a dependency lock, code digest, or proof that two installations contain identical source. Numeric conventions and version reproducibility require more than a module attribute.

## 5.2.10 File 2 — Explicit Import Styles

Save as import_styles.py:

```python
"""Compare explicit import bindings without copying implementation code."""

from decimal import Decimal
import quantity_rules
import quantity_rules as qr
from quantity_rules import checked_quantity as validate_units


def validate_three_ways(value: object) -> tuple[Decimal, Decimal, Decimal]:
    """Call the same quantity policy via three names."""
    return (
        quantity_rules.checked_quantity(value),
        qr.checked_quantity(value),
        validate_units(value),
    )


def main() -> int:
    values = validate_three_ways(Decimal("12.5"))
    print("Validated units: " + ", ".join(str(value) for value in values))
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

The module alias qr and quantity_rules refer to the same module. validate_units refers to the imported function object at the time the from-import executes. The sample runner prints `Validated units: 12.5, 12.5, 12.5`.

The tuple expressions are evaluated in order. If validation raises on the first call, later calls are not reached. That is ordinary exception behavior, not evidence that a particular import form accepts different inputs.

## 5.2.11 File 3 — Binding and Behavior Tests

Save as test_import_styles.py:

```python
"""Test import bindings in fresh processes and the shared quantity contract."""

from decimal import Decimal
from pathlib import Path
import subprocess
import sys
import unittest

import import_styles
import quantity_rules
import quantity_rules as qr
from quantity_rules import checked_quantity as validate_units

LAB_DIR = Path(__file__).resolve().parent


def launch(*arguments: str) -> subprocess.CompletedProcess[str]:
    return subprocess.run(
        [sys.executable, *arguments], cwd=LAB_DIR, text=True,
        capture_output=True, check=False, timeout=10,
    )


class ImportTests(unittest.TestCase):
    def check_child(self, code: str, expected_output: str = "") -> None:
        result = launch("-c", code)
        self.assertEqual(result.returncode, 0, result.stderr)
        self.assertEqual(result.stdout, expected_output)
        self.assertEqual(result.stderr, "")

    def test_valid_quantities(self) -> None:
        for value in (Decimal("0"), Decimal("12.5")):
            with self.subTest(value=value):
                self.assertEqual(import_styles.validate_three_ways(value), (value, value, value))

    def test_invalid_quantities_for_every_binding(self) -> None:
        validators = (
            quantity_rules.checked_quantity,
            qr.checked_quantity,
            validate_units,
        )
        for validator in validators:
            for value in (None, True, 1, 1.5, "1"):
                with self.subTest(validator=validator, value=value):
                    with self.assertRaises(TypeError):
                        validator(value)
            for value in ("NaN", "sNaN", "Infinity", "-Infinity", "-1"):
                with self.assertRaises(ValueError):
                    validator(Decimal(value))

    def test_aliases_share_module_and_function(self) -> None:
        self.check_child(
            "import import_styles, quantity_rules\n"
            "assert import_styles.quantity_rules is import_styles.qr\n"
            "assert import_styles.validate_units is quantity_rules.checked_quantity\n"
        )

    def test_from_import_binds_only_requested_name(self) -> None:
        self.check_child(
            "from quantity_rules import checked_quantity as validate_units\n"
            "assert 'quantity_rules' not in globals()\n"
            "assert callable(validate_units)\n"
        )

    def test_rebinding_does_not_update_imported_name(self) -> None:
        self.check_child(
            "import quantity_rules as qr\n"
            "from quantity_rules import POLICY_LABEL as original_label\n"
            "qr.POLICY_LABEL = 'temporary-label'\n"
            "assert original_label == 'nonnegative-units-v1'\n"
            "assert qr.POLICY_LABEL == 'temporary-label'\n"
        )
        self.assertEqual(quantity_rules.POLICY_LABEL, "nonnegative-units-v1")

    def test_mutable_import_is_not_a_copy(self) -> None:
        self.check_child(
            "import quantity_rules as qr\n"
            "qr.demo_rows = []\n"
            "from quantity_rules import demo_rows\n"
            "demo_rows.append('A')\n"
            "assert qr.demo_rows == ['A']\n"
            "qr.demo_rows = []\n"
            "assert demo_rows == ['A']\n"
        )
        self.assertFalse(hasattr(quantity_rules, "demo_rows"))

    def test_import_error_and_attribute_error(self) -> None:
        with self.assertRaises(ImportError):
            exec("from quantity_rules import name_not_present_in_this_lab", {})
        with self.assertRaises(AttributeError):
            getattr(quantity_rules, "name_not_present_in_this_lab")
        # A missing top-level module name is checked in a disposable empty path.
        self.check_child(
            "import importlib, sys\n"
            "sys.path[:] = []\n"
            "try:\n"
            "    importlib.import_module('missing_lab_quantity_dependency_52')\n"
            "except ModuleNotFoundError as exc:\n"
            "    assert exc.name == 'missing_lab_quantity_dependency_52'\n"
            "else:\n"
            "    raise AssertionError('missing module unexpectedly imported')\n"
        )

    def test_quiet_import_and_origin(self) -> None:
        self.check_child(
            "import import_styles, quantity_rules\n"
            "from pathlib import Path\n"
            "assert Path(quantity_rules.__file__).resolve() == Path('quantity_rules.py').resolve()\n"
        )

    def test_runner(self) -> None:
        for args in (("import_styles.py",), ("-m", "import_styles")):
            with self.subTest(args=args):
                result = launch(*args)
                self.assertEqual(result.returncode, 0, result.stderr)
                self.assertEqual(result.stdout, "Validated units: 12.5, 12.5, 12.5\n")
                self.assertEqual(result.stderr, "")


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

Only the disposable missing-module test empties its own import path to isolate the deliberate failure. This is a test fixture, not an application configuration technique. Other tests use the normal sibling-file layout.

The subprocess strings deliberately contain dynamic namespace experiments. Static checking of the surrounding test file does not type-check those strings. The tests execute them in fresh processes and verify both successful exit and captured output.

## 5.2.13 Diagnosing Real Import Problems

Confirm the intended interpreter, file names, and launch directory first. A package installed for one interpreter may not be available in another; package installation and environments are covered later in this chapter.

Inspect a source module's __file__ attribute where available to detect local shadowing. Some modules do not have source-file locations, so do not assume __file__ exists universally. Restart long-running interpreters after renaming conflicting files or changing source.

Keep the original traceback. If importing your module fails while it imports a dependency, correcting the top-level module name alone will not resolve the nested failure. Do not create fake replacement modules or silently switch implementations to hide that condition.

## 5.2.15 Key Takeaways

Import spelling determines local bindings and affects how clearly call sites reveal their dependencies. Aliases and explicit imports share existing objects; they do not create isolated financial implementations.

Keep ownership, module initialization, and exception behavior explicit. Use fresh processes to verify import behavior without relying on stale interpreter state.
