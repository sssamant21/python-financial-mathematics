# 1.11 — Numerical Precision, Rounding, and Tolerances

**Workflow Stage:** Revised Final / Canonical Edition  
**Status:** Canonical — Complete

Numerical calculations are fundamental to financial programming. Interest calculations, portfolio returns, loan balances, fees, exchange rates, prices, accounting reports, and reconciliation processes all depend on numbers being represented and manipulated correctly.

A calculation can be mathematically correct yet still produce an unexpected result in software because computers do not represent every decimal value exactly. Reliable financial programs therefore need an explicit numerical policy covering representation, calculation precision, rounding policy, rounding stage, comparison tolerance, validation, and testing.

The appropriate policy depends on the calculation. Python's `float`, `int`, and `Decimal` types solve different problems, and none should be treated as universally correct for every financial workload.

---

## 1.11.1 Why Numerical Precision Matters

Consider:

```python
price = 19.99
quantity = 3
total = price * quantity
print(total)
```

The mathematical result is `59.97`, and Python normally displays the same value. However, the underlying `float` does not necessarily contain the exact decimal number `59.97`.

The reason becomes clearer with the classic example:

```python
print(0.1 + 0.2)
```

Output:

```text
0.30000000000000004
```

This is not a Python arithmetic defect. Python's `float` uses binary floating-point arithmetic. On almost all modern platforms, it is implemented using IEEE 754 binary64 double precision, providing 53 bits of binary precision. Many decimal fractions, including `0.1`, cannot be represented as finite binary fractions, so the computer stores a nearby representable binary value.

For many analytical calculations, these differences are insignificant. For calculations governed by decimal financial rules, however, the numerical representation itself can be part of the business requirement.

## 1.11.2 Binary Floating-Point Arithmetic

Values such as `0.05`, `0.1`, and `0.01` generally cannot be represented exactly as finite binary fractions. Repeated calculations can expose these approximations:

```python
value = 0.0
for _ in range(10):
    value += 0.1
print(value)
```

A typical result is:

```text
0.9999999999999999
```

Mathematically, `10 × 0.1 = 1`. The difference comes from repeated binary floating-point operations and their associated rounding.

This does **not** mean that `float` is unsuitable for financial work. It means that developers must understand when approximate binary arithmetic is appropriate and when decimal semantics are required.

## 1.11.3 Exact Equality and Approximate Equality

```python
result = 0.1 + 0.2
print(result == 0.3)
```

Output:

```text
False
```

Direct equality is not inherently wrong for floating-point values. It is appropriate when exact representation equality is actually the requirement. The problem arises when independently calculated floating-point values are expected to be mathematically close rather than bit-for-bit equal.

Python provides `math.isclose()` for approximate numerical equality:

```python
import math
actual = 0.1 + 0.2
expected = 0.3
print(math.isclose(actual, expected))
```

Output:

```text
True
```

## 1.11.4 Relative and Absolute Tolerances

`math.isclose()` supports relative and absolute tolerance:

```python
math.isclose(a, b, rel_tol=1e-9, abs_tol=0.0)
```

Conceptually, Python evaluates:

```text
abs(a - b) <= max(rel_tol × max(abs(a), abs(b)), abs_tol)
```

A relative tolerance scales according to the magnitude of the numbers. An absolute tolerance defines a fixed maximum difference and becomes particularly important when comparing against zero.

Tolerance values must reflect the purpose of the calculation. They should never be chosen simply to make a failing test pass.

## 1.11.5 Numerical Tolerance vs. Reconciliation Tolerance

**Numerical tolerance** addresses acceptable approximation arising from numerical computation.

**Reconciliation tolerance** defines an operationally acceptable difference between financial records, balances, systems, or reports.

```python
from decimal import Decimal

system_a = Decimal("1250000.00")
system_b = Decimal("1250000.01")
RECONCILIATION_TOLERANCE = Decimal("0.01")

difference = abs(system_a - system_b)

if difference <= RECONCILIATION_TOLERANCE:
    print("Within reconciliation tolerance")
else:
    print("Reconciliation exception")
```

The `$0.01` value is illustrative. A real tolerance must come from the applicable accounting, contractual, operational, or control requirement. It should never be invented merely to suppress discrepancies.

## 1.11.6 Precision, Scale, Rounding, and Formatting

These concepts are related but distinct.

| Concept | Meaning |
|---|---|
| Precision | Amount of numerical information represented |
| Scale | Number of digits to the right of the decimal point in a decimal representation |
| Rounding | Changing a numerical value according to a defined rule |
| Formatting | Controlling how a value is presented |

```python
amount = 123.456789
print(f"${amount:.2f}")
```

Output:

```text
$123.46
```

The underlying variable has not been changed. Formatting is a presentation operation and should not be confused with the application's numerical rounding policy.

## 1.11.7 Python's `round()`

```python
amount = 123.4567
rounded_amount = round(amount, 2)
print(rounded_amount)
```

Output:

```text
123.46
```

For exact halfway cases, Python uses nearest-value rounding with ties going toward the even choice:

```python
print(round(2.5))
print(round(3.5))
```

Output:

```text
2
4
```

This behavior is commonly called **round half to even** or **banker's rounding**.

However, the binary representation of a `float` can affect whether a value is actually an exact halfway case:

```python
print(round(2.675, 2))
```

Output:

```text
2.67
```

The binary floating-point value represented by the literal `2.675` is not exactly the mathematical decimal value `2.675`. Ties-to-even defines what happens when the numerical value is exactly halfway between two choices; a decimal literal ending in `5` is not necessarily an exact halfway value after conversion to binary floating point.

## 1.11.8 Rounding Is Part of the Business Rule

Financial systems may define explicit rounding requirements for prices, fees, taxes, interest, exchange rates, invoices, security quantities, accounting balances, and regulatory reports.

> **Production Rule:** Rounding policy is part of the calculation specification, not merely output formatting.

The implementation should follow the sequence: business requirement → numerical representation → explicit rounding policy → implementation → automated tests.

## 1.11.9 Decimal Arithmetic

Python provides the `decimal` module when decimal arithmetic and explicit decimal rounding behavior are required.

```python
from decimal import Decimal

price = Decimal("19.99")
quantity = Decimal("3")
total = price * quantity
print(total)
```

Output:

```text
59.97
```

This representation is useful when the calculation must follow decimal semantics. It does not mean that every financial calculation should automatically use `Decimal`; analytical calculations, statistical models, simulations, and many numerical algorithms may appropriately use `float`.

## 1.11.10 Constructing `Decimal` Values Correctly

```python
from decimal import Decimal

exact_decimal = Decimal("0.1")
from_float = Decimal(0.1)

print(exact_decimal)
print(from_float)
```

The first represents the intended decimal value `0.1`. The second represents the exact decimal value corresponding to the already-created binary floating-point number and therefore exposes its binary approximation.

`Decimal(float_value)` is not inherently erroneous. It faithfully converts the float it receives. The issue is the source.

> **Rule:** When an input is intended to represent an exact decimal literal, construct `Decimal` from an exact source such as a string rather than first converting that value through `float`.

Prefer `Decimal("19.99")` over `Decimal(19.99)` when the intended source value is exactly decimal `19.99`.

## 1.11.11 `float` vs. `Decimal`

```python
float_result = 0.1 + 0.2
print(float_result)
```

Output:

```text
0.30000000000000004
```

With decimal arithmetic:

```python
from decimal import Decimal

decimal_result = Decimal("0.1") + Decimal("0.2")
print(decimal_result)
```

Output:

```text
0.3
```

The question is not whether finance should always use `Decimal`. The better question is: **What numerical semantics does this calculation require?**

## 1.11.12 Quantizing Decimal Values

`Decimal.quantize()` can enforce a particular decimal exponent and rounding behavior.

```python
from decimal import Decimal

amount = Decimal("123.4567")
rounded = amount.quantize(Decimal("0.01"))
print(rounded)
```

Output:

```text
123.46
```

For monetary code, policy constants can make the intended scale visible:

```python
USD_CENT = Decimal("0.01")
```

Do not assume that `Decimal("0.01")` is universally correct for every currency, security, price, exchange rate, or financial instrument.

## 1.11.13 Explicit Decimal Rounding Modes

```python
from decimal import Decimal, ROUND_HALF_UP

CENT = Decimal("0.01")
amount = Decimal("10.125")
rounded = amount.quantize(CENT, rounding=ROUND_HALF_UP)
print(rounded)
```

Output:

```text
10.13
```

`ROUND_HALF_UP` means rounding to the nearest value with exact ties rounded **away from zero**.

```python
from decimal import Decimal, ROUND_HALF_UP

QUANTUM = Decimal("0.1")
print(Decimal("1.25").quantize(QUANTUM, rounding=ROUND_HALF_UP))
print(Decimal("-1.25").quantize(QUANTUM, rounding=ROUND_HALF_UP))
```

Output:

```text
1.3
-1.3
```

> **Do not select a rounding mode merely because its name sounds financially appropriate.**

Banking, taxation, accounting, trading, pricing, and regulatory systems can specify different rounding policies. The required policy must come from the applicable business or regulatory specification.

## 1.11.14 Avoid Unnecessary Mixing of `float` and `Decimal`

Avoid mixing representations inside the same decimal calculation without a deliberate conversion policy.

```python
from decimal import Decimal

price = Decimal("10.25")
rate = Decimal("0.05")
fee = price * rate
print(fee)
```

Output:

```text
0.5125
```

The application can then apply its required rounding policy explicitly.

## 1.11.15 Integer Minor Units

Some financial systems represent monetary amounts using integer minor units:

```python
price_minor_units = 1999
quantity = 3
total_minor_units = price_minor_units * quantity
print(total_minor_units)
```

Output:

```text
5997
```

Integer arithmetic avoids fractional binary representation issues. However, not every currency or financial instrument uses the same scale, and some calculations require precision beyond the currency's settlement minor unit. Use integer minor units only when they correctly model the domain.

## 1.11.16 Percentages and Rates

```python
initial = 10_000
final = 10_500
return_rate = (final - initial) / initial
print(return_rate)
```

Output:

```text
0.05
```

Formatting controls presentation:

```python
print(f"{return_rate:.2%}")
```

Output:

```text
5.00%
```

The calculated value and displayed value are different concerns.

## 1.11.17 Basis Points

A **basis point** is one hundredth of a percentage point:

```text
1 basis point = 0.01 percentage point
100 basis points = 1 percentage point
```

A move from `4.25%` to `4.50%` is an increase of 25 basis points.

```python
old_rate = 0.0425
new_rate = 0.0450
basis_point_change = (new_rate - old_rate) * 10_000
print(basis_point_change)
```

Floating-point representation may produce a value extremely close to `25` rather than an exact integer representation. Production code should apply the numerical policy appropriate to the calculation before converting such a result into an exact business quantity.

## 1.11.18 Accumulated Floating-Point Effects

Small representation differences can become visible when many operations are performed:

```python
total = 0.0
for _ in range(1_000_000):
    total += 0.01
print(total)
```

When decimal semantics are required:

```python
from decimal import Decimal

total = Decimal("0.00")
increment = Decimal("0.01")

for _ in range(1_000_000):
    total += increment

print(total)
```

Output:

```text
10000.00
```

This distinction can matter in systems processing large volumes of transactions, trades, payments, fees, invoices, accruals, and pricing calculations.

## 1.11.19 More Accurate Floating-Point Summation

Switching to `Decimal` is not the only response to floating-point summation issues. When binary floating point is appropriate but more accurate summation is desired, Python provides `math.fsum()`.

```python
import math

values = [0.1] * 10
total = math.fsum(values)
print(total)
```

`math.fsum()` is designed to reduce loss of precision when adding floating-point values. It improves floating-point summation; it does not change the underlying numerical model from binary floating point to decimal arithmetic.

## 1.11.20 Rounding at the Correct Stage

Consider three values:

```text
10.125
10.125
10.125
```

If each is rounded to `10.13` before aggregation, the result is `30.39`. If the exact values are aggregated first, the total is `30.375`, which under the same example policy can round to `30.38`.

Neither approach is universally correct.

> **Production Rule:** The correct rounding stage must come from the business, accounting, contractual, or regulatory rule governing the calculation.

The required stage may be per transaction, per invoice line, per account, per security, per day, per reporting period, or after aggregation.

## 1.11.21 Dangerous Numerical Patterns

Avoid direct equality when approximate equality is intended. Avoid creating intended exact decimal inputs through `float`. Avoid arbitrary repeated rounding merely to "fix precision." Do not treat formatting as calculation policy. Do not assume all money has two decimal places. Do not use tolerance to hide missing or duplicate transactions, incorrect exchange rates, incorrect rounding stages, calculation defects, data corruption, or incorrect source data.

A tolerance is a control—not a substitute for root-cause analysis.

## 1.11.22 Production Calculation Pattern

A production-oriented numerical function should make its policy visible and testable:

```python
from decimal import Decimal, ROUND_HALF_UP

MONEY_QUANTUM = Decimal("0.01")
ROUNDING_MODE = ROUND_HALF_UP


def calculate_fee(amount: Decimal, rate: Decimal) -> Decimal:
    fee = amount * rate
    return fee.quantize(MONEY_QUANTUM, rounding=ROUNDING_MODE)


transaction_amount = Decimal("1250.75")
fee_rate = Decimal("0.0125")
fee = calculate_fee(transaction_amount, fee_rate)
print(fee)
```

The important design characteristic is not the particular constants used in this example. It is that representation, precision, rounding scale, and rounding mode are explicit rather than hidden inside unrelated calculation logic.

## 1.11.23 Testing Numerical Calculations

Financial calculations require deliberate boundary testing.

```python
from decimal import Decimal

assert Decimal("0.10") + Decimal("0.20") == Decimal("0.30")
```

Rounding behavior should also be tested:

```python
from decimal import Decimal, ROUND_HALF_UP

CENT = Decimal("0.01")
assert Decimal("1.125").quantize(CENT, rounding=ROUND_HALF_UP) == Decimal("1.13")
```

Important test categories include zero values, negative values, very large and very small values, exact midpoint cases, values immediately below and above rounding boundaries, large transaction counts, percentage and rate conversions, currency conversion, reconciliation thresholds, and rounding-stage behavior.

Numerical policy should become an executable business invariant.

## 1.11.24 Practical Example — Loan Interest

```python
from decimal import Decimal, ROUND_HALF_UP

principal = Decimal("10000.00")
annual_rate = Decimal("0.0525")
periods_per_year = Decimal("12")

monthly_interest = principal * annual_rate / periods_per_year
monthly_interest = monthly_interest.quantize(
    Decimal("0.01"),
    rounding=ROUND_HALF_UP,
)

print(monthly_interest)
```

Output:

```text
43.75
```

This is an illustration of Python numerical mechanics, **not a universal loan-interest formula**. Production loan calculations may depend on day-count conventions, compounding rules, calendars, payment timing, contractual provisions, and regulatory requirements.

## 1.11.25 Practical Example — Portfolio Return Validation

Binary floating point remains appropriate for many analytical calculations:

```python
import math

expected_return = 0.075
calculated_return = 0.07499999999999998

if math.isclose(calculated_return, expected_return, rel_tol=1e-9):
    print("Return calculation validated")
```

A statistical portfolio model and an accounting ledger do not necessarily require the same numerical strategy.

## 1.11.26 Choosing the Right Numerical Strategy

| Requirement | Typical Python approach |
|---|---|
| General numerical calculations | `float` |
| Scientific/statistical computation | `float` or specialized numerical libraries |
| Approximate float comparison | `math.isclose()` |
| Improved float summation | `math.fsum()` |
| Exact integer quantities | `int` |
| Decimal financial calculations | `Decimal` |
| Explicit decimal rounding | `Decimal.quantize()` |
| Minor-unit monetary model | `int`, when appropriate |
| Display formatting | format specification / f-strings |
| Financial reconciliation | domain-defined tolerance |

The choice should follow the semantics of the calculation rather than a blanket rule based solely on the fact that the application deals with finance.

## 1.11.27 Engineering Guidelines

For reliable numerical financial programs:

1. Understand the numerical domain before selecting a representation.
2. Do not assume decimal fractions are represented exactly by `float`.
3. Distinguish exact equality from approximate numerical equality.
4. Use `math.isclose()` with justified tolerances when approximate float comparison is intended.
5. Distinguish numerical tolerances from business reconciliation tolerances.
6. Use `Decimal` when decimal semantics and explicit decimal rounding are required.
7. Construct intended exact decimal literals from exact sources such as strings.
8. Keep numerical representations consistent within a calculation unless conversion is deliberate.
9. Make rounding modes explicit.
10. Define the stage at which rounding occurs.
11. Separate calculation policy from display formatting.
12. Centralize important precision, scale, and rounding policies.
13. Do not assume every currency or financial instrument uses two decimal places.
14. Use integer minor units only when they correctly represent the domain.
15. Consider `math.fsum()` when binary floating point is appropriate but summation accuracy matters.
16. Test midpoint and boundary behavior explicitly.
17. Test rounding-stage requirements.
18. Treat reconciliation tolerances as business controls.
19. Never use rounding or tolerance merely to conceal numerical defects.
20. Derive financial numerical policies from authoritative business, contractual, accounting, or regulatory requirements.

## 1.11.28 Key Takeaways

Reliable numerical programming requires more than applying arithmetic operators.

Python's `float` provides efficient binary floating-point arithmetic, but many decimal fractions cannot be represented exactly. Approximate calculations therefore sometimes require tolerance-based comparison rather than exact equality.

`Decimal` provides decimal arithmetic and explicit control over rounding behavior, making it appropriate when calculations require decimal semantics. `int` can be effective for exact quantities and carefully modeled monetary minor units. Formatting controls presentation and should not be confused with numerical policy.

Most importantly, reliable numerical behavior requires correct representation, calculation semantics, explicit rounding policy, the correct rounding stage, appropriate tolerance, and boundary testing. Financial software should make these decisions explicit, reviewable, and testable.
