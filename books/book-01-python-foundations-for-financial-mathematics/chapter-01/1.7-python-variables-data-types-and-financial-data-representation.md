## 1.7.1 Why Data Representation Matters in Finance

Financial quantities require more than a number. A robust conceptual model is:

**Financial Quantity = Value + Representation + Unit + Meaning**

For example:

```python
principal = 10_000
interest_rate = 0.0525
periods = 10
```

The Python types and financial meanings are related but not identical.

## 1.7.2 Variables and Names

Python names can be rebound to different objects. Financial programs should nevertheless keep names semantically consistent and descriptive.

```python
annual_effective_rate = 0.05
investment_years = 10
```

Descriptive computational names can coexist with concise mathematical notation such as `P`, `r`, and `n` in derivations.

## 1.7.3 Core Numeric Types

Python provides built-in numeric types including `int`, `float`, and `complex`; `bool` is a subtype of `int`. The standard library also provides `decimal.Decimal` and `fractions.Fraction` for specialized numerical requirements.

For early financial work we focus primarily on `int`, `float`, and `Decimal`.

## 1.7.4 Integers

Integers are useful for whole-number quantities such as period counts, simulation counts, and integer security quantities. Python integers have arbitrary precision subject to available memory.

A digit-based identifier should not automatically be represented as an integer. For example:

```python
account_id = "001234567"
```

preserves leading zeros and correctly signals that arithmetic is not the identifier's purpose.

## 1.7.5 Floating-Point Numbers

Rates, model prices, weights, volatilities, and other fractional quantities are often represented using `float`:

```python
interest_rate = 0.0525
volatility = 0.18
portfolio_weight = 0.35
```

Python `float` uses binary floating-point representation. Most decimal fractions cannot be represented exactly as finite binary fractions.

## 1.7.6 Representation Error

The classic example is:

```python
print(0.1 + 0.2)
```

which commonly displays `0.30000000000000004`. Likewise, `0.1 + 0.1 + 0.1 == 0.3` evaluates to `False`.

The issue is representation, not a failure of arithmetic: decimal `0.1` has no exact finite binary floating-point representation.

## 1.7.7 `float` Is Not Inherently Wrong for Finance

Binary floating point is fundamental to scientific and numerical computing. Statistical estimation, Monte Carlo simulation, matrix operations, optimization, and many quantitative models naturally use floating-point arithmetic.

The correct rule is to choose representation from requirements rather than declaring either `float` or `Decimal` universally correct.

## 1.7.8 Decimal Arithmetic

Python's `decimal.Decimal` supports decimal arithmetic with configurable precision, rounding modes, and signal handling.

```python
from decimal import Decimal

price = Decimal("19.99")
tax_rate = Decimal("0.07")
tax = price * tax_rate
```

`Decimal` is particularly relevant when exact decimal representation and explicit decimal rounding behavior are part of the requirements.

## 1.7.9 Construct `Decimal` Carefully

```python
Decimal("0.1")
```

starts from exact decimal text. In contrast:

```python
Decimal(0.1)
```

converts the already-existing binary floating-point value exactly, which can expose many decimal digits.

When the source quantity is intended as exact human-entered decimal text, constructing from a string is often the appropriate boundary representation.

## 1.7.10 Exact Decimal Input Does Not Make Every Result Exact

`Decimal` can exactly represent values such as decimal `0.1`, but operations such as `1 / 3` still require a finite working precision and rounding context.

**Exact decimal input ≠ every mathematical result has a finite exact decimal representation.**

## 1.7.11 Money Is More Than an Amount

```python
amount = Decimal("1000.00")
currency = "USD"
```

A monetary model also needs currency and applicable business, contractual, accounting, or rounding rules.

**Money = Amount + Currency + Rules**

## 1.7.12 Strings and Financial Identifiers

Strings are appropriate for tickers, currency codes, names, CUSIPs or other identifiers, and digit sequences whose leading zeros or textual semantics matter.

```python
ticker = "AAPL"
currency = "USD"
security_id = "00012345"
```

## 1.7.13 Booleans

Booleans represent genuinely binary conditions:

```python
is_callable = False
is_market_open = True
```

A domain with more than two states should not be compressed into a single Boolean without justification.

## 1.7.14 Missing Is Not Zero

```python
interest_rate = None
```

can represent absence of a value in application logic. This differs from `0.0`, `False`, and an empty string.

**0 ≠ missing**.

## 1.7.15 Collections

Lists can represent ordered mutable sequences such as introductory cash-flow collections. Tuples are immutable sequences. Dictionaries associate keys with values and can represent simple structured financial records.

```python
bond = {
    "face_value": 1_000,
    "coupon_rate": 0.05,
    "maturity_years": 10,
    "currency": "USD",
}
```

More specialized structures will be introduced as the book progresses.

## 1.7.16 Dates Are Financial Data

Python's `datetime` module provides dedicated date and time types:

```python
from datetime import date
maturity_date = date(2035, 6, 30)
```

A financial year fraction should not automatically be computed as calendar days divided by 365. Financial instruments use explicit day-count conventions such as Actual/360, Actual/365, Actual/Actual, and 30/360 families.

## 1.7.17 Date and Time Are Different Concepts

Python distinguishes `date`, `time`, `datetime`, and `timedelta`, and distinguishes naive from aware date/time objects with respect to timezone information. Timezone semantics matter in market data, transaction timestamps, and global systems.

## 1.7.18 Type Conversion at Boundaries

Raw financial input often arrives as text. A useful workflow is:

**Raw Input → Validation → Conversion → Financial Representation**

For decimal requirements:

```python
principal = Decimal(principal_text)
rate = Decimal(rate_text)
periods = int(periods_text)
```

## 1.7.19 External Data Requires Interpretation

Values such as `$1,250.75`, `5.25%`, `N/A`, or a date string cannot all be converted with one generic numeric operation. Robust financial data workflows parse, validate, normalize, and then calculate.

## 1.7.20 Units Must Be Explicit

```python
spread_bps = 125
spread_decimal = spread_bps / 10_000
```

One basis point is `0.01% = 0.0001`, so 125 basis points correspond to `0.0125` in decimal-rate form.

Names that expose units reduce ambiguity.

## 1.7.21 Percent, Decimal, and Basis Points

`5% = 0.05 = 500 basis points`.

These are different representations of the same rate magnitude under the stated unit definitions. Programs should convert explicitly rather than relying on implicit assumptions.

## 1.7.22 Avoid Careless Numeric Mixing

If decimal arithmetic is chosen for a calculation, inputs should generally be converted deliberately at the boundary rather than repeatedly mixing `float`, text, and `Decimal` without understanding the conversions.

**Choose representation at the boundary → remain consistent through the calculation.**

## 1.7.23 Precision Is Not Formatting

Representation precision, calculation precision, rounding policy, and display precision are distinct concepts. Formatting a value to two decimal places changes presentation; it does not redefine the arithmetic that produced it.

## 1.7.24 A Small Financial Data Model

```python
from datetime import date
from decimal import Decimal

investment = {
    "instrument": "Example Bond",
    "face_value": Decimal("1000.00"),
    "coupon_rate": Decimal("0.05"),
    "quantity": 10,
    "currency": "USD",
    "maturity_date": date(2035, 6, 30),
    "is_callable": False,
}
```

Financial software manipulates structured information, not merely numbers.

## 1.7.25 Python Type vs. Financial Semantics

`type(0.05)` tells us that the object is a `float`; it does not tell us whether the number represents an annual rate, monthly rate, portfolio weight, or probability.

**Python type ≠ financial semantics.**

## 1.7.26 Practical Early-Book Guide

Possible representations include `int` for period counts, `float` for many numerical-model quantities, `Decimal` when exact decimal behavior is required, `str` for identifiers/currency codes, `bool` for binary states, `None` for absent optional values, lists/tuples/dictionaries for introductory structures, and `datetime` types for dates/timestamps.

These are teaching defaults, not universal production architecture.

## 1.7.27 Common Mistakes

Common risks include treating identifiers as numbers, treating missing values as zero, assuming `float` stores decimals exactly, unintentionally constructing `Decimal` from `float`, mixing rate units, assuming display formatting fixes precision, and treating financial dates as ordinary numeric differences.

3. Build a bond dictionary containing name, face value, coupon rate, currency, maturity date, and callable status.
4. Convert 250 basis points to decimal rate form (`0.025`).
5. Explain why a zero coupon and a missing coupon value are not equivalent.

## 1.7.29 Key Takeaways

Financial data requires value, type, unit, convention, and meaning. `float` uses binary floating point and is appropriate for many numerical workloads; `Decimal` supports exact decimal representation and configurable decimal arithmetic where required. Strings, booleans, missing-value semantics, collections, dates, and explicit units are all part of reliable financial modeling.

The central design rule is:

**Financial Data = Value + Type + Unit + Convention + Meaning**
