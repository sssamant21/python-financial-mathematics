## 1.7.1 Why Data Representation Matters in Finance

Financial mathematics deals with values that have both computational representation and financial meaning.

```python
principal = 10_000
annual_effective_rate = 0.0525
periods = 10
```

A value such as `0.05` does not tell us whether it represents an annual rate, monthly rate, portfolio weight, probability, volatility, or discount rate.

**Financial Data = Value + Type + Unit + Convention + Meaning**

## 1.7.2 Variables and Names

Python names can be rebound to different objects. Financial programs should nevertheless use names with stable, descriptive financial semantics.

```python
principal = 10_000
annual_effective_rate = 0.05
investment_years = 10
future_value = principal * (1 + annual_effective_rate) ** investment_years
```

Concise mathematical notation such as `P`, `r`, and `n` remains useful in derivations, while descriptive names generally improve implementation clarity.

## 1.7.3 Core Numeric Types

Python's principal built-in numeric types are `int`, `float`, and `complex`; `bool` is a subtype of `int`. The standard library also provides facilities such as `decimal.Decimal` and `fractions.Fraction`. [1]

Early financial work in this book focuses primarily on `int`, `float`, and `Decimal`.

## 1.7.4 Integers

Integers are useful for whole-number quantities such as periods, simulation counts, and integer security quantities. Python integers have arbitrary precision subject to available memory. [1]

A digit-based identifier should not automatically be represented as an integer:

```python
account_id = "001234567"
```

This preserves leading zeros and avoids implying that arithmetic is meaningful.

**Looks Numeric ≠ Should Be Numeric.**

## 1.7.5 Floating-Point Numbers

Rates, model prices, weights, volatilities, and many other numerical-model quantities are commonly represented using `float`:

```python
interest_rate = 0.0525
volatility = 0.18
portfolio_weight = 0.35
```

Python floating-point values use binary floating-point representation. Most decimal fractions cannot be represented exactly as finite binary fractions. [2]

## 1.7.6 Representation Error

```python
print(0.1 + 0.2)
print(0.1 + 0.1 + 0.1 == 0.3)
```

The first expression commonly displays `0.30000000000000004`; the second evaluates to `False`. This is a representation issue, not failed arithmetic: decimal `0.1` has no exact finite binary floating-point representation. [2]

## 1.7.7 `float` Is Not Inherently Wrong for Finance

Binary floating point is fundamental to numerical computing. Statistical estimation, Monte Carlo simulation, matrix operations, optimization, regression, and many quantitative models naturally use floating-point arithmetic.

Conversely, contractual decimal rules, accounting, ledger reconciliation, or strict decimal behavior may require another representation.

**Choose numeric representation from requirements.**

## 1.7.8 Comparing Floating-Point Results

Exact equality may be inappropriate for approximate floating-point calculations. Python provides `math.isclose()` for approximate comparisons. [5]

```python
import math

result = 0.1 + 0.1 + 0.1
expected = 0.3

print(math.isclose(result, expected))
```

Explicit tolerances can be supplied:

```python
math.isclose(result, expected, rel_tol=1e-9, abs_tol=0.0)
```

The tolerance shown is an example, not a universal financial tolerance. Appropriate tolerances must follow the numerical algorithm, scale, units, financial requirements, and validation policy.

## 1.7.9 Decimal Arithmetic

Python's `decimal.Decimal` supports decimal arithmetic with configurable precision, rounding modes, contexts, and signals. [3]

```python
from decimal import Decimal

price = Decimal("19.99")
tax_rate = Decimal("0.07")
tax = price * tax_rate
```

`Decimal` is particularly relevant when decimal representation and explicit decimal arithmetic behavior are requirements.

## 1.7.10 Constructing `Decimal` Carefully

```python
Decimal("0.1")
```

starts from exact decimal text. In contrast:

```python
Decimal(0.1)
```

converts the actual already-existing binary floating-point value exactly, which can expose a long decimal expansion. [3]

When the intended source value is human-entered exact decimal text, construction from a string is often an appropriate boundary representation.

## 1.7.11 Exact Decimal Representation vs. Arithmetic Precision

It is misleading to say simply that `Decimal` is exact. `Decimal` can exactly represent finite decimal inputs such as `"0.1"`, while arithmetic remains governed by the active decimal context and the mathematical operation. [3]

```python
from decimal import Decimal, getcontext

getcontext().prec = 10
result = Decimal(1) / Decimal(3)
```

`1/3` has no finite decimal representation, so the result is constrained by the configured precision.

**Exact decimal input ≠ every arithmetic result is exact.**

## 1.7.12 Avoid Careless `float` / `Decimal` Boundaries

If decimal arithmetic is intentionally required, inputs should be converted deliberately at the boundary and handled consistently:

```python
amount = Decimal("100.00")
rate = Decimal("0.05")
```

Avoid uncontrolled conversion chains among `float`, text, and `Decimal`. The `decimal` module also provides a `FloatOperation` signal that can help detect certain accidental interactions with binary floating-point values. [3]

**Choose representation at the boundary → remain deliberate throughout the calculation.**

## 1.7.13 Money Is More Than a Number

```python
amount = Decimal("1000.00")
currency = "USD"
```

A monetary model also needs applicable business, contractual, accounting, or rounding rules.

**Money = Amount + Currency + Rules.**

Production systems may additionally require currency-specific minor-unit rules, contractual rounding, accounting policies, settlement rules, and domain-specific money types.

## 1.7.14 Strings and Financial Identifiers

Strings are appropriate for tickers, currency codes, names, and identifiers whose textual semantics or leading zeros matter:

```python
ticker = "AAPL"
currency = "USD"
security_id = "00012345"
```

## 1.7.15 Booleans

Booleans represent genuinely binary conditions:

```python
is_callable = False
is_market_open = True
```

A domain containing states such as approved, rejected, and pending should not be compressed into one Boolean without justification.

## 1.7.16 Missing Financial Data Is Not Zero

```python
interest_rate = 0.0
```

states that the rate is zero. This differs from:

```python
interest_rate = None
```

which can represent absence in ordinary Python application logic.

**0 ≠ Missing. False ≠ Missing. `""` ≠ Missing.**

Later NumPy and pandas sections introduce additional missing-data representations and semantics; `None` is not a universal missing-data representation.

## 1.7.17 Collections

Lists are mutable sequences, tuples are immutable sequences, and dictionaries associate keys with values. [1]

```python
cash_flows = [100.0, 150.0, 200.0, 250.0]
price_range = (95.0, 105.0)

bond = {
    "face_value": 1_000,
    "coupon_rate": 0.05,
    "maturity_years": 10,
    "currency": "USD",
}
```

These are introductory structures; later sections introduce stronger numerical, tabular, and domain representations.

## 1.7.18 Dates Are Financial Data

Finance is time-dependent. Important dates include valuation, trade, settlement, coupon, payment, and maturity dates.

```python
from datetime import date
maturity_date = date(2035, 6, 30)
```

Python's `datetime` module provides dedicated date/time types. [4]

## 1.7.19 `date`, `time`, `datetime`, and Awareness

The `datetime` module provides types including `date`, `time`, `datetime`, and `timedelta`. `date` objects are always naive; `time` and `datetime` objects may be aware or naive with respect to timezone information. [4]

Timezone semantics matter for market data, transaction timestamps, trading systems, and global portfolios.

## 1.7.20 Calendar Time Is Not Automatically Financial Time

A financial year fraction should not automatically be calculated as calendar days divided by 365.

Financial instruments may use contractual or market-specific day-count conventions, including Actual/360, Actual/365-family, Actual/Actual-family, and 30/360-family conventions. Their precise definitions and variants are deferred to later sections using appropriate financial-industry references.

**Calendar Difference ≠ Automatically a Financial Year Fraction.**

## 1.7.21 Type Conversion at Boundaries

Raw financial input often arrives as text. A disciplined workflow is:

**Raw Input → Validation → Conversion → Financial Representation**

For decimal requirements:

```python
principal = Decimal(principal_text)
rate = Decimal(rate_text)
periods = int(periods_text)
```

## 1.7.22 External Data Requires Interpretation

Values such as `$1,250.75`, `5.25%`, `N/A`, `—`, and date strings cannot all be processed by one generic numeric conversion. Robust workflows parse, validate, normalize, and only then calculate.

**Acquire → Parse → Validate → Normalize → Calculate.**

## 1.7.23 Units Must Be Explicit

```python
spread_bps = 125
spread_decimal = spread_bps / 10_000
```

One basis point is `0.01% = 0.0001`, so 125 basis points correspond to `0.0125` in decimal-rate form.

**Numbers without units are dangerous.**

## 1.7.24 Percent, Decimal, and Basis Points

`5% = 0.05 = 500 bp` represents the same rate magnitude under three unit representations, but the raw numeric values differ.

```python
rate_percent = 5
rate_decimal = 0.05
rate_bps = 500
```

Likewise, `250 bp = 2.5% = 0.025`.

## 1.7.25 Precision Is Not Formatting

```python
result = 10.0 / 3.0
print(f"{result:.2f}")
```

Formatting changes presentation; it does not define the internal representation, calculation precision, comparison tolerance, financial rounding policy, or settlement rule. [2]

**Representation ≠ Arithmetic Precision ≠ Tolerance ≠ Rounding Policy ≠ Display Precision.**

## 1.7.26 A Small Financial Data Model

```python
from datetime import date
from decimal import Decimal

investment = {
    "instrument": "Example Bond",
    "face_value": Decimal("1000.00"),
    "coupon_rate": Decimal("0.05"),
    "quantity": 10,
    "currency": "USD",
    "maturity_date": date(2035, 6, 30),
    "is_callable": False,
}
```

This is intentionally an introductory structure, not a universal production financial-domain model.

**Financial software manipulates structured information, not merely numbers.**

## 1.7.27 Python Type vs. Financial Semantics

`type(0.05)` tells us that the object is a `float`; it does not tell us whether it represents annual interest, monthly interest, volatility, portfolio weight, or probability.

**Python type ≠ financial semantics.**

## 1.7.28 Practical Representation Guide

| Financial information | Possible introductory representation |
|---|---|
| Number of periods | `int` |
| Simulation count | `int` |
| Numerical-model rate | often `float` |
| Numerical-model price | often `float` |
| Decimal monetary/accounting amount | often `Decimal` when exact decimal behavior is required |
| Currency code | `str` |
| Security identifier | usually `str` |
| Binary condition | `bool` |
| Absent optional application value | `None` |
| Introductory cash-flow sequence | `list` |
| Fixed small sequence | `tuple` |
| Simple structured instrument | `dict` |
| Calendar date | `datetime.date` |
| Timestamp | `datetime.datetime` |

These are teaching defaults, not universal production architecture. Correct representation depends on domain, calculation method, precision requirements, performance, scale, interfaces, and data contracts.

## 1.7.29 Common Failure Patterns

Common risks include treating identifiers as numbers, treating missing values as zero, assuming `float` stores decimal fractions exactly, unintentionally constructing `Decimal` from `float`, mixing rate units, treating formatting as a numerical policy, using exact equality blindly for approximate calculations, and treating calendar differences as financial year fractions.

## 1.7.31 Key Takeaways

Financial data requires value, type, unit, convention, and meaning. `float` uses binary floating point and remains appropriate for many numerical workloads. `Decimal` supports exact representation of finite decimal inputs and configurable decimal arithmetic where required, but arithmetic remains governed by precision and rounding rules. Approximate numerical comparisons require justified tolerances. Strings, booleans, missing-value semantics, collections, dates, and explicit units are all part of reliable financial modeling.

The canonical design rule is:

**Financial Data = Value + Type + Unit + Convention + Meaning**
