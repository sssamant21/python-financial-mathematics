## 1.5.1 Why Environment Setup Matters

Before writing financial mathematics programs, we need a controlled Python environment. A program may work correctly on one computer and fail on another because of differences in Python versions, package versions, installed dependencies, operating systems, or environment configuration.

For quantitative work, we want a workflow that supports correctness, isolation, reproducibility, and maintainability. A calculation whose software environment cannot be identified or recreated becomes much harder to validate.

Our initial environment contains Python, an isolated virtual environment, NumPy, pandas, Matplotlib, and JupyterLab. More specialized libraries will be added only when the mathematics requires them.

## 1.5.2 Install and Verify Python

Use a currently supported Python 3 release unless a later section explicitly requires another version. Obtain Python from a trusted distribution appropriate for the operating system; the official project provides downloads at https://www.python.org/downloads/.

Verify the interpreter:

```bash
python --version
```

On systems where Python 3 is exposed separately:

```bash
python3 --version
```

On Windows, the Python launcher can commonly be used:

```powershell
py --version
```

The important question is not merely the version number, but **which Python interpreter is actually running**.

## 1.5.3 Verify pip

`pip` is Python's package installer. Prefer an interpreter-explicit form:

```bash
python -m pip --version
```

or, where appropriate:

```bash
python3 -m pip --version
```

On Windows before activating a project environment:

```powershell
py -m pip --version
```

The `python -m pip` form makes the relationship between the selected Python interpreter and pip explicit.

## 1.5.4 Why We Use a Virtual Environment

Different projects can require different package versions. Installing everything into one global environment can create conflicts. Python's standard-library `venv` module creates isolated virtual environments with their own installed packages.

Conceptually:

```text
Computer
├── Project A
│   └── .venv
└── Project B
    └── .venv
```

Each project can maintain its own working dependency set.

## 1.5.5 Create the Virtual Environment

From the project directory:

```bash
python -m venv .venv
```

Where Python 3 is exposed as `python3`:

```bash
python3 -m venv .venv
```

On Windows using the Python launcher:

```powershell
py -m venv .venv
```

`.venv` is a convenient project-local environment name.

## 1.5.6 Activate the Environment

For bash/zsh on macOS/Linux:

```bash
source .venv/bin/activate
```

For Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

For Windows Command Prompt:

```cmd
.venv\Scripts\activate.bat
```

Activation is a shell convenience: it adjusts the shell environment so commands such as `python` resolve to the virtual environment.

## 1.5.7 Activation Is Convenient, Not Required

Activation is not the same thing as environment creation, and Python does not require an environment to be activated before it can be used. Its interpreter can be invoked directly.

macOS/Linux:

```bash
.venv/bin/python --version
```

Windows:

```powershell
.venv\Scripts\python.exe --version
```

For this book we normally activate the environment because it keeps commands readable.

## 1.5.8 Verify the Active Interpreter

After activation:

```bash
python --version
python -m pip --version
```

From Python:

```python
import sys
print(sys.executable)
```

This leads to a durable troubleshooting rule: **identify the interpreter before changing packages**.

## 1.5.9 Windows PowerShell Note

Some Windows systems may prevent `Activate.ps1` from executing because of PowerShell execution-policy settings. On corporate or managed systems, do not weaken security policy indiscriminately merely to activate an environment. Follow organizational policy, consult the Python documentation, ask the appropriate administrator when necessary, or invoke the environment's Python executable directly. Activation itself is optional.

## 1.5.10 Install the Initial Scientific Python Stack

With the environment active:

```bash
python -m pip install numpy pandas matplotlib jupyterlab
```

- **NumPy** provides multidimensional arrays and fundamental numerical-computing capabilities.
- **pandas** provides data structures and tools for structured and tabular data.
- **Matplotlib** provides visualization capabilities.
- **JupyterLab** provides an interactive computational environment combining explanatory text, mathematical notation, executable Python, tables, and plots.

Packages will be introduced as the mathematics requires them rather than treated as substitutes for understanding the underlying theory.

## 1.5.11 Verify the Installed Packages

Run:

```bash
python -m pip list
```

A focused test is:

```python
import sys
import numpy as np
import pandas as pd
import matplotlib

print("Python:", sys.version)
print("Python executable:", sys.executable)
print("NumPy:", np.__version__)
print("pandas:", pd.__version__)
print("Matplotlib:", matplotlib.__version__)
```

This checks the interpreter, environment, imports, and package versions.

## 1.5.12 Start JupyterLab

After installation:

```bash
jupyter lab
```

Notebooks are especially useful while learning financial mathematics because explanation, mathematics, Python, results, and visualization can coexist. As programs become larger, reusable logic should increasingly move into ordinary Python modules and be tested independently.

A useful pattern is:

- **Notebook → explore and explain**
- **Python module + tests → reuse and maintain**

## 1.5.13 First Financial Environment Test

Verify the complete environment with a financial calculation:

```python
principal = 1_000.0
rate = 0.05
periods = 3

future_value = principal * (1 + rate) ** periods
print(future_value)
```

Using

\[
FV=P(1+r)^n
\]

with \(P=1000\), \(r=0.05\), and \(n=3\):

\[
FV=1000(1.05)^3=1157.625
\]

Expected output:

```text
1157.625
```

This validates the interpreter, environment, execution path, and financial calculation.

## 1.5.14 Test NumPy

```python
import numpy as np

cash_flows = np.array([100.0, 120.0, 150.0])

print(cash_flows)
print(cash_flows.sum())
```

The expected sum is `370.0`. The purpose is not yet to teach NumPy in depth, but to confirm that the numerical environment works.

## 1.5.15 Virtual Environments Should Be Disposable

A virtual environment should be treated as a local, recreatable working environment rather than an irreplaceable or portable project artifact. The important project assets are source code, notebooks, tests, dependency declarations, configuration, and documentation.

Do not treat `.venv` as something to archive, share, or move between systems. Recreate it from retained dependency information.

## 1.5.16 Do Not Commit `.venv`

Add the environment directory to `.gitignore`:

```gitignore
.venv/
```

The principle is simple: **commit dependency information, not the virtual environment**.

## 1.5.17 Recording Dependencies

A beginner project may start with `requirements.txt`:

```text
numpy
pandas
matplotlib
jupyterlab
```

Install it with:

```bash
python -m pip install -r requirements.txt
```

A requirements file records installation requirements, but it does not automatically guarantee perfect reproducibility. Unpinned requirements can resolve to different compatible versions over time; tighter constraints or lock strategies provide stronger repeatability.

## 1.5.18 `pyproject.toml` and Modern Project Metadata

Modern Python projects commonly use `pyproject.toml` for standardized project metadata and related packaging configuration. This book will introduce it when we begin creating reusable Python projects. Later chapters will cover dependency organization, version constraints, packaging, dependency groups, and stronger reproducibility strategies.

## 1.5.19 Recommended Repository Pattern

A working project may eventually resemble:

```text
python-financial-mathematics/
├── .venv/                 # local only — ignored by Git
├── books/
├── examples/
├── notebooks/
├── tests/
├── references/
├── .gitignore
├── requirements.txt
└── pyproject.toml         # when introduced
```

The repository stores source material and dependency/project metadata; the virtual environment is recreated locally.

## 1.5.20 Common Environment Problems

### Package installed but Python cannot import it

A package may have been installed into one interpreter while the program runs under another. Check:

```bash
python -m pip --version
```

and:

```python
import sys
print(sys.executable)
```

### Notebook cannot import an installed package

The notebook may be using a different Python environment. Inspect `sys.executable` before reinstalling anything.

### Environment becomes inconsistent

If dependency information is preserved, recreating a disposable environment may be safer than repeatedly modifying an unknown environment.

### `.venv` accidentally committed

Remove it from version control and ensure `.venv/` is present in `.gitignore`.

### Wrong Python version

Check both `python --version` and `sys.executable` before changing packages.

## 1.5.21 Environment Troubleshooting Rule

Use this diagnostic sequence:

```text
Which Python?
      ↓
Which environment?
      ↓
Which pip?
      ↓
Which package version?
      ↓
Which notebook/kernel?
      ↓
What actual error?
```

The engineering habit is: **identify → verify → diagnose → change**.

## 1.5.22 Key Takeaways

1. Use a currently supported Python 3 release unless a project specifies otherwise.
2. Verify which Python interpreter is running before installing packages.
3. Use a virtual environment to isolate project dependencies.
4. Prefer `python -m pip` when you want an explicit interpreter/pip relationship.
5. Activation is convenient but not technically required.
6. Verify environments with `sys.executable`.
7. Use NumPy, pandas, Matplotlib, and JupyterLab as the initial scientific stack for this book.
8. Use notebooks for interactive exploration and explanation; move reusable logic into modules and tests as programs mature.
9. Treat virtual environments as disposable and recreatable.
10. Do not commit `.venv`.
11. Store dependency information with the project.
12. A requirements file helps recreate dependencies but does not guarantee perfect reproducibility by itself.
13. When troubleshooting, identify the interpreter and environment before modifying packages.
14. Verify the environment with an executable financial calculation.

The core environment principle is:

\[
\boxed{\text{Source Code}+\text{Dependency Information}+\text{Recreatable Environment}=\text{Maintainable Quantitative Project}}
\]
