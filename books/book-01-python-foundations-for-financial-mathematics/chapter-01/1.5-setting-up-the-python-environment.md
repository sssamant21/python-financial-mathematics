# 1.5 — Setting Up the Python Environment

**Workflow Stage:** Draft  
**Book:** Python Foundations for Financial Mathematics

## 1.5.1 Why Environment Setup Matters

Financial mathematics code should be reproducible. A calculation that works only on one computer, depends on unknown package versions, or accidentally uses packages from an unrelated project is difficult to validate and maintain.

A disciplined Python environment gives us a controlled place for the interpreter, installed packages, notebooks, examples, and tests used by this book.

## 1.5.2 Verify Python and pip

Before installing finance or scientific-computing packages, verify the Python interpreter and package installer associated with it.

On macOS/Linux:

```bash
python --version
python -m pip --version
```

On Windows, the Python launcher can be used:

```powershell
py --version
py -m pip --version
```

Using `python -m pip` explicitly associates pip with the selected Python interpreter, which helps avoid ambiguity when multiple Python installations exist.

## 1.5.3 Create a Virtual Environment

Python's standard-library `venv` module creates isolated virtual environments. This lets different projects maintain different dependency sets without forcing all packages into one global environment.

From the project directory:

```bash
python -m venv .venv
```

On Windows:

```powershell
py -m venv .venv
```

The `.venv` directory should normally remain local to the working machine and should not be committed to Git.

## 1.5.4 Activate the Environment

On macOS/Linux shells:

```bash
source .venv/bin/activate
```

On Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

After activation, verify the interpreter and pip again:

```bash
python --version
python -m pip --version
```

The objective is not merely to see a version number; it is to confirm that subsequent package installation occurs in the intended environment.

## 1.5.5 Install the Initial Scientific Stack

For early chapters, a useful baseline is:

```bash
python -m pip install numpy pandas matplotlib jupyterlab
```

These packages serve different purposes:

- **NumPy** — numerical arrays and numerical computation.
- **pandas** — tabular and time-series-oriented data manipulation.
- **Matplotlib** — plotting and visualization.
- **JupyterLab** — interactive notebooks and computational documents.

Packages will be introduced when the mathematics requires them rather than treated as substitutes for understanding the underlying theory.

## 1.5.6 Start JupyterLab

Project Jupyter documents installation of JupyterLab with pip and launching it with:

```bash
jupyter lab
```

Jupyter is especially useful for financial mathematics because explanatory text, mathematical notation, executable Python, tables, and plots can coexist in a computational document.

However, notebooks should complement—not replace—reusable Python modules and tests when code becomes substantial.

## 1.5.7 A First Environment Check

Create a Python file or notebook and run:

```python
import sys
import numpy as np

print(sys.version)
print(np.__version__)
```

Then perform a simple financial calculation:

```python
principal = 1_000.0
rate = 0.05
periods = 3

future_value = principal * (1 + rate) ** periods
print(future_value)
```

This should produce approximately:

```text
1157.625
```

The purpose is to validate the complete path:

`Python interpreter → environment → package imports → executable financial calculation`

## 1.5.8 Reproducibility and Dependency Records

A virtual environment isolates dependencies, but the `.venv` directory itself is not the dependency specification. Projects should retain machine-readable dependency information so an environment can be recreated.

A simple learning project may use a requirements file, installed with:

```bash
python -m pip install -r requirements.txt
```

As the repository matures, dependency metadata can be managed through modern Python project metadata such as `pyproject.toml`. The exact packaging strategy will be introduced when the book reaches reusable project structure rather than overloading the beginner setup with packaging details.

## 1.5.9 Recommended Repository Practice

For this series, the local development pattern is:

```text
repository/
├── .venv/              # local; do not commit
├── books/
├── examples/
├── notebooks/
├── tests/
└── requirements.txt or project metadata
```

The repository stores source material and dependency specifications; the virtual environment is recreated locally.

## 1.5.10 Common Setup Mistakes

Common problems include installing packages globally without realizing it, invoking a different Python interpreter than expected, committing `.venv`, running notebooks from an unintended environment, and failing to record dependencies.

A useful diagnostic sequence is:

```bash
python --version
python -m pip --version
python -m pip list
```

When troubleshooting, first establish **which Python interpreter and environment are actually running** before changing packages.

## 1.5.11 Key Takeaways

1. Use an isolated environment for the book project.
2. Python's standard `venv` module provides a straightforward starting point.
3. Prefer `python -m pip` (or `py -m pip` on Windows) when you need to make the interpreter/pip relationship explicit.
4. Keep `.venv` out of Git.
5. Record dependencies separately so environments can be recreated.
6. JupyterLab is useful for interactive mathematical exploration, while reusable code should increasingly move into Python modules and tests.
7. Always verify the interpreter and environment before diagnosing package problems.
