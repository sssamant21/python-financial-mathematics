## 1.10.1 From Formulas to Interactive Financial Programs

Sections 1.7–1.9 established how financial values are represented, how operators act on those values, and how mathematical formulas become Python expressions. This section addresses the next question: **How do financial values enter and leave a Python program?**

- 1.7: Represent Financial Values
- 1.8: Perform Operations
- 1.9: Translate Mathematical Expressions
- 1.10: Move Values Across Program Boundaries

A hard-coded future-value calculation is:

```python
principal = 10_000
rate = 0.05
periods = 3
future_value = principal * (1 + rate) ** periods
print(future_value)
```

An interactive program can obtain those values externally:

```python
principal = float(input("Principal: "))
rate = float(input("Rate as a decimal, for example 0.05: "))
periods = int(input("Number of whole periods: "))
future_value = principal * (1 + rate) ** periods
print(f"Future value: {future_value}")
```

**External Input → Python Representation → Financial Calculation → Output**

Input and output are therefore part of the financial model's interface.

## 1.10.2 Input Is a Boundary

External input arrives from outside the calculation. The text `10000` could mean USD 10,000, EUR 10,000, 10,000 shares, 10,000 basis points, 10,000 periods, or an identifier whose characters happen to be digits. The characters themselves do not establish financial meaning.

**External Text + Interpretation → Financial Input**

The program must establish that interpretation explicitly.

## 1.10.3 Python's `input()` Function

For simple interactive programs, Python provides the built-in `input()` function:

```python
investment_name = input("Investment name: ")
```

For normal successful input, `input()` reads a line, removes the trailing newline, and returns the resulting string. If the user enters `Growth Fund`, `investment_name` contains `"Growth Fund"`.

**`input()` → `str`**

This remains true when the characters look numeric.

## 1.10.4 Numeric-Looking Input Is Still Text

```python
principal = input("Principal: ")
```

If the user enters `10000`, `type(principal)` shows that `principal` is a string.

**Numeric-Looking Text != Numeric Python Value**

A financial program requiring numeric arithmetic must explicitly interpret and convert the text.

## 1.10.5 Parsing and Converting Numeric Input

```python
principal = float(input("Principal: "))
periods = int(input("Number of whole periods: "))
```

Conceptually:

**External Text → Parse / Convert → Typed Value**

`float("10000")` produces `10000.0`, while `int("5")` produces the integer `5`. The parser must match the model's input contract.

## 1.10.6 Conversion Is Also Interpretation

If `rate = float(input("Rate: "))` receives `5`, Python can convert it to `5.0`, but cannot determine whether the financial meaning is 5, 5% = 0.05, or perhaps five basis points.

A better interface states the expected representation:

```python
rate = float(input("Rate as a decimal, for example 0.05 for 5%: "))
```

or:

```python
rate_percent = float(input("Rate as a percentage, for example 5 for 5%: "))
rate = rate_percent / 100
```

**Successful Type Conversion != Correct Financial Interpretation**

## 1.10.7 Normalize Inputs at the Boundary

```python
annual_rate_percent = float(input("Annual rate (%), for example 5.25: "))
annual_rate = annual_rate_percent / 100
future_value = principal * (1 + annual_rate) ** years
```

Here 5.25% is entered as `5.25` and normalized to `0.0525` for the model.

**External Representation → Normalize Once → Consistent Internal Representation**

## 1.10.8 Variable Names Should Preserve Meaning

Compare an ambiguous `rate` with:

```python
annual_rate_percent = float(input("Annual rate (%): "))
annual_rate = annual_rate_percent / 100
```

`annual_rate_percent = 5.25` and `annual_rate = 0.0525` communicate both meaning and representation. Descriptive names reduce the chance of mixing percentage and decimal-rate representations.

**Clear Financial Name = Value + Expected Meaning**

## 1.10.9 Integer Inputs Must Match the Model

Some simplified models use whole periods, whole years, numbers of payments, or security counts:

```python
periods = int(input("Number of whole periods: "))
```

The word **whole** matters. A user entering `2.5` does not satisfy this particular input contract. This does not mean financial time is inherently integer-valued; another model may legitimately accept fractional years.

**Choose the Type from the Model != Choose the Type from Convenience**

**Prompt ↔ Parser ↔ Model Domain**

## 1.10.10 Invalid Numeric Input

If `float(input("Principal: "))` receives `ten thousand`, Python cannot convert the text and raises `ValueError`. Likewise, `int("five")` raises `ValueError`.

**External Input Must Be Treated as Potentially Invalid**

## 1.10.11 Handling Conversion Failure

```python
try:
    principal = float(input("Principal: "))
except ValueError:
    print("Principal must be numeric.")
```

The `try` block contains the operation that may fail. The `except ValueError` block handles the specific conversion problem. Advanced exception design belongs later in the book.

## 1.10.12 Parsing Success Is Not Validation Success

`principal = float("-10000")` parses successfully. Whether a negative principal is acceptable depends on the model. A simplified calculator might specify:

```python
if principal <= 0:
    print("Principal must be greater than zero for this model.")
```

The qualifier **for this model** matters. Financial quantities are not universally required to be positive.

**Parsing != Domain Validation**

**Parseable does not imply Financially Valid**

## 1.10.13 Layers of Input Processing

1. **Acquire** — receive the external representation.
2. **Parse** — convert it into the required Python type.
3. **Validate** — determine whether it satisfies the mathematical domain.
4. **Financially Validate** — determine whether it satisfies the assumptions and conventions of the financial model.
5. **Normalize** — convert the valid external representation into the internal unit or convention expected by the calculation.

For example, `5.25` may be valid numeric input representing 5.25%. Normalization converts it to `0.0525` for a model expecting decimal rates.

**Acquire → Parse → Validate → Financially Validate → Normalize**

## 1.10.14 Finite Values and Financial Validation

Successful `float()` conversion can still produce a value unsuitable for a particular financial model. For models requiring finite values:

```python
import math
value = float(input("Value: "))
if not math.isfinite(value):
    print("Value must be finite.")
```

Values representing infinity or NaN may need to be rejected depending on the input contract.

**Successfully Parsed != Suitable for the Financial Model**

The deeper numerical implications belong in Section 1.11.

## 1.10.15 Whitespace and Text Input

For textual fields, explicit normalization may be appropriate:

```python
investment_name = input("Investment name: ").strip()
```

With no argument, `str.strip()` removes leading and trailing whitespace according to Python's string-method rules. Do not conclude that every external value should always be stripped; normalization policy depends on the input contract.

## 1.10.16 Separating Input, Calculation, and Output

```python
principal = float(input("Principal: "))
rate_percent = float(input("Annual rate (%): "))
years = int(input("Number of whole years: "))
rate = rate_percent / 100
future_value = principal * (1 + rate) ** years
print(f"Future value: {future_value}")
```

The program has recognizable stages:

**Input → Normalization → Calculation → Output**

Keeping those stages visible makes the code easier to inspect and later refactor.

## 1.10.17 The `print()` Function

Python's built-in `print()` function provides a simple output mechanism:

```python
print("Financial Mathematics")
print(future_value)
print("Future value:", future_value)
```

For the command-line programs in this chapter, `print()` provides the primary presentation boundary.

## 1.10.18 Output Should Carry Meaning

Compare an unlabeled `11576.25` with `Future value: $11,576.25`. The latter communicates what the number represents, the intended currency presentation, grouping, and deliberate display precision. Raw floating-point results can sometimes expose representation artifacts or more digits than are useful for user-facing output.

**Financial Output = Value + Meaning + Unit**

## 1.10.19 Formatted String Literals

Formatted string literals, commonly called **f-strings**, allow expressions to appear inside strings:

```python
principal = 10_000
print(f"Principal: {principal}")
print(f"Principal: ${principal:,.2f}")
```

The latter displays `Principal: $10,000.00`. The braces contain a replacement field, and the portion following `:` supplies a format specification.

## 1.10.20 Displaying Monetary Values

```python
future_value = 11_576.25
print(f"Future value: ${future_value:,.2f}")
```

displays `Future value: $11,576.25`. For the numeric value used here, `,` requests comma grouping and `.2f` requests fixed-point formatting with two digits after the decimal point. This describes the formatted representation; it does not define the application's monetary arithmetic policy.

**Display Formatting != Arithmetic Policy**

## 1.10.21 Displaying Percentages

```python
rate = 0.0525
print(f"Rate: {rate:.2%}")
```

displays `Rate: 5.25%`.

**0.0525 = Internal Calculation Representation**  
**5.25% = Display Representation**

**Internal Representation != Display Representation**

## 1.10.22 Formatting Does Not Change the Original Value

```python
value = 1234.5678
formatted_value = f"{value:,.2f}"
```

`value` remains numeric; `formatted_value` is a string intended for presentation.

**Numeric Value → Formatted String**

Formatting does not replace the underlying variable with the displayed representation.

## 1.10.23 Calculation Precision vs. Display Precision

If `value = 1234.5678`, then `print(f"{value:.2f}")` displays `1234.57`. That does not imply that `value` itself has become `1234.57`.

**Calculation Precision != Display Precision**

**Formatting != Quantization Policy**

Precision, rounding, quantization, and tolerance policies are developed systematically in Section 1.11.

## 1.10.24 Labels and Units

Compare `print(result)` with:

```python
print(f"Future value: ${result:,.2f}")
print(f"Annual rate: {annual_rate:.2%}")
```

A useful presentation contract is:

**Output = Label + Formatted Value + Unit or Convention**

Depending on the quantity, output may need to identify currency, percentage, decimal rate, basis points, periods, dates, counts, or ratios.

## 1.10.25 Currency Symbols Require Care

In `f"Value: ${value:,.2f}"`, `$` appears because the programmer explicitly inserted it. The numeric value itself does not identify a currency. `1000.00` does not inherently mean USD, EUR, GBP, JPY, or another currency.

**Amount != Currency**

Production financial systems require explicit decisions about currency identifiers, localization, decimal conventions, and contractual rules. The `$` examples here are deliberately simplified instructional displays.

## 1.10.26 Input Prompts Are Part of the Interface

Compare `rate = float(input("Rate: "))` with:

```python
rate_percent = float(input("Annual interest rate (%), for example 5.25: "))
years = int(input("Number of whole years: "))
```

The latter prompts communicate the quantity, time convention, unit, example representation, and integer expectation.

**Good Input Design Prevents Some Errors Before They Occur**

## 1.10.27 Do Not Mix External and Internal Units

```python
rate_percent = float(input("Annual rate (%): "))
rate = rate_percent / 100
future_value = principal * (1 + rate) ** years
```

Once normalization is complete, calculations should consistently use `rate`, not `rate_percent`.

**External Unit → Normalize Once → Consistent Internal Unit**

## 1.10.28 Input and Output as Contracts

An **input contract** specifies expected quantity, representation, unit, mathematical domain, financial assumptions, and handling of invalid values. An **output contract** specifies result meaning, unit, presentation convention, displayed precision, and assumptions or context that should accompany the result.

Example:

```text
Input Contract
--------------
Principal: USD amount, greater than zero for this model
Annual rate: percentage, such as 5.25 for 5.25%
Years: whole number, zero or greater

Output Contract
---------------
Future value: USD
Rate: percentage display
Future value displayed to two decimal places
```

The contract makes assumptions explicit.

## 1.10.29 A First Interactive Financial Calculator

```python
print("Future Value Calculator")

principal = float(input("Principal amount ($): "))
annual_rate_percent = float(input("Annual interest rate (%): "))
years = int(input("Number of whole years: "))

annual_rate = annual_rate_percent / 100
future_value = principal * (1 + annual_rate) ** years

print()
print(f"Principal:    ${principal:,.2f}")
print(f"Annual rate:  {annual_rate:.2%}")
print(f"Years:        {years}")
print(f"Future value: ${future_value:,.2f}")
```

For principal 10000, rate 5%, and three whole years, the displayed future value is `$11,576.25`.

**Prompt → Text Input → Parse → Normalize → Calculate → Format → Present**

## 1.10.30 Adding Basic Validation

```python
import math

try:
    principal = float(input("Principal amount ($): "))
    rate_percent = float(input("Annual interest rate (%): "))
    years = int(input("Number of whole years: "))
except ValueError:
    print("Please enter valid numeric values.")
else:
    if not math.isfinite(principal) or not math.isfinite(rate_percent):
        print("Principal and rate must be finite.")
    elif principal <= 0:
        print("Principal must be greater than zero for this model.")
    elif years < 0:
        print("Years cannot be negative for this model.")
    else:
        rate = rate_percent / 100
        future_value = principal * (1 + rate) ** years
        print(f"Future value: ${future_value:,.2f}")
```

This remains an introductory example rather than a complete production validation framework.

**Acquire → Parse → Validate → Normalize → Calculate → Present**

## 1.10.31 Why `eval()` Is Not an Input Parser

Do not use arbitrary expression evaluation as ordinary financial input parsing:

```python
eval(input("Enter value: "))
```

`eval()` evaluates a string as a Python expression. It is not a substitute for a defined parser and validation policy. Evaluating untrusted input can execute unintended code.

**Untrusted Input must not flow to `eval()`**

**Known Input Contract → Explicit Parsing → Validation**

Use explicit conversions such as `float(...)` or `int(...)` when those representations match the contract.

## 1.10.32 Separating Input/Output from Financial Logic

Interactive input is useful for learning, but financial calculation should not fundamentally depend on where values originated.

```text
Input Layer
    ↓
Financial Logic
    ↓
Output Layer
```

Later, input may come from a file, notebook, test, API, database, or financial data pipeline. A result may be returned to another function rather than printed directly. Separating the layers improves reuse, testing, verification, and reproducibility.

## 1.10.33 Common Input Mistakes

1. Forgetting that `input()` returns a string.
2. Using an ambiguous rate prompt that does not say whether 5% is `5` or `0.05`.
3. Assuming successful conversion equals validation.
4. Mixing percentage and decimal-rate representations.
5. Using a parser inconsistent with the prompt, such as `int()` while failing to say whole years are required.
6. Assuming currency from an amount.
7. Evaluating arbitrary user input with `eval()`.

## 1.10.34 Common Output Mistakes

1. Printing an unlabeled value with little financial context.
2. Confusing formatting such as `f"{value:.2f}"` with arithmetic or monetary policy.
3. Omitting units.
4. Mixing calculation and display representations.
5. Displaying unnecessary raw numeric detail.

The appropriate presentation policy depends on the application.

## 1.10.35 The Financial Input/Output Pipeline

The complete model is:

**External Data → Acquire → Parse → Validate → Normalize → Calculate → Format → Present**

- **Acquire** — What external representation was supplied?
- **Parse** — Can it become the required Python value?
- **Validate** — Is it acceptable for the mathematical and financial model?
- **Normalize** — Is it represented in the internal unit and convention expected by the calculation?
- **Calculate** — What result does the model produce?
- **Format** — How should the result be represented for presentation?
- **Present** — What label, unit, convention, and context should accompany it?

The same architecture can later scale from interactive command-line input to files, APIs, databases, market data, and larger financial pipelines.

## 1.10.37 Key Takeaways

1. `input()` returns a string for normal successful interactive input.
2. Numeric-looking text is not automatically a numeric Python value.
3. `int()` and `float()` provide explicit parsing/conversion for appropriate numeric input contracts.
4. Successful parsing does not establish financial meaning.
5. Input prompts should communicate units and expected representations.
6. User-facing percentages should be normalized to the representation expected by the model.
7. Normalize external representations once and use consistent internal representations.
8. Variable names can document financial meaning and units.
9. The prompt, parser, and model domain should agree.
10. External input must be treated as potentially invalid.
11. Parsing and domain validation are separate operations.
12. Mathematical validity and financial validity are distinct.
13. Successfully parsed floating-point values may still require finite-value validation.
14. `try` / `except ValueError` can handle expected conversion failures.
15. Input, financial logic, and output should remain conceptually separable.
16. `print()` provides a simple presentation mechanism for introductory programs.
17. F-strings provide readable formatted output.
18. Formatting does not change the original numeric value.
19. Calculation precision and display precision are different concerns.
20. Formatting does not define a monetary rounding or arithmetic policy.
21. Decimal rates and percentage displays can use different representations.
22. A numeric amount does not inherently identify its currency.
23. Meaningful financial output should communicate labels, values, units, and conventions.
24. `eval()` is not an ordinary input parser and must not be used with untrusted input.
25. Input and output contracts make model assumptions explicit.

**External Data → Acquire → Parse → Validate → Normalize → Calculate → Format → Present**
