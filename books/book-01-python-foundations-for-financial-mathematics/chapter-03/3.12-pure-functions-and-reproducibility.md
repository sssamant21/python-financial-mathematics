## 3.12.1 Purpose

A calculation is easier to reason about when its output depends on declared inputs and it leaves caller-visible state unchanged.

Earlier functions used explicit rates but still depended on the active Decimal context. This section makes that dependency concrete and develops a calculation with its own fully specified numerical context.

Purity is a design property, not a decorator that certifies a Python function. Reproducibility is broader: it also requires recorded inputs, conventions, code, and execution environment.

## 3.12.2 Learning Objectives

You should be able to:

1. Identify hidden dependencies and observable side effects.
2. Distinguish determinism, purity, and reproducibility.
3. Explain why explicit rate inputs do not fully control Decimal arithmetic.
4. Isolate a complete arithmetic policy without changing the caller's context.
5. Verify repeatability, scenario independence, and context preservation.
6. Describe evidence needed to reproduce a financial calculation.

## 3.12.3 Purity and Determinism

For this section, a pure financial calculation returns an output determined by its inputs and documented fixed implementation policy, without changing caller-visible state.

A deterministic function gives the same outcome for the same complete inputs and policy. It can still have side effects, such as appending the same audit message every time.

A function can also avoid writes while reading a changing market rate. That absence of mutation does not make its result independent of external state.

| Property | Question |
|---|---|
| Determinism | Does the same complete input and policy produce the same outcome? |
| Absence of side effects | Does execution leave caller-visible state unchanged? |
| Reproducibility | Can someone reconstruct the inputs, policy, code, and environment? |
| Financial correctness | Does the implementation represent the intended financial model? |

Repeatedly obtaining the same wrong number does not establish correctness.

## 3.12.4 Hidden Financial Inputs

A calculation can depend on module-global rates, mutable configuration, today's date, a file, a network response, a random generator, or arithmetic context.

Prefer resolving changing external facts at an application boundary and passing the selected values into the computational function.

Logging, saving results, and displaying output are useful application operations. Keep those effects outside the calculation when their separation improves review and testing.

## 3.12.5 Local Assignment Is Not Automatically a Side Effect

Rebinding a local numeric variable does not change the caller's binding. Creating a fresh local list and returning it does not inherently mutate caller-owned data.

Appending to a supplied list, modifying a configuration dictionary, printing, or writing a file is observable outside the calculation.

A shallow copy may still share nested mutable objects. Scope and local variable names alone cannot establish isolation.

## 3.12.6 Demonstrate the Decimal Context Dependency

```python
from decimal import Decimal, localcontext


def ambient_present_value(amount: Decimal) -> Decimal:
    """Illustrate a calculation that uses ambient arithmetic precision."""
    return amount / Decimal("3")


with localcontext() as context:
    context.prec = 6
    low_precision = ambient_present_value(Decimal("100"))

with localcontext() as context:
    context.prec = 28
    high_precision = ambient_present_value(Decimal("100"))

assert low_precision != high_precision
assert low_precision == Decimal("33.3333")
```

The explicit amount did not change. The surrounding precision did.

Decimal operations can also set context signal flags or raise exceptions depending on trap settings. Consequently, a function using ambient arithmetic can affect or depend on state even when it does not change precision explicitly.

## 3.12.7 localcontext Alone Is Not a Complete Fixed Policy

Using localcontext() without an explicit context copies the current context. Setting only its precision still leaves inherited rounding, exponent limits, and traps.

For a fixed-policy calculation, construct a Context with the chosen precision, rounding, exponent limits, clamp behavior, flags, and traps, then use a local copy of that context.

The lab fixes all of these policy fields rather than relying on DefaultContext or whatever the caller previously configured.

This creates an intentional new interface for the reproducibility exercise. Earlier canonical examples retain their documented ambient-context policies.

## 3.12.8 Fixed Numerical Policy for This Lab

| Setting | Lab choice |
|---|---|
| Precision | 40 significant digits |
| Rounding | ROUND_HALF_EVEN |
| Emin / Emax | -999999 / 999999 |
| clamp | 0 |
| capitals | 1 |
| Initial flags | Clear |
| Trapped signals | InvalidOperation, DivisionByZero, Overflow |
| Currency quantization | None |
| Reporting | Outside the valuation function |

These settings are a versioned teaching policy, not a universal financial standard. Forty digits do not guarantee adequate accuracy for every supported finite input.

Inexact and Rounded signals are not trapped. Finite underflow may still occur. Factor and result guards reject selected unusable outcomes but do not prove complete numerical accuracy.

## 3.12.9 Financial Contract

The lab discounts one nonnegative amount at a constant effective periodic rate to period 0:

PV = future_amount / (1 + periodic_rate)^periods.

All inputs use the original currency; rate and horizon periods must match. There are no intermediate cash flows, fees, taxes, currency conversion, or inflation adjustment.

Supported inputs are finite nonnegative Decimal amount, finite Decimal rate greater than -1, and integer periods from 0 through 1000, excluding bool.

The function validates all inputs, including at zero horizon. It preserves input objects and the caller's context settings and flags. Its internal context is temporary.

## 3.12.10 Hands-On Lab — Isolate the Numerical Policy

Save the complete module as reproducibility_lab.py. It requires Python 3.10 or later and only the standard library.

```python
"""Repeatable single-amount valuation with a fixed local Decimal policy."""

from decimal import (
    Context,
    Decimal,
    DivisionByZero,
    Inexact,
    InvalidOperation,
    Overflow,
    ROUND_DOWN,
    ROUND_HALF_EVEN,
    getcontext,
    localcontext,
)
import doctest


def fixed_present_value(
    future_amount: Decimal,
    *,
    periodic_rate: Decimal,
    periods: int,
) -> Decimal:
    """Discount one amount under the fixed 40-digit policy below.

    Require finite nonnegative Decimal amount, finite Decimal rate > -1,
    and integer periods 0..1000 excluding bool. Interpret the rate as
    effective per matching period and return a period-0 Decimal amount
    in the same currency, without sign reversal or quantization.

    Assume a constant rate and no intermediate cash flows, taxes, fees,
    inflation adjustment, or currency/rate conversion. Validate all
    inputs even at zero horizon.

    Use a fresh fully specified context with precision 40, half-even
    rounding, exponent limits +/-999999, clamp 0, capitals 1, clear
    flags, and traps for InvalidOperation, DivisionByZero, and Overflow.
    Do not alter the caller's context or mutate inputs. Other rounding
    and finite underflow remain possible.

    Raise TypeError or ValueError for unsupported inputs. Propagate
    trapped Decimal exceptions; raise ArithmeticError for a nonpositive
    or non-finite growth factor or a non-finite result.

    >>> fixed_present_value(Decimal("125"), periodic_rate=Decimal("0.25"), periods=1) == Decimal("100")
    True
    >>> fixed_present_value(Decimal("100"), periodic_rate=Decimal("0.05"), periods=0) == Decimal("100")
    True
    """
    if not isinstance(future_amount, Decimal):
        raise TypeError("future_amount must be Decimal")
    if not isinstance(periodic_rate, Decimal):
        raise TypeError("periodic_rate must be Decimal")
    if not isinstance(periods, int) or isinstance(periods, bool):
        raise TypeError("periods must be an integer excluding bool")
    if not future_amount.is_finite() or future_amount < 0:
        raise ValueError("future_amount must be finite and nonnegative")
    if not periodic_rate.is_finite() or periodic_rate <= Decimal("-1"):
        raise ValueError("periodic_rate must be finite and greater than -1")
    if not 0 <= periods <= 1000:
        raise ValueError("periods must be between 0 and 1000")

    policy = Context(
        prec=40,
        rounding=ROUND_HALF_EVEN,
        Emin=-999999,
        Emax=999999,
        capitals=1,
        clamp=0,
        flags=[],
        traps=[InvalidOperation, DivisionByZero, Overflow],
    )
    with localcontext(policy):
        growth = (Decimal("1") + periodic_rate) ** periods
        if not growth.is_finite() or growth <= 0:
            raise ArithmeticError("growth factor must be finite and positive")
        result = future_amount / growth
        if not result.is_finite():
            raise ArithmeticError("present value must be finite")
        return result


def run_checks() -> None:
    """Verify repeatability and preservation under different caller contexts."""
    amount = Decimal("1000")
    rate = Decimal("0.037")

    expected = fixed_present_value(amount, periodic_rate=rate, periods=17)
    assert fixed_present_value(amount, periodic_rate=rate, periods=17) == expected

    # Change multiple ambient settings and enable a trap the inner policy
    # deliberately does not inherit. Preserve an existing signal flag.
    with localcontext() as outer:
        outer.prec = 6
        outer.rounding = ROUND_DOWN
        outer.Emin = -9
        outer.Emax = 9
        outer.traps[Inexact] = True
        outer.flags[Inexact] = True
        flags_before = dict(outer.flags)
        traps_before = dict(outer.traps)
        settings_before = (
            outer.prec, outer.rounding, outer.Emin, outer.Emax,
            outer.capitals, outer.clamp,
        )

        actual = fixed_present_value(amount, periodic_rate=rate, periods=17)
        assert actual == expected
        assert dict(outer.flags) == flags_before
        assert dict(outer.traps) == traps_before
        assert (
            outer.prec, outer.rounding, outer.Emin, outer.Emax,
            outer.capitals, outer.clamp,
        ) == settings_before
        assert getcontext() is outer

    rates = [Decimal("0.03"), Decimal("0.07")]
    forward = [
        fixed_present_value(amount, periodic_rate=r, periods=2)
        for r in rates
    ]
    backward = [
        fixed_present_value(amount, periodic_rate=r, periods=2)
        for r in reversed(rates)
    ]
    assert forward == list(reversed(backward))
    assert amount == Decimal("1000")
    assert rates == [Decimal("0.03"), Decimal("0.07")]

    assert fixed_present_value(
        Decimal("125"), periodic_rate=Decimal("0.25"), periods=1
    ) == Decimal("100")
    assert fixed_present_value(
        amount, periodic_rate=Decimal("0"), periods=2
    ) == amount
    assert fixed_present_value(
        Decimal("0"), periodic_rate=rate, periods=2
    ) == Decimal("0")
    assert fixed_present_value(
        Decimal("900"), periodic_rate=Decimal("-0.10"), periods=1
    ) == Decimal("1000")

    # Preserve context flags even when a valid input causes overflow.
    with localcontext() as outer:
        flags_before = dict(outer.flags)
        try:
            fixed_present_value(
                amount, periodic_rate=Decimal("1e999999"), periods=2
            )
        except Overflow:
            pass
        else:
            raise AssertionError("Expected internal overflow")
        assert dict(outer.flags) == flags_before
        assert getcontext() is outer

    try:
        fixed_present_value(amount, periodic_rate=rate, periods=True)
    except TypeError:
        pass
    else:
        raise AssertionError("Expected bool rejection")

    try:
        fixed_present_value(amount, periodic_rate=Decimal("NaN"), periods=0)
    except ValueError:
        pass
    else:
        raise AssertionError("Expected non-finite rate rejection")


if __name__ == "__main__":
    results = doctest.testmod()
    if results.failed:
        raise SystemExit(1)
    run_checks()
    value = fixed_present_value(
        Decimal("125"), periodic_rate=Decimal("0.25"), periods=1
    )
    print(f"Present value: {value:.2f}")
    print(f"PASS: {results.attempted} doctests and reproducibility checks")
```


## 3.12.11 What the Lab Demonstrates

The fixed-policy function gives the same selected result under materially different ambient settings. It leaves the caller's flags and settings unchanged during successful arithmetic and a trapped overflow.

The rate scenarios are independent of evaluation order, and input values remain unchanged.

This supports a pure computational interface under the documented implementation policy. It is not a formal proof over every Python implementation, every possible input, concurrency behavior, or future code revision.

The caller-context test covers the same thread of execution. No cross-thread context-sharing mechanism is introduced.

## 3.12.12 Why a Fresh Context Matters

A module-global Context object can itself be mutated. Accepting a caller-owned Context without a clear ownership policy can introduce similar problems.

The lab constructs its policy within each invocation and enters a local context copy. That keeps mutable policy state from being shared between calls.

A larger system may prefer an explicit immutable policy object or a small set of named policies. Document their settings and version changes, and avoid silently changing precision or rounding for existing callers.

## 3.12.13 Reproducibility Beyond One Function

For a rerunnable financial result, retain enough evidence to reconstruct:

| Evidence | Why it matters |
|---|---|
| Exact input strings | Avoid reconstructing Decimal values through binary floats |
| Rate convention and period units | Preserve financial meaning |
| Valuation date and dataset identity | Identify the information used |
| Code revision | Reproduce the implementation |
| Numerical policy | Reproduce precision, rounding, limits, and traps |
| Runtime and dependency versions | Identify the execution environment |
| Quantization and reporting rules | Reconcile numeric and displayed results |
| Expected result and tolerance | Define what successful reproduction means |

Do not store secrets or sensitive raw records merely because a reproduction record is useful. Retain the necessary authorized evidence according to the surrounding application's data policy.

The lab contains fixed educational inputs and needs no external dataset.

## 3.12.14 Randomness, Time, and External Data

A simulation should receive an explicitly managed random generator or a documented random-state policy. A fixed seed alone does not preserve changing datasets, code, or all library behavior.

A valuation dependent on today's date should receive a selected valuation date rather than reading the clock deep inside arithmetic.

Read source data once at a documented boundary, identify its version, validate it, then pass the required values into calculation functions.

Later chapters develop simulation and data engineering in more detail. These principles establish the boundary without adding those systems to this lab.

## 3.12.15 Reproducibility Is Not Financial Validity

A fixed 40-digit result can still use the wrong rate or timeline. A reproducible implementation can preserve an incorrect formula.

Combine reproducibility checks with independent known values, domain tests, numerical analysis, and financial review. The one-period 25% example supplies a simple independently calculable check; scenario order alone cannot establish correctness.

Avoid caching results solely by amount and rate when the horizon, conventions, or numerical policy also affect the result. A cache must account for the complete relevant contract.

## 3.12.17 Troubleshooting Guide

| Symptom | Likely cause | Correction |
|---|---|---|
| Identical arguments produce different digits | Ambient context changed | Specify and isolate the numerical policy |
| Unexpected Inexact exception | Caller trap inherited | Set the intended trap policy explicitly |
| Later calculation observes new flags | Arithmetic used caller context | Isolate flags in a local context |
| Scenario order changes results | Shared state or mutation | Localize state and test order independence |
| Reproduction fails after an update | Code or dependency version changed | Record versions and review numerical compatibility |
| Localcontext still gives different behavior | Only selected settings overridden | Define all relevant settings |
| Repeated results remain wrong | Model or units are incorrect | Use independent financial checks |
| Reporting changes calculation behavior | I/O and arithmetic intertwined | Separate effects from the computation |

## 3.12.18 Key Takeaways

Pure computational interfaces make dependencies explicit and avoid changing caller-visible state. For Decimal arithmetic, the numerical context is part of that design.

Reproducibility also requires inputs, conventions, code, and environment evidence. Preserve those deliberately, and verify financial correctness separately.
