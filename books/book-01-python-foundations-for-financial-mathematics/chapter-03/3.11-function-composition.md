## 3.11.1 Purpose

Function composition connects the output of one operation to the input of another. For financial computing, the connection must preserve meaning as well as Python types.

A nominal annual rate can become an effective monthly rate, then a discount factor, then a present value. Every boundary must agree on rate convention, period units, currency, and numerical policy.

This section develops readable composition through nested calls, named intermediate values, and a wrapper function. Pure functions and reproducibility are developed further in Section 3.12.

## 3.11.2 Learning Objectives

You should be able to:

1. Explain f(g(x)) and its execution dependencies.
2. Build the same calculation with nested calls and named intermediate results.
3. Compose helpers without confusing rates, factors, and amounts.
4. Design an explicit wrapper with a documented public contract.
5. Test each component and the assembled calculation.
6. Keep validation, rounding, and reporting at deliberate boundaries.

## 3.11.3 Composition as Input and Output

For ordinary functions f and g, f(g(x)) first needs the result of g(x) before f can receive that argument.

Composition does not require a special library or a generic compose utility. Ordinary function calls are sufficient.

```python
from decimal import Decimal


def percentage_to_fraction(percentage: Decimal) -> Decimal:
    """Convert a prevalidated percentage number to its fractional form."""
    return percentage / Decimal("100")


def one_period_growth(periodic_rate: Decimal) -> Decimal:
    """Return one plus a prevalidated effective periodic rate."""
    return Decimal("1") + periodic_rate


growth = one_period_growth(percentage_to_fraction(Decimal("5")))
assert growth == Decimal("1.05")
```

The input 5 is explicitly a percentage number here. Elsewhere in this chapter, rate parameters receive fractional values such as 0.05. Conversion should occur once at a clearly named boundary.

These introductory helpers assume validated finite Decimal inputs. They demonstrate composition rather than a complete public validation contract.

## 3.11.4 Named Intermediate Values

The same calculation can be written as:

```python
percentage = Decimal("5")
periodic_rate = percentage_to_fraction(percentage)
growth = one_period_growth(periodic_rate)

assert growth == Decimal("1.05")
```

Named intermediates make it easier to inspect values, attach unit descriptions, and locate a failure. Nesting is useful for a short expression; named stages are often clearer when conventions change.

Prefer names such as monthly_rate, discount, and present_amount over temporary variables that hide the role of each quantity.

## 3.11.5 A Financial Composition Contract

Consider a nominal annual rate j, quoted as convertible m times per year, and an amount due after n matching compounding periods:

1. Convert the quotation: r = j/m.
2. Calculate a discount factor: d = 1/(1+r)^n.
3. Discount the amount: PV = future_amount × d.

| Stage | Input meaning | Output meaning |
|---|---|---|
| Nominal conversion | Annual nominal quotation and frequency | Effective rate per compounding period |
| Discounting | Effective rate and matching period count | Dimensionless factor from period n to 0 |
| Apply factor | Future amount and dimensionless multiplier | Period-0 amount in the same currency |

A Decimal output from one function is not automatically appropriate for every Decimal input in another function. Applying an annual effective rate where a monthly rate is expected can remain type-correct while producing the wrong valuation.

## 3.11.6 Periods Must Match the Converted Rate

For monthly compounding, n is a count of months. A two-year horizon must become 24 monthly periods before it enters this interface.

The wrapper in the lab accepts periods directly. It does not accept years and does not infer a calendar. A frequency of 12 establishes equal compounding periods for the named quotation; it does not implement actual day-count conventions.

At zero periods, the full contract is still validated before returning an equivalent amount.

## 3.11.7 Composition Order Changes Meaning

A fee applied to a balance before growth is not generally equivalent to a fee deducted afterward.

```python
balance = Decimal("1000")
growth = Decimal("1.05")
fee = Decimal("10")

fee_before_growth = (balance - fee) * growth
fee_after_growth = balance * growth - fee

assert fee_before_growth == Decimal("1039.50")
assert fee_after_growth == Decimal("1040")
```

The difference is the foregone growth on the fee. This is an independently defined timing illustration, not a universal fee policy.

Choose the financial sequence before arranging function calls. Equivalent-looking operations may represent different timelines.

## 3.11.8 Failure Propagation

If an inner calculation raises an exception, no normal result is available for the outer calculation on that path. Do not turn failed rate conversion into a zero rate or a failed discount calculation into a zero valuation.

A wrapper may translate errors when it can provide more useful domain context. It should preserve the failure meaning rather than hide the cause.

Argument expressions are evaluated before the called function body executes. Consequently, a nested factor calculation may execute before an outer function validates its monetary argument. Use explicit statements when the required validation order matters.

## 3.11.9 Keep Reporting Outside the Numeric Chain

A numeric result can be passed to formatting at the final reporting step. Formatting produces a string, which is not a Decimal amount for later valuation.

Do not compose a printing function into a calculation expecting a returned number. As Section 3.4 showed, printing and returning serve different purposes.

Likewise, early quantization is a modeling decision. Rounding a factor before multiplication changes the computation; formatting the final display does not change the numeric result.

## 3.11.10 Hands-On Lab — Compose a Nominal-Rate Valuation

Save this complete module as composition_lab.py. It uses Python 3.10 or later and only the standard library.

The helper contracts are local restatements of the policies developed in Sections 3.9–3.10 so this lab runs independently. They do not replace earlier canonical implementations.

```python
"""Compose nominal-rate conversion, discounting, and amount valuation."""

from decimal import Decimal, localcontext
import doctest


def _validate_amount(amount: Decimal) -> None:
    """Require a finite nonnegative Decimal monetary amount."""
    if not isinstance(amount, Decimal):
        raise TypeError("amount must be Decimal")
    if not amount.is_finite() or amount < 0:
        raise ValueError("amount must be finite and nonnegative")


def periodic_rate_from_nominal(
    nominal_annual_rate: Decimal,
    *,
    periods_per_year: int,
) -> Decimal:
    """Return j/m under a nominal annual convertible-rate convention.

    Require finite Decimal j and integer m in 1..366, excluding bool.
    The implied periodic rate must exceed -1. Use the active Decimal
    context; reject unsupported inputs and unusable computed rates.
    Arithmetic exceptions may propagate.

    >>> periodic_rate_from_nominal(Decimal("0.12"), periods_per_year=12) == Decimal("0.01")
    True
    """
    if not isinstance(nominal_annual_rate, Decimal):
        raise TypeError("nominal_annual_rate must be Decimal")
    if not nominal_annual_rate.is_finite():
        raise ValueError("nominal_annual_rate must be finite")
    if not isinstance(periods_per_year, int) or isinstance(periods_per_year, bool):
        raise TypeError("periods_per_year must be an integer excluding bool")
    if not 1 <= periods_per_year <= 366:
        raise ValueError("periods_per_year must be between 1 and 366")
    if nominal_annual_rate <= -Decimal(periods_per_year):
        raise ValueError("implied periodic rate must be greater than -1")
    rate = nominal_annual_rate / Decimal(periods_per_year)
    if not rate.is_finite() or rate <= Decimal("-1"):
        raise ArithmeticError("computed periodic rate is unusable")
    return rate


def discount_factor(
    periodic_rate: Decimal,
    *,
    periods: int,
) -> Decimal:
    """Return a factor from period n to 0 for constant effective rate r.

    Require finite Decimal r > -1 and integer n in 0..1000, not bool.
    Return a finite positive dimensionless Decimal using the active
    context. Reject unsupported inputs and unusable factors.
    Decimal arithmetic exceptions may propagate.

    >>> discount_factor(Decimal("0.25"), periods=1) == Decimal("0.8")
    True
    """
    if not isinstance(periodic_rate, Decimal):
        raise TypeError("periodic_rate must be Decimal")
    if not periodic_rate.is_finite() or periodic_rate <= Decimal("-1"):
        raise ValueError("periodic_rate must be finite and greater than -1")
    if not isinstance(periods, int) or isinstance(periods, bool):
        raise TypeError("periods must be an integer excluding bool")
    if not 0 <= periods <= 1000:
        raise ValueError("periods must be between 0 and 1000")
    growth = (Decimal("1") + periodic_rate) ** periods
    if not growth.is_finite() or growth <= 0:
        raise ArithmeticError("growth factor must be finite and positive")
    discount = Decimal("1") / growth
    if not discount.is_finite() or discount <= 0:
        raise ArithmeticError("discount factor must be finite and positive")
    return discount


def apply_factor(amount: Decimal, *, factor: Decimal) -> Decimal:
    """Multiply a finite nonnegative amount by a finite positive factor.

    Return a Decimal in the amount's currency. Do not reverse its sign
    or quantize it. Use the active context; arithmetic exceptions may
    propagate. Reject representation/domain errors and non-finite output.
    """
    _validate_amount(amount)
    if not isinstance(factor, Decimal):
        raise TypeError("factor must be Decimal")
    if not factor.is_finite() or factor <= 0:
        raise ValueError("factor must be finite and positive")
    result = amount * factor
    if not result.is_finite():
        raise ArithmeticError("computed amount must be finite")
    return result


def present_value_from_nominal(
    future_amount: Decimal,
    *,
    nominal_annual_rate: Decimal,
    periods_per_year: int,
    periods: int,
) -> Decimal:
    """Return the period-0 equivalent of one future amount.

    future_amount is a finite nonnegative Decimal due at the end of
    periods matching the quotation's compounding periods. The nominal
    annual rate is a finite Decimal convertible periods_per_year times
    yearly. Frequency is an integer 1..366; horizon is an integer
    0..1000. Boolean counts are excluded. Implied periodic rate exceeds -1.

    Validate the amount, convert the nominal quotation to j/m, compute
    the discount factor, and apply it. No intervening cash flows, fees,
    taxes, inflation adjustment, currency conversion, calendar handling,
    or conversion from effective annual rates is performed.

    Return a Decimal at period 0 in the original currency. Validate all
    stages at zero horizon. Apply the active Decimal context without
    explicit quantization. Do not mutate inputs or change context
    settings; arithmetic may set context flags. Finite underflow and
    rounding remain possible.

    Propagate TypeError/ValueError for unsupported inputs and arithmetic
    failures, including helper ArithmeticError guards. Financial
    convention compatibility beyond these checks remains the caller's
    responsibility.

    >>> present_value_from_nominal(Decimal("101"), nominal_annual_rate=Decimal("0.12"), periods_per_year=12, periods=1) == Decimal("100")
    True
    >>> present_value_from_nominal(Decimal("100"), nominal_annual_rate=Decimal("0"), periods_per_year=12, periods=24) == Decimal("100")
    True
    """
    _validate_amount(future_amount)
    periodic_rate = periodic_rate_from_nominal(
        nominal_annual_rate,
        periods_per_year=periods_per_year,
    )
    discount = discount_factor(periodic_rate, periods=periods)
    return apply_factor(future_amount, factor=discount)


def run_checks() -> None:
    """Verify components, assembled calculation, and rejection paths."""
    amount = Decimal("1126.825030131969720661201")
    nominal = Decimal("0.12")

    # Named stages and nested calls should agree under the same context.
    monthly = periodic_rate_from_nominal(nominal, periods_per_year=12)
    discount = discount_factor(monthly, periods=12)
    staged = apply_factor(amount, factor=discount)

    nested = apply_factor(
        amount,
        factor=discount_factor(
            periodic_rate_from_nominal(nominal, periods_per_year=12),
            periods=12,
        ),
    )
    wrapped = present_value_from_nominal(
        amount, nominal_annual_rate=nominal,
        periods_per_year=12, periods=12,
    )
    assert staged == nested == wrapped
    assert abs(wrapped - Decimal("1000")) <= Decimal("1e-20")

    # Independent known case: one period at 25% discounts 125 to 100.
    assert present_value_from_nominal(
        Decimal("125"), nominal_annual_rate=Decimal("0.25"),
        periods_per_year=1, periods=1,
    ) == Decimal("100")

    assert present_value_from_nominal(
        Decimal("0"), nominal_annual_rate=nominal,
        periods_per_year=12, periods=12,
    ) == Decimal("0")
    assert present_value_from_nominal(
        Decimal("100"), nominal_annual_rate=nominal,
        periods_per_year=12, periods=0,
    ) == Decimal("100")

    with localcontext() as context:
        context.prec = 40
        negative = present_value_from_nominal(
            Decimal("900"), nominal_annual_rate=Decimal("-0.10"),
            periods_per_year=1, periods=1,
        )
        assert abs(negative - Decimal("1000")) <= Decimal("1e-30")

    try:
        present_value_from_nominal(
            amount, nominal_annual_rate=nominal,
            periods_per_year=0, periods=0,
        )
    except ValueError:
        pass
    else:
        raise AssertionError("Expected frequency rejection at zero horizon")

    try:
        present_value_from_nominal(
            amount, nominal_annual_rate=Decimal("NaN"),
            periods_per_year=12, periods=0,
        )
    except ValueError:
        pass
    else:
        raise AssertionError("Expected non-finite quotation rejection")

    try:
        present_value_from_nominal(
            amount, nominal_annual_rate=nominal,
            periods_per_year=12, periods=True,
        )
    except TypeError:
        pass
    else:
        raise AssertionError("Expected bool horizon rejection")

    assert amount == Decimal("1126.825030131969720661201")
    assert nominal == Decimal("0.12")


if __name__ == "__main__":
    results = doctest.testmod()
    if results.failed:
        raise SystemExit(1)
    run_checks()
    value = present_value_from_nominal(
        Decimal("1126.825030131969720661201"),
        nominal_annual_rate=Decimal("0.12"),
        periods_per_year=12,
        periods=12,
    )
    print(f"Present value: {value:.2f}")
    print(f"PASS: {results.attempted} doctests and composition checks")
```

## 3.11.11 Why a Wrapper Helps

The wrapper exposes a complete user-facing operation: discount a future amount using a specific nominal quotation convention.

It delegates conversion and factor arithmetic, while documenting the overall timeline and exclusions. A caller can use one meaningful operation without reproducing the assembly at every call site.

The wrapper validates the monetary input before calculating rate stages. apply_factor also validates it because that helper is independently callable. This modest duplication keeps both public boundaries safe; it is not a reason to duplicate the underlying financial formulas.

## 3.11.12 Component Tests and Integration Tests

The nominal converter and discount helper need independent known-value checks. The wrapper also needs assembled behavior checks.

Agreement between nested, staged, and wrapped calculations verifies wiring for selected inputs. It does not independently establish the formula: all three forms share the same helpers.

The one-period 25% case adds independent evidence. The twelve-month example is independently specified as 1000 multiplied by 1.01 twelve times.

Use both component and assembled checks so a helper defect and a parameter-wiring defect have a chance to be detected.

## 3.11.13 Numerical Boundaries in a Chain

Each additional arithmetic operation can introduce rounding under the active context. Multiplying by a precomputed reciprocal can differ from direct division by a growth factor.

Do not require exact equality between algebraically equivalent implementations for every input. Choose tolerances based on the context, quantity scale, and intended use.

The lab's 1e-20 and 1e-30 tolerances apply to its selected small examples. They are not universal currency tolerances.

Finite factors and results are necessary safeguards, but they do not rule out underflow to zero in a final amount or loss of a tiny rate during conversion. Context control remains part of the numerical contract.

## 3.11.14 Composition and Side Effects

Small functions are easier to assemble when they return values and avoid surprising mutation. A function that reads changing global configuration or mutates a shared schedule may make order significant beyond the financial sequence.

The lab passes rates and horizons explicitly, uses immutable numeric inputs, and leaves reporting to its entry point. The active Decimal context remains a dependency.

Section 3.12 develops the distinction between pure functions, controlled numerical context, and reproducible calculations in more detail.

## 3.11.16 Troubleshooting Guide

| Symptom | Likely cause | Correction |
|---|---|---|
| Type-correct chain gives wrong value | Financial units or conventions disagree | Review meaning at each boundary |
| A stage receives None | Earlier function printed instead of returning | Return the computational result |
| Monthly valuation uses annual periods | Horizon not matched to converted rate | Use matching compounding-period counts |
| Error becomes a zero valuation | Failure hidden by fallback | Preserve explicit failure behavior |
| Nested expression is hard to investigate | Important stages unnamed | Use meaningful intermediate values |
| Staged calculation differs slightly from direct formula | Different rounding path | Review precision and tolerance |
| Components pass but wrapper fails | Arguments wired incorrectly | Test assembled known cases |
| Fee result differs by operation order | Timing contract differs | Specify sequence before implementation |

## 3.11.17 Key Takeaways

Composition connects financial operations through their returned values. The connections must preserve conventions, units, timing, and numerical policies.

Use readable stages and documented wrappers. Verify the components independently, then test the assembled behavior. Keep reporting and error handling from obscuring the numeric contract.
