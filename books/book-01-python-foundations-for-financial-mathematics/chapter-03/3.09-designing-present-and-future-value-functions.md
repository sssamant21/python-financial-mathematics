## 3.9.1 Purpose

This section combines parameters, return values, keyword arguments, scope, annotations, and financial docstrings into a pair of reusable valuation functions.

The goal is a clear interface for a single amount moving between period 0 and a specified future period. Annuities, multiple cash flows, term structures, and rate conversion require additional models and are developed later.

## 3.9.2 Learning Objectives

You should be able to:

1. Derive accumulation and discounting under a constant effective periodic rate.
2. Specify consistent present- and future-value interfaces.
3. Validate representations separately from financial domains.
4. Preserve valuation meaning and numerical policy.
5. Verify known values, boundaries, inverse relationships, and rejected inputs.
6. Explain why round-trip checks alone cannot prove correctness.

## 3.9.3 Start with the Timeline

Let P be an amount at period 0, F its equivalent amount at period n, r a constant effective rate per period, and n a nonnegative integer.

One period of accumulation gives P(1+r). Applying the same factor repeatedly gives:

FV = P × (1+r)^n.

For r > -1, the mathematical factor is positive. Solving for P gives:

PV = F / (1+r)^n.

The returned PV is valued at period 0. The returned FV is valued at period n. Both use the input amount's currency.

The two amounts are equivalents under the stated rate model. This does not establish that the chosen rate is appropriate for a particular security, risk, or investment decision.

## 3.9.4 Worked Example

A period-0 amount of 1000 growing at an effective annual rate of 5% for two annual periods becomes:

1000 × 1.05 × 1.05 = 1102.50.

Discounting that amount with the same rate and timeline gives:

1102.50 / 1.05^2 = 1000.

A future receipt of 1000 in two periods has a present value of approximately 907.03 at the same rate. It is a different question from accumulating 1000 today.

## 3.9.5 Define the Interface Before Coding

| Function | Amount parameter | Output interpretation |
|---|---|---|
| future_value | principal at period 0 | Accumulated amount at period n |
| present_value | future_amount at period n | Discounted equivalent at period 0 |

Both functions use required keyword-only periodic_rate and periods parameters. This extends the earlier examples with an explicit interface choice: callers must name the rate and horizon.

Use periodic_rate rather than an ambiguous rate when no annual convention is built in. The functions perform no nominal-to-effective or annual-to-monthly conversion.

The present-value function takes a nonnegative amount and returns a nonnegative equivalent when arithmetic succeeds. It does not automatically negate the result as some spreadsheet or cash-flow-sign APIs do.

## 3.9.6 Choose a Supported Domain

For these teaching functions:

- Monetary inputs are finite, nonnegative Decimal values.
- The rate is a finite Decimal strictly greater than -1.
- Periods is an integer from 0 through 1000, excluding bool.
- No intermediate cash flows, fees, taxes, currency conversion, or inflation adjustment are modeled.
- Fractional periods and calendar dates are not accepted.
- All inputs are validated even for zero periods or zero amounts.

Nonnegative amount inputs preserve the principal policy established earlier. Signed cash-flow valuation is a useful later extension, but it should be introduced deliberately rather than silently changing this contract.

The horizon cap is an operating policy, not a mathematical restriction on compound interest.

## 3.9.7 Negative and Zero Rates

Zero rate leaves an amount unchanged. Zero periods likewise preserves it under the supported domain.

A supported negative rate decreases FV and increases the PV of a fixed positive future amount. At a rate of -10%, one-period FV of 1000 is 900, and one-period PV of 900 is 1000.

The rate -1 is excluded because discounting divides by a zero growth factor for positive periods. Rates below -1 are outside this model's positive-factor domain.

The rule also rejects -1 at zero periods, making validation independent of whether the arithmetic could bypass a problematic value in a special case.

## 3.9.8 Numerical Design

The reference implementation uses the active Decimal context. It does not set global precision, quantize each operation to cents, or return formatted text.

Finite inputs alone do not guarantee a usable intermediate factor in finite-precision arithmetic. An extreme exponent can overflow; a very small positive mathematical factor can underflow to zero. The implementation checks that the computed factor is finite and positive before using it.

If a context trap raises a Decimal arithmetic exception, it propagates. If traps are disabled and a non-finite factor or result is produced, an explicit ArithmeticError prevents it from being returned silently.

An extreme final result may underflow to finite zero under the active context. A finiteness check cannot detect every loss of accuracy. Applications needing stricter guarantees must control context precision, exponent limits, traps, and acceptance tolerances.

## 3.9.9 Hands-On Lab — A Paired Valuation Interface

Save this complete module as pv_fv_lab.py. It requires Python 3.10 or later and only the standard library.

```python
"""Single-amount valuation with explicit periodic-rate contracts."""

from decimal import Decimal, localcontext
import doctest


def _validate_amount(amount: Decimal) -> None:
    """Require a finite, nonnegative Decimal monetary amount."""
    if not isinstance(amount, Decimal):
        raise TypeError("amount must be Decimal")
    if not amount.is_finite() or amount < 0:
        raise ValueError("amount must be finite and nonnegative")


def _growth_factor(periodic_rate: Decimal, periods: int) -> Decimal:
    """Validate rate and periods; return a finite positive factor."""
    if not isinstance(periodic_rate, Decimal):
        raise TypeError("periodic_rate must be Decimal")
    if not isinstance(periods, int) or isinstance(periods, bool):
        raise TypeError("periods must be an integer excluding bool")
    if not periodic_rate.is_finite() or periodic_rate <= Decimal("-1"):
        raise ValueError("periodic_rate must be finite and greater than -1")
    if not 0 <= periods <= 1000:
        raise ValueError("periods must be between 0 and 1000")

    factor = (Decimal("1") + periodic_rate) ** periods
    if not factor.is_finite() or factor <= 0:
        raise ArithmeticError("growth factor must be finite and positive")
    return factor


def future_value(
    principal: Decimal,
    *,
    periodic_rate: Decimal,
    periods: int,
) -> Decimal:
    """Return a period-0 principal's amount at the end of periods.

    principal must be a finite nonnegative Decimal. periodic_rate must
    be a finite Decimal effective rate per matching period, greater
    than -1. periods must be an integer from 0 through 1000, not bool.

    Compute principal * (1 + periodic_rate) ** periods. Assume one
    constant rate and no intermediate cash flows, taxes, fees, inflation
    adjustment, currency conversion, or rate conversion. Return a
    Decimal in the principal's currency; do not reverse its sign.

    Use the active Decimal context with no explicit quantization.
    Validate all arguments even for zero periods or zero principal.
    Do not mutate inputs or change context settings; arithmetic may
    set context signal flags.

    Raise TypeError for unsupported representations and ValueError for
    unsupported values. Decimal arithmetic exceptions may propagate.
    Raise ArithmeticError for an unusable factor or non-finite result.
    Finite underflow and other accuracy loss remain context-dependent.

    >>> future_value(Decimal("1000"), periodic_rate=Decimal("0.05"), periods=2) == Decimal("1102.50")
    True
    >>> future_value(Decimal("1000"), periodic_rate=Decimal("0"), periods=2) == Decimal("1000")
    True
    """
    _validate_amount(principal)
    factor = _growth_factor(periodic_rate, periods)
    result = principal * factor
    if not result.is_finite():
        raise ArithmeticError("future value must be finite")
    return result


def present_value(
    future_amount: Decimal,
    *,
    periodic_rate: Decimal,
    periods: int,
) -> Decimal:
    """Return a future amount's discounted equivalent at period 0.

    future_amount must be a finite nonnegative Decimal observed at the
    end of periods. Rate and period domains match future_value.

    Compute future_amount / (1 + periodic_rate) ** periods using a
    constant effective periodic rate and matching period count.
    Return a Decimal in the original currency without sign reversal.
    No intermediate cash flows, taxes, fees, currency conversion,
    inflation adjustment, or rate conversion are modeled.

    Use the active Decimal context with no explicit quantization.
    Validate all inputs even for zero periods or zero amount.
    Do not mutate inputs or change context settings; arithmetic may
    set context signal flags.

    Raise TypeError for unsupported representations and ValueError for
    unsupported values. Decimal arithmetic exceptions may propagate.
    Raise ArithmeticError for an unusable factor or non-finite result.
    Finite underflow and other accuracy loss remain context-dependent.

    >>> present_value(Decimal("1102.50"), periodic_rate=Decimal("0.05"), periods=2) == Decimal("1000")
    True
    >>> present_value(Decimal("900"), periodic_rate=Decimal("-0.10"), periods=1) == Decimal("1000")
    True
    """
    _validate_amount(future_amount)
    factor = _growth_factor(periodic_rate, periods)
    result = future_amount / factor
    if not result.is_finite():
        raise ArithmeticError("present value must be finite")
    return result


def run_checks() -> None:
    """Verify known values, boundaries, inverse behavior, and rejection."""
    principal = Decimal("1000")
    rate = Decimal("0.05")

    fv = future_value(principal, periodic_rate=rate, periods=2)
    assert fv == Decimal("1102.50")
    assert present_value(fv, periodic_rate=rate, periods=2) == principal

    for valuation in (future_value, present_value):
        assert valuation(principal, periodic_rate=rate, periods=0) == principal
        assert valuation(principal, periodic_rate=Decimal("0"), periods=2) == principal
        assert valuation(Decimal("0"), periodic_rate=rate, periods=2) == Decimal("0")

    assert future_value(
        principal, periodic_rate=Decimal("-0.10"), periods=1
    ) == Decimal("900")
    assert present_value(
        Decimal("900"), periodic_rate=Decimal("-0.10"), periods=1
    ) == principal

    # Nonterminating decimal division uses a documented local tolerance.
    with localcontext() as context:
        context.prec = 40
        source = Decimal("1234.56")
        future = future_value(
            source, periodic_rate=Decimal("0.037"), periods=17
        )
        recovered = present_value(
            future, periodic_rate=Decimal("0.037"), periods=17
        )
        assert abs(recovered - source) <= Decimal("1e-30")

    # Wrong representations are rejected at runtime, even with type hints.
    for valuation in (future_value, present_value):
        try:
            valuation(principal, periodic_rate=rate, periods=True)
        except TypeError:
            pass
        else:
            raise AssertionError("Expected bool rejection")

        try:
            valuation(principal, periodic_rate=Decimal("NaN"), periods=0)
        except ValueError:
            pass
        else:
            raise AssertionError("Expected non-finite-rate rejection")

        try:
            valuation(Decimal("-1"), periodic_rate=rate, periods=2)
        except ValueError:
            pass
        else:
            raise AssertionError("Expected negative-amount rejection")

        try:
            valuation(principal, periodic_rate=Decimal("-1"), periods=2)
        except ValueError:
            pass
        else:
            raise AssertionError("Expected invalid-rate rejection")

        try:
            valuation(principal, periodic_rate=rate, periods=1001)
        except ValueError:
            pass
        else:
            raise AssertionError("Expected horizon rejection")

    # Verify broad directional behavior for a fixed positive amount.
    assert future_value(
        principal, periodic_rate=Decimal("0.06"), periods=2
    ) > future_value(principal, periodic_rate=rate, periods=2)
    assert present_value(
        principal, periodic_rate=Decimal("0.06"), periods=2
    ) < present_value(principal, periodic_rate=rate, periods=2)


if __name__ == "__main__":
    results = doctest.testmod()
    if results.failed:
        raise SystemExit(1)
    run_checks()
    fv = future_value(
        Decimal("1000"), periodic_rate=Decimal("0.05"), periods=2
    )
    pv = present_value(
        fv, periodic_rate=Decimal("0.05"), periods=2
    )
    print(f"Future value: {fv:.2f}")
    print(f"Recovered present value: {pv:.2f}")
    print(f"PASS: {results.attempted} doctests and valuation checks")
```

## 3.9.10 Why Share Validation?

Both public functions require the same rate and horizon contract. A small internal helper keeps those rules aligned.

The leading underscore marks an internal-use convention. It does not prevent someone from calling the helper.

The helper here also computes a factor to keep this lab self-contained. Section 3.10 develops reusable rate and discounting functions more explicitly.

Keep validation ownership clear. If a future change permits signed amounts in one function, revise its own contract and tests rather than weakening shared checks without review.

## 3.9.11 What the Verification Establishes

The lab combines several forms of evidence:

| Check | Purpose |
|---|---|
| FV of 1000 at 5% for two periods | Independently calculable known value |
| PV of 1102.50 under the same timeline | Known discounted value |
| Zero amount, rate, and horizon | Boundary behavior |
| Supported negative rate | Positive-factor domain behavior |
| Round trip at controlled precision | Selected inverse consistency |
| Invalid inputs | Failure contract |
| Rate-direction checks | Selected qualitative financial behavior |
| Doctests | Executable documentation |

Round-trip consistency is necessary evidence but insufficient by itself. Two functions containing the same mistaken factor can reverse each other while both compute the wrong valuation.

Known values and independently reasoned assumptions therefore remain essential.

## 3.9.12 Tolerances and Rounding

The exact two-period example permits exact equality at the ordinary context. More general decimal division can require a tolerance.

The lab's absolute tolerance of 1e-30 is chosen for a small example at 40-digit precision. It is not a universal currency tolerance. Choose tolerances based on quantity scale, operation, context, and the use of the result.

Do not round both sides to cents merely to hide a numerical discrepancy. Separate arithmetic accuracy from business quantization and display requirements.

The localcontext block restores the surrounding context after the numerical experiment; it does not globally change the reader's arithmetic policy.

## 3.9.13 Interface Compatibility with Earlier Examples

Earlier sections allowed positional rate and period arguments to teach ordinary calls. This section deliberately requires those two inputs by keyword.

A caller migrating earlier code must replace a call such as future_value(principal, rate, periods) with named rate and period arguments.

Changing parameter kinds in a public library is a compatibility change. In this educational sequence, the new self-contained lab demonstrates the design explicitly; it does not silently modify earlier canonical examples.

## 3.9.14 Extending the Model Deliberately

Before adding additional capabilities, define their contracts:

- Multiple dated cash flows need timing for every amount.
- Nominal annual rates need an explicit compounding frequency.
- Fractional periods need a convention for how accrual works.
- Signed cash flows need an explicit investor or borrower perspective.
- Transaction rounding needs a documented boundary and mode.
- Currency conversion needs a conversion rate, direction, and valuation convention.
- Term structures need period-specific discount factors.

Adding a parameter without settling these questions can make a larger function less reliable.

## 3.9.16 Troubleshooting Guide

| Symptom | Likely cause | Correction |
|---|---|---|
| PV increases at a higher positive discount rate | Wrong direction or formula | Divide by the factor |
| FV is far too large | Percent entered as 5 rather than 0.05 | Enforce input convention at conversion boundary |
| Annual and monthly results disagree | Rate/period mismatch | Convert conventions explicitly |
| Invalid inputs accepted at zero horizon | Early return before validation | Validate the full contract first |
| Round trip passes but known value fails | Shared formula error | Use independently derived known values |
| Decimal exception occurs | Context limits or trapped signals | Inspect numerical policy and input scale |
| Negative spreadsheet value differs from this API | Cash-flow-sign convention mismatch | Compare documented sign contracts |
| Positional call fails | Rate and periods are keyword-only | Name both arguments |

## 3.9.17 Key Takeaways

Present- and future-value functions need more than correct algebra. Their interfaces should expose rate conventions, matching periods, valuation time, signs, and supported inputs.

Use independent known values alongside inverse and boundary checks. Keep numerical precision, currency quantization, and display formatting separate.
