## Purpose

Chapter 2 introduced control flow: conditions, loops, validation rules, stopping rules, scenario processing, and explicit financial state transitions. As financial models grow, repeated calculations become harder to maintain, test, review, and reuse. Python functions allow a calculation or operation to be given a meaningful name and invoked whenever needed.

```python
from decimal import Decimal

def future_value(present_value, rate, periods):
    return present_value * (Decimal("1") + rate) ** periods

value = future_value(Decimal("10000"), Decimal("0.05"), 10)
```

Defining a Python function creates the function and binds its name. Statements in its body execute when the function is called.

> **A financial function should make a model easier to reuse without making its assumptions harder to understand.**

## From Formula to Reusable Component

For periodic compound accumulation:

\[
FV = PV(1+r)^n
\]

where `r` is the effective rate per modeled period and `n` is the number of corresponding periods. Rate and period frequency must agree.

A reusable implementation centralizes the relationship and reduces duplicated logic, maintenance risk, review effort, and accidental inconsistency.

## Abstraction and Readability

A call such as:

```python
future_value(Decimal("10000"), Decimal("0.05"), 10)
```

allows the caller to reason in financial terms rather than repeatedly rewriting the formula. Abstraction should follow understanding of the underlying mathematics.

Meaningful names such as `present_value`, `future_value`, `discount_factor`, `loan_payment`, `portfolio_return`, and `bond_price` expose financial intent.

## Calculation Versus Orchestration

A reusable state transition can be separated from scenario and time orchestration:

```python
def next_balance(balance, rate, contribution):
    return balance * (Decimal("1") + rate) + contribution
```

The function represents the financial state transition; loops and conditions represent model orchestration.

## Financial Assumptions

A future-value function can still depend on assumptions including a constant effective rate per modeled period, matching rate/period units, no intermediate cash flows, and a particular compounding convention. Functions provide a place to define, document, validate, and test assumptions; they do not eliminate them.

A function name is not a complete financial specification. `future_value(...)` alone does not establish simple versus compound accumulation, discrete versus continuous compounding, nominal versus effective rates, period frequency, timing conventions, or adjustments such as taxes and fees.

> **Function names communicate intent, but the implementation and documented assumptions define the model.**

## Testability and Invariants

Centralized financial logic is easier to verify. Illustrative invariants include:

```python
assert future_value(Decimal("1000"), Decimal("0"), 10) == Decimal("1000")
assert future_value(Decimal("1000"), Decimal("0.05"), 0) == Decimal("1000")
```

These follow from `FV(PV,0,n)=PV` and `FV(PV,r,0)=PV`. Formal testing architecture is developed in Section 3.13.

## Reproducibility

Functions support reproducibility by reducing independent reimplementation of the same calculation. They do not guarantee reproducibility, which can also depend on input data, assumptions, numerical representation, rounding and quantization policy, configuration, software versions, and execution environment.

## Numerical Policy

Financial functions should preserve the distinction:

```text
input representation
        ↓
internal arithmetic
        ↓
optional business quantization
        ↓
presentation formatting
```

A computational function should generally return a numeric value rather than a formatted string when downstream calculations may use the result. `Decimal` representation does not imply unlimited precision; decimal arithmetic operates under a context controlling precision and rounding.

## Contract Boundaries

A financial function contract should make the following dimensions understandable:

- inputs,
- financial interpretation,
- units,
- timing convention,
- supported domain,
- implemented relationship,
- numerical policy,
- output semantics,
- failure behavior.

Validation should occur at the appropriate system boundary. Public functions may enforce their own contract; trusted internal functions may receive values already validated by an external boundary.

> **A financial function should define the assumptions required by its contract and enforce them at the appropriate system boundary.**

## Error Localization and Auditability

Meaningful function boundaries allow calculations such as rate conversion, discount factors, present values, and aggregation to be inspected independently. This improves debugging and creates smaller review units. Functions can support auditability, but complete auditability also depends on documentation, inputs, configuration, versioning, execution records, and other controls.

## Small Functions and Composition

A small function can represent a meaningful financial relationship:

```python
def discount_factor(rate, period):
    return Decimal("1") / (Decimal("1") + rate) ** period


def present_value(cash_flow, rate, period):
    return cash_flow * discount_factor(rate, period)
```

with:

\[
DF_t=\frac{1}{(1+r)^t}
\]

and:

\[
PV_t=CF_t\times DF_t.
\]

Here the effective discount rate and modeled period use matching units. Function composition is treated directly in Section 3.11.

## Clear Responsibilities

Avoid combining unrelated responsibilities such as input acquisition, calculation, currency formatting, persistence, and notification into one function unless that combined responsibility is intentional. Separating financial calculation from presentation improves reuse and testing.

## Scenario Analysis

When a financial function is applied across scenarios, the scenario loop determines which assumptions are evaluated while the function determines how the financial quantity is calculated. Reusing a function across scenarios does not turn scenarios into forecasts or probabilities.

## Pure Computation

Functions whose intended results depend only on explicit inputs and which do not modify external state are especially easy to reason about. This supports testing, reproducibility, debugging, composition, and review. Pure functions are treated directly in Section 3.12.

## Reusability Does Not Guarantee Correctness

A reusable function can still implement the wrong formula, assumptions, domain, timing convention, or numerical policy.

```text
reusability
    ≠
correctness
```

Functions make logic easier to centralize, test, document, and review; correctness still has to be established.

## Financial Understanding Remains Essential

A strong workflow is:

```text
understand financial relationship
        ↓
understand assumptions
        ↓
understand function contract
        ↓
validate inputs
        ↓
execute function
        ↓
verify or reconcile result
        ↓

```

Functions make financial reasoning more manageable; they do not replace it.

## When to Create a Function

A function is especially useful when a calculation is repeated, an operation has clear financial meaning, logic requires independent testing, assumptions need documentation, implementation should be isolated for review, or abstraction makes the larger model easier to understand. Not every statement needs to become a function; the objective is clear model structure rather than the maximum number of functions.

## Common Design Mistakes

Common mistakes include copying financial formulas throughout a program, mixing calculation and presentation, hiding assumptions, overloading one function with unrelated responsibilities, assuming reuse means correctness, using ambiguous names, mixing rate and period units, and hiding timing conventions.

## Production Perspective

Production financial functions may eventually require documented assumptions, type expectations, input validation, numerical policy, known-value tests, boundary tests, invariant tests, explicit failure behavior, version control, and review. The exact architecture depends on the system.

## Key Takeaways

Functions reduce duplicated financial logic, expose intent, create useful abstraction and review boundaries, and support testing and reproducibility. Financial assumptions remain necessary. Rate and period units must agree. Function names do not replace financial specifications. Internal arithmetic, business quantization, and display formatting are distinct. A useful financial function has an understandable contract, including timing and numerical policy. Reusability does not imply correctness, and functions do not replace understanding of financial mathematics.
