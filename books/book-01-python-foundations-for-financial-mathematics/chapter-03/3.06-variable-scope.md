## 3.6.1 Purpose

A financial function should make it clear where its inputs come from and which state it can change. Scope determines which binding a name refers to; it does not determine whether the underlying object is shared or financially appropriate.

This section explains local names, enclosing function scopes, module globals, built-ins, shadowing, and common name-resolution failures. It also connects scope to scenario isolation and reproducibility.

Examples use ordinary Python functions. Classes, annotation scopes, dynamic execution, and asynchronous behavior require additional rules and are outside this section's introductory scope.

## 3.6.2 Learning Objectives

After completing this section, you should be able to:

1. Identify local, enclosing, global, and built-in name lookups.
2. Explain why a parameter can have the same spelling as a caller's variable.
3. Diagnose NameError and UnboundLocalError.
4. Distinguish rebinding a name from mutating an object.
5. Recognize global and nonlocal declarations.
6. Avoid hidden rate dependencies and cross-scenario state contamination.
7. Verify scope behavior with a complete runnable lab.

## 3.6.3 Names, Objects, and Namespaces

A name refers to an object. A namespace associates names with objects. Different namespaces can contain the same spelling without those names being the same binding.

For example, a module may have a name balance while a function invocation has its own local balance parameter. Both may initially refer to the same Decimal object, yet rebinding one name does not automatically rebind the other.

Scope concerns name visibility and resolution. Object identity and mutability are related but separate concerns.

## 3.6.4 Parameters and Local Variables

```python
from decimal import Decimal


def next_balance(balance, periodic_rate):
    interest = balance * periodic_rate
    ending_balance = balance + interest
    return ending_balance


balance = Decimal("1000")
result = next_balance(balance, Decimal("0.05"))

assert result == Decimal("1050")
assert balance == Decimal("1000")
```

The parameters balance and periodic_rate, and the assigned names interest and ending_balance, are local to this invocation.

The function models one period's growth at an effective periodic rate, with no contributions, withdrawals, taxes, or fees. All amounts use the same currency. These teaching examples assume validated finite Decimal inputs unless validation is shown explicitly.

## 3.6.5 Rebinding a Parameter Does Not Rebind the Caller

```python
def replace_local_balance(balance):
    balance = Decimal("0")
    return balance


account_balance = Decimal("1000")
replacement = replace_local_balance(account_balance)

assert replacement == Decimal("0")
assert account_balance == Decimal("1000")
```

The assignment changes the local name's binding. It does not reach into the caller and assign to account_balance.

Returning the new amount lets the caller explicitly choose whether to update its own binding:

```python
account_balance = replace_local_balance(account_balance)
assert account_balance == Decimal("0")
```

## 3.6.6 Local Names Are Not Caller Variables

A local name is not automatically installed in the caller's namespace:

```python
def compute_interest(balance, periodic_rate):
    section36_interest = balance * periodic_rate
    return section36_interest


assert compute_interest(Decimal("1000"), Decimal("0.05")) == Decimal("50")

try:
    section36_interest
except NameError:
    pass
else:
    raise AssertionError("Function-local name unexpectedly visible")
```

Run this demonstration in a fresh script. Interactive sessions can retain an unrelated name from an earlier cell or command and mask the intended failure.

A returned object may remain alive after the function returns. Closures can also retain access to enclosing bindings. Avoid assuming that every object created locally disappears immediately on return.

## 3.6.7 The LEGB Lookup Guide

For ordinary bare-name references in the nested functions used here, a useful lookup guide is Local → Enclosing function scopes → Global module scope → Built-ins.

| Lookup location | Example |
|---|---|
| Local | A parameter named periodic_rate |
| Enclosing function | A rate parameter captured by an inner function |
| Global | A name defined at module level |
| Built-ins | len, sum, or ValueError |

LEGB is an instructional guide rather than the complete rule for every Python construct. Assignment, global, nonlocal, class bodies, comprehensions, and newer annotation-related constructs need their specific rules.

## 3.6.8 Reading a Module Global

```python
MODEL_RATE = Decimal("0.05")


def balance_using_module_rate(balance):
    return balance * (Decimal("1") + MODEL_RATE)


assert balance_using_module_rate(Decimal("1000")) == Decimal("1050")

MODEL_RATE = Decimal("0.10")

assert balance_using_module_rate(Decimal("1000")) == Decimal("1100")
```

The function resolves MODEL_RATE when it executes. The same explicit argument now produces a different answer because another dependency changed.

Uppercase naming signals a constant by convention; Python does not enforce immutability of the binding.

A global belongs to the module where the function was defined. It does not mean one universal namespace shared automatically by every module or process.

## 3.6.9 Make Changing Financial Inputs Explicit

```python
def balance_with_explicit_rate(balance, periodic_rate):
    return balance * (Decimal("1") + periodic_rate)


assert balance_with_explicit_rate(
    Decimal("1000"), Decimal("0.05")
) == Decimal("1050")
assert balance_with_explicit_rate(
    Decimal("1000"), Decimal("0.10")
) == Decimal("1100")
```

This interface makes the rate dependency visible to callers and tests. A configuration layer can still choose a rate, but it should pass the selected value to the calculation.

Explicit arguments do not alone guarantee full reproducibility: Decimal context, input data, timing conventions, and other dependencies also need control.

## 3.6.10 Shadowing

A nearer binding can hide a name with the same spelling in an outer scope:

```python
periodic_rate = Decimal("0.10")


def local_rate_example(balance):
    periodic_rate = Decimal("0.05")
    return balance * (Decimal("1") + periodic_rate)


assert local_rate_example(Decimal("1000")) == Decimal("1050")
assert periodic_rate == Decimal("0.10")
```

This is legal. It can become confusing when a reviewer assumes that the outer rate governs the calculation.

Avoid assigning financial amounts to built-in names such as sum, list, or input. Such shadowing can make later calls fail because the name now refers to an amount or container rather than the built-in function.

## 3.6.11 UnboundLocalError

A name assigned within a function is normally treated as local throughout that function's body, even before the assignment executes.

This intentional defect demonstrates the consequence:

```python
scenario_rate = Decimal("0.05")


def broken_rate_adjustment():
    scenario_rate = scenario_rate + Decimal("0.01")
    return scenario_rate


try:
    broken_rate_adjustment()
except UnboundLocalError:
    pass
else:
    raise AssertionError("Expected UnboundLocalError")
```

The right side attempts to read the local scenario_rate before it has a value. Python does not fall back to the module binding just because that local read fails.

Prefer an explicit input and returned result:

```python
def adjusted_rate(periodic_rate, spread):
    return periodic_rate + spread


assert adjusted_rate(
    Decimal("0.05"), Decimal("0.01")
) == Decimal("0.06")
assert scenario_rate == Decimal("0.05")
```

The spread uses the same rate convention and period units. Adding spreads is an assumption of this simple scenario transformation, not a general conversion between rate conventions.

## 3.6.12 Conditional Assignment Can Leave a Local Unbound

```python
def incomplete_gain(starting_amount, ending_amount):
    if ending_amount > starting_amount:
        gain = ending_amount - starting_amount
    return gain


try:
    incomplete_gain(Decimal("100"), Decimal("100"))
except UnboundLocalError:
    pass
else:
    raise AssertionError("Expected unbound local")
```

The name is local, but the equal-balance path never binds it. For signed gain, calculate it unconditionally:

```python
def signed_gain(starting_amount, ending_amount):
    gain = ending_amount - starting_amount
    return gain


assert signed_gain(Decimal("100"), Decimal("100")) == Decimal("0")
assert signed_gain(Decimal("100"), Decimal("90")) == Decimal("-10")
```

This amount comparison assumes no intervening cash flows.

## 3.6.13 If and For Do Not Create Separate Function-Local Scopes

```python
def sum_cash_flows(cash_flows):
    total = Decimal("0")
    for cash_flow in cash_flows:
        total += cash_flow
    return total


assert sum_cash_flows([]) == Decimal("0")
assert sum_cash_flows(
    [Decimal("100"), Decimal("-20")]
) == Decimal("80")
```

The loop reuses bindings in the surrounding function scope. A loop target may remain available after a nonempty loop, but it will not be newly bound if the iterable is empty.

Initialize accumulated results before a loop. Do not rely on the last loop item existing when the input might be empty.

Comprehensions have their own scope behavior in modern Python and are developed with data structures later.

## 3.6.14 Global Rebinding

The global declaration directs assignments to the defining module's namespace:

```python
active_rate = Decimal("0.05")


def set_active_rate(new_rate):
    global active_rate
    active_rate = new_rate


set_active_rate(Decimal("0.07"))
assert active_rate == Decimal("0.07")
```

Declare the name before using or assigning it in that function. A declaration does not validate the replacement or coordinate simultaneous callers.

Module-level mutable configuration may be appropriate in some application designs, but using it inside valuation functions creates dependencies that must be managed. Passing scenario inputs explicitly usually makes educational financial models easier to review and isolate.

## 3.6.15 Enclosing Functions and Closures

```python
def make_growth_function(periodic_rate):
    def grow(balance):
        return balance * (Decimal("1") + periodic_rate)
    return grow


grow_at_five_percent = make_growth_function(Decimal("0.05"))
grow_at_ten_percent = make_growth_function(Decimal("0.10"))

assert grow_at_five_percent(Decimal("1000")) == Decimal("1050")
assert grow_at_ten_percent(Decimal("1000")) == Decimal("1100")
```

The inner function accesses periodic_rate from its enclosing function scope. Separate factory calls establish separate enclosing bindings.

This returned function is called a closure. It makes the selected rate persistent without requiring a module-global rate.

## 3.6.16 Nonlocal Rebinding

The nonlocal declaration permits rebinding an existing name in a nearest enclosing function scope:

```python
def make_running_total():
    total = Decimal("0")

    def add(amount):
        nonlocal total
        total += amount
        return total

    return add


add_to_total = make_running_total()

assert add_to_total(Decimal("100")) == Decimal("100")
assert add_to_total(Decimal("-20")) == Decimal("80")
```

Here each call depends on previous calls. This stateful accumulator is an educational scope example, not a thread-safe ledger.

Nonlocal requires an existing binding in an enclosing function scope. It cannot create an arbitrary outer name or target a module-global binding.

## 3.6.17 Closure Lookup Is Not Automatically a Frozen Snapshot

Closures resolve captured names when called. Functions created in a loop can therefore share the same later binding:

```python
def make_shared_rate_functions(rates):
    functions = []
    for rate in rates:
        def grow(balance):
            return balance * (Decimal("1") + rate)
        functions.append(grow)
    return functions


shared = make_shared_rate_functions(
    [Decimal("0.03"), Decimal("0.07")]
)
assert shared[0](Decimal("1000")) == Decimal("1070")
assert shared[1](Decimal("1000")) == Decimal("1070")
```

Use the earlier factory to establish separate bindings:

```python
separate = [
    make_growth_function(Decimal("0.03")),
    make_growth_function(Decimal("0.07")),
]

assert separate[0](Decimal("1000")) == Decimal("1030")
assert separate[1](Decimal("1000")) == Decimal("1070")
```

A default argument evaluated during each function definition can also capture a chosen object, as Section 3.5 explains. The factory is useful here because it exposes the rate-selection step clearly.

## 3.6.18 Mutation Is Separate from Scope

```python
def append_observation(observations, amount):
    observations.append(amount)


observations = []
append_observation(observations, Decimal("100"))

assert observations == [Decimal("100")]
```

The parameter is local, but the list object is shared. No global or nonlocal declaration is needed to mutate the list through the local reference.

A local dictionary reference can likewise mutate a shared configuration dictionary. Scope isolation does not automatically provide object isolation.

## 3.6.19 Hands-On Lab — Independent Financial Scenarios

Save this complete program as variable_scope_lab.py. It uses only the standard library.

The model compounds a period-0 principal at a constant effective rate for matching periods, without intermediate cash flows. It returns a Decimal in the original currency and does not explicitly quantize to cents. Arithmetic uses the active Decimal context.

The supported domain is finite nonnegative Decimal principal, finite Decimal rate greater than -1, and integer periods from 0 to 1000, excluding bool. Arithmetic overflow and other Decimal signals remain context-dependent.

```python
from decimal import Decimal


def project_balance(principal, periodic_rate, periods):
    if not isinstance(principal, Decimal):
        raise TypeError("principal must be Decimal")
    if not isinstance(periodic_rate, Decimal):
        raise TypeError("periodic_rate must be Decimal")
    if not isinstance(periods, int) or isinstance(periods, bool):
        raise TypeError("periods must be an integer excluding bool")
    if not principal.is_finite() or principal < 0:
        raise ValueError("principal must be finite and nonnegative")
    if not periodic_rate.is_finite() or periodic_rate <= Decimal("-1"):
        raise ValueError("periodic_rate must be finite and greater than -1")
    if not 0 <= periods <= 1000:
        raise ValueError("periods must be between 0 and 1000")

    balance = principal
    for period in range(periods):
        balance *= Decimal("1") + periodic_rate
    return balance


def make_projector(periodic_rate):
    def project(principal, periods):
        return project_balance(principal, periodic_rate, periods)
    return project


principal = Decimal("1000")
rates = [Decimal("0.03"), Decimal("0.07")]

first_results = [
    project_balance(principal, rate, 2)
    for rate in rates
]
reverse_results = [
    project_balance(principal, rate, 2)
    for rate in reversed(rates)
]

assert first_results == [Decimal("1060.90"), Decimal("1144.90")]
assert reverse_results == list(reversed(first_results))
assert principal == Decimal("1000")
assert rates == [Decimal("0.03"), Decimal("0.07")]

low_projector = make_projector(rates[0])
high_projector = make_projector(rates[1])
assert low_projector(principal, 2) == first_results[0]
assert high_projector(principal, 2) == first_results[1]

assert project_balance(principal, Decimal("0"), 2) == principal
assert project_balance(principal, Decimal("0.05"), 0) == principal
assert project_balance(principal, Decimal("-0.10"), 1) == Decimal("900")
assert project_balance(Decimal("0"), Decimal("0.05"), 2) == Decimal("0")

module_rate = Decimal("0.05")


def broken_adjustment():
    module_rate += Decimal("0.01")
    return module_rate


try:
    broken_adjustment()
except UnboundLocalError:
    pass
else:
    raise AssertionError("Expected UnboundLocalError")

assert module_rate == Decimal("0.05")

invalid_cases = [
    (1000, Decimal("0.05"), 2, TypeError),
    (principal, 0.05, 2, TypeError),
    (principal, Decimal("0.05"), True, TypeError),
    (principal, Decimal("0.05"), 1.5, TypeError),
    (Decimal("-1"), Decimal("0.05"), 2, ValueError),
    (Decimal("NaN"), Decimal("0.05"), 2, ValueError),
    (principal, Decimal("Infinity"), 2, ValueError),
    (principal, Decimal("-1"), 2, ValueError),
    (principal, Decimal("0.05"), -1, ValueError),
    (principal, Decimal("0.05"), 1001, ValueError),
]

for amount, rate, periods, expected_error in invalid_cases:
    try:
        project_balance(amount, rate, periods)
    except expected_error:
        pass
    else:
        raise AssertionError("Expected input rejection")

print(f"3% scenario: {first_results[0]:.2f}")
print(f"7% scenario: {first_results[1]:.2f}")
print(f"Original principal: {principal:.2f}")
print("PASS: variable scope and scenario isolation checks")
```

Run on Windows:

```powershell
py variable_scope_lab.py
```

Run on macOS or Linux:

```bash
python3 variable_scope_lab.py
```

Expected output:

```text
3% scenario: 1060.90
7% scenario: 1144.90
Original principal: 1000.00
PASS: variable scope and scenario isolation checks
```

The lab checks order independence for these scenarios, separate captured rates, unchanged inputs, boundary cases, and a deliberate local-binding failure. It does not establish concurrency safety or production model certification.

Run normally without -O so the instructional assertions execute. External input validation uses exceptions.

## 3.6.21 Troubleshooting Guide

| Symptom | Likely explanation | Corrective action |
|---|---|---|
| NameError | No accessible binding | Check spelling and intended namespace |
| UnboundLocalError | Function-local name read before binding | Initialize every path or accept an explicit input |
| Same arguments produce different valuations | Hidden dependency changed | Pass and record effective inputs |
| Every generated function uses the final rate | Closures share an enclosing binding | Create independent factory invocations |
| Caller data changes unexpectedly | Shared mutable object | Clarify ownership and mutation policy |
| Built-in call raises a type error | Built-in name was shadowed | Rename the conflicting binding |
| Notebook behaves differently from script | Retained interactive state | Restart and execute from a clean state |
| Separate scenarios affect each other | Shared global or enclosing state | Reset state locally and verify order independence |

## 3.6.22 Key Takeaways

Scope determines which binding a name resolves to. Parameters and assignments establish local names, while ordinary reads can access enclosing functions, module globals, and built-ins.

Keep changing financial inputs visible. Distinguish local rebinding from shared-object mutation, recognize closure state, and verify scenario independence. These habits prepare for type hints, documented contracts, and pure-function design in later sections.
