## 3.5.1 Purpose

Sections 3.3 and 3.4 connected function inputs to returned outputs. This section develops interfaces that make repeated calls convenient while keeping financial assumptions visible.

A default specifies what happens when an eligible argument is omitted. A keyword identifies an argument by parameter name. These are separate features: a required parameter can accept a keyword, and a defaulted parameter can sometimes accept a positional argument.

Defaults are part of the model contract. Omitting an argument should select a documented assumption rather than silently introduce an unknown rate, currency, or timing convention.

## 3.5.2 Learning Objectives

By the end of this section, you should be able to:

1. Define and override default argument values.
2. Use positional and keyword arguments without ambiguous binding.
3. Require important conventions through keyword-only parameters.
4. Explain when default expressions are evaluated.
5. Avoid shared mutable default state.
6. Distinguish omission, explicit None, and valid zero.
7. Verify a financial interface using known values and rejected calls.

## 3.5.3 Required Parameters Can Accept Keywords

```python
from decimal import Decimal


def future_value(present_value, periodic_rate, periods):
    return present_value * (Decimal("1") + periodic_rate) ** periods


amount = future_value(
    present_value=Decimal("1000"),
    periodic_rate=Decimal("0.05"),
    periods=2,
)
assert amount == Decimal("1102.50")
```

All three inputs are required, even though the caller supplies them by keyword. Ordinary parameters in this signature accept either positional or keyword arguments.

The model applies one constant effective rate per period to a principal at period 0, with no intermediate cash flows. Rate units and period counts must match. These introductory examples assume validated inputs; the lab supplies explicit checks.

## 3.5.4 Adding a Default

```python
def future_value_one_period(
    present_value,
    periodic_rate,
    periods=1,
):
    return present_value * (Decimal("1") + periodic_rate) ** periods


assert future_value_one_period(
    Decimal("1000"), Decimal("0.05")
) == Decimal("1050")

assert future_value_one_period(
    Decimal("1000"), Decimal("0.05"), periods=2
) == Decimal("1102.50")
```

The omitted period count selects one modeled period. It does not mean one year unless the rate is an effective annual rate and that interpretation is documented.

A supplied argument replaces the default for that invocation. It does not modify the signature's default.

## 3.5.5 Omission Is Different from Explicit None

```python
def selected_periods(periods=1):
    return periods


assert selected_periods() == 1
assert selected_periods(0) == 0
assert selected_periods(None) is None
```

Python applies the default when the argument is omitted. Passing None supplies an object; it does not instruct Python to substitute the default.

Whether None is accepted is the function author's contract decision. The guarded financial function later in this section rejects it.

## 3.5.6 Defaults Do Not Validate Inputs

A default of 1 does not require later arguments to be integers. Parameter defaults alone impose neither types nor financial domains.

For example, a caller can supply a Boolean or a negative count unless the implementation rejects it. A keyword makes the mapping explicit but does not prove that a 5% annual rate belongs with 24 monthly periods.

Validation remains necessary at the appropriate boundary.

## 3.5.7 Keyword Calls Make Mapping Visible

These calls bind the same inputs:

```python
positional = future_value(Decimal("1000"), Decimal("0.05"), 2)

named = future_value(
    periods=2,
    periodic_rate=Decimal("0.05"),
    present_value=Decimal("1000"),
)

mixed = future_value(
    Decimal("1000"),
    periodic_rate=Decimal("0.05"),
    periods=2,
)

assert positional == named == mixed
```

Keyword order need not match parameter order. For ordinary calls without argument unpacking, place positional arguments before keyword arguments.

Use named arguments where adjacent numeric inputs are easy to transpose or where a convention needs emphasis.

## 3.5.8 Invalid Calls Fail During Binding

The following examples are intentionally invalid. They are stored as strings so the demonstration can verify each failure.

```python
invalid_calls = [
    (
        'future_value(Decimal("1000"), '
        'present_value=Decimal("2000"), '
        'periodic_rate=Decimal("0.05"), periods=2)'
    ),
    (
        'future_value(present_value=Decimal("1000"), '
        'periodic_rate=Decimal("0.05"), years=2)'
    ),
    'future_value(Decimal("1000"), Decimal("0.05"))',
]

for expression in invalid_calls:
    try:
        eval(expression)
    except TypeError:
        pass
    else:
        raise AssertionError("Expected argument-binding failure")
```

The cases respectively bind one parameter twice, supply an unsupported keyword, and omit a required parameter. Each raises TypeError before this function body runs.

Putting an ordinary positional argument after a keyword is a syntax error:

```python
try:
    compile(
        'future_value(present_value=Decimal("1000"), Decimal("0.05"), 2)',
        "<invalid-call>",
        "exec",
    )
except SyntaxError:
    pass
else:
    raise AssertionError("Expected SyntaxError")
```

The string and compile call let the lesson demonstrate invalid syntax without making the entire lab file unparseable.

## 3.5.9 Parameter Ordering in Definitions

For positional-or-keyword parameters, required parameters precede defaulted parameters. A definition equivalent to `def model(periods=1, rate): ...` is invalid.

Keyword-only parameters may be required even after another keyword-only parameter has a default. The rule therefore depends on parameter kind; it is not a blanket restriction on every parameter after a default.

## 3.5.10 Keyword-Only Parameters

A bare star in a signature makes following parameters keyword-only:

```python
def next_balance(
    balance,
    periodic_rate,
    contribution=Decimal("0"),
    *,
    contribution_timing,
):
    if contribution_timing == "end":
        return balance * (Decimal("1") + periodic_rate) + contribution
    if contribution_timing == "beginning":
        return (balance + contribution) * (Decimal("1") + periodic_rate)
    raise ValueError("Unsupported contribution timing")


end_balance = next_balance(
    Decimal("1000"),
    Decimal("0.05"),
    Decimal("100"),
    contribution_timing="end",
)
beginning_balance = next_balance(
    Decimal("1000"),
    Decimal("0.05"),
    Decimal("100"),
    contribution_timing="beginning",
)

assert end_balance == Decimal("1150")
assert beginning_balance == Decimal("1155")
```

Here contribution has a default, but contribution_timing is required by keyword. The timing decision remains visible even when the caller chooses a zero contribution.

The formulas differ because beginning-of-period contributions earn one period's return; end-of-period contributions do not.

## 3.5.11 Defaulting a Financial Convention

An interface may instead document an end-of-period convention as its default:

```python
def balance_with_default_timing(
    balance,
    periodic_rate,
    contribution=Decimal("0"),
    *,
    contribution_timing="end",
):
    return next_balance(
        balance,
        periodic_rate,
        contribution,
        contribution_timing=contribution_timing,
    )


assert balance_with_default_timing(
    Decimal("1000"), Decimal("0.05"), Decimal("100")
) == Decimal("1150")
```

This is an interface choice, not a universal financial rule. Changing the default from end to beginning would change callers' results even if their source code remained unchanged.

For important calculations, recording the effective conventions alongside results improves reproducibility. Document defaults and treat changes deliberately.

## 3.5.12 A Brief Note on Positional-Only Parameters

A slash marks parameters before it as positional-only:

```python
def signed_difference(ending_amount, starting_amount, /):
    return ending_amount - starting_amount


assert signed_difference(Decimal("110"), Decimal("100")) == Decimal("10")
```

The slash and star serve different purposes.

| Signature marker | Meaning |
|---|---|
| Parameters before slash | Positional-only |
| Ordinary parameters between markers | Positional-or-keyword |
| Parameters after bare star | Keyword-only |

Financial interfaces often benefit from keyword readability. Positional-only parameters are included here for recognition, rather than as a requirement for financial functions. Variadic argument collection and unpacking are outside this section's scope.

## 3.5.13 Defaults Are Evaluated When the Definition Executes

```python
configured_periods = 2


def saved_default(periods=configured_periods):
    return periods


configured_periods = 5

assert saved_default() == 2
assert saved_default(configured_periods) == 5
```

The default expression is evaluated when the def statement executes, not again for every call. Rebinding configured_periods afterward does not replace the saved default object.

The same issue affects default expressions that read today's date, a configuration value, or a market rate. A default computed at definition time may become stale. Fetch changing information deliberately at a documented boundary.

Section 3.6 develops scope and name lookup in more detail.

## 3.5.14 Mutable Defaults Can Share State Across Calls

This is a deliberate defect demonstration:

```python
def shared_cash_flows(cash_flow, cash_flows=[]):
    cash_flows.append(cash_flow)
    return cash_flows


first = shared_cash_flows(Decimal("100"))
second = shared_cash_flows(Decimal("200"))

assert first is second
assert first == [Decimal("100"), Decimal("200")]
```

The omitted list is created once when the definition executes. Both calls mutate that same list, so first also changes after the second call.

This can mix observations from separate instruments, scenarios, or users.

## 3.5.15 Use None to Request a Fresh Container

```python
def append_cash_flow(cash_flow, cash_flows=None):
    if cash_flows is None:
        cash_flows = []
    cash_flows.append(cash_flow)
    return cash_flows


first = append_cash_flow(Decimal("100"))
second = append_cash_flow(Decimal("200"))

assert first == [Decimal("100")]
assert second == [Decimal("200")]
assert first is not second
```

For this contract, omitted input and explicit None both request a fresh list. An explicitly supplied list is still mutated:

```python
provided = []
returned = append_cash_flow(Decimal("300"), provided)

assert returned is provided
assert provided == [Decimal("300")]
```

Using None prevents an accidentally shared default. It does not make the function pure or remove mutation of caller-owned objects.

## 3.5.16 Preserve Valid Empty and Zero Inputs

Avoid `cash_flows = cash_flows or []` when an explicitly supplied empty list must retain its identity. That expression replaces any false-valued input, including an empty list.

Likewise, `rate = rate or fallback_rate` overwrites a valid zero rate. Use an explicit None check only if None has a documented fallback meaning.

An immutable Decimal zero is a suitable default representation for the contribution examples. Its immutability does not remove the need to validate supplied contributions.

## 3.5.17 Hands-On Lab — A Documented Balance Interface

Save the complete program below as `default_keyword_arguments_lab.py`.

The model advances one period using a constant effective periodic rate. It supports finite nonnegative Decimal balances and contributions, finite Decimal rates greater than -1, and two contribution timings. Withdrawals, taxes, fees, and currency conversion are excluded.

The end timing default is explicitly part of this educational interface. Arithmetic follows the active Decimal context, with no explicit quantization; returned amounts use the same currency as the inputs.

```python
from decimal import Decimal


def advance_balance(
    balance,
    periodic_rate,
    *,
    contribution=Decimal("0"),
    contribution_timing="end",
):
    values = [
        ("balance", balance),
        ("periodic_rate", periodic_rate),
        ("contribution", contribution),
    ]
    for name, value in values:
        if not isinstance(value, Decimal):
            raise TypeError(f"{name} must be Decimal")
        if not value.is_finite():
            raise ValueError(f"{name} must be finite")

    if balance < 0 or contribution < 0:
        raise ValueError("balance and contribution must be nonnegative")
    if periodic_rate <= Decimal("-1"):
        raise ValueError("periodic_rate must be greater than -1")
    if not isinstance(contribution_timing, str):
        raise TypeError("contribution_timing must be a string")
    if contribution_timing not in ("end", "beginning"):
        raise ValueError("Unsupported contribution timing")

    factor = Decimal("1") + periodic_rate
    if contribution_timing == "beginning":
        return (balance + contribution) * factor
    return balance * factor + contribution


def append_cash_flow(cash_flow, cash_flows=None):
    if cash_flows is None:
        cash_flows = []
    cash_flows.append(cash_flow)
    return cash_flows


principal = Decimal("1000")
rate = Decimal("0.05")

default_result = advance_balance(principal, rate)
assert default_result == Decimal("1050")

explicit_result = advance_balance(
    balance=principal,
    periodic_rate=rate,
    contribution=Decimal("0"),
    contribution_timing="end",
)
assert default_result == explicit_result

end_result = advance_balance(
    principal, rate, contribution=Decimal("100")
)
beginning_result = advance_balance(
    principal,
    rate,
    contribution=Decimal("100"),
    contribution_timing="beginning",
)

assert end_result == Decimal("1150")
assert beginning_result == Decimal("1155")
assert beginning_result - end_result == Decimal("5")
assert advance_balance(
    principal, Decimal("0"), contribution=Decimal("100")
) == Decimal("1100")
assert advance_balance(principal, Decimal("-0.10")) == Decimal("900")
assert advance_balance(Decimal("0"), rate) == Decimal("0")

first = append_cash_flow(Decimal("100"))
second = append_cash_flow(Decimal("200"))
assert first == [Decimal("100")]
assert second == [Decimal("200")]
assert first is not second

supplied = []
assert append_cash_flow(Decimal("300"), supplied) is supplied
assert supplied == [Decimal("300")]

binding_failures = [
    lambda: advance_balance(principal, rate, Decimal("100")),
    lambda: advance_balance(principal, rate, annual_rate=rate),
    lambda: advance_balance(principal, rate, balance=principal),
    lambda: advance_balance(principal),
]
for call in binding_failures:
    try:
        call()
    except TypeError:
        pass
    else:
        raise AssertionError("Expected binding failure")

invalid_values = [
    ({"contribution": None}, TypeError),
    ({"contribution": 100}, TypeError),
    ({"contribution": Decimal("-1")}, ValueError),
    ({"contribution": Decimal("NaN")}, ValueError),
    ({"contribution_timing": None}, TypeError),
    ({"contribution_timing": "monthly"}, ValueError),
]
for options, expected_error in invalid_values:
    try:
        advance_balance(principal, rate, **options)
    except expected_error:
        pass
    else:
        raise AssertionError("Expected invalid-value rejection")

print(f"No contribution: {default_result:.2f}")
print(f"End contribution: {end_result:.2f}")
print(f"Beginning contribution: {beginning_result:.2f}")
print("PASS: default and keyword argument checks")
```

The small lambda expressions defer calls until the verification loop executes. The `**options` expression expands a dictionary into keyword arguments for testing; neither technique is needed to use advance_balance in ordinary application code.

Run on Windows:

```powershell
py default_keyword_arguments_lab.py
```

Run on macOS or Linux:

```bash
python3 default_keyword_arguments_lab.py
```

Expected output:

```text
No contribution: 1050.00
End contribution: 1150.00
Beginning contribution: 1155.00
PASS: default and keyword argument checks
```

Run without `-O`, because these instructional assertions are removed by optimization. Input validation uses exceptions and remains active. The examples verify interface behavior and selected financial values, not production readiness.

## 3.5.19 Common Failure Patterns

| Problem | Explanation | Correction |
|---|---|---|
| None unexpectedly reaches arithmetic | Explicit None bypasses an ordinary default | Validate or define an explicit None policy |
| Scenarios accumulate each other's data | Mutable default reused | Allocate a fresh container inside the call |
| Zero rate is replaced | Truthiness used as absence | Test for None when appropriate |
| Timing changes silently | Convention hidden in a changed default | Document and manage contract changes |
| Duplicate-value TypeError | Parameter supplied positionally and by keyword | Supply one binding |
| Keyword call breaks after rename | Public parameter name changed | Treat names as interface commitments |
| Default configuration is stale | Expression evaluated at definition | Resolve changing inputs deliberately |
| Readable call still gives wrong valuation | Units or conventions incompatible | Validate the financial contract |

## 3.5.20 Key Takeaways

Defaults select documented behavior for omitted inputs. Keywords show argument mapping, and keyword-only parameters can require important conventions to be named.

Review defaults as model assumptions. Keep zero distinct from absence, avoid shared mutable state, and verify both successful calculations and rejected calls. Clear binding supports correct use but cannot replace financial-domain validation.
