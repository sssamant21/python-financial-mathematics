## 3.8.1 Purpose

A type hint can say that a rate is Decimal. It cannot explain whether that rate is annual, monthly, effective, or nominal. A function name can suggest valuation, but it cannot fully establish the valuation date or cash-flow timing.

Docstrings put that meaning next to the implementation. This section develops a practical documentation contract for financial functions, then verifies selected examples with doctest and explicit checks.

Detailed present- and future-value function design follows in Section 3.9. Here the emphasis is documenting assumptions accurately and making documentation agree with observable behavior.

## 3.8.2 Learning Objectives

You should be able to:

1. Write and inspect a function docstring.
2. Distinguish documentation from annotations and runtime validation.
3. State financial units, timing, rate conventions, and supported domains.
4. Describe numerical policy and failure behavior accurately.
5. Create executable documentation examples.
6. Detect documentation drift through review and tests.

## 3.8.3 What Makes a Function Docstring?

A string literal placed as the first statement in the function body becomes its docstring.

```python
from decimal import Decimal


def signed_difference(
    ending_amount: Decimal,
    starting_amount: Decimal,
) -> Decimal:
    """Return ending amount minus starting amount in the same currency."""
    return ending_amount - starting_amount


assert signed_difference.__doc__ is not None
assert "same currency" in signed_difference.__doc__
```

Triple double quotes are the convention used in this book. A longer docstring begins with a concise summary, followed by a blank line and supporting detail.

PEP 257 provides conventions rather than a requirement to use a particular Parameters or Returns markup. The headings used below are this book's readable house style.

## 3.8.4 Comments, Annotations, and Docstrings

| Mechanism | Main purpose | Example |
|---|---|---|
| Annotation | Expected representation | periodic_rate: Decimal |
| Docstring | Public computational and financial contract | Effective rate per modeled period |
| Comment | Explain implementation reasoning | Validate before comparing |
| Runtime check | Enforce supported actual inputs | Reject non-finite rates |
| Test | Verify selected observable behavior | Zero periods preserves principal |

A comment saying “multiply principal by factor” adds little if the expression already shows that. A comment explaining why rounding is deferred can preserve a consequential design decision.

Documentation describes the contract. It does not make unsupported inputs valid or enforce the statements it contains.

## 3.8.5 Inspecting Documentation

```python
import inspect

documentation = inspect.getdoc(signed_difference)
assert documentation is not None
assert documentation.startswith("Return ending amount")
```

inspect.getdoc retrieves documentation with indentation cleaned for presentation. help(signed_difference) is also useful interactively.

Ordinary Python execution retains docstrings. Python's -OO optimization can remove them, so documentation-inspection checks in this section should run without optimization.

## 3.8.6 A Financial Contract Checklist

Before implementing a reusable financial function, answer these questions:

| Contract element | Question |
|---|---|
| Purpose | What quantity is computed? |
| Inputs | What does each parameter mean? |
| Units | Currency, amount scale, rate units, and period units? |
| Timing | When are principal, contributions, and valuation observed? |
| Rate convention | Effective periodic, nominal annual, or another convention? |
| Domain | Which representations and values are supported? |
| Output | What does the returned quantity represent and when? |
| Numerical policy | Precision context, quantization boundaries, and display rules? |
| Failure | Which inputs are rejected and how? |
| State | Are inputs mutated or external state consulted? |
| Limits | Which real-world features are excluded? |

A function's supported domain may be narrower than the mathematical expression's possible domain. State the implemented policy rather than implying universal financial restrictions.

## 3.8.7 Rate Units and Period Counts

For accumulation:

FV = principal × (1 + periodic_rate) ** periods.

A periodic_rate of Decimal("0.05") means 5% per modeled period. It does not mean 5 percentage points added to another rate, or necessarily 5% annually.

If the modeled period is a month, the rate must match that monthly period. A nominal annual rate compounded monthly and an effective annual rate require different conversions before being used as effective monthly inputs.

A docstring should say whether conversion occurs inside the function. The lab performs no rate conversion.

## 3.8.8 Timing Changes the Model

For one period:

- End contribution: ending_balance = balance × (1 + rate) + contribution.
- Beginning contribution: ending_balance = (balance + contribution) × (1 + rate).

For a balance of 1000, a rate of 5%, and a contribution of 100, the results are 1150 and 1155 respectively.

Both formulas can be correct under their stated assumptions. A docstring that says only “calculate balance with contribution” leaves an important modeling choice unresolved.

When a parameter controls timing, document every accepted option and the default. When timing is fixed, state it directly.

## 3.8.9 Currency and Valuation Time

Returning Decimal("1102.50") does not specify its currency or date. State that the output uses the same currency as the principal and represents the end of the requested number of periods.

This chapter's amount functions do not convert currency. The caller must supply compatible quantities. A Decimal type check cannot distinguish dollars from cents or USD from EUR.

Document the valuation timeline even when actual dates are not modeled. Date conventions, calendars, and irregular cash flows require additional models later.

## 3.8.10 Numerical Policy

Avoid claiming that Decimal results are always exact. Arithmetic depends on the active Decimal context, and some operations round.

A useful policy distinguishes:

1. Input construction: controlled Decimal values constructed from strings.
2. Arithmetic precision: active Decimal context.
3. Business quantization: any explicit rounding to currency increments.
4. Presentation: caller-selected display formatting.

If no explicit cent rounding occurs, say so. Formatting a result to two decimal places does not mean the returned object was quantized to cents.

If arithmetic can raise Decimal signals for extreme inputs, document that qualification instead of promising a finite result for every finite input.

## 3.8.11 Failure and Boundary Behavior

Document representation errors separately from unsupported values.

A function can use TypeError for a string where Decimal is required, and ValueError for a Decimal principal that is negative or non-finite.

The period-count policy used here rejects bool, allows zero, and caps the count at 1000. That cap is an implementation limit for the teaching model, not a mathematical law.

At zero periods the function returns the principal under its supported domain. It still validates all arguments, including the rate, before computing. A zero-period call therefore does not bypass an invalid rate.

## 3.8.12 Executable Examples

doctest finds interactive examples in documentation and compares their executed output with the stated output.

```python
def net_cash_flow(inflow: Decimal, outflow: Decimal) -> Decimal:
    """Return inflow minus outflow for one currency and period.

    Inputs are assumed to be validated finite Decimal amounts.
    Negative net cash flow is a supported result.

    >>> net_cash_flow(Decimal("100"), Decimal("120"))
    Decimal('-20')
    """
    return inflow - outflow
```

Examples should demonstrate the intended interface and consequential boundaries. doctest checks the examples supplied; it does not prove the formula, validate every possible input, or detect every undocumented assumption.

Decimal representations can preserve trailing zeros. Formatting in an example can make a display result easier to read, but separate checks should still verify the numeric value.

## 3.8.13 Hands-On Lab — Document, Inspect, and Verify

Save the following complete module as docstrings_lab.py. It requires Python 3.10 or later and only standard-library modules.

The docstring is deliberately detailed because it is the central learning artifact. Smaller internal functions may need less detail when their contract is already clear.

```python
"""Demonstrate a documented compound-accumulation contract."""

from decimal import Decimal
import doctest
import inspect


def future_value(
    principal: Decimal,
    periodic_rate: Decimal,
    periods: int,
) -> Decimal:
    """Return a principal's accumulated amount after matching periods.

    Parameters
    ----------
    principal:
        Finite, nonnegative Decimal amount at period 0.
    periodic_rate:
        Finite Decimal effective rate per modeled period, greater than -1.
        Supply 5% as Decimal("0.05"), not Decimal("5").
    periods:
        Integer number of matching periods from 0 through 1000.
        Boolean values are not supported.

    Returns
    -------
    Decimal
        Amount at the end of the specified periods, in the principal's
        currency. Zero periods returns the principal after validation.

    Assumptions
    -----------
    One constant effective rate applies to every modeled period.
    No intermediate contributions, withdrawals, fees, taxes, inflation
    adjustment, currency conversion, or rate conversion is performed.
    The caller is responsible for currency and period compatibility.

    Numerical policy
    ----------------
    Arithmetic follows the active Decimal context. No explicit currency
    quantization is applied. The caller controls display formatting.
    Decimal arithmetic signals, including overflow, may propagate.

    Raises
    ------
    TypeError
        An amount or rate is not Decimal, or periods is not an integer
        excluding bool.
    ValueError
        A Decimal input is non-finite, principal is negative, rate is
        at or below -1, or periods is outside the supported range.

    State
    -----
    Does not mutate inputs or read a market rate, clock, or file.
    The active Decimal arithmetic context remains a numerical dependency.

    Examples
    --------
    >>> future_value(Decimal("1000"), Decimal("0.05"), 2) == Decimal("1102.50")
    True
    >>> future_value(Decimal("1000"), Decimal("0.05"), 0) == Decimal("1000")
    True
    >>> future_value(Decimal("1000"), Decimal("0"), 10) == Decimal("1000")
    True
    >>> format(future_value(Decimal("1000"), Decimal("-0.10"), 1), ".2f")
    '900.00'
    >>> future_value(Decimal("1000"), Decimal("-1"), 2)
    Traceback (most recent call last):
        ...
    ValueError: periodic_rate must be finite and greater than -1
    """
    if not isinstance(principal, Decimal):
        raise TypeError("principal must be Decimal")
    if not isinstance(periodic_rate, Decimal):
        raise TypeError("periodic_rate must be Decimal")
    if not isinstance(periods, int) or isinstance(periods, bool):
        raise TypeError("periods must be an integer excluding bool")
    if not principal.is_finite() or principal < 0:
        raise ValueError("principal must be finite and nonnegative")
    if not periodic_rate.is_finite() or periodic_rate <= Decimal("-1"):
        raise ValueError("periodic_rate must be finite and greater than -1")
    if not 0 <= periods <= 1000:
        raise ValueError("periods must be between 0 and 1000")

    return principal * (Decimal("1") + periodic_rate) ** periods


def run_contract_checks() -> None:
    """Verify selected documented boundary and failure behavior."""
    documentation = inspect.getdoc(future_value)
    assert documentation is not None
    assert "effective rate per modeled period" in documentation
    assert "No explicit currency" in documentation
    assert "Does not mutate inputs" in documentation

    principal = Decimal("1000")
    rate = Decimal("0.05")
    amount = future_value(principal, rate, 2)
    assert amount == Decimal("1102.50")
    assert isinstance(amount, Decimal)
    assert principal == Decimal("1000")
    assert rate == Decimal("0.05")
    assert future_value(Decimal("0"), rate, 2) == Decimal("0")

    # A negative period is an integer but violates the documented domain.
    try:
        future_value(principal, rate, -1)
    except ValueError:
        pass
    else:
        raise AssertionError("Expected negative-period rejection")

    # bool requires a runtime exclusion beyond an int annotation.
    try:
        future_value(principal, rate, True)
    except TypeError:
        pass
    else:
        raise AssertionError("Expected bool rejection")

    # Even a zero-period call validates the non-finite rate first.
    try:
        future_value(principal, Decimal("NaN"), 0)
    except ValueError:
        pass
    else:
        raise AssertionError("Expected non-finite-rate rejection")


if __name__ == "__main__":
    results = doctest.testmod()
    if results.failed:
        raise SystemExit(1)
    run_contract_checks()
    print(f"PASS: {results.attempted} docstring examples")
    print("PASS: financial contract boundary checks")
```

The __main__ guard runs verification when the file is executed directly. Importing this module defines its functions without running those checks or printing the success messages.

Run on Windows:

```powershell
py docstrings_lab.py
py -m doctest -v docstrings_lab.py
```

Run on macOS or Linux:

```bash
python3 docstrings_lab.py
python3 -m doctest -v docstrings_lab.py
```

Expected output from the direct script command:

```text
PASS: 5 docstring examples
PASS: financial contract boundary checks
```

The verbose doctest command separately reports each of the five examples. It does not call run_contract_checks, because importing the module does not enter the __main__ block.

Run normally without -O or -OO. Assertions support this instructional verification; production input rejection is implemented using exceptions.

## 3.8.14 Documentation Drift Exercise

Make a temporary copy of the lab and change the first example's expected Boolean from True to False. The doctest command should report a failure.

Then restore that expectation. Change only the prose to claim beginning-of-period contributions are supported. The examples may still pass because they contain no contribution input or check.

The exercise shows two different review needs: executable examples catch selected behavioral mismatches, while a human contract review must also compare claims with the actual interface and implementation.

Do not publish an intentionally broken copy as canonical material.

## 3.8.15 Reviewing a Contract Against Code

For the lab, trace each promise to evidence:

| Claim | Implementation or check |
|---|---|
| Decimal principal and rate | Explicit isinstance guards |
| Finite inputs | is_finite checks before comparisons |
| Nonnegative principal | Domain check |
| Rate greater than -1 | Domain check |
| Integer periods excluding bool | Separate representation guard |
| Zero through 1000 periods | Range check |
| Zero-period behavior | Docstring example and numeric check |
| No rate conversion | Formula uses supplied periodic_rate directly |
| No explicit currency quantization | No quantize operation |
| No input mutation | Immutable numeric inputs and result calculation |
| Active numerical context | Decimal arithmetic follows its context |

A keyword search for “quantize” or “currency” alone cannot prove the contract. Review data flow, arithmetic, and boundaries together.

A source reference supports technical behavior, but it does not verify that the financial assumptions chosen for a specific use case are appropriate.

## 3.8.16 A Reusable Docstring Outline

For substantial financial functions, use this outline as a starting point:

1. Concise summary of the quantity computed.
2. Parameters, including units and supported values.
3. Returns, including currency, valuation time, and absence semantics.
4. Assumptions and excluded features.
5. Numerical policy and external dependencies.
6. Raises, including known domain failures and propagated arithmetic signals.
7. State and mutation behavior when consequential.
8. Executable examples covering normal use and an important boundary.

Adapt the detail to the function. Avoid copying a large template with claims that have not been implemented.

Module documentation can hold shared conventions, while each function should make deviations and consequential local assumptions discoverable.

## 3.8.18 Troubleshooting Guide

| Symptom | Likely issue | Correction |
|---|---|---|
| Function has no __doc__ text | String is not its first statement, or docstrings removed | Fix placement and run without -OO |
| Example fails on displayed output | Expected representation differs | Check numeric correctness and intended display policy |
| Documentation says annual but code uses monthly inputs | Unit contract mismatch | Reconcile names, conversions, and examples |
| Raises section misses a failure | Domain or arithmetic path omitted | Review all guards and numerical operations |
| Examples pass but real use is wrong | Important assumption undocumented or untested | Review the financial contract |
| help text is hard to read | Weak summary or inconsistent indentation | Use a concise summary and clean sections |
| Import prints verification output | Top-level test execution | Use an entry-point guard |
| Rounding promise does not match returned object | Formatting confused with quantization | Document and implement boundaries separately |

## 3.8.19 Key Takeaways

A financial docstring explains meaning that types and names cannot fully express. Document rate conventions, units, timing, supported values, output semantics, numerical policy, and failures.

Keep that contract aligned with the implementation. Executable examples strengthen documentation, while boundary tests and direct review cover what examples leave unstated.
