## 3.7.1 Purpose

Type hints describe the representations a function expects and returns. They help readers, editors, and static analysis tools review a financial interface before it executes.

They do not automatically validate inputs, convert values, establish currency, or prove financial correctness. A Decimal rate can still be infinite, use the wrong period convention, or be assigned to the principal parameter.

This section adds annotations to the financial functions developed earlier. It uses Python 3.10 or later syntax; the examples are verified with Python 3.12. Detailed financial docstrings follow in Section 3.8.

## 3.7.2 Learning Objectives

You should be able to:

1. Annotate parameters, return values, and local variables.
2. Keep Decimal and float policies explicit.
3. Represent optional results and simple collections.
4. Distinguish static checking from runtime validation.
5. Recognize the limitations of aliases, Literal, and Any.
6. Run a typed financial lab and interpret deliberately invalid call examples.

## 3.7.3 An Annotated Financial Function

```python
from decimal import Decimal


def future_value(
    principal: Decimal,
    periodic_rate: Decimal,
    periods: int,
) -> Decimal:
    return principal * (Decimal("1") + periodic_rate) ** periods


amount: Decimal = future_value(
    Decimal("1000"),
    Decimal("0.05"),
    2,
)
assert amount == Decimal("1102.50")
```

The annotations describe the three inputs and returned amount. A colon introduces a parameter or variable annotation; the arrow introduces the return annotation.

The model applies a constant effective rate per matching period to a period-0 principal, without intermediate cash flows. The introductory function assumes validated finite Decimal inputs and a nonnegative integer period count. The lab supplies explicit validation.

## 3.7.4 Annotations Do Not Enforce the Contract

This deliberate misuse demonstrates that Python does not enforce the annotation automatically:

```python
def identity_amount(amount: Decimal) -> Decimal:
    return amount


incorrect_result = identity_amount("1000")
assert incorrect_result == "1000"
```

A static checker should report the incompatible argument. Ordinary execution still returns the string because the function simply returns its input.

Other invalid calls may fail during arithmetic. That failure is a consequence of executed operations, rather than automatic enforcement of the annotations.

## 3.7.5 Static Checking and Runtime Validation Have Different Jobs

| Mechanism | Checks | Important limit |
|---|---|---|
| Type hint | Declares expected representation | Python does not automatically enforce it |
| Static checker | Analyzes annotated code and calls | Depends on coverage, configuration, and available type information |
| Runtime validation | Checks actual supplied values | Must be implemented at the relevant boundary |
| Known-value test | Compares selected results | Cannot cover every financial assumption |
| Financial contract | Explains units, timing, and conventions | Must be implemented and reviewed |

A Decimal annotation cannot exclude NaN or infinity. An int annotation does not express a nonnegative period count or a maximum supported horizon.

Python treats bool as a subclass of int, so an integer annotation alone does not express this book's policy of rejecting Boolean period counts.

## 3.7.6 Decimal and Float Are Distinct Policies

Use Decimal inputs for the Decimal functions in this chapter. Construct controlled decimal values from strings.

```python
principal = Decimal("1000")
rate = Decimal("0.05")

assert isinstance(future_value(principal, rate, 2), Decimal)
```

Do not annotate a Decimal-based function with float merely because both represent numbers. An annotation such as Decimal | float also creates an implementation obligation: every accepted combination must have defined arithmetic behavior.

Scientific computing later uses binary floating-point arrays where appropriate. Type annotations should describe the implementation's actual numerical contract, not imply one numeric representation fits every task.

Annotations do not set Decimal precision, establish a quantization policy, or eliminate rounding error.

## 3.7.7 Return Types and None

A function that performs reporting without a meaningful returned result can declare None:

```python
def print_amount(amount: Decimal) -> None:
    print(f"Amount: {amount:.2f}")


assert print_amount(Decimal("100")) is None
```

A function returning a number on successful calculation should declare the numeric output. It should not return a display string from an error branch while claiming to return Decimal.

An exception interrupts normal completion; it does not require adding an exception class to the return annotation.

## 3.7.8 Optional Results

```python
from collections.abc import Sequence


def first_target_period(
    balances: Sequence[Decimal],
    target: Decimal,
) -> int | None:
    for period, balance in enumerate(balances):
        if balance >= target:
            return period
    return None


period = first_target_period([Decimal("100")], Decimal("100"))

if period is None:
    message = "Target absent from observations"
else:
    following_period: int = period + 1
    message = f"Following period: {following_period}"

assert message == "Following period: 1"
```

The sequence begins with period 0. None means no supplied observation meets the target, including an empty sequence. This function assumes its balances and target are already validated finite Decimal values.

The None check narrows the remaining possibility to int for a static checker. A truthiness check would incorrectly combine period 0 with absence.

The older spelling Optional[int] means int | None. It does not mean that the caller may omit a required parameter.

## 3.7.9 Collection Annotations

```python
def total_cash_flows(cash_flows: Sequence[Decimal]) -> Decimal:
    total = Decimal("0")
    for cash_flow in cash_flows:
        total += cash_flow
    return total


assert total_cash_flows([Decimal("100"), Decimal("-20")]) == Decimal("80")
assert total_cash_flows((Decimal("100"), Decimal("-20"))) == Decimal("80")
assert total_cash_flows([]) == Decimal("0")
```

Sequence communicates that this interface can consume suitable sequence objects, such as lists or tuples. It does not require a mutable list.

An Iterable[Decimal] annotation could be appropriate for a function that only iterates once, including over a generator. Choose the abstraction matching the operations actually needed.

These amounts must share a currency. A simple total is not a discounted valuation and does not account for cash-flow dates.

## 3.7.10 Structured Results

```python
def investment_summary(
    starting_amount: Decimal,
    ending_amount: Decimal,
) -> tuple[Decimal, Decimal]:
    return ending_amount, ending_amount - starting_amount


ending, gain = investment_summary(Decimal("1000"), Decimal("1100"))
assert ending == Decimal("1100")
assert gain == Decimal("100")
```

The annotation specifies a two-element tuple. It does not explain the financial meaning of each position; names and documentation still matter.

A dict[str, Decimal] describes a mapping with string keys and Decimal values. It does not require particular keys to exist. More explicit structured result types can be introduced when their additional machinery is useful.

## 3.7.11 Keyword-Only Conventions and Literal

```python
from typing import Literal


def next_balance(
    balance: Decimal,
    periodic_rate: Decimal,
    *,
    contribution: Decimal = Decimal("0"),
    timing: Literal["end", "beginning"] = "end",
) -> Decimal:
    if timing not in ("end", "beginning"):
        raise ValueError("Unsupported timing")
    factor = Decimal("1") + periodic_rate
    if timing == "beginning":
        return (balance + contribution) * factor
    return balance * factor + contribution


assert next_balance(
    Decimal("1000"),
    Decimal("0.05"),
    contribution=Decimal("100"),
    timing="beginning",
) == Decimal("1155")
```

Literal helps a static checker identify unsupported timing strings. The explicit value check handles actual invalid values that reach this function at runtime.

The calculation assumes already validated Decimal amounts and rate. The contribution occurs either before or after the one-period return, according to timing.

## 3.7.12 Type Aliases Do Not Establish Units

```python
from typing import TypeAlias

Amount: TypeAlias = Decimal
PeriodicRate: TypeAlias = Decimal


def one_period_amount(
    principal: Amount,
    rate: PeriodicRate,
) -> Amount:
    return principal * (Decimal("1") + rate)


assert one_period_amount(Decimal("1000"), Decimal("0.05")) == Decimal("1050")
```

These aliases improve vocabulary, but both still mean Decimal to the type checker. They do not prevent swapping an amount and a rate.

NewType can introduce distinct static identities, but still needs deliberate construction, validation, and conventions. It is not used in this introductory lab.

Similarly, a parameter named usd_amount or annual_rate helps communication without proving currency or periodicity.

## 3.7.13 Any Can Conceal Missing Checks

Any permits operations without ordinary static type restrictions. It can be useful at selected integration boundaries, but widespread use weakens the checks annotations are meant to provide.

For unknown external input, an object parameter plus explicit runtime checks can communicate that validation has not happened yet. Parsing a string into Decimal should be an explicit boundary operation; a type annotation does not perform that parsing.

Do not use a cast merely to silence an input mismatch. A typing cast changes the static view; it does not convert or validate the runtime value.

## 3.7.14 A Practical Annotation Policy

For this chapter:

- Annotate reusable function parameters and return values.
- Use Decimal for the monetary model examples.
- Use int for period counts, with explicit value and bool checks where required.
- Use int | None for a meaningful absent period result.
- Keep financial conventions in descriptive names, documentation, and validation.
- Add collection annotations when their contents and required operations are clear.
- Keep annotations readable; avoid introducing complex generic structures before they solve a real problem.

Type hints supplement the contracts developed in Sections 3.3–3.6. They do not replace them.

## 3.7.15 Hands-On Lab — Typed Functions with Runtime Guards

Save this complete program as type_hints_lab.py. It requires Python 3.10 or later and uses only the standard library for execution.

The model compounds a period-0 principal using a constant effective periodic rate for matching periods. There are no intermediate cash flows, taxes, or fees. Inputs and returned amounts use the same currency.

Supported values are finite nonnegative Decimal principal, finite Decimal rate greater than -1, and integer periods from 0 through 1000, excluding bool. Arithmetic follows the active Decimal context with no explicit quantization.

```python
from collections.abc import Sequence
from decimal import Decimal


def future_value(
    principal: Decimal,
    periodic_rate: Decimal,
    periods: int,
) -> Decimal:
    if not isinstance(principal, Decimal):
        raise TypeError("principal must be Decimal")
    if not isinstance(periodic_rate, Decimal):
        raise TypeError("periodic_rate must be Decimal")
    if not isinstance(periods, int) or isinstance(periods, bool):
        raise TypeError("periods must be an integer excluding bool")
    if not principal.is_finite() or principal < 0:
        raise ValueError("principal must be finite and nonnegative")
    if not periodic_rate.is_finite() or periodic_rate <= Decimal("-1"):
        raise ValueError("periodic_rate must be finite and greater than -1")
    if not 0 <= periods <= 1000:
        raise ValueError("periods must be between 0 and 1000")
    return principal * (Decimal("1") + periodic_rate) ** periods


def first_target_period(
    balances: Sequence[Decimal],
    target: Decimal,
) -> int | None:
    if not isinstance(target, Decimal):
        raise TypeError("target must be Decimal")
    if not target.is_finite():
        raise ValueError("target must be finite")

    # Validate every supplied observation before searching.
    for balance in balances:
        if not isinstance(balance, Decimal):
            raise TypeError("each balance must be Decimal")
        if not balance.is_finite():
            raise ValueError("each balance must be finite")

    for period, balance in enumerate(balances):
        if balance >= target:
            return period
    return None


amount: Decimal = future_value(Decimal("1000"), Decimal("0.05"), 2)
assert amount == Decimal("1102.50")
assert future_value(Decimal("1000"), Decimal("0"), 2) == Decimal("1000")
assert future_value(Decimal("1000"), Decimal("0.05"), 0) == Decimal("1000")
assert future_value(Decimal("0"), Decimal("0.05"), 2) == Decimal("0")
assert future_value(Decimal("1000"), Decimal("-0.10"), 1) == Decimal("900")

observations = [Decimal("100"), Decimal("110"), Decimal("121")]
period: int | None = first_target_period(observations, Decimal("110"))
assert period == 1
assert first_target_period(observations, Decimal("100")) == 0
assert first_target_period(observations, Decimal("122")) is None
assert first_target_period([], Decimal("100")) is None

# These calls satisfy the basic representation annotations,
# but violate a financial value rule or an additional runtime policy.
try:
    future_value(Decimal("1000"), Decimal("-1"), 2)
except ValueError:
    pass
else:
    raise AssertionError("Expected invalid rate rejection")

try:
    future_value(Decimal("1000"), Decimal("0.05"), True)
except TypeError:
    pass
else:
    raise AssertionError("Expected bool period rejection")

try:
    first_target_period(
        [Decimal("100"), Decimal("NaN")],
        Decimal("50"),
    )
except ValueError:
    pass
else:
    raise AssertionError("Expected full sequence validation")

print(f"Future value: {amount:.2f}")
print(f"First target period: {period}")
print("PASS: typed financial function runtime checks")
```

Run on Windows:

```powershell
py type_hints_lab.py
```

Run on macOS or Linux:

```bash
python3 type_hints_lab.py
```

Expected output:

```text
Future value: 1102.50
First target period: 1
PASS: typed financial function runtime checks
```

Run without -O so the instructional assertions execute. Runtime input checks use exceptions. Decimal arithmetic signals, including overflow for extreme accepted finite values, remain governed by the active context.

The sequence is validated fully before search so a qualifying first item does not hide a later non-finite observation.

## 3.7.18 Troubleshooting Guide

| Symptom | Explanation | Correction |
|---|---|---|
| Annotation accepts a bad runtime object | No automatic enforcement | Implement boundary validation |
| Optional period cannot be incremented safely | None remains possible | Narrow with an explicit None check |
| Checker reports Decimal/float mismatch | Numerical policies are mixed | Use the intended representation |
| Static checking misses unannotated code | Coverage or configuration is limited | Annotate reusable boundaries and review checker settings |
| NaN produces unexpected comparisons | Type is correct but value is invalid | Validate finiteness before arithmetic |
| Alias does not prevent swapped inputs | Aliases describe equivalent types | Use explicit names and domain contracts |
| Tests pass but units are wrong | Type hints do not establish financial conventions | Document and validate units and timing |

## 3.7.19 Key Takeaways

Type hints make expected representations visible and support static analysis. They do not automatically enforce values or financial meaning.

Use annotations alongside runtime guards, numerical policies, known-value checks, and documented assumptions. A function can be type-correct while still being financially wrong.
