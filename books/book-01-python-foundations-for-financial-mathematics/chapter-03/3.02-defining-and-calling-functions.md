## 3.2.1 Purpose

Section 3.1 explained why functions matter in financial computing. Functions turn meaningful financial operations into reusable computational components. This section explains the `def` statement, function names and bodies, indentation, calls and call expressions, execution order, repeated calls, function references versus invocations, and common definition/call errors. Parameters and arguments are developed in 3.3; return values in 3.4.

> **Understand what happens when Python defines a function and what happens when the program calls it.**

## 3.2.2 A First Financial Function

```python
from decimal import Decimal

def future_value():
    present_value = Decimal("10000")
    rate = Decimal("0.05")
    periods = 10
    value = present_value * (Decimal("1") + rate) ** periods
    print(value)
```

Executing `def` creates a function object and binds `future_value` to it. The calculation inside the body is not executed merely because the function is defined. To execute it:

```python
future_value()
```

```text
execute definition
        ↓
function object created
        ↓
name bound to function object

later

function call
        ↓
function body executes
```

## 3.2.3 The `def` Statement

A basic definition is:

```python
def function_name():
    statement
```

The definition contains `def`, a function name, parameter list, colon, and indented function body. In formal Python terminology, the header ends with a colon and its associated indented **suite** forms the function body. Executing `def` creates a function object and binds its name; it does not normally execute the body.

## 3.2.4 Function Names

Function names are Python identifiers and should communicate financial intent. Prefer names such as `future_value`, `present_value`, `discount_factor`, `calculate_payment`, and `project_balance` over vague names such as `calc` or `process`.

> **Function names are part of financial-model communication.**

## 3.2.5 Naming Conventions

Python commonly uses lowercase `snake_case` function names. Financial names should describe the operation or result. A name such as `calculate_return()` may be ambiguous because return could mean simple, logarithmic, annualized, total, or portfolio return. More specific names such as `calculate_simple_return()` can reduce ambiguity. A good name improves readability but does not fully specify the financial model.

## 3.2.6 The Function Body

```python
def show_balance():
    balance = Decimal("12500")
    print(balance)
```

The indented statements belong to the function. Indentation has structural meaning in Python; it is not merely visual formatting.

## 3.2.7 Indentation Is Part of Python Syntax

```python
def show_rate():
    rate = Decimal("0.05")
    print(rate)
```

Python uses indentation to delimit suites such as function bodies. A malformed indentation structure can prevent the program from being parsed or executed as intended.

## 3.2.8 Defining a Function Does Not Call It

```python
def show_model_started():
    print("Model started.")
```

The body runs only when invoked:

```python
show_model_started()
```

```text
function definition ≠ function invocation
```

## 3.2.9 A Function Call

A basic call consists of an expression identifying a callable followed by call parentheses:

```python
show_model_started()
```

Arguments may appear inside the parentheses:

```python
future_value(Decimal("10000"), Decimal("0.05"), 10)
```

Section 3.3 develops parameter/argument binding.

## 3.2.10 Function Reference Versus Function Call

`future_value` refers to the function object; `future_value(...)` invokes it.

```text
function reference ≠ function call
```

## 3.2.11 Missing Parentheses

```python
result = future_value
```

assigns the function object itself. It does not perform the financial calculation. To calculate, invoke the function with the appropriate call syntax.

## 3.2.12 Function Calls Are Expressions

A call can participate in a larger computation:

```python
portfolio_value = (
    future_value(Decimal("10000"), Decimal("0.05"), 10)
    + future_value(Decimal("5000"), Decimal("0.04"), 10)
)
```

Return-value mechanics are developed in 3.4.

## 3.2.13 Execution Order

```python
from decimal import Decimal

def show_initial_balance():
    print(Decimal("10000"))

print("Before call")
show_initial_balance()
print("After call")
```

Simplified sequence: import, execute definition and bind name, print before-call message, invoke function, execute body, invocation finishes, continue after the call. When an invocation finishes normally, execution continues with the surrounding computation or following statement. This should not be confused with an explicit `return` statement.

## 3.2.14 Definition Must Execute Before Its Name Is Needed

At module level:

```python
show_balance()

def show_balance():
    print("10000")
```

execution reaches the call before `def` binds `show_balance`, so the name cannot be resolved and Python raises `NameError`.

> **The relevant definition must have executed before execution reaches an operation that requires that name.**

## 3.2.15 Repeated Function Calls

Once defined and available, a function can normally be called repeatedly. Each invocation executes the body again. This is one foundation of code reuse.

## 3.2.16 Repeated Calls with Different Financial Inputs

```python
def future_value(present_value, rate, periods):
    return present_value * (Decimal("1") + rate) ** periods

value_1 = future_value(Decimal("10000"), Decimal("0.05"), 10)
value_2 = future_value(Decimal("25000"), Decimal("0.04"), 20)
value_3 = future_value(Decimal("5000"), Decimal("0.07"), 5)
```

The implementation remains centralized while inputs vary.

## 3.2.17 Parameters and Arguments — Preview

In `def future_value(present_value, rate, periods):`, the names are parameters. In `future_value(Decimal("10000"), Decimal("0.05"), 10)`, the supplied values are arguments. Precise binding rules are developed in 3.3.

## 3.2.18 Calling with Incompatible Arguments

Calls with missing or extra arguments may not bind to the parameters. When binding cannot be performed appropriately, Python typically raises `TypeError`. Full rules belong in 3.3.

## 3.2.19 Return Values — Preview

```python
def future_value(present_value, rate, periods):
    value = present_value * (Decimal("1") + rate) ** periods
    return value
```

The caller can use the value produced by the call. Detailed `return` semantics are covered in 3.4.

## 3.2.20 Printing Is Not Returning

A function that calls `print(value)` produces visible output. A function that executes `return value` provides a value to its call expression. Therefore:

```text
print ≠ return
```

This distinction is important for reusable financial calculations.

## 3.2.21 Functions Without an Explicit `return`

If execution reaches the end of an ordinary function without executing a `return` statement, the function call returns `None`. A function may visibly print a financial result while its call still produces `None`.

```text
visible output ≠ returned value
```

## 3.2.22 Function Calls Inside Loops

```python
return_scenarios = [Decimal("0.03"), Decimal("0.05"), Decimal("0.07")]

for rate in return_scenarios:
    value = future_value(Decimal("50000"), rate, 10)
    print(f"{rate:.1%}", f"${value:,.2f}")
```

The loop determines which scenario is evaluated; the function determines how future value is calculated. Scenario rates are assumptions, not automatically forecasts or probabilities.

## 3.2.23 Function Calls Inside Conditions

```python
def target_reached(balance, target):
    return balance >= target

if target_reached(current_balance, target_balance):
    print("Target reached.")
```

A call expression can supply the Boolean value used by a condition.

## 3.2.24 Function Calls Inside Other Functions

```python
def discount_factor(rate, period):
    return Decimal("1") / (Decimal("1") + rate) ** period

def present_value(cash_flow, rate, period):
    return cash_flow * discount_factor(rate, period)
```

One function can call another. This previews function composition, developed in 3.11.

## 3.2.25 Interdependent Function Definitions

A function body may refer to a function defined later in the source, provided the required name is resolvable when execution reaches that call. Thus textual position alone is not the complete execution-order rule.

## 3.2.26 Nested Calls

```python
print(future_value(Decimal("10000"), Decimal("0.05"), 10))
```

The inner call produces a financial result used by the outer call.

## 3.2.27 Calls Inside Larger Expressions

Return-producing calls can participate in arithmetic and allow small reusable functions to become components of larger financial models.

## 3.2.28 Functions Can Contain Conditions

```python
def classify_cash_flow(cash_flow):
    if cash_flow > Decimal("0"):
        return "positive"
    if cash_flow < Decimal("0"):
        return "negative"
    return "zero"
```

Chapter 2 control flow can live inside Chapter 3 reusable functions.

## 3.2.29 Functions Can Contain Loops

```python
def total_cash_flows(cash_flows):
    total = Decimal("0")
    for cash_flow in cash_flows:
        total += cash_flow
    return total
```

The loop performs repeated processing; the function packages it as a reusable operation.

## 3.2.30 Functions and Program Structure

A useful introductory organization is imports → function definitions → model inputs → function calls → results → presentation. This is not the only valid Python architecture, but it helps separate reusable calculations from execution and presentation.

## 3.2.31 Definition Versus Execution

Function definitions answer “what operations does this program provide?” Calls answer “which operations should execute now?” This distinction becomes increasingly important in modules and libraries.

## 3.2.32 Financial Calculation Functions and Presentation

A calculation function that formats and prints internally couples calculation to presentation. A more reusable computational function returns the numeric value and lets presentation occur separately.

```text
financial calculation ≠ presentation
```

## 3.2.33 Function Calls and Side Effects

Not every function primarily returns a computational value. Printing, writing a file, logging, updating external state, or communicating with another system are observable effects. Financial computational functions are often easier to test and reuse when calculation is separated from unrelated side effects. Pure functions are developed in 3.12.

## 3.2.34 Common Function-Definition Errors

Common errors include a missing colon, missing indented body, invalid identifier such as `3year_value`, and using a Python keyword such as `return` as the function name.

## 3.2.35 Common Function-Call Errors

Common errors include referencing instead of calling, incompatible arguments, calling before the name is bound, misspelling the function name, and calling the wrong financial operation. Programming correctness and financial correctness are different concerns.

## 3.2.36 Valid Python Does Not Guarantee a Correct Financial Model

```python
def future_value(present_value, rate, periods):
    return present_value * (Decimal("1") + rate * periods)
```

Python can execute this function, but if the intended relationship is periodic compound accumulation,

\[
FV=PV(1+r)^n,
\]

the implementation is financially wrong.

```text
valid Python ≠ correct financial model
```

## 3.2.37 Successful Definition Does Not Validate the Model

Successfully defining a function does not establish that its formula, rate units, period units, timing assumptions, input domain, numerical policy, or results are correct. Function definition is a programming operation; financial-model validation is separate.

## 3.2.38 Successful Invocation Does Not Verify the Result

A call completing without exception does not prove the financial result is correct.

```text
define → call → obtain result → verify/reconcile → interpret
```

```text
successful execution ≠ verified financial result
```

## 3.2.39 Worked Example — Compound Future Value

For present value $10,000, effective annual rate 5%, and 10 annual periods:

\[
FV=PV(1+r)^n
\]

```python
from decimal import Decimal

def future_value(present_value, rate, periods):
    return present_value * (Decimal("1") + rate) ** periods

result = future_value(Decimal("10000"), Decimal("0.05"), 10)
print(f"${result:,.2f}")
```

The internal result is `16288.94626777441406250000`; presentation to two decimal places gives `$16,288.95`. Internal computational value and formatted display are distinct. Two-decimal presentation should not itself be confused with explicit business quantization.

## 3.2.40 Reusing the Function Across Scenarios

```python
return_scenarios = [Decimal("0.03"), Decimal("0.05"), Decimal("0.07")]

for rate in return_scenarios:
    result = future_value(Decimal("10000"), rate, 10)
    print(f"Rate: {rate:.1%} | Future Value: ${result:,.2f}")
```

The loop selects assumptions; the function implements the calculation. The rates are scenarios, not forecasts, probabilities, or investment recommendations.

## 3.2.41 Function Definition Checklist

Before considering a simple financial function definition complete, ask whether its name is meaningful, syntax and indentation are valid, it represents a coherent operation, assumptions are understood, numerical representations are consistent, calculation is separated from presentation where appropriate, intended behavior is clear, its definition executes before its name is required, and it can be invoked consistently with the intended financial model.

## 3.2.42 Function Call Checklist

When calling a financial function, ask whether you are invoking the intended function, supplying required and appropriately represented inputs, respecting rate/period units and assumptions, storing returned values when needed, distinguishing visible output from returned output, formatting only at the presentation boundary, and verifying or reconciling results when correctness matters.
