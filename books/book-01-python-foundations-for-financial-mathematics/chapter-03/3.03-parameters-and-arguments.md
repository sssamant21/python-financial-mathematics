## 3.3.1 Purpose

Section 3.2 established how Python functions are **defined** and **called**.

```python
from decimal import Decimal


def future_value(
    present_value,
    periodic_rate,
    periods,
):
    return (
        present_value
        * (Decimal("1") + periodic_rate) ** periods
    )
```

A call might be:

```python
future_value(
    Decimal("10000"),
    Decimal("0.05"),
    10,
)
```

```text
function definition
        ↓
parameters

function call
        ↓
arguments
```

Parameters provide names through which a function receives inputs. Arguments are expressions supplied by a particular call.

> **Design and call financial functions so that each input has a clear computational and financial meaning.**

Default parameter values and deeper keyword-argument design are developed in Section 3.5. Variable scope is developed in Section 3.6, type hints in Section 3.7, financial-assumption documentation in Section 3.8, and pure-function design in Section 3.12.

## 3.3.2 Parameters

```python
def future_value(
    present_value,
    periodic_rate,
    periods,
):
    ...
```

`present_value`, `periodic_rate`, and `periods` are parameters. When the function is invoked, these parameters establish local name bindings for that invocation.

## 3.3.3 Arguments

```python
future_value(
    Decimal("10000"),
    Decimal("0.05"),
    10,
)
```

The supplied expressions are arguments. For this ordinary positional call:

```text
Decimal("10000") → present_value
Decimal("0.05")   → periodic_rate
10                → periods
```

## 3.3.4 Parameters and Arguments Are Different Concepts

```text
parameter
    ↓
name in function definition

argument
    ↓
expression supplied in function call
```

> **Functions define parameters; calls supply arguments.**

## 3.3.5 Argument Expressions Are Evaluated

```python
future_value(
    Decimal("10000") + Decimal("2500"),
    Decimal("0.05"),
    5 + 5,
)
```

```text
argument expressions
        ↓
evaluate expressions
        ↓
resulting objects
        ↓
parameter binding
        ↓
execute function body
```

## 3.3.6 Argument Binding

Python associates supplied arguments with eligible parameters according to the function's calling rules. For the ordinary call above:

```text
present_value = Decimal("10000")
periodic_rate = Decimal("0.05")
periods       = 10
```

## 3.3.7 Positional Arguments

For ordinary positional-or-keyword parameters, positional arguments fill eligible parameter slots from left to right. Position therefore carries meaning and forms part of the interface. Python also supports specialized parameter forms outside this section's scope.

## 3.3.8 Argument Order Can Change Financial Meaning

```python
future_value(
    Decimal("0.05"),
    Decimal("10000"),
    10,
)
```

may satisfy basic positional binding while being financially nonsensical.

```text
successful argument binding
        ≠
financially correct argument mapping
```

## 3.3.9 Parameter Names Should Communicate Financial Meaning

Prefer:

```python
def future_value(
    present_value,
    periodic_rate,
    periods,
):
    ...
```

over vague parameters such as `x`, `y`, and `z`.

> **Parameter names are part of financial-model communication.**

## 3.3.10 Parameter Names and Units

When a function is tied to annual periods, `annual_rate` and `years` may be appropriate. For a generic periodic function, `periodic_rate` and `periods` make the relationship clearer. Parameter names, documentation, or both should make financially important units and conventions unambiguous.

## 3.3.11 Rate and Period Parameters Must Agree

For periodic compound accumulation:

\[
FV=PV(1+r)^n,
\]

where \(r\) is the effective rate per modeled period and \(n\) is the corresponding number of modeled periods.

An annual rate combined directly with a monthly period count is generally inconsistent unless explicit conversion is part of the model.

> **The parameter interface should make compatible financial units easy to understand and difficult to misuse.**

## 3.3.12 Arguments Can Be Literal Values

```python
future_value(
    Decimal("10000"),
    Decimal("0.05"),
    10,
)
```

Literal arguments are useful for demonstrations, known-value checks, examples, and one-off calculations.

## 3.3.13 Arguments Can Be Variables

```python
present_value = Decimal("10000")
periodic_rate = Decimal("0.05")
periods = 10

result = future_value(
    present_value,
    periodic_rate,
    periods,
)
```

## 3.3.14 Caller Variable Names Need Not Match Parameter Names

```python
starting_balance = Decimal("10000")
annual_return = Decimal("0.05")
years = 10

future_value(
    starting_balance,
    annual_return,
    years,
)
```

For this positional call:

```text
starting_balance → present_value
annual_return    → periodic_rate
years            → periods
```

The caller remains responsible for ensuring that the units are compatible.

## 3.3.15 Arguments Can Be Results of Other Calls

```python
def discount_factor(periodic_rate, period):
    return Decimal("1") / (Decimal("1") + periodic_rate) ** period


def discounted_amount(cash_flow, factor):
    return cash_flow * factor


value = discounted_amount(
    Decimal("10000"),
    discount_factor(Decimal("0.05"), 3),
)
```

This prepares the way for function composition in Section 3.11.

## 3.3.16 Required Parameters

For a function with no defaults, each required parameter needs a corresponding argument. Omitting `periods` from the simple `future_value` call raises `TypeError`. Defaults are introduced in Section 3.5.

## 3.3.17 Additional Positional Arguments

For the simple `future_value` interface, which has no variadic positional parameter, supplying an additional positional argument raises `TypeError`.

## 3.3.18 Keyword Arguments — Introduction

For parameters eligible to receive keyword arguments, a keyword argument identifies the corresponding parameter by name:

```python
future_value(
    present_value=Decimal("10000"),
    periodic_rate=Decimal("0.05"),
    periods=10,
)
```

Keyword arguments can make financial calls easier to review. Deeper keyword design belongs in Section 3.5.

## 3.3.19 Keyword Arguments Can Reduce Positional Ambiguity

```python
present_value(
    cash_flow=Decimal("10000"),
    periodic_rate=Decimal("0.05"),
    period=3,
)
```

makes the mapping visible, but keyword arguments do not validate financial meaning.

```text
clearer binding
    ≠
financial validation
```

## 3.3.20 Combining Positional and Keyword Arguments

```python
future_value(
    Decimal("10000"),
    periodic_rate=Decimal("0.05"),
    periods=10,
)
```

The first eligible parameter is filled positionally and the remaining parameters by keyword. Detailed keyword-call design belongs in Section 3.5.

## 3.3.21 A Parameter Cannot Be Bound Twice in the Same Call

```python
future_value(
    Decimal("10000"),
    present_value=Decimal("20000"),
    periodic_rate=Decimal("0.05"),
    periods=10,
)
```

attempts to bind `present_value` twice and raises `TypeError`.

## 3.3.22 Parameter Order Is Interface Design

The order `present_value`, `periodic_rate`, `periods` naturally mirrors \(FV=PV(1+r)^n\). A useful financial ordering often places the primary amount first, followed by rate, time/period, and model-specific inputs. This is design guidance rather than a Python requirement.

## 3.3.23 Parameters Should Represent Distinct Concepts

Prefer financially meaningful interfaces such as:

```python
def calculate_net_cash_flow(inflow, outflow):
    return inflow - outflow
```

or:

```python
def next_balance(balance, periodic_rate, contribution):
    return balance * (Decimal("1") + periodic_rate) + contribution
```

A good interface exposes financial structure instead of hiding it.

## 3.3.24 Parameters Do Not Fully Describe Timing

For an end-of-period contribution:

\[
B_t=B_{t-1}(1+r)+C.
\]

For a beginning-of-period contribution:

\[
B_t=(B_{t-1}+C)(1+r).
\]

```text
same parameter names
        ≠
same financial model
```

> **Parameter names help describe inputs, but they do not replace documentation of timing and model assumptions.**

## 3.3.25 Parameters Do Not Fully Describe Rate Conventions

A parameter named `rate` alone does not establish whether the rate is effective periodic, nominal annual, annual effective, continuously compounded, or another convention. A name such as `periodic_rate` helps, but the complete contract must document the interpretation.

## 3.3.26 Parameters Establish Local Bindings

When a function is invoked, its parameters establish local name bindings for that invocation. A parameter named `present_value` can be bound to the supplied argument without rebinding an outer name that happens to have the same spelling. Detailed scope rules belong in Section 3.6.

## 3.3.27 Arguments, Objects, and Parameter Binding

Do not model calls as textual substitution. A more useful model is:

```text
caller expression
      ↓
evaluate
      ↓
object
      ↓
parameter binding
      ↓
local parameter name
```

Arguments are evaluated and the resulting objects are bound to parameter names for the invocation.

## 3.3.28 Parameter Rebinding Does Not Rebind the Caller's Name

```python
def replace_balance(balance):
    balance = Decimal("0")


account_balance = Decimal("10000")
replace_balance(account_balance)
```

Rebinding local `balance` does not rebind the caller's `account_balance` name.

## 3.3.29 Object Mutation Is Different from Parameter Rebinding

```python
def add_cash_flow(cash_flows, cash_flow):
    cash_flows.append(cash_flow)
```

If the caller supplies a list, the function can mutate the same list object visible through the caller's reference.

```text
parameter rebinding
        ≠
object mutation
```

Passing an object does not automatically create an independent copy. Pure functions and side effects are developed further in Section 3.12.

## 3.3.30 Multiple Calls Establish Their Own Parameter Bindings

Each invocation establishes its own parameter-name bindings, although different invocations may still refer to the same underlying object if the caller supplies it.

```text
separate parameter bindings
        ≠
guaranteed separate objects
```

## 3.3.31 Parameter Names Do Not Enforce Runtime Types

A parameter named `present_value` does not itself require a `Decimal`.

```text
parameter name
    ≠
runtime type guarantee
```

Type hints are developed in Section 3.7.

## 3.3.32 Argument Binding Does Not Validate Financial Domains

A call can satisfy argument binding while containing financially invalid inputs.

```text
argument binding
        ≠
representation validation
        ≠
domain validation
        ≠
financial plausibility
```

## 3.3.33 A Financial Function Contract Extends Beyond Its Parameter List

A stronger contract includes:

```text
parameter names
        +
expected representations
        +
financial interpretation
        +
units
        +
timing convention
        +
supported domain
        +
numerical policy
        +
output semantics
        +
failure behavior
```

The parameter list exposes inputs. The contract explains what those inputs mean.

## 3.3.34 Parameter Design for Present Value

For:

\[
PV_t=\frac{CF_t}{(1+r)^t},
\]

```python
def present_value(cash_flow, periodic_rate, period):
    return cash_flow / (Decimal("1") + periodic_rate) ** period
```

The parameters communicate the amount being discounted, the effective rate per modeled period, and the distance from valuation time.

## 3.3.35 Parameter Design for a Balance Transition

For end-of-period contributions:

\[
B_t=B_{t-1}(1+r)+C,
\]

```python
def next_balance(balance, periodic_rate, contribution):
    return balance * (Decimal("1") + periodic_rate) + contribution
```

The timing assumption remains part of the financial contract.

## 3.3.36 Parameter Design for Financial Decision Functions

```python
def target_reached(balance, target):
    return balance >= target
```

Clear parameter names make financial decision functions easier to interpret and review.

## 3.3.37 Boolean Arguments and Hidden Meaning

A call ending in a bare positional `True` may hide an important convention. Boolean parameters are not inherently wrong, but bare Boolean positional arguments can obscure financially important meaning when their interpretation is not obvious at the call site.

## 3.3.38 Long Positional Argument Lists

Long sequences of similar numeric arguments increase transposition and review risk. Selective keyword arguments, smaller functions, clearer responsibilities, or structured inputs may improve the design.

```text
callable
    ≠
reviewable
```

## 3.3.39 Validation at Appropriate Boundaries

```text
external input
      ↓
representation / conversion
      ↓
validation
      ↓
validated financial values
      ↓
internal function arguments
```

> **Parameter design and validation design should work together, but they are not the same concern.**

## 3.3.40 Argument Binding Does Not Establish Numerical Policy

```text
argument binding
        ≠
arithmetic precision
        ≠
business quantization
        ≠
display formatting
```

Controlled decimal inputs continue to use forms such as `Decimal("10000")`, `Decimal("0.05")`, and `Decimal("1")`.

## 3.3.41 Common Parameter and Argument Mistakes

1. Confusing parameters with arguments.
2. Reversing positional arguments.
3. Omitting a required argument.
4. Supplying an unexpected positional argument to a non-variadic interface.
5. Binding one parameter twice.
6. Using ambiguous parameter names.
7. Mixing rate and period units without conversion.
8. Assuming binding means validation.
9. Hiding timing conventions.
10. Mutating caller-owned objects unintentionally.

## 3.3.42 Production Perspective

In production financial software, parameter design affects readability, correctness, auditability, testability, maintainability, reproducibility, and operational safety.

```text
clear financial operation
        ↓
clear parameter names
        ↓
clear units and conventions
        ↓
predictable argument binding
        ↓
validation at appropriate boundary
        ↓
consistent numerical policy
        ↓
reusable financial computation
```

Correct mathematics behind a confusing interface can still create operational risk.

## 3.3.43 Parameter Design Checklist

1. Does each parameter represent a clear financial concept?
2. Are names understandable without reverse-engineering the implementation?
3. Are rate conventions clear?
4. Are period units clear?
5. Are timing assumptions documented or explicit?
6. Is positional order natural?
7. Could similar numeric parameters easily be reversed?
8. Would selective keyword arguments improve readability?
9. Does the function require too many unrelated inputs?
10. Are expected representations understood?
11. Is validation performed at the appropriate boundary?
12. Could mutable arguments be modified unintentionally?
13. Does the interface expose rather than hide the financial model?

## 3.3.44 Function Call Checklist

1. Am I calling the intended function?
2. Does each positional argument correspond to the intended parameter?
3. Are keyword names correct?
4. Is any parameter being bound more than once?
5. Are all required arguments supplied?
6. Are unexpected additional arguments present?
7. Are financial values represented appropriately?
8. Do rate and period units agree?
9. Does the timing convention match the intended model?
10. Are argument values within the supported financial domain?
11. Could a mutable argument be changed by the function?
12. Does the call communicate enough meaning for another reviewer to understand it?

## 3.3.45 Key Takeaways

1. Parameters belong to function definitions.
2. Arguments belong to function calls.
3. Functions define parameters; calls supply arguments.
4. Argument expressions are evaluated before the function body executes.
5. Resulting objects participate in parameter binding for the invocation.
6. Argument binding is not textual source substitution.
7. For ordinary positional-or-keyword parameters, positional arguments fill eligible slots from left to right.
8. Positional order is part of a function's interface.
9. For eligible parameters, keyword arguments can identify parameters by name.
10. Keyword arguments can improve readability without validating financial meaning.
11. A parameter cannot be successfully bound twice in the same ordinary call.
12. Missing required arguments produce `TypeError`.
13. Unexpected extra positional arguments produce `TypeError` for the simple non-variadic interfaces used here.
14. Successful binding does not imply financial correctness.
15. Parameter names should communicate financial concepts.
16. Parameter names and documentation should make important units and conventions clear.
17. Rate and period conventions must be compatible.
18. Parameter lists do not fully describe timing assumptions.
19. Parameters establish local name bindings for an invocation.
20. Caller variable names do not need to match parameter names.
21. Parameter rebinding is different from rebinding a caller's variable.
22. Parameter rebinding is different from object mutation.
23. Passing an object does not automatically create an independent copy.
24. Separate invocations establish separate parameter-name bindings but may still reference the same underlying object.
25. Parameter names do not enforce runtime types.
26. Type hints are treated separately in Section 3.7.
27. Argument binding does not perform financial-domain validation.
28. A financial function contract extends beyond its parameter list.
29. Binding is distinct from arithmetic precision, quantization, and display formatting.
30. Clear parameter interfaces reduce opportunities for financial-model misuse.
