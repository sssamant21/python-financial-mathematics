## 4.1.1 Purpose

Chapter 3 developed functions with explicit financial contracts. Chapter 4 examines the information those functions consume and produce.

A number becomes useful financial information when its identity, units, timing, and interpretation are known. A payment of 1000 means little without currency, payment date, and the perspective from which its sign is recorded.

This section introduces records, collections, and schemas. Lists, tuples, dictionaries, sets, nested structures, and their operations are developed individually in Sections 4.2–4.12. The examples here introduce only enough syntax to make the data contract concrete.

## 4.1.2 Learning Objectives

You should be able to:

1. Distinguish a value from a complete financial observation.
2. Identify a record's fields, types, and meaning.
3. Recognize records, collections, and schemas.
4. Preserve currency, dates, identifiers, and sign conventions.
5. Separate missing values from valid zero.
6. Validate a small financial record without silently changing its meaning.

## 4.1.3 From a Scalar to an Observation

Consider Decimal("1000"). It could represent a principal, a payment, a quoted price, or a quantity.

A payment record supplies context:

| Field | Example | Meaning |
|---|---|---|
| payment_id | P001 | Unique identifier within the chosen dataset |
| amount | Decimal("1000.00") | Signed amount in whole currency units |
| currency | USD | Currency label supported by the dataset |
| payment_date | date(2027, 1, 15) | Scheduled calendar payment date |
| perspective | investor | Positive means receipt; negative means payment |

The identifier distinguishes this payment from another payment with identical date and amount. These examples are invented teaching data, not actual transactions.

## 4.1.4 A Record Has Named Fields

```python
from datetime import date
from decimal import Decimal

payment = {
    "payment_id": "P001",
    "amount": Decimal("1000.00"),
    "currency": "USD",
    "payment_date": date(2027, 1, 15),
    "perspective": "investor",
}

assert payment["currency"] == "USD"
assert payment["amount"] == Decimal("1000.00")
```

A Python dictionary associates keys with values. The quoted field names identify those values. Access by a field name communicates more meaning than relying on an unexplained positional index.

A dictionary does not enforce a schema automatically. A misspelled field can coexist with the intended field unless the application validates its keys.

## 4.1.5 Collections Preserve Multiple Observations

A collection contains records:

```python
payments = [
    payment,
    {
        "payment_id": "P002",
        "amount": Decimal("-250.00"),
        "currency": "USD",
        "payment_date": date(2027, 2, 15),
        "perspective": "investor",
    },
]

assert len(payments) == 2
```

The outer list preserves the supplied sequence. It does not prove chronological ordering or unique identifiers. Those are separate dataset rules.

Each record describes one observation. Do not combine unrelated fields from different payments merely because their positions happen to match.

## 4.1.6 A Schema Combines Structure and Meaning

A useful schema describes:

- Required and optional field names.
- Supported representations.
- Allowed values and missing-value rules.
- Units, currency, signs, and dates.
- Identity and duplication policy.
- Relationships between fields.
- Version and source information when needed.

For the lab, all five fields are required and unknown fields are rejected. This strict policy makes typos visible. An evolving production dataset may choose a different policy, but that policy should be explicit and versioned.

The lab supports USD and EUR as a small allowlist. It does not claim these are the only valid currencies.

## 4.1.7 Representation Is Not Financial Compatibility

Two amounts may both be Decimal but use different currencies or scales. Adding USD 100 to EUR 100 does not create a meaningful single-currency total without a conversion policy.

Likewise, a nominal annual rate and an effective monthly rate may have the same Python representation. Data records should preserve convention metadata so the Chapter 3 functions receive appropriate inputs.

A date object identifies a calendar date. It does not establish a payment instant, timezone, settlement rule, business-day adjustment, or accrual fraction.

## 4.1.8 Sign Convention Is Part of the Record Contract

Under the lab's investor perspective, positive amounts are receipts and negative amounts are payments. Zero is permitted.

The Chapter 3 project deliberately accepted nonnegative valuation amounts. A signed payment record does not silently widen that API's domain. An application must choose a documented signed-valuation extension before passing negative flows into it.

Preserve both the data contract and the function contract at their boundary.

## 4.1.9 Missing, Zero, and Invalid Are Different

| Value or condition | Meaning under the lab contract |
|---|---|
| Decimal("0") | Valid zero payment |
| None amount | Unsupported missing value |
| Missing amount key | Incomplete record |
| Decimal("NaN") | Non-finite amount; rejected |
| Empty payment_id | Invalid identifier |
| String "1000" | Unparsed representation; rejected |

Do not replace unknown amounts with zero merely to make calculations run. That changes the data's meaning.

The lab validates already constructed objects. Parsing external strings is a separate boundary operation.

## 4.1.10 Identity, Dates, and Provenance

Two records can contain the same amount and date while representing separate payments. Conversely, the same identifier received twice may represent a duplicate, correction, or versioned event.

A row validator cannot decide the whole dataset's duplicate policy. The lab requires a nonblank identifier but does not enforce collection-wide uniqueness.

Real datasets may need source system, source record identifier, observation timestamp, effective date, ingestion timestamp, and revision. Preserve enough context to understand corrections and avoid using information before it was available in historical analysis.

## 4.1.11 Hands-On Lab — Validate a Payment Record

Save this self-contained module as structured_information_lab.py. It uses Python 3.10 or later and only the standard library.

The validator accepts a dictionary with exactly five string keys. It returns a new dictionary, preserving the original validated values. Decimal, date, and string values in this schema are immutable.

Calendar dates must be date objects rather than datetime objects. The exact-type check deliberately excludes datetime's date subclass relationship. This policy is specific to a date-only record.

```python
"""Validate a small date-only investor payment schema."""

from datetime import date
from decimal import Decimal
import unittest


def validate_payment(record: object) -> dict[str, object]:
    """Validate a payment and return a new record dictionary.

    Require exactly payment_id, amount, currency, payment_date, perspective.
    ID is nonblank text; amount is finite Decimal and may be signed or zero.
    Currency is USD or EUR; payment_date is exactly datetime.date.
    Perspective is investor: positive receipt, negative payment.

    Do not parse, normalize, convert currencies, calculate a valuation,
    enforce collection-wide identity, or mutate the input.
    Raise TypeError for representations and ValueError for schema/domains.
    """
    if not isinstance(record, dict):
        raise TypeError("record must be a dictionary")
    required = {
        "payment_id", "amount", "currency", "payment_date", "perspective"
    }
    if set(record) != required:
        raise ValueError("record must contain exactly the required fields")

    identifier = record["payment_id"]
    if not isinstance(identifier, str):
        raise TypeError("payment_id must be text")
    if not identifier.strip():
        raise ValueError("payment_id must be nonblank")

    amount = record["amount"]
    if not isinstance(amount, Decimal):
        raise TypeError("amount must be Decimal")
    if not amount.is_finite():
        raise ValueError("amount must be finite")

    currency = record["currency"]
    if not isinstance(currency, str):
        raise TypeError("currency must be text")
    if currency not in ("USD", "EUR"):
        raise ValueError("currency must be USD or EUR")

    payment_date = record["payment_date"]
    if type(payment_date) is not date:
        raise TypeError("payment_date must be a date-only object")

    perspective = record["perspective"]
    if not isinstance(perspective, str):
        raise TypeError("perspective must be text")
    if perspective != "investor":
        raise ValueError("perspective must be investor")

    return {
        "payment_id": identifier,
        "amount": amount,
        "currency": currency,
        "payment_date": payment_date,
        "perspective": perspective,
    }


def sample_payment() -> dict[str, object]:
    """Return a fresh invented payment record for the demonstration."""
    return {
        "payment_id": "P001",
        "amount": Decimal("1000.00"),
        "currency": "USD",
        "payment_date": date(2027, 1, 15),
        "perspective": "investor",
    }


class TestPaymentSchema(unittest.TestCase):
    """Check selected structural and financial schema boundaries."""

    def test_valid_copy(self) -> None:
        source = sample_payment()
        result = validate_payment(source)
        self.assertEqual(result, source)
        self.assertIsNot(result, source)
        result["currency"] = "EUR"
        self.assertEqual(source["currency"], "USD")

    def test_zero_and_signed_amounts(self) -> None:
        for amount in ("0", "-250", "1000"):
            with self.subTest(amount=amount):
                source = sample_payment()
                source["amount"] = Decimal(amount)
                self.assertEqual(validate_payment(source)["amount"], Decimal(amount))

    def test_missing_and_extra_fields(self) -> None:
        missing = sample_payment()
        del missing["amount"]
        with self.assertRaises(ValueError):
            validate_payment(missing)
        extra = sample_payment()
        extra["ammount"] = Decimal("10")
        with self.assertRaises(ValueError):
            validate_payment(extra)

    def test_invalid_amounts(self) -> None:
        for value in (None, "1000", 1000.0):
            source = sample_payment()
            source["amount"] = value
            with self.assertRaises(TypeError):
                validate_payment(source)
        source = sample_payment()
        source["amount"] = Decimal("NaN")
        with self.assertRaises(ValueError):
            validate_payment(source)

    def test_metadata_domains(self) -> None:
        cases = [
            ("payment_id", ""),
            ("currency", "usd"),
            ("perspective", "borrower"),
        ]
        for field, value in cases:
            with self.subTest(field=field):
                source = sample_payment()
                source[field] = value
                with self.assertRaises(ValueError):
                    validate_payment(source)

    def test_date_representation(self) -> None:
        from datetime import datetime

        for value in ("2027-01-15", datetime(2027, 1, 15)):
            source = sample_payment()
            source["payment_date"] = value
            with self.assertRaises(TypeError):
                validate_payment(source)


if __name__ == "__main__":
    unittest.main()
```

Run on Windows:

```powershell
py -m unittest -v structured_information_lab
```

Run on macOS or Linux:

```bash
python3 -m unittest -v structured_information_lab
```

Expected summary: **6 tests, OK**. Subtests cover additional input cases.

The validator performs no monetary arithmetic and does not set a numerical context. Downstream calculation functions must still apply their documented numerical policy.

## 4.1.12 What the Validator Does Not Establish

A valid record is structurally and semantically compatible with this small schema. It is not evidence that the payment occurred, the amount is correct, or the identifier is globally unique.

The copy is shallow. It is sufficient for this schema's immutable field values, but a later nested mutable field would require revisiting the ownership contract.

TypedDict, dataclasses, and external schema libraries can offer additional tools when appropriate. This introductory section uses built-in structures and explicit validation so the rules remain visible.

## 4.1.15 Troubleshooting Guide

| Symptom | Likely cause | Correction |
|---|---|---|
| KeyError during calculation | Required field missing or misspelled | Validate the schema before calculation |
| Total has unclear currency | Incompatible amount metadata | Group or convert under an explicit policy |
| Missing payment becomes zero | Absence silently defaulted | Preserve and resolve missing-value meaning |
| Valid date object used as a timestamp | Calendar date confused with instant | Define the needed temporal representation |
| Copied nested data changes the source | Shallow copy shares mutable values | Review ownership and nested copying |
| Duplicate rows inflate a result | Dataset identity rule absent | Validate collection-level keys |
| Valid schema gives wrong valuation | Data compatibility mistaken for model correctness | Review the calculation contract separately |

## 4.1.16 Key Takeaways

Financial data combines values with identity, units, time, and interpretation. Containers hold that information; schemas define what it means and which representations are supported.

Validate records before calculation, preserve missing-value meaning, and keep record-level checks distinct from dataset identity and financial-model review.
