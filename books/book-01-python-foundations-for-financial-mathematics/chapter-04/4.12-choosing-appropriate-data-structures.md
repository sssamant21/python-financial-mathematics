## 4.12.1 Purpose

Choose a representation by the questions the program must answer and the information it must preserve. A cash-flow schedule needs event identity and time; a security catalog needs lookup by identity; a membership check may need only a set of identifiers.

One dataset may support several views. The design challenge is to specify which view is authoritative, which information each derived view omits, and how changes propagate. This section combines the chapter's structures in a small, validated holdings example that prepares for the portfolio-manager project.

## 4.12.2 Learning Objectives

You should be able to:

1. Select structures by order, identity, multiplicity, and ownership requirements.
2. Explain the information lost by a conversion.
3. Separate an authoritative snapshot from derived lookup and membership views.
4. Define how derived views are refreshed after changes.
5. Reject duplicate keys before building a lookup.
6. Preserve zero records and empty snapshots deliberately.
7. Verify consistency and independence across multiple representations.

## 4.12.3 Begin with Required Operations

Before choosing syntax, write the contract: What identifies a record? Can the same identity occur twice? Does source order matter? Will callers change the result? Must events with equal values remain distinct?

For example, a list can preserve two same-day payments, whereas a mapping from date to one amount cannot preserve both without a separate aggregation rule. A set can answer whether an instrument occurs but cannot retain its position quantity or repeated occurrences.

## 4.12.4 Decision Matrix

| Requirement | Candidate | Design check |
|---|---|---|
| Ordered working records, repetitions retained | List | Define ordering and mutation policy |
| Fixed ordered scalar record or snapshot | Tuple | Validate descendants before claiming immutability |
| Record lookup by unique identity | Dictionary | Reject or resolve duplicate keys explicitly |
| Membership or identity comparison | Set | No business ordering or multiplicity retained |
| Immutable membership view | Frozenset | Elements still need valid hash/equality behavior |
| Parent/child relationship | Nested records | Preserve parent identity and validate every layer |
| Many children under one key | Dictionary of lists or tuples | Define group order and child identity |

Lists and tuples preserve sequence; dictionaries retain insertion order, but that is not automatically the desired report order. Sets and frozensets do not define a business sequence. Dictionary keys and set elements must be hashable. A tuple containing a list is unsuitable as a hash key.

These properties constrain the representation. Financial rules still come from the schema: a dictionary does not enforce unique positions in an input list, and a tuple does not establish correct unit conventions.

## 4.12.5 Make Information Loss Visible

Run the introductory Python blocks in order in one session.

```python
from decimal import Decimal

records = [
    ("SEC-A", Decimal("1")),
    ("SEC-A", Decimal("2")),
    ("SEC-B", Decimal("0")),
]
ids_only = {security_id for security_id, quantity in records}
assert ids_only == {"SEC-A", "SEC-B"}
assert len(records) == 3
assert len(ids_only) == 2

last_quantity = {security_id: quantity for security_id, quantity in records}
assert last_quantity == {"SEC-A": Decimal("2"), "SEC-B": Decimal("0")}
```

The ID set intentionally discards quantities and multiplicity. The dictionary replaces the first SEC-A quantity rather than aggregating it. Neither conversion is a substitute for resolving whether the source represents lots, transactions, or aggregate positions.

A legitimate aggregation requires compatible units and an explicit arithmetic policy. The lab instead defines one record per security and rejects duplicates.

## 4.12.6 One Snapshot, Several Derived Views

```python
snapshot = (("SEC-B", Decimal("0")), ("SEC-A", Decimal("12.5")))
lookup = dict(snapshot)  # This known fixture already has unique IDs.
members = frozenset(lookup)
assert snapshot[0][0] == "SEC-B"
assert lookup["SEC-A"] == Decimal("12.5")
assert "SEC-B" in members
assert sorted(members) == ["SEC-A", "SEC-B"]
```

The tuple supplies the authoritative holdings order for this example. The lookup supports ID-based access; the frozenset describes membership. An explicit sort supplies a display order for IDs.

The lab's snapshot has only exact strings and Decimal values. It is the holdings component of a portfolio, not a complete persisted portfolio record. Portfolio identity, snapshot identity, units, and provenance remain application metadata.

## 4.12.7 Derived Views Do Not Update Themselves

```python
lookup["SEC-A"] = Decimal("99")
lookup["SEC-C"] = Decimal("1")
assert snapshot[1][1] == Decimal("12.5")
assert "SEC-C" not in members
```

The views now disagree because the mutable lookup was edited. The lab returns a disposable lookup: callers may edit it, but those edits do not update the authoritative tuple. To change the source of truth, build a new validated snapshot and rebuild its derived views together.

Keeping two independently editable masters creates a synchronization problem. A helper that returns a dictionary is not automatically a live index or cache-invalidation mechanism.

## 4.12.8 Lab Contract — Build Purpose-Specific Views

Save the complete next block as `data_structure_choice_lab.py`. Use Python 3.10 or later with the standard library.

| Item | Contract |
|---|---|
| Input | List of records with exactly security_id and quantity |
| security_id | Exact nonempty unpadded str; unique in input |
| quantity | Exact finite nonnegative Decimal units |
| Authoritative result | Immutable scalar-pair tuple in input order |
| Lookup result | Fresh mutable dictionary mapping ID to quantity |
| Membership result | Frozenset of all IDs, including zero holdings |
| Empty input | Empty tuple, dictionary, and frozenset |
| All results | Built from one complete validated input pass |
| Ownership | No input dictionaries retained; lookup changes cannot change snapshot or membership |
| Failure | TypeError for types; ValueError for schema/domain/duplicates |

The result is a tuple containing the three views. They agree at return time. The function does not monitor future changes to a returned lookup. It performs no arithmetic, aggregation, valuation, or currency conversion.

## 4.12.9 Complete Runnable Lab

```python
"""Choose ordered snapshot, lookup, and membership views deliberately."""

from decimal import Decimal
import unittest

Holding = tuple[str, Decimal]
Snapshot = tuple[Holding, ...]
Views = tuple[Snapshot, dict[str, Decimal], frozenset[str]]


def build_views(value: object) -> Views:
    """Validate unique scalar holdings and return three independent-purpose views.

    Snapshot order follows input. Zero holdings remain present in every view.
    The lookup is disposable; editing it does not update the other results.
    """
    if not isinstance(value, list):
        raise TypeError("holdings must be a list")
    validated: list[Holding] = []
    seen: set[str] = set()
    for index, row in enumerate(value):
        if not isinstance(row, dict):
            raise TypeError(f"holding {index} must be a dictionary")
        if set(row) != {"security_id", "quantity"}:
            raise ValueError(f"holding {index} has incorrect fields")
        security_id = row["security_id"]
        quantity = row["quantity"]
        if type(security_id) is not str:
            raise TypeError("security_id must be an exact str")
        if not security_id or security_id.strip() != security_id:
            raise ValueError("security_id must be nonempty and unpadded")
        if type(quantity) is not Decimal:
            raise TypeError("quantity must be an exact Decimal")
        if not quantity.is_finite() or quantity < 0:
            raise ValueError("quantity must be finite and nonnegative")
        if security_id in seen:
            raise ValueError(f"duplicate security_id: {security_id}")
        seen.add(security_id)
        validated.append((security_id, quantity))

    snapshot = tuple(validated)
    lookup = dict(snapshot)
    members = frozenset(lookup)
    return snapshot, lookup, members


def sample_holdings() -> list[dict[str, object]]:
    return [
        {"security_id": "SEC-B", "quantity": Decimal("0")},
        {"security_id": "SEC-A", "quantity": Decimal("12.5")},
    ]


class StructureChoiceTests(unittest.TestCase):
    def test_exact_views_and_order(self) -> None:
        snapshot, lookup, members = build_views(sample_holdings())
        self.assertEqual(snapshot, (("SEC-B", Decimal("0")), ("SEC-A", Decimal("12.5"))))
        self.assertEqual(lookup, {"SEC-B": Decimal("0"), "SEC-A": Decimal("12.5")})
        self.assertEqual(list(lookup), ["SEC-B", "SEC-A"])
        self.assertEqual(members, frozenset({"SEC-A", "SEC-B"}))
        self.assertIs(type(snapshot), tuple)
        self.assertIs(type(members), frozenset)
        for row in snapshot:
            self.assertIs(type(row), tuple)
            self.assertIs(type(row[0]), str)
            self.assertIs(type(row[1]), Decimal)

    def test_empty(self) -> None:
        self.assertEqual(build_views([]), ((), {}, frozenset()))

    def test_source_and_lookup_independence(self) -> None:
        source = sample_holdings()
        snapshot, lookup, members = build_views(source)
        self.assertEqual(source, sample_holdings())
        source[0]["quantity"] = Decimal("88")
        source.append({"security_id": "SOURCE-ONLY", "quantity": Decimal("1")})
        lookup["SEC-A"] = Decimal("99")
        lookup["LOOKUP-ONLY"] = Decimal("2")
        del lookup["SEC-B"]
        self.assertEqual(snapshot, (("SEC-B", Decimal("0")), ("SEC-A", Decimal("12.5"))))
        self.assertEqual(members, frozenset({"SEC-A", "SEC-B"}))
        self.assertEqual(source[1]["quantity"], Decimal("12.5"))

    def test_rebuild_from_new_source(self) -> None:
        source = sample_holdings()
        old_snapshot, old_lookup, old_members = build_views(source)
        source.append({"security_id": "SEC-C", "quantity": Decimal("3")})
        new_snapshot, new_lookup, new_members = build_views(source)
        self.assertEqual(new_snapshot[-1], ("SEC-C", Decimal("3")))
        self.assertEqual(new_lookup["SEC-C"], Decimal("3"))
        self.assertIn("SEC-C", new_members)
        self.assertEqual(len(old_snapshot), 2)
        self.assertNotIn("SEC-C", old_lookup)
        self.assertNotIn("SEC-C", old_members)

    def test_duplicate_rejection_including_zero(self) -> None:
        with self.assertRaises(ValueError):
            build_views([
                {"security_id": "A", "quantity": Decimal("0")},
                {"security_id": "A", "quantity": Decimal("1")},
            ])

    def test_schema_identity_and_quantity(self) -> None:
        bad_sources: list[object] = [None, {}, (), [None]]
        for source in bad_sources:
            with self.subTest(source=source):
                with self.assertRaises(TypeError):
                    build_views(source)
        for row in ({}, {"security_id": "A", "quantity": Decimal("0"), "extra": 1}):
            with self.assertRaises(ValueError):
                build_views([row])
        for sid in ("", " A", "A "):
            with self.assertRaises(ValueError):
                build_views([{"security_id": sid, "quantity": Decimal("0")}])
        with self.assertRaises(TypeError):
            build_views([{"security_id": 1, "quantity": Decimal("0")}])
        for quantity in (None, True, 1, 1.5, "1"):
            with self.subTest(quantity=quantity):
                with self.assertRaises(TypeError):
                    build_views([{"security_id": "A", "quantity": quantity}])
        for text in ("NaN", "sNaN", "Infinity", "-Infinity", "-1"):
            with self.subTest(text=text):
                with self.assertRaises(ValueError):
                    build_views([{"security_id": "A", "quantity": Decimal(text)}])

    def test_invalid_later_record_preserves_source(self) -> None:
        source = sample_holdings()
        source.append({"security_id": "BAD", "quantity": "missing"})
        before = [dict(row) for row in source]
        with self.assertRaises(TypeError):
            build_views(source)
        self.assertEqual(source, before)


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

## 4.12.11 Cost and Scale Without Guesswork

Each additional view stores extra references and container bookkeeping. That cost can be worthwhile when the application repeatedly needs both ordered traversal and lookup. Avoid creating every possible index simply because it is convenient.

Measure representative input size, lookup frequency, rebuild frequency, and memory use before optimizing. The lab is a design demonstration, not a benchmark. It makes no claim that three views are necessary for every portfolio.

Large analytical tables and numerical arrays appear in later chapters. Databases can supply persistence, query execution, and transaction semantics. Changing the storage technology does not remove the need to define identity, units, order, duplicates, and missing values.

## 4.12.12 Design Review Checklist

For a concrete representation, answer the following before adding calculations:

1. What is the authoritative input or snapshot?
2. What identifies each record, and within which scope?
3. Which repetitions are valid, and which are errors?
4. Which order is preserved or explicitly constructed?
5. Which fields or distinctions does each conversion discard?
6. Which mutable objects can callers change?
7. When must derived views be rebuilt?
8. How are empty, zero, missing, and invalid inputs distinguished?

These questions connect the structures to a financial contract. They should produce specific answers, such as “one holding per security in this portfolio snapshot,” rather than broad claims such as “a dictionary is best.”

## 4.12.13 Troubleshooting

| Symptom | Cause to inspect | Correction |
|---|---|---|
| Duplicate holdings disappear | Lookup created before identity checks | Validate before indexing |
| Report order changes | Set iteration treated as report order | Sort explicitly or retain a sequence |
| Lookup edits do not appear in snapshot | Views are independent | Update the authoritative input and rebuild |
| Baseline changes through a report | Mutable rows shared | Reconstruct or capture supported immutable fields |
| Empty snapshot loses identity | Metadata stored only in holdings | Keep a parent wrapper |
| Zero position absent from membership | Truth filter applied | Include every valid ID under this contract |
| Lots disappear | Aggregate-position key used for lots | Define lot-level identity |

## 4.12.15 Key Takeaways

Choose structures by preserved meaning and required operations. Use sequences for order, dictionaries for identity lookup, and sets for membership when those contracts fit.

Define one authoritative version, make information loss explicit, and rebuild derived views consistently. Representation choices support financial correctness only when identity, units, validation, and ownership are specified.
