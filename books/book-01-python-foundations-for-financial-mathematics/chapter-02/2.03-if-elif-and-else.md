## 2.3.1 From Conditions to Conditional Execution

Sections 2.1 and 2.2 developed financial conditions and compound Boolean expressions. These expressions answer questions, but a financial program often needs to perform an action based on the answer. Python provides `if`, `elif`, and `else` for conditional execution.

```text
financial values
      ↓
comparison
      ↓
Boolean condition
      ↓
if / elif / else
      ↓
selected execution path
```

## 2.3.2 What Is Control Flow?

Python normally executes statements sequentially. Conditional statements change that sequence by allowing execution to follow different paths based on truth-value testing. This selection of execution paths is part of control flow.

## 2.3.3 Anatomy of an `if` Statement

```python
from decimal import Decimal

profit_loss = Decimal("1250.00")

if profit_loss > 0:
    print("The investment is profitable.")
```

If the condition is truthy, the controlled statements execute. If it is falsy, the suite is skipped and execution continues after the `if` statement.

## 2.3.4 Conditions, Clauses, and Suites

Python's language reference describes the `if`, `elif`, and `else` parts as clauses. The indented statements controlled by a clause header form its suite. This book also uses the terms branch and block where they make the decision structure easier to understand.

```python
if profit_loss > 0:
    classification = "Profit"
elif profit_loss < 0:
    classification = "Loss"
else:
    classification = "Break-even"
```

## 2.3.5 Colon and Indentation

A conditional clause header ends with a colon, and its suite is indented.

```python
if balance >= minimum_balance:
    print("Minimum balance satisfied.")
```

Indentation is syntactically significant in Python. This book uses four spaces per indentation level, consistent with PEP 8 style guidance. Four spaces are a style recommendation rather than a requirement that defines Python's grammar.

## 2.3.6 Named Boolean Conditions

```python
meets_minimum_balance = balance >= minimum_balance

if meets_minimum_balance:
    print("Minimum balance satisfied.")
```

Named conditions can make important financial reasoning easier to inspect and test.

## 2.3.7 Two-Way Decisions with `else`

```python
if balance >= minimum_balance:
    status = "Minimum Balance Satisfied"
else:
    status = "Minimum Balance Not Satisfied"
```

For an `if`/`else` statement, exactly one of the two suites executes. `else` has no condition; it handles the path where the preceding condition did not select its suite.

## 2.3.8 Multiway Decisions with `elif`

`elif` tests another condition when earlier conditions in the same `if` statement were not truthy.

```python
if condition_1:
    ...
elif condition_2:
    ...
else:
    ...
```

Multiple `elif` clauses are allowed.

## 2.3.9 Profit, Loss, and Break-Even

A two-way profit/loss model can incorrectly classify zero when the financial model recognizes break-even separately.

```python
profit_loss = Decimal("0.00")

if profit_loss > 0:
    classification = "Profit"
elif profit_loss < 0:
    classification = "Loss"
else:
    classification = "Break-even"
```

The control-flow structure should reflect the states defined by the financial model.

## 2.3.10 First-Match Execution

Python evaluates `if` and `elif` conditions in order. The suite belonging to the first truthy condition executes. Later conditions and suites in that same `if` statement are skipped.

If no condition is truthy, the `else` suite executes when `else` is present; otherwise, no suite in that `if` statement executes.

## 2.3.11 Branch Ordering

```python
return_rate = Decimal("0.12")

if return_rate >= Decimal("0.10"):
    classification = "High"
elif return_rate >= Decimal("0.05"):
    classification = "Target"
else:
    classification = "Below Target"
```

For overlapping lower-bound thresholds such as these, the more restrictive threshold must be tested before the broader one. Branch order is part of the model. Other decision structures may require different ordering.

## 2.3.12 Multiple `elif` Clauses

```python
if return_rate >= Decimal("0.15"):
    classification = "Exceptional"
elif return_rate >= Decimal("0.10"):
    classification = "High"
elif return_rate >= Decimal("0.05"):
    classification = "Target"
else:
    classification = "Below Target"
```

These categories are instructional examples rather than universal investment classifications.

## 2.3.13 Independent `if` Statements Versus `elif`

Separate `if` statements are independent, so more than one suite can execute.

```python
if return_rate >= Decimal("0.05"):
    reached_target = True

if return_rate >= Decimal("0.10"):
    reached_high_return = True
```

A single `if`/`elif` chain selects at most one suite. A useful design heuristic is to use separate `if` statements for independent conditions or actions and an `if`/`elif`/`else` chain for alternative paths, subject to the actual model requirements.

## 2.3.14 Optional `elif` and `else`

Neither `elif` nor `else` is mandatory. Python supports `if` alone, `if` with `else`, and multiway `if`/`elif`/`else` forms. The appropriate structure depends on how many execution paths the model requires.

## 2.3.15 Compound Conditions

```python
is_profitable = profit_loss > 0
meets_target_return = return_rate >= target_return
meets_requirements = is_profitable and meets_target_return

if meets_requirements:
    print("Scenario meets the model requirements.")
```

For consequential or complicated logic, named conditions can make the model easier to review.

## 2.3.16 Multiline Conditions

```python
if (
    investment_amount >= minimum_investment
    and return_rate >= target_return
    and profit_loss > 0
):
    classification = "Meets Model Requirements"
```

This book generally prefers parenthesized multiline formatting for longer conditions because it exposes their structure clearly. Python permits other valid formatting approaches.

## 2.3.17 Truthiness in Conditional Statements

The expression following `if` does not need to produce the literal object `True` or `False`; Python tests its truth value.

```python
balance = Decimal("100.00")

if balance:
    print("Balance is nonzero.")
```

Financial code often benefits from expressing the intended question explicitly:

```python
if balance != 0:
    print("Balance is nonzero.")
```

Similarly, `if currency:` tests whether a string is nonempty; it does not establish that the currency is approved. Truth-value testing is not a substitute for financial-domain validation.

## 2.3.18 Missing Values and `None`

```python
if rate is None:
    print("Rate is unavailable.")
```

An application may choose to interpret `None` as missing or unavailable data, but Python itself does not assign a financial meaning to it. `None` is also distinct from a numerical value such as `Decimal("0")`.

## 2.3.19 Guarding Dependent Calculations

```python
initial_investment = Decimal("0.00")
profit_loss = Decimal("500.00")

if initial_investment != 0:
    return_rate = profit_loss / initial_investment
else:
    return_rate = None
```

The `if` statement prevents a zero-denominator calculation. Assigning `None` is only one instructional representation of an unavailable result; actual treatment depends on the specification.

## 2.3.20 `else` Is Not a Validation Guarantee

```python
if rate >= minimum_rate:
    status = "Accepted"
else:
    status = "Rejected"
```

`else` does not inherently mean valid, safe, or rejected. It means that none of the preceding conditions in that `if` statement was truthy. Real systems may need to distinguish valid alternatives from missing, malformed, non-finite, or otherwise unsupported states. Defensive input validation is developed in Section 2.11.

## 2.3.21 Nested Control Flow — Preview

```python
if investment_amount > 0:
    if return_rate >= target_return:
        print("Requirements satisfied.")
```

In a simple case, a combined condition may produce the same visible outcome, but nesting and Boolean combination are not universally interchangeable. Substantial treatment of nesting is reserved for Section 2.9.

## 2.3.22 Decision Tables Before Branches

| Profit/Loss | Expected Classification |
|---:|---|
| greater than 0 | Profit |
| equal to 0 | Break-even |
| less than 0 | Loss |

A decision table states the intended model independently before the branch structure is implemented. It can expose missing cases, overlapping conditions, incorrect boundaries, and problematic branch ordering.

## 2.3.23 Boundary Testing

For a minimum balance of 10,000:

| Balance | Expected |
|---:|---|
| 9,999.99 | Requirement Not Satisfied |
| 10,000.00 | Requirement Satisfied |
| 10,000.01 | Requirement Satisfied |

Testing below, at, and above an important threshold verifies the intended equality boundary.

## 2.3.24 Multi-Branch Testing

For the instructional return classification:

| Return Rate | Expected |
|---:|---|
| 0.049 | Below Target |
| 0.050 | Target |
| 0.099 | Target |
| 0.100 | High |
| 0.149 | High |
| 0.150 | Exceptional |
| 0.200 | Exceptional |

This verifies both threshold boundaries and branch ordering.

## 2.3.25 Branch Completeness

Before coding a multiway decision, identify the meaningful states defined by the current model. For profit/loss, positive, zero, and negative values have explicit outcomes. This is branch completeness relative to the model; it does not imply that every introductory example must handle every malformed or unsupported input.

## 2.3.26 Common Mistakes

Common mistakes include missing the colon, incorrect indentation, using assignment `=` instead of equality comparison `==`, testing broader overlapping thresholds before more restrictive ones, treating zero as loss when break-even is a separate state, confusing independent `if` statements with `elif`, relying on truthiness when an explicit financial question would be clearer, treating `else` as proof of validity, and creating excessive nesting.

## 2.3.27 Financial Conditional Design Pattern

```text
1. Write the financial requirement
             ↓
2. Identify meaningful states
             ↓
3. Define mathematical boundaries
             ↓
4. Determine whether conditions are independent or alternative
             ↓
5. Calculate required values
             ↓
6. Construct Boolean conditions
             ↓
7. Order overlapping branches deliberately
             ↓
8. Implement if / elif / else
             ↓
9. Test below, at, and above important boundaries
             ↓
10. Test every meaningful branch
             ↓
11. Verify the financial interpretation
```

A useful correctness hierarchy is:

```text
syntactically valid
       ↓
computationally valid
       ↓
mathematically valid
       ↓
branch-complete
       ↓
model-valid
       ↓
financially meaningful
```

A program can execute without error and still select the wrong financial path.

## 2.3.28 Production-Minded Perspective

Conditional statements can influence whether calculations proceed, exceptions are identified, scenarios receive classifications, transactions enter processing paths, reconciliation items require review, or operational thresholds are considered crossed.

Production financial control flow should trace back to explicit requirements. Important practices include separating calculations from decisions when practical, using precise boundaries, distinguishing missing values from legitimate zero values, deliberately ordering overlapping branches, distinguishing independent actions from alternative paths, avoiding accidental catch-all behavior, using descriptive conditions, testing every meaningful execution path, testing equality boundaries, handling invalid or unsupported input states appropriately, and keeping complicated decision logic reviewable.

The examples in this section are instructional models, not universal accounting, banking, trading, investment, contractual, compliance, credit, fraud, regulatory, or risk-management policies.

## 2.3.29 From Branching Syntax to Financial Decision Rules

This section established the mechanics of conditional execution. Production-minded models must additionally define actual decision states, thresholds, inclusive or exclusive boundaries, independent versus overlapping conditions, rule priority, expected actions, and verification strategy. Section 2.4 develops this next layer: systematic financial decision-rule modeling.

## 2.3.30 Section Summary

Python conditional execution is built primarily around `if`, `elif`, and `else`. Clause headers end with a colon, indentation defines suites, and Python evaluates `if` and `elif` conditions from top to bottom. The first truthy condition selects its suite; later conditions in that same `if` statement are not evaluated. Without `else`, no suite may execute when every condition is falsy.

Branch ordering matters when conditions overlap. Separate `if` statements can execute independently. Truthiness does not establish financial validity, `None` is distinct from numerical zero, control flow can guard dependent calculations, `else` is not a validation guarantee, and decision tables plus boundary and multi-branch tests help verify intended behavior.

```text
financial specification
       ↓
calculation
       ↓
comparison
       ↓
Boolean condition
       ↓
if / elif / else
       ↓
selected execution path
       ↓
financial result or action
```
