## From Financial Conditions to Operators

Section 2.1 introduced Boolean financial conditions. Comparison operators construct individual conditions, while logical operators combine or modify them to form compound rules. This section develops those operators while reserving conditional execution for Section 2.3.

## Comparison Operators

| Operator | Meaning |
|---|---|
| `==` | equal to |
| `!=` | not equal to |
| `<` | less than |
| `<=` | less than or equal to |
| `>` | greater than |
| `>=` | greater than or equal to |

For the ordinary built-in numeric and `Decimal` values used in this book, these comparisons produce Boolean results.

```python
from decimal import Decimal

balance = Decimal("12500.00")
minimum_balance = Decimal("10000.00")
meets_minimum_balance = balance >= minimum_balance
```

## Assignment Versus Equality

`=` assigns a value; `==` compares values.

```python
balance = Decimal("1000.00")
is_exact_value = balance == Decimal("1000.00")
```

## Inclusive and Exclusive Boundaries

`<` and `>` exclude equality. `<=` and `>=` include equality. A single equality boundary can change the financial meaning of a rule.

Common translations include: equal to → `==`; different from → `!=`; below → `<`; at most → `<=`; above → `>`; at least → `>=`. These are translation aids; the governing specification determines the actual boundary.

## Exact Equality Versus Financial Tolerance

```python
system_a = Decimal("1000.000")
system_b = Decimal("1000.006")
tolerance = Decimal("0.010")

difference = abs(system_a - system_b)
is_reconciled = difference <= tolerance
```

Although the systems are numerically unequal, the reconciliation condition is `True` under this tolerance-based model. Numerical inequality does not necessarily imply a financial reconciliation exception when an acceptable tolerance is defined.

## Storing Comparison Results

```python
meets_minimum_balance = balance >= minimum_balance
exceeds_exposure_limit = exposure > exposure_limit
has_reconciliation_exception = difference > tolerance
```

Descriptive Boolean names make the financial meaning of `True` visible.

## Logical Operators

Python's primary logical operators are `and`, `or`, and `not`.

| A | B | `A and B` | `A or B` |
|---|---|---|---|
| `True` | `True` | `True` | `True` |
| `True` | `False` | `False` | `True` |
| `False` | `True` | `False` | `True` |
| `False` | `False` | `False` | `False` |

| A | `not A` |
|---|---|
| `True` | `False` |
| `False` | `True` |

## Compound Financial Conditions

```python
investment_amount = Decimal("25000.00")
profit_loss = Decimal("2000.00")
return_rate = Decimal("0.08")
target_return = Decimal("0.05")
minimum_investment = Decimal("10000.00")

is_profitable = profit_loss > 0
meets_target_return = return_rate >= target_return
meets_minimum_investment = investment_amount >= minimum_investment

meets_model_requirements = (
    is_profitable
    and meets_target_return
    and meets_minimum_investment
)
```

Named intermediate conditions improve readability, testing, debugging, and reviewability when they expose important financial reasoning.

## Truthiness and Operand-Returning Behavior

`and` and `or` use truth-value testing and do not necessarily return literal `True` or `False`.

```python
print(0 or 100)    # 100
print(50 and 100)  # 100
```

They can return operands. By contrast, `not` produces a Boolean result. Explicit comparisons and descriptive Boolean variables are generally clearer for financial rules.

## Logical Versus Bitwise Operators

Do not confuse logical `and`, `or`, and `not` with bitwise operators such as `&`, `|`, and `^`. For the ordinary Boolean financial conditions developed here, use logical operators. Bitwise operations serve different purposes.

## Short-Circuit Evaluation

Python evaluates `and` and `or` from left to right and may stop before evaluating every operand.

```python
initial_investment = Decimal("0.00")
profit_loss = Decimal("500.00")
target_rate = Decimal("0.05")

has_nonzero_investment = initial_investment != 0

meets_target = (
    has_nonzero_investment
    and (
        profit_loss / initial_investment >= target_rate
    )
)
```

Because the left operand is false, the dependent division is not evaluated. Short-circuit evaluation can guard a dependent expression, but it does not make invalid input valid and does not replace proper input validation.

## Operator Precedence and Parentheses

For the operators relevant here, a useful hierarchy is:

```text
comparisons
     ↓
not
     ↓
and
     ↓
or
```

Thus `A or B and C` is interpreted as `A or (B and C)`, and `not a == b` means `not (a == b)`. An expression such as `a == not b` is invalid syntax.

Even when precedence already produces the desired result, parentheses can expose financial intent:

```python
requires_review = (
    exceeds_limit
    or (
        is_unreconciled
        and is_material
    )
)
```

## Chained Comparisons

Python supports chained comparisons:

```python
minimum_rate = Decimal("0.02")
maximum_rate = Decimal("0.10")
rate = Decimal("0.06")

is_within_range = minimum_rate <= rate <= maximum_rate
```

This maps naturally to the mathematical relationship `minimum_rate ≤ rate ≤ maximum_rate`. The middle expression is evaluated only once, and chained comparisons short-circuit if an earlier comparison fails.

Boundary behavior:

| Rate | Expected |
|---:|---|
| 0.019 | `False` |
| 0.020 | `True` |
| 0.060 | `True` |
| 0.100 | `True` |
| 0.101 | `False` |

## Equality Versus Identity

`==` tests value equality; `is` tests object identity. Do not use `amount is Decimal("100.00")` to test financial value equality. Use `amount == Decimal("100.00")`.

Identity testing is appropriate for singleton objects such as `None`:

```python
value is None
```

## Membership Conditions

```python
allowed_currencies = {"USD", "EUR", "GBP"}
currency = "USD"
is_supported_currency = currency in allowed_currencies
```

`in` and `not in` support conditions based on membership in approved categories. For dictionaries, membership tests keys.

## Decimal Special Values

`Decimal` can represent `NaN`, `Infinity`, and `-Infinity`.

```python
rate = Decimal("NaN")
is_finite_rate = rate.is_finite()
```

For `Decimal` NaN values, equality comparisons return `False`, inequality comparisons return `True`, and ordering comparisons using `<`, `<=`, `>`, or `>=` signal `InvalidOperation`. Whether that signal raises an exception depends on the active decimal context and its trap configuration; when not trapped, the ordering comparison returns `False`.

Financial quantities expected to be ordinary finite values should normally be validated before ordered comparisons are relied upon.

exceeds_limit = exposure > exposure_limit

## Common Mistakes

Common mistakes include confusing `=` with `==`, choosing the wrong equality boundary, using exact equality where tolerance is specified, assuming `and` and `or` always return `bool`, confusing logical and bitwise operators, ignoring short-circuit evaluation order, using unnecessarily complex negation, relying on implicit precedence in complex rules, confusing identity with equality, and assuming every `Decimal` represents an ordinary finite amount.

## Financial Condition Design Pattern

```text
1. Write the financial rule
          ↓
2. Identify independent conditions
          ↓
3. Define boundaries explicitly
          ↓
4. Validate numerical prerequisites
          ↓
5. Perform required calculations
          ↓
6. Implement individual comparisons
          ↓
7. Give important conditions descriptive names
          ↓
8. Combine conditions with logical operators
          ↓
9. Use parentheses to expose intended grouping
          ↓
10. Test boundaries and logical scenarios
          ↓
11. Verify the financial interpretation
```

A useful correctness hierarchy is:

```text
Python-valid
     ↓
numerically valid
     ↓
mathematically valid
     ↓
model-valid
     ↓
financially meaningful
```

Valid syntax is only the beginning; executable code can still implement the wrong financial rule.

## Production-Minded Perspective

Important financial conditions should trace to explicit requirements, use the intended numerical representation, validate necessary prerequisites, define inclusive and exclusive boundaries precisely, distinguish exact equality from tolerance-based equivalence, expose important logical structure, account for evaluation order, and be tested at boundaries and across meaningful logical combinations.

The examples here demonstrate programming and modeling principles; they are not complete production financial policy engines or universal accounting, investment, contractual, compliance, credit, fraud, regulatory, or risk-management rules.
