## 2.6.1 From Item-Based Iteration to Condition-Based Repetition

Section 2.5 introduced the `for` loop. A `for` loop is especially natural when repetition follows items supplied through iteration. Financial models also contain situations in which repetition should continue while a condition remains satisfied. Python provides the `while` statement for condition-controlled repetition.

The central model is:

```text
financial state
      ↓
continuation rule
      ↓
financial transition
      ↓
new state
      ↓
repeat or terminate
```

## 2.6.2 What Is a `while` Loop?

The basic syntax is:

```python
while condition:
    statement
```

A `while` statement evaluates its controlling expression before each iteration. While that expression is truthy, Python executes the loop suite and then evaluates the expression again. Under ordinary condition-controlled completion, repetition stops when the controlling expression becomes falsy.

Financial models should generally prefer explicit continuation conditions such as:

```python
while balance < target_balance:
    ...
```

because the comparison communicates the model rule directly. Explicit loop-control mechanisms are developed later in Section 2.10.

## 2.6.3 Conditions and Pre-Test Behavior

A `while` loop is a pre-test loop. The condition is evaluated before the suite executes.

```python
balance = Decimal("12000.00")
target_balance = Decimal("10000.00")

while balance < target_balance:
    print(balance)
```

The first test is `12000 < 10000`, which is false, so the suite executes zero times. A `while` loop does not guarantee even one iteration.

## 2.6.4 State and Model Parameters

```python
balance = Decimal("8000.00")
target_balance = Decimal("10000.00")
contribution = Decimal("500.00")
periods = 0
```

In this simplified model, `balance` and `periods` are changing state, while `target_balance` and `contribution` are fixed model parameters. These roles are model-specific; a value fixed in one model may change in another.

## 2.6.5 First Financial `while` Loop

```python
balance = Decimal("8000.00")
target_balance = Decimal("10000.00")
contribution = Decimal("500.00")

while balance < target_balance:
    balance += contribution
```

State progression:

```text
8000 → 8500 → 9000 → 9500 → 10000
```

At `10000`, `balance < target_balance` is false and ordinary condition-controlled repetition ends.

## 2.6.6 Counting Iterations

```python
balance = Decimal("8000.00")
target_balance = Decimal("10000.00")
contribution = Decimal("500.00")
periods = 0

while balance < target_balance:
    balance += contribution
    periods += 1
```

Final state:

```text
balance = 10000.00
periods = 4
```

The counter placement should correspond to the event being counted. Here one period is counted with each applied contribution.

## 2.6.7 Financial Meaning of an Iteration

A loop iteration is a programming event. It is not automatically one month, year, payment period, trading day, or reporting cycle. The financial model must define what one iteration represents.

## 2.6.8 Repeated Growth Example

```python
balance = Decimal("10000.00")
target_balance = Decimal("12000.00")
growth_rate = Decimal("0.05")
periods = 0

while balance < target_balance:
    balance *= Decimal("1") + growth_rate
    periods += 1
```

The modeled recurrence is:

\[
B_{t+1}=B_t(1+r)
\]

Ignoring any separate quantization policy, the balance crosses the target after four modeled growth steps:

```text
10000 → 10500 → 11025 → 11576.25 → 12155.0625
```

This is an instructional compound-growth model, not a universal investment-crediting rule.

## 2.6.9 Threshold Boundaries and Overshoot

```python
balance = Decimal("9000.00")
target_balance = Decimal("10000.00")
contribution = Decimal("700.00")

while balance < target_balance:
    balance += contribution
```

Progression:

```text
9000 → 9700 → 10400
```

A stopping condition does not guarantee that the final state lands exactly on its boundary. Boundary inclusivity also matters: `<` and `<=` behave differently at equality, so the financial specification must define the intended operator.

## 2.6.10 Debt Reduction and Constrained Updates

A naive simplified debt transition can overshoot zero:

```text
2500 → 1900 → 1300 → 700 → 100 → -500
```

A constrained instructional transition is:

```python
balance = Decimal("2500.00")
regular_payment = Decimal("600.00")
payments = 0

while balance > 0:
    payment = min(regular_payment, balance)
    balance -= payment
    payments += 1
```

The final payment is `100.00`, ending at zero after five payments. `min()` constrains the state transition in this simplified model; it does not validate the inputs. Real debt servicing can involve interest, fees, timing, contractual rules, and other requirements.

The broader lesson is:

```text
correct loop termination ≠ correct financial transition
```

## 2.6.11 Designing for Termination

A `while` loop should have a clear termination story. Ask what condition allows repetition, what state affects that condition, how the state changes, whether the state moves in the intended direction, what assumptions make progress possible, and why ordinary repetition should eventually stop.

In deterministic financial models like those in this section, the suite usually updates state that affects the continuation condition.

## 2.6.12 Progress Toward Termination

For the target-balance example, define a progress measure:

\[
RemainingGap=TargetBalance-Balance
\]

The gap changes:

```text
2000 → 1500 → 1000 → 500 → 0
```

Thinking explicitly about progress helps identify loops whose state fails to move or moves in the wrong direction. This is introductory reasoning rather than a formal proof technique.

## 2.6.13 Infinite-Loop Risks

In the basic condition-controlled model developed here, an infinite loop occurs when execution continues indefinitely because no terminating event is reached. A relevant state that never changes, or one that moves away from the stopping boundary, can create this risk.

A syntactically valid loop is not necessarily a terminating or financially meaningful loop.

## 2.6.14 Tolerance-Based Stopping Rules

Suppose a model defines a result as acceptable when:

\[
Difference\le Tolerance
\]

Then continuation can be expressed as:

```python
while difference > tolerance:
    difference = refinement_step
```

The model must define what `difference` means. A reconciliation rule might use `|Actual - Expected|` rather than a signed difference. Boundary semantics must also come from the governing rule.

## 2.6.15 Update Ordering and Financial Timing

These loops observe different states:

```python
while balance < target_balance:
    print(balance)
    balance += contribution
```

```python
while balance < target_balance:
    balance += contribution
    print(balance)
```

The first prints pre-update state; the second prints post-update state. When iterations represent modeled financial periods, ordering of growth, contributions, withdrawals, payments, fees, and other events must come from the financial specification.

## 2.6.16 Multiple State Variables

A loop can update several pieces of state:

```python
while balance < target_balance:
    balance += contribution
    periods += 1
```

Ask which variables control continuation, which record results, which are fixed parameters, and whether the updates remain internally consistent.

## 2.6.17 `for` Versus `while`

A useful distinction is:

```text
for   → repetition naturally driven by iteration
while → repetition naturally driven by a continuation condition
```

This is more accurate than the oversimplification `for = known count` and `while = unknown count`.

## 2.6.18 Known and Discovered Iteration Counts

If observations already exist as a collection, a `for` loop naturally expresses processing them. If the model says to continue until changing state reaches a boundary, a `while` loop can naturally discover the required number of iterations during execution.

This is a modeling tendency, not a universal restriction on either construct.

## 2.6.19 `Decimal` Arithmetic and Numerical Policy

Financial state may use `Decimal`, whose arithmetic remains subject to the active decimal context, including precision, rounding, signals, and traps.

```text
control-flow policy ≠ numerical policy
```

The loop determines whether another iteration occurs. The numerical specification determines how financial values are represented and calculated.

## 2.6.20 Rounding and Termination

A condition such as:

```python
while balance < target_balance:
    ...
```

can behave differently depending on whether `balance` represents a raw calculated, rounded, posted, or settled value. Likewise, tolerance comparisons can change if values are rounded before comparison.

Apply the continuation condition to the numerical representation defined by the model.

## 2.6.21 Non-Finite Numerical State

`Decimal` supports non-finite values including infinities and NaNs. An ordering comparison such as `value < target` must not be treated as validation of `value`. Ordering comparisons involving a Decimal NaN can signal `InvalidOperation`; if that signal is not trapped, the comparison returns `False`.

`value.is_finite()` can help distinguish finite values from infinities and NaNs, but:

```text
finite ≠ financially valid
```

Detailed defensive validation is developed in Section 2.11.

## 2.6.22 Safety Limits and Maximum Iterations

Some procedures benefit from an execution safeguard:

```python
iterations = 0
max_iterations = 1000

while condition and iterations < max_iterations:
    ...
    iterations += 1
```

An iteration cap is an execution safeguard, not a convergence proof or evidence of financial success. A value such as `1000` should also have a reason.

```text
technical safeguard ≠ financial policy
```

## 2.6.23 Verifying Why the Loop Stopped

A critical principle is:

```text
loop terminated ≠ financial objective achieved
```

After a capped target loop, verify the outcome explicitly:

```python
if balance >= target_balance:
    outcome = "Target reached"
else:
    outcome = "Target not reached"
```

Stopping because a guardrail was reached must not be silently reported as successful financial completion.

## 2.6.24 Testing and Trace Tables

Useful tests include an initially false condition, one and multiple iterations, exact boundaries, overshoot, stalled or wrong-direction progress, tolerance boundaries, iteration caps, and counter timing.

For the `8000` balance with `500` contributions:

| Iteration | Beginning Balance | Contribution | Ending Balance | Periods |
|---:|---:|---:|---:|---:|
| 1 | 8000.00 | 500.00 | 8500.00 | 1 |
| 2 | 8500.00 | 500.00 | 9000.00 | 2 |
| 3 | 9000.00 | 500.00 | 9500.00 | 3 |
| 4 | 9500.00 | 500.00 | 10000.00 | 4 |

The next test is `10000 < 10000`, which is false. Trace tables help expose off-by-one errors, update-order mistakes, incorrect counters, overshoot, missing progress, and incorrect stopping conditions.

Testing should verify both the final financial result and termination behavior.

## 2.6.25 Common `while` Loop Mistakes

Common mistakes include failing to change relevant state, moving state in the wrong direction, using the wrong boundary operator, incorrect initialization, off-by-one counters, confusing iterations with financial periods, ignoring overshoot, using an incorrect financial transition, rounding at the wrong stage, treating comparisons as validation, treating a safety cap as success, using arbitrary limits without justification, and using `while` when direct iteration would express the model more clearly.

## 2.6.26 Financial `while` Loop Design Pattern

A disciplined workflow is:

```text
1. Define the financial objective
2. Identify changing state
3. Identify fixed model parameters
4. Define the continuation condition
5. Verify boundary inclusivity
6. Initialize state
7. Define the financial state transition
8. Identify a progress measure
9. Confirm progress toward termination
10. Define what one iteration means
11. Apply the numerical policy
12. Add a justified safeguard if required
13. Execute repeated updates
14. Verify why repetition stopped
15. Verify the final financial result
```

## 2.6.27 Production-Minded Perspective

Condition-controlled loops can appear in iterative numerical procedures, reconciliation workflows, payment simulations, threshold searches, scenario adjustments, convergence-style procedures, and retry-like processing.

Production systems may require stronger controls around maximum iterations, timeouts, observability, logging, non-finite numerical states, unexpected non-convergence, partial failures, deterministic behavior, numerical precision, performance, and auditability.

A production design should be able to explain why repetition began, what state controlled continuation, what changed, what demonstrated progress, why repetition stopped, whether the financial objective was achieved, whether a safeguard was reached instead, and which numerical representation drove the decision.

```text
program stopped ≠ model succeeded
```

## 2.6.28 Section Summary

A `while` statement provides condition-controlled repetition. The condition is tested before each iteration, so the suite may execute zero times. Financial models should distinguish changing state from fixed parameters, define what an iteration means, specify boundary inclusivity, reason about progress and termination, preserve event timing and numerical policy, handle non-finite state deliberately, and distinguish safety limits from financial success.

The most important reliability principle is:

```text
loop terminated ≠ financial objective achieved
```
