## 2.11.1 Why Input Validation Matters in Financial Models

Financial calculations depend on assumptions and data supplied to the model. Examples include principal amounts, investment balances, interest rates, discount rates, growth rates, cash flows, payment amounts, contribution amounts, time periods, scenario assumptions, and model horizons.

A financial formula can be mathematically correct and its Python implementation can execute successfully while the resulting answer is still inappropriate because the inputs violate the assumptions of the model.

```python
from decimal import Decimal

principal = Decimal("-10000.00")
years = -5
```

Python can represent both values. Whether they are acceptable depends on the financial model.

The complete validation pipeline used in this chapter is:

```text
raw input
    ↓
presence
    ↓
conversion / representation
    ↓
finite-value validation
    ↓
domain validation
    ↓
relationship validation
    ↓
financial plausibility
    ↓
accepted model state
    ↓
financial calculation
```

> **Validate financial assumptions before allowing them to become model state.**

## 2.11.2 Validation Is More Than Type Checking

Financial models generally need to ask whether an input is present, representable, finite, inside the permitted domain, compatible with other assumptions, and financially plausible.

```python
discount_rate = Decimal("-2.50")
```

This is a valid `Decimal` object, but that does not establish that a discount rate of -250% is appropriate for a particular model. A valid Python representation and a valid financial assumption are different concepts.

## 2.11.3 The Validation Layers

A useful financial-validation framework contains several layers: presence, conversion/representation, finite-value validation, domain validation, relationship validation, and financial plausibility. These layers address different failure modes and should generally be evaluated in dependency order.

## 2.11.4 Validation Dependencies Matter

For external input, dependent validation should execute only after its prerequisites succeed:

```text
presence
    ↓
conversion
    ↓
finite check
    ↓
range/domain check
    ↓
relationship check
```

Do not attempt a numeric comparison such as `annual_rate <= Decimal("-1")` until the program knows that `annual_rate` has been converted into the expected numeric representation.

> **Validation itself should not fail because prerequisite validation was skipped.**

## 2.11.5 Validate Before Calculating

Before a calculation such as:

```python
future_value = principal * (Decimal("1") + annual_rate) ** years
```

the model should know whether the principal, rate, period count, and related assumptions belong to the supported model domain. The correct sequence is validate → accept → calculate.

## 2.11.6 Required Values and `None`

Python commonly uses `None` to represent absence of a value.

```python
if annual_rate is None:
    print("Annual rate is required.")
```

When specifically testing for Python's `None` singleton, use `is None` rather than relying on a generic truthiness check.

## 2.11.7 Missing and Zero Are Different States

A generic test such as `if not annual_rate:` can reject a legitimate zero rate because numeric zero is falsy. A precise missing-value test is `if annual_rate is None:`.

Zero can legitimately represent zero growth, return, fee, contribution, inflation, or balance.

> **Missing and zero are not interchangeable financial states.**

## 2.11.8 Validating Finite `Decimal` Values

A value being a `Decimal` does not guarantee that it is an ordinary finite number. Python's `Decimal` supports special values:

```python
Decimal("NaN")
Decimal("Infinity")
Decimal("-Infinity")
```

For most ordinary financial inputs, these should not enter the model as accepted assumptions.

```python
if not annual_rate.is_finite():
    print("Annual rate must be finite.")
```

Finite-value validation should occur before ordinary range and relationship comparisons.

## 2.11.9 Type Validation Alone Is Insufficient

`isinstance(annual_rate, Decimal)` can return `True` even for `Decimal("NaN")`. Correct representation does not by itself establish a valid financial value.

## 2.11.10 Validating Positive Amounts

If an investment model requires `I₀ > 0`, a check such as `if initial_investment <= 0:` is appropriate for that model. Do not generalize this rule to every financial amount. Negative values may legitimately represent cash outflows, withdrawals, losses, liabilities, or other signed quantities.

## 2.11.11 Validating Nonnegative Values

Some values may permit zero but prohibit negative values:

```python
if annual_contribution < 0:
    print("Annual contribution cannot be negative.")
```

The distinction between `x > 0` and `x >= 0` is part of the financial specification.

## 2.11.12 Validating Rates

Suppose a simplified compounding model defines its supported annual-return domain as `r > -1`:

```python
if annual_return <= Decimal("-1"):
    print("Annual return must exceed -100% for this model.")
```

This is a model-domain rule, not a universal restriction imposed by Python or `Decimal`. The example assumes a positive post-return growth factor `1 + r > 0`.

## 2.11.13 Percentage Representation Must Be Explicit

If rates are stored internally as decimal fractions, 8% is `0.08`, 5.5% is `0.055`, and -2% is `-0.02`. `Decimal("8")` has numeric value 8 and corresponds to 800% when interpreted as a rate.

> **All internal rates should use one documented representation convention.**

## 2.11.14 Validating Time Periods

A period count may need to be present, integer-valued, non-Boolean, positive, and within the model horizon. Checking only `years <= 0` is insufficient when `years` has not already been validated as the expected integer type.

## 2.11.15 Boolean Values Require Special Attention

In Python, `bool` is a subclass of `int`, so `isinstance(True, int)` returns `True`. For financial period counts, a stricter check is:

```python
if not isinstance(years, int) or isinstance(years, bool):
    print("Years must be an integer.")
```

## 2.11.16 Validate Model Horizons

A positive integer can still fall outside the intended model domain.

```python
maximum_projection_years = 100

if years > maximum_projection_years:
    print("Projection exceeds the supported model horizon.")
```

The model horizon is both a financial-model constraint and a defensive computational boundary.

## 2.11.17 Cross-Field Validation

Some assumptions are acceptable individually but invalid together. For the simplified stable-growth terminal-value formulation:

`TV_n = CF_(n+1) / (r - g)`

this implementation requires `r > g`.

```python
if discount_rate <= growth_rate:
    print("Discount rate must exceed growth rate for this model.")
```

This is relationship validation.

## 2.11.18 Mathematical Validity Versus Financial Plausibility

If `discount_rate = Decimal("0.051")` and `growth_rate = Decimal("0.050")`, then `r > g` is satisfied, but `r - g = 0.001` creates a very small denominator. The calculation is mathematically executable, but the result may be extremely sensitive to small assumption changes.

> **Mathematical validity does not guarantee financial plausibility.**

## 2.11.19 Compound Validation Conditions

Several requirements can be combined when prerequisites are already guaranteed, but compound conditions may lose information about which rule failed. User-facing, educational, and production models often benefit from more specific validation.

## 2.11.20 Prefer Specific Validation Messages

Specific messages such as `Initial investment must be greater than zero.` are more useful than `Invalid input.` because they improve debugging, user feedback, testing, auditability, model review, and operational support.

## 2.11.21 Fail Fast Versus Collect Multiple Errors

Fail-fast validation stops at the first relevant failure. Error collection can report several independent failures at once. However, collecting errors does not mean executing dependent validations blindly. If representation validation fails, dependent numeric range checks should not run.

## 2.11.22 Dependency-Aware Error Collection

A safe sequence is: present → convertible → finite → within domain → cross-field validation. Once a value has been confirmed as a finite `Decimal`, ordinary range validation becomes appropriate.

## 2.11.23 Validate Before Mutating Financial State

Financial state should not change before assumptions are accepted. Prefer validate assumption → accept assumption → initialize state → mutate state. This reduces partially processed or contaminated model state.

## 2.11.24 Validation Inside Loops

```python
cash_flows = [Decimal("1000.00"), None, Decimal("1200.00")]

for cash_flow in cash_flows:
    if cash_flow is None:
        print("Missing cash flow.")
        continue
    # process accepted cash flow
```

`continue` controls program flow; validation policy determines whether missing cash flow should be skipped, rejected, replaced, reported, or cause execution to stop.

## 2.11.25 Validate Before `continue`

If invalid observations are excluded, record the reason before skipping them. This supports reconciliation such as `input observations = processed observations + excluded observations + rejected observations` when those categories are exhaustive.

## 2.11.26 Validating Scenario Grids

Scenario combinations can be counted as evaluated or skipped, then reconciled against the total Cartesian combinations. This combines validation, loop control, and auditability.

## 2.11.27 Assertions and Runtime Input Validation

Assertions are useful for internal invariants and programmer expectations, for example an exhaustive reconciliation check. They should not be the sole mechanism for validating external or business input because Python can run with optimization that removes assertion statements.

```text
external / business input → explicit runtime validation
internal invariant → assertion may be appropriate
```

## 2.11.28 Input Conversion Is Part of the Boundary

Conversion answers whether an input can become the required representation. Validation answers whether the converted value is acceptable to the model. Invalid decimal text can cause decimal conversion to signal an invalid operation; detailed exception-handling mechanics are introduced later in the book.

## 2.11.29 Constructing `Decimal` from Intended Decimal Text

`Decimal("0.1")` directly represents the intended decimal value 0.1. `Decimal(0.1)` constructs a `Decimal` from the binary floating-point value already represented by the Python `float`. That conversion is exact with respect to the supplied binary value, but the binary value itself is generally not exactly the human-entered decimal fraction 0.1.

For controlled financial inputs, prefer `Decimal("0.1")` or `Decimal(validated_text)` when preserving intended decimal representation matters.

## 2.11.30 Text Normalization

Text input may contain surrounding whitespace. `raw_rate.strip()` can normalize it before conversion. Normalization should be deliberate; removing harmless whitespace differs from silently changing financial meaning.

## 2.11.31 Do Not Silently Correct Invalid Inputs

Unless explicitly part of the model specification, do not silently replace an invalid assumption with a boundary value. Prefer detect → report → reject/request correction.

## 2.11.32 Validation Versus Defaulting

```python
if annual_contribution is None:
    annual_contribution = Decimal("0")
```

This applies a defaulting policy; it does not merely validate. Validation asks whether input is acceptable. Defaulting asks what should replace an absent input.

## 2.11.33 Validation Versus Clamping

Clamping forces a value into a permitted interval. It is not equivalent to validation. Financial assumptions should not be silently clamped unless that behavior is explicitly part of the methodology.

## 2.11.34 Practical Example — Investment Projection Validation

```python
from decimal import Decimal

initial_investment = Decimal("50000.00")
annual_return = Decimal("0.07")
years = 20
maximum_projection_years = 100
errors = []

if not initial_investment.is_finite():
    errors.append("Initial investment must be finite.")
elif initial_investment <= 0:
    errors.append("Initial investment must be greater than zero.")

years_valid = True
if not isinstance(years, int) or isinstance(years, bool):
    errors.append("Years must be an integer.")
    years_valid = False

if years_valid:
    if years <= 0:
        errors.append("Years must be greater than zero.")
    elif years > maximum_projection_years:
        errors.append("Years exceeds the supported model horizon.")

if not annual_return.is_finite():
    errors.append("Annual return must be finite.")
elif annual_return <= Decimal("-1"):
    errors.append("Annual return must exceed -100% for this model.")

if errors:
    for error in errors:
        print(error)
else:
    balance = initial_investment
    for year in range(1, years + 1):
        balance *= Decimal("1") + annual_return
    print(f"Projected balance: ${balance:,.2f}")
```

The calculation does not mutate investment state until required validation succeeds.

## 2.11.35 Practical Example — Terminal-Value Validation

```python
from decimal import Decimal

terminal_year_cash_flow = Decimal("100000.00")
growth_rate = Decimal("0.03")
discount_rate = Decimal("0.08")
errors = []

if not terminal_year_cash_flow.is_finite():
    errors.append("Terminal-year cash flow must be finite.")
if not growth_rate.is_finite():
    errors.append("Growth rate must be finite.")
if not discount_rate.is_finite():
    errors.append("Discount rate must be finite.")

cash_flow_valid = terminal_year_cash_flow.is_finite()
rates_valid = growth_rate.is_finite() and discount_rate.is_finite()

if cash_flow_valid and terminal_year_cash_flow <= 0:
    errors.append("Terminal-year cash flow must be positive for this example.")
if rates_valid and discount_rate <= growth_rate:
    errors.append("Discount rate must exceed growth rate.")

if errors:
    for error in errors:
        print(error)
else:
    next_period_cash_flow = terminal_year_cash_flow * (Decimal("1") + growth_rate)
    terminal_value = next_period_cash_flow / (discount_rate - growth_rate)
    print(f"Terminal value: ${terminal_value:,.2f}")
```

Passing these checks establishes that the calculation is permitted by this simplified implementation. It does not prove that the perpetual-growth assumptions are economically credible.

## 2.11.36 Practical Example — Cash-Flow Dataset Validation

```python
cash_flows = [
    Decimal("-10000.00"),
    Decimal("2500.00"),
    None,
    Decimal("3000.00"),
    Decimal("3500.00"),
]

processed = 0
missing = 0
non_finite = 0

for period, cash_flow in enumerate(cash_flows):
    if cash_flow is None:
        missing += 1
        print(f"Missing cash flow at period {period}.")
        continue

    if not cash_flow.is_finite():
        non_finite += 1
        print(f"Non-finite cash flow at period {period}.")
        continue

    processed += 1

assert processed + missing + non_finite == len(cash_flows)
```

Negative cash flow is not automatically invalid because it may represent an outflow. The reconciliation categories are exhaustive for the validation rules used here.

## 2.11.37 Practical Example — User-Supplied Rate Boundary

```python
raw_rate = " 0.075 "
normalized_rate = raw_rate.strip()
annual_rate = Decimal(normalized_rate)

if not annual_rate.is_finite():
    print("Annual rate must be finite.")
elif annual_rate <= Decimal("-1"):
    print("Rate is outside the permitted domain for this model.")
else:
    print(f"Accepted annual rate: {annual_rate:.2%}")
```

Detailed handling of failed conversion is intentionally deferred to later exception-handling material.

## 2.11.38 Financial State Integrity

A strong architecture is receive assumptions → normalize → convert → validate → accept assumptions → initialize financial state → calculate. This reduces the chance that invalid assumptions contaminate downstream calculations.

## 2.11.39 Validation and Auditability

Important validation decisions should be observable when they can materially affect financial results. Useful information may include input received, validation rule, result, rejection reason, default applied, observation excluded, scenario skipped, and execution stopped.

> **A financially material validation decision should be explainable after the calculation has run.**

## 2.11.40 Name Complex Validation Rules

Complex rules can benefit from descriptive Boolean names such as `within_supported_horizon` or `discount_rate_exceeds_growth`. Named expressions can improve readability, reviewability, testing, and maintenance.

## 2.11.41 Avoid Magic Validation Numbers

Prefer a named boundary such as `maximum_projection_years = 100` over embedding unexplained values directly in conditions. Named boundaries communicate intent and make model specifications easier to maintain.

## 2.11.42 Validation Is Part of the Model Specification

Rules such as projection years between 1 and 100, internal rates stored as decimal fractions, or discount rate exceeding perpetual growth rate for a particular formulation define the supported domain of the model. Validation rules belong alongside the assumptions they enforce.

## 2.11.43 Common Failure Patterns

1. Validating too late.
2. Treating zero as missing.
3. Type-only validation.
4. Ignoring non-finite values.
5. Performing dependent checks too early.
6. Ignoring cross-field relationships.
7. Accepting `bool` as an integer period.
8. Mixing percent and decimal representations.
9. Silent defaulting.
10. Silent clamping.
11. Using `assert` for required external validation.
12. Silent exclusion.
13. Confusing mathematical validity with financial plausibility.
14. Magic validation boundaries.
15. Partial state mutation.
16. Vague validation messages.

## 2.11.44 Testing Validation Logic

Validation tests should cover missing and present values; negative, zero, and positive amounts; finite, NaN, positive-infinity, and negative-infinity numeric values; Boolean and integer period cases; model-horizon boundaries; rate boundaries; `r > g`, `r = g`, and `r < g`; missing-data patterns; and reconciliation identities where categories are exhaustive.

Boundary tests are especially important around `<`, `<=`, `>`, and `>=` transitions.

## 2.11.45 Production Validation Checklist

Before accepting financial inputs, verify presence semantics, missing versus zero behavior, representation and normalization rules, successful conversion, finite-value requirements, rate representation, Python type expectations, Boolean exclusion where needed, mathematical domains, model horizons, cross-field constraints, financial plausibility, validation dependency ordering, documented defaults, clamping policy, state-mutation ordering, exclusion/rejection counts, reconciliation, specific messages, named complex rules, named boundaries, appropriate assertion use, boundary tests, and reviewer explainability.

## 2.11.46 Key Takeaways

1. Financial assumptions should be validated before becoming model state.
2. Correct Python types do not guarantee valid financial inputs.
3. Validation should follow dependency order.
4. Presence, conversion, finite-value, domain, relationship, and plausibility checks address different risks.
5. Missing and zero are distinct financial states.
6. Positive and nonnegative constraints represent different domains.
7. Rate constraints belong to specific financial models and are not universal Python restrictions.
8. Internal percentage representation should be explicit and consistent.
9. `bool` requires special attention when validating integer-valued financial periods.
10. Positive period counts can still exceed the supported model horizon.
11. A `Decimal` can represent `NaN` or infinity, so type validation alone is insufficient.
12. Cross-field validation is essential when assumptions depend on one another.
13. Mathematical validity does not guarantee financial plausibility.
14. Error collection must respect validation dependencies.
15. Specific validation messages improve testing and auditability.
16. Financial state should not be mutated until required validation succeeds.
17. Skipped observations should remain auditable when financially material.
18. Assertions are useful for appropriate internal invariants, not as the sole validation of external business input.
19. Conversion and validation are separate boundary operations.
20. Constructing `Decimal` from intended decimal text avoids inheriting an unintended binary floating-point approximation.

> **Validate financial assumptions before allowing them to become model state.**

Defensive validation does more than prevent Python errors. It protects the financial meaning, numerical integrity, state consistency, auditability, and reliability of the model.
