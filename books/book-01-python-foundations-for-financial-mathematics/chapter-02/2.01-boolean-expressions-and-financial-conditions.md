## From Financial Calculation to Financial Decision

Chapter 1 focused primarily on calculating financial values such as interest, future value, percentage change, profit and loss, transaction fees, and reconciliation differences. Chapter 2 begins the transition from calculation to decision-making.

A calculation may answer, “What is the account balance?” A financial condition asks, “Does the account balance satisfy a particular requirement?” The result of that condition is normally `True` or `False`.

```text
financial values
      ↓
calculation
      ↓
numerical result
      ↓
financial condition
      ↓
True / False
      ↓
later control-flow decision
```

## Boolean Values — `True` and `False`

Python provides the Boolean type `bool` with the Boolean values `True` and `False`.

```python
is_reconciled = True
is_profitable = False
```

These differ from strings such as `"True"` and `"False"`.

```python
print(type(True))
print(type("True"))
```

The first is `bool`; the second is `str`.

## Boolean Expressions

For the financial comparisons developed here, a Boolean expression is an expression whose result is `True` or `False`.

```python
account_balance = 12500
minimum_balance = 10000

has_sufficient_balance = (
    account_balance >= minimum_balance
)
```

The expression asks whether the balance is at least the minimum. Python also supports broader truth-value testing, in which non-Boolean objects can be interpreted as true or false in Boolean contexts. Section 2.2 develops that behavior further.

## Financial Conditions

A financial condition represents a financial question, rule, or boundary, such as whether an investment is profitable, an account satisfies a threshold, a reconciliation difference is within tolerance, or a rate lies within a model's permitted range.

```python
balance = 12500
required_balance = 10000

meets_requirement = (
    balance >= required_balance
)
```

The ordinary numeric comparisons used throughout this book produce `True` or `False`. Section 2.2 examines the comparison operators systematically.

## Decimal Values and Boolean Results

```python
from decimal import Decimal

account_balance = Decimal("12500.00")
required_balance = Decimal("10000.00")

meets_requirement = (
    account_balance >= required_balance
)
```

The financial quantities are `Decimal` values while `meets_requirement` is a `bool`.

```text
financial quantity → Decimal
financial condition result → bool
```

## Calculation Versus Condition

```python
purchase_value = Decimal("8000.00")
sale_value = Decimal("9200.00")

profit_loss = sale_value - purchase_value
is_profitable = profit_loss > 0
```

These answer different questions:

```text
profit_loss   → How much profit or loss?
is_profitable → Was the result profitable?
```

A financial program may need both.

## Reading Conditions as Questions

Read a condition as a plain-language financial question.

```python
is_profitable = profit_loss > 0
```

means: Is profit/loss greater than zero?

```python
is_reconciled = difference <= tolerance
```

means: Is the reconciliation difference less than or equal to the permitted tolerance?

```text
financial requirement
       ↓
plain-language question
       ↓
Boolean condition
       ↓
True / False
```

## Profitability and Break-Even Boundaries

```python
purchase_value = Decimal("5000.00")
sale_value = Decimal("5750.00")
profit_loss = sale_value - purchase_value
is_profitable = profit_loss > 0
```

The profit/loss is `750.00`, so `is_profitable` is `True`.

At break-even, `profit_loss` is zero. Under the rule `profit_loss > 0`, `is_profitable` is therefore `False`. That does not imply a loss; it means the profitability condition is not satisfied.

```python
is_profitable = profit_loss > 0
is_loss = profit_loss < 0
is_break_even = profit_loss == 0
```

Section 2.3 will show how conditions like these can determine which code block executes.

## Boolean Conditions Encode Boundaries

`balance > minimum_balance` and `balance >= minimum_balance` differ at equality. “Must exceed $10,000” and “must be at least $10,000” are different financial rules.

Python can implement either condition, but the governing specification must determine which boundary is correct.

## Reconciliation Condition

For a simplified reconciliation model:

\[
Difference=|SystemA-SystemB|
\]

```python
system_a = Decimal("1000.000")
system_b = Decimal("1000.006")
tolerance = Decimal("0.010")

difference = abs(system_a - system_b)
is_reconciled = difference <= tolerance
```

The difference is `0.006`, so the condition is `True`.

### Boundary testing

| Difference | Tolerance | Expected |
|---:|---:|---|
| 0.009 | 0.010 | `True` |
| 0.010 | 0.010 | `True` |
| 0.011 | 0.010 | `False` |

Important financial conditions should normally be tested below, at, and above their boundaries.

## Do Not Round Away the Decision

Suppose the raw reconciliation difference is `0.011` and the tolerance is `0.010`.

```text
0.011 <= 0.010 → False
```

If `0.011` is first rounded to `0.01` for display and that display-rounded value is then compared, the result could become `True`.

Unless the specification explicitly requires a rounded or posted value to control the decision, prefer:

```text
computational value
       ↓
financial condition
       ↓
required presentation
```

The rounding stage is part of the financial model.

## Threshold and Rate Examples

```python
account_balance = Decimal("27500.00")
required_balance = Decimal("25000.00")
meets_requirement = account_balance >= required_balance
```

This evaluates to `True`.

For a model-specific rate boundary:

```python
rate = Decimal("0.075")
maximum_rate = Decimal("0.10")
is_within_limit = rate <= maximum_rate
```

This also evaluates to `True`. The 10% boundary is an instructional model rule, not a universal financial limit.

## Descriptive Boolean Variables

Prefer names that communicate what `True` means:

```python
is_profitable
is_reconciled
is_break_even
has_sufficient_balance
meets_minimum_balance
is_within_limit
```

A name such as `is_reconciled` communicates more financial meaning than a generic name such as `result` or `flag`.

## Truth Values and `bool()`

Python's `bool()` converts values according to truth-value rules.

```python
print(bool(0))          # False
print(bool(1))          # True
print(bool(""))         # False
print(bool("Finance"))  # True
```

Numeric zero values are generally false in Boolean contexts, while nonzero numeric values are generally true.

```python
print(bool(Decimal("0")))       # False
print(bool(Decimal("100.00")))  # True
```

An explicit financial condition is often clearer than implicit truthiness. `account_balance > 0`, for example, communicates a more precise financial question than `bool(account_balance)`.

Python's `bool` type is a subclass of `int`, but financial programs should normally keep Boolean state conceptually separate from financial numeric quantities.

## Non-Finite Decimal Values

`Decimal` can represent special values including `NaN`, `Infinity`, and `-Infinity`. Financial quantities expected to be ordinary finite amounts should normally be validated before ordering comparisons are relied upon.

```python
balance = Decimal("NaN")
is_valid_balance = balance.is_finite()
```

`is_valid_balance` is `False`.

Ordering comparisons involving a `Decimal` NaN can signal `InvalidOperation` rather than behaving like ordinary finite comparisons. A disciplined sequence is therefore:

```text
parse value
    ↓
validate numerical domain
    ↓
evaluate financial condition
```

Defensive branching is developed later in Chapter 2.

## Mathematical Condition Versus Financial Rule

Python can evaluate:

```python
account_balance >= Decimal("10000")
```

but it cannot determine whether $10,000 is the correct threshold. That threshold must come from the model, requirement, contract, policy, or another authoritative specification.

```text
financial specification
       ↓
financial rule
       ↓
Boolean expression
       ↓
Python evaluation
```

A condition can therefore be syntactically valid and executable while still implementing the wrong financial rule.

For example, if reconciliation succeeds when the difference is less than or equal to the tolerance, `difference < tolerance` is incorrect at the equality boundary even though it is valid Python.

## Scenario Tables Before Code

Write expected scenarios before implementing important conditions.

| Difference | Tolerance | Expected |
|---:|---:|---|
| 0.000 | 0.010 | `True` |
| 0.009 | 0.010 | `True` |
| 0.010 | 0.010 | `True` |
| 0.011 | 0.010 | `False` |

Then implement the condition and compare its behavior with the independently stated expectations.

## Financial Condition Design Pattern

```text
1. Define the financial rule
           ↓
2. Identify required inputs
           ↓
3. Validate the numerical domain
           ↓
4. Calculate derived values
           ↓
5. Translate the rule into a condition
           ↓
6. Test below the boundary
           ↓
7. Test at the boundary
           ↓
8. Test above the boundary
           ↓
9. Verify the financial interpretation
```

This pattern helps separate Python syntax from financial correctness.

## Common Mistakes

Common errors include using strings such as `"False"` instead of Boolean values, hiding financial meaning behind generic variable names, selecting the wrong equality boundary, comparing display-rounded values instead of computational values, confusing an amount with the condition derived from it, and assuming every representable `Decimal` is an ordinary finite financial amount.

## Testing Financial Conditions

For a minimum-balance requirement of `$10,000.00`, test values such as:

```text
9999.99  → False
10000.00 → True
10000.01 → True
```

For profitability under the rule `profit_loss > 0`:

| Profit/Loss | Expected |
|---:|---|
| 100.00 | `True` |
| 0.01 | `True` |
| 0.00 | `False` |
| -0.01 | `False` |
| -100.00 | `False` |

Tests should reflect the financial meaning of the boundary rather than merely exercising Python syntax.

## Production-Minded Perspective

Boolean conditions may eventually influence consequential behavior such as identifying reconciliation exceptions, detecting threshold breaches, classifying financial results, or selecting calculation paths. Important conditions should come from explicit requirements, use appropriate computational values, validate relevant numerical domains, communicate their meaning through descriptive names, and be tested at important boundaries.

These examples demonstrate disciplined foundations; they are not complete production financial policy engines.

## Section Summary

The central pattern is:

```text
financial data
      ↓
calculation
      ↓
financial condition
      ↓
Boolean result
```

A Boolean condition implements a boundary defined by a financial model or business rule. Reliable financial conditions therefore require attention to numerical representation, domain validation, boundary definition, financial meaning, and verification.
