## 2.4.1 From Conditional Syntax to Financial Rules

Section 2.3 introduced conditional execution:

```python
if condition:
    ...
elif another_condition:
    ...
else:
    ...
```

Knowing this syntax is necessary, but financial modeling requires another layer of reasoning.

Before writing the branch, determine:

- What financial question is being answered?
- Which inputs does the decision depend on?
- Which calculated value drives the decision?
- What states are meaningful?
- Where are the mathematical boundaries?
- Are the boundaries inclusive or exclusive?
- Can several conditions be true simultaneously?
- If several classification rules match, which has priority?
- What should happen for each state?
- Which assumptions make the comparison meaningful?
- How will the decision be verified?

The progression is:

```text
financial requirement
        ↓
inputs + assumptions
        ↓
decision variable
        ↓
mathematical rule
        ↓
decision states
        ↓
boundaries + precedence
        ↓
Boolean conditions
        ↓
control flow
        ↓
financial outcome
        ↓
verification
```

The central principle of this section is:

> **Specification first; code second.**

## 2.4.2 What Is a Financial Decision Rule?

In this book, a **financial decision rule** is an instructional modeling abstraction that maps defined financial inputs or calculated values to a specified classification, state, or action.

For example:

> Under this model, classify two balances as reconciled when their absolute difference is no more than one cent.

This rule contains:

```text
input values
    ↓
difference calculation
    ↓
tolerance
    ↓
comparison
    ↓
classification
```

Python might implement it as:

```python
difference = abs(system_a - system_b)

if difference <= tolerance:
    status = "Reconciled"
else:
    status = "Review Required"
```

The Python is straightforward. The important modeling decision is `difference <= tolerance` rather than `difference < tolerance` or `difference == 0`. The governing requirement determines the correct condition.

The term **financial decision rule** here is a modeling concept used by this book; it should not be interpreted as a claim that every financial organization uses this exact terminology or structure.

## 2.4.3 Specification First, Code Second

Write the requirement before the implementation.

### Requirement

> A balance satisfies the model requirement when it is at least $10,000.

### Mathematical rule

\[
B \geq 10{,}000
\]

### Python condition

```python
balance >= Decimal("10000.00")
```

### Control flow

```python
if balance >= Decimal("10000.00"):
    status = "Requirement Satisfied"
else:
    status = "Requirement Not Satisfied"
```

The translation is:

```text
requirement
    ↓
mathematics
    ↓
condition
    ↓
Python
```

If the requirement says **at least**, then `>=` is part of the model. Starting with code instead of the requirement can hide modeling mistakes behind syntactically correct Python.

## 2.4.4 Inputs, Calculations, Decisions, and Outputs

Financial decision logic becomes easier to inspect when four concerns are separated.

### Inputs

```python
purchase_value = Decimal("8000.00")
sale_value = Decimal("9250.00")
```

### Calculation

```python
profit_loss = sale_value - purchase_value
```

### Decision

```python
if profit_loss > 0:
    classification = "Profit"
elif profit_loss < 0:
    classification = "Loss"
else:
    classification = "Break-even"
```

### Output

```python
print(classification)
```

Conceptually:

```text
inputs
   ↓
calculation
   ↓
decision
   ↓
output
```

This separation makes it easier to determine whether an error came from the data, the mathematics, the decision rule, or the presentation of the result.

## 2.4.5 Identify the Decision Variable

A rule should make clear which value actually drives the decision.

```python
purchase_value = Decimal("8000.00")
sale_value = Decimal("9250.00")
profit_loss = sale_value - purchase_value
```

The profit classification does not depend directly on either input in isolation. It depends on `profit_loss`. For this rule, `profit_loss` is the **decision variable**.

```text
profit_loss > 0 → Profit
profit_loss = 0 → Break-even
profit_loss < 0 → Loss
```

Identifying the decision variable separates financial calculation from financial classification.

## 2.4.6 Identify Meaningful States

Before coding branches, identify the states defined by the model.

For profit/loss: positive, zero, and negative. For reconciliation: within tolerance and outside tolerance. For an instructional return model: below target, target, high, and exceptional.

The goal is not to create unnecessary categories. The goal is to ensure that every state that matters to the current financial specification is deliberately considered.

For profit/loss:

```text
positive → Profit
zero     → Break-even
negative → Loss
```

These states are mutually exclusive for an ordinary finite numerical profit/loss value and cover the intended valid domain of that simple model.

## 2.4.7 Mathematical Boundaries and Inclusivity

Suppose the requirement says: **Return must be at least 5%.** Mathematically, `r >= 0.05`.

```python
return_rate >= Decimal("0.05")
```

At exactly 5%:

```text
r > 0.05   → False
r >= 0.05  → True
```

Now consider `0.05 <= r < 0.10`. This includes 5% and excludes 10%.

```python
is_target_range = (
    Decimal("0.05") <= return_rate < Decimal("0.10")
)
```

Inclusive and exclusive boundaries are part of the financial rule. They should come from the specification, not from whichever comparison operator is most convenient to type.

## 2.4.8 Decision Tables as Model Specifications

A decision table can represent an authoritative requirement in a structured form.

| Return Rate | Classification |
|---|---|
| `r < 5%` | Below Target |
| `5% <= r < 10%` | Target |
| `10% <= r < 15%` | High |
| `r >= 15%` | Exceptional |

Implementation:

```python
if return_rate >= Decimal("0.15"):
    classification = "Exceptional"
elif return_rate >= Decimal("0.10"):
    classification = "High"
elif return_rate >= Decimal("0.05"):
    classification = "Target"
else:
    classification = "Below Target"
```

The decision table is a representation of the governing requirement. In real systems, the underlying authority might instead be an approved model specification, approved business rule, contract, accounting policy, regulatory requirement, or another controlled source. The implementation should remain traceable to whichever source actually governs the rule.

## 2.4.9 Exclusive States and Domain Completeness

The return model defines mutually exclusive states for ordinary finite return-rate values: below 5%, 5% through below 10%, 10% through below 15%, and 15% or above. Exactly one applies, and together they cover the intended domain of ordinary finite return-rate values for this instructional classification.

However:

```text
exhaustive classification
          ≠
complete input validation
```

The table does not automatically define behavior for missing values, malformed input, NaN, Infinity, -Infinity, incompatible units, or unsupported financial states. Those concerns require separate treatment.

## 2.4.10 Overlapping Threshold Tests and First-Match Execution

There is an important distinction between model states and one possible Python implementation. The model intervals are mutually exclusive, but Python lower-bound tests such as `r >= 15%`, `r >= 10%`, and `r >= 5%` overlap mathematically.

At `r = 16%`, all three lower-bound tests are true. Python's first-match execution resolves the overlap:

```python
if return_rate >= Decimal("0.15"):
    classification = "Exceptional"
elif return_rate >= Decimal("0.10"):
    classification = "High"
elif return_rate >= Decimal("0.05"):
    classification = "Target"
else:
    classification = "Below Target"
```

The first truthy condition selects its suite, and later conditions in the same `if` statement are not evaluated.

```text
mutually exclusive model states
              ↓
overlapping lower-bound tests
              ↓
deliberate branch ordering
              ↓
one classification
```

## 2.4.11 Independent Facts Versus Exclusive Classifications

Not every financial condition should compete for one winning classification.

```python
is_profitable = profit_loss > 0
meets_target_return = return_rate >= target_return
exceeds_exposure_limit = exposure > exposure_limit
```

A scenario can simultaneously be profitable, meet target, and exceed an exposure limit. These are independent facts. By contrast, Below Target, Target, High, and Exceptional are alternative classifications in the instructional return model.

Before choosing the control-flow structure, ask: **Do I need to preserve several independent facts, or select one outcome?**

## 2.4.12 Rule Priority

When several classification conditions can match, precedence must be deliberate. At 16%, conditions for at least 5%, 10%, and 15% are all true. If only one classification is allowed, the rule needs priority: Exceptional, then High, then Target.

Source-code order should express the required precedence rather than accidentally invent it.

## 2.4.13 Classification Rules Versus Action Rules

A **classification rule** answers: *What state is this?*

```python
if difference <= tolerance:
    reconciliation_status = "Reconciled"
else:
    reconciliation_status = "Review Required"
```

An **action rule** answers: *What should happen?*

```python
if requires_review:
    print("Send item for review.")
```

Separating these concepts can improve clarity, testing, and explainability.

## 2.4.14 Separate Calculation from Model or Policy Rules

```python
difference = abs(system_a - system_b)
```

This calculates a numerical fact. Then:

```python
is_reconciled = difference <= tolerance
```

applies a model or policy rule. A difference of `0.008` may be reconciled under a tolerance of `0.010` but not under `0.005`. The numerical calculation did not change; the rule parameter changed.

Not every instructional threshold represents a formal organizational policy. In this book, some are simply model parameters chosen to demonstrate financial reasoning.

## 2.4.15 Named Thresholds and Rule Parameters

```python
target_return = Decimal("0.05")

if return_rate >= target_return:
    ...
```

Similarly:

```python
materiality_threshold = Decimal("10000.00")
is_material = amount >= materiality_threshold
```

Important rule parameters should usually have meaningful names when doing so improves clarity, reuse, testing, or auditability. Not every numeric literal requires a variable; the purpose is to avoid hiding important model assumptions inside unexplained values.

## 2.4.16 Units, Rate Representations, and Time Basis

```python
return_rate = Decimal("0.08")
target_return = Decimal("0.05")
```

Both use decimal-rate representation: `0.08` means 8% and `0.05` means 5%. Another system might represent 5% as the percentage-number value `5` or as `500` basis points.

Comparable financial values require more than matching Python types. They need:

```text
compatible numeric representation
              +
compatible financial meaning
              +
compatible time basis
```

An annual return of `0.05` should not automatically be compared with a monthly target of `0.04` merely because both use decimal-rate representation.

## 2.4.17 Basis Points

A basis point is:

```text
1 bp = 0.01 percentage point = 0.0001 decimal rate
100 bp = 1 percentage point = 0.01 decimal rate
```

For example:

```python
spread = Decimal("0.0125")
spread_limit = Decimal("0.0100")
```

This represents a 1.25% (125 bp) spread and a 1.00% (100 bp) limit. The comparison `spread > spread_limit` is meaningful because the values use compatible representations and financial meaning.

## 2.4.18 Tolerances and Reconciliation Rules

```python
system_a = Decimal("1000.000")
system_b = Decimal("1000.006")
difference = abs(system_a - system_b)
tolerance = Decimal("0.010")
is_reconciled = difference <= tolerance
```

The difference is `0.006`, so the result is `True`.

```text
calculation
    ↓
difference = 0.006

model/policy parameter
    ↓
tolerance = 0.010

decision
    ↓
0.006 <= 0.010
```

The tolerance is not a property of subtraction. It is a parameter of the decision rule. Whether the specification uses `< tolerance` or `<= tolerance` must also be defined explicitly. Neither boundary is universally correct.

## 2.4.19 Raw, Rounded, Posted, and Decision Values

Suppose:

```python
difference = Decimal("0.011")
tolerance = Decimal("0.010")
```

The raw comparison `difference <= tolerance` is `False`. But if the difference is changed to `0.01` before comparison, `0.01 <= 0.010` becomes `True`.

The outcome changed because the representation changed before the decision.

The principle is not *never round before a decision*. The principle is:

> **Apply the decision rule to the representation defined by the specification.**

Depending on the model, the correct decision value may be raw, calculated, rounded, posted, settled, or another explicitly defined value. If a downstream specification explicitly uses a posted fee, for example, then the rounded posted value is the correct input to that decision.

## 2.4.20 Investment Return Classification Example

Consider a simple instructional investment scenario:

```python
initial_investment = Decimal("20000.00")
ending_value = Decimal("22400.00")
```

This example assumes `initial_investment != 0`.

```python
profit_loss = ending_value - initial_investment
return_rate = profit_loss / initial_investment
```

The results are a profit/loss of `2400` and return rate of `0.12`.

The formula `(EndingValue - InitialInvestment) / InitialInvestment` is a simple instructional return calculation, not a universal definition of investment return. Real calculations may need to account for intermediate cash flows, distributions, fees, taxes, timing, compounding, measurement period, and other model-specific assumptions.

```python
if return_rate >= Decimal("0.15"):
    classification = "Exceptional"
elif return_rate >= Decimal("0.10"):
    classification = "High"
elif return_rate >= Decimal("0.05"):
    classification = "Target"
else:
    classification = "Below Target"
```

At `0.12`, the result is `High`. These thresholds and classifications are instructional examples rather than universal investment standards.

## 2.4.21 Compound Review Rules

Suppose a model states: **Review an item when exposure exceeds the limit, or when the item is both unreconciled and material.**

```python
exceeds_exposure_limit = exposure > exposure_limit
is_unreconciled = difference > tolerance
is_material = amount >= materiality_threshold

requires_review = (
    exceeds_exposure_limit
    or (
        is_unreconciled
        and is_material
    )
)
```

The named conditions expose the financial meaning more clearly than a dense expression containing several unnamed comparisons.

## 2.4.22 Scenario Matrices

The compound review rule can be verified independently of particular monetary values.

| Exposure Exceeded | Unreconciled | Material | Review? |
|---|---|---|---|
| False | False | False | False |
| False | False | True | False |
| False | True | False | False |
| False | True | True | True |
| True | False | False | True |
| True | False | True | True |
| True | True | False | True |
| True | True | True | True |

This gives a clean sequence: rule → Boolean scenario matrix → financial-value tests. The first layer verifies logical structure; the second verifies that actual financial values generate the expected Boolean conditions.

## 2.4.23 Boundary and Intersection Testing

For a single threshold, test below, at, and above it.

```python
materiality_threshold = Decimal("10000.00")
is_material = amount >= materiality_threshold
```

| Amount | Expected |
|---:|---|
| 9,999.99 | False |
| 10,000.00 | True |
| 10,000.01 | True |

When rules interact, test their intersections. For a rule requiring `difference > 0.010` and `amount >= 10000.00`:

| Difference | Amount | Expected Review |
|---:|---:|---|
| 0.010 | 10,000.00 | False |
| 0.011 | 9,999.99 | False |
| 0.011 | 10,000.00 | True |
| 0.011 | 10,000.01 | True |

Testing intersections catches errors that isolated threshold tests may miss.

## 2.4.24 Missing and Non-Finite Inputs

A decision table designed for ordinary finite financial values does not automatically define behavior for missing, malformed, NaN, Infinity, or -Infinity values.

`Decimal` can represent finite values, infinities, and NaNs. Finite-value checking can use:

```python
value.is_finite()
```

A NaN should not simply flow into an ordinary threshold classification. Ordering comparisons involving a `Decimal` NaN can signal `InvalidOperation`; under normal trapped behavior this raises rather than producing an ordinary financial ordering result. Therefore, special values may need to be handled before ordinary threshold logic.

This section does not build the complete validation layer. The important distinction is that classification over valid values is not the same as validation of every possible input. Section 2.11 develops defensive input validation systematically.

## 2.4.25 Financially Meaningful Rule Names

Compare generic names such as `condition1` with names that communicate model meaning:

```python
is_material = amount >= materiality_threshold
is_unreconciled = difference > tolerance
meets_target_return = return_rate >= target_return
```

Useful prefixes include `is_`, `has_`, `meets_`, `exceeds_`, and `requires_`. Names should describe the financial concept rather than merely the mechanics of the comparison.

## 2.4.26 Explainable Decisions

A model should be structured so important outcomes can be explained when necessary.

```text
exceeds_exposure_limit = False
is_unreconciled        = True
is_material            = True
requires_review        = True
```

The reasoning becomes: not exposure-driven, but unreconciled and material, therefore review required.

This structure can help with debugging, testing, operational support, audit trails, model review, and reconciliation investigation. This does not imply that every Boolean must be permanently stored or that every application has the same audit or explainability requirements. The principle is that consequential logic should be inspectable when the model requires it.

## 2.4.27 Rule Reuse and Changing Inputs

For a stable set of values at the same logical point:

```python
is_material = amount >= materiality_threshold
```

can make reuse clearer than repeatedly reconstructing the same condition. However, a Boolean result represents the values used when it was calculated. If `amount` or `materiality_threshold` changes later, the old Boolean may no longer describe the current state.

> Reuse a named Boolean when the underlying inputs and logical point remain the same; recompute the condition when the relevant values may have changed.

Later chapters introduce functions and other abstractions that provide stronger ways to organize reusable rules.

## 2.4.28 Requirements and Model Assumptions

A requirement such as **Flag high returns** is incomplete. Questions remain: What counts as high? Is the threshold inclusive? Which return definition is used? What time period does the return cover? Which numeric representation is used? How are fees or cash flows handled? What happens if the value is missing?

A more precise instructional requirement is:

> Under this model, classify an annual decimal return rate as High when it is at least 0.10 but below 0.15.

Now the rule identifies the metric, representation, time basis, lower boundary, upper boundary, and boundary inclusivity.

A simple model may also explicitly assume compatible currencies, decimal rate representation, compatible time bases, finite ordinary classification inputs, exclusion of taxes or fees unless stated, thresholds supplied correctly, and basic validation already performed.

Code cannot repair an undefined financial specification.

## 2.4.29 Common Decision-Rule Mistakes

Common mistakes include coding before defining the rule, missing meaningful states, using the wrong boundary operator, allowing accidental precedence, confusing independent facts with exclusive classifications, comparing incompatible units or time bases, prematurely changing the decision representation, treating `else` as validation, hiding important rule parameters, reusing stale Boolean results, testing only typical values, and relying on ambiguous requirements.

## 2.4.30 Financial Decision-Rule Design Pattern

```text
1. State the financial question
              ↓
2. Identify required inputs
              ↓
3. Define units, representations,
   time bases, and assumptions
              ↓
4. Calculate the decision variable
              ↓
5. Identify meaningful states
              ↓
6. Define mathematical boundaries
              ↓
7. Decide inclusive/exclusive behavior
              ↓
8. Determine whether conditions are
   independent or mutually exclusive
              ↓
9. Define precedence where rules overlap
              ↓
10. Represent the requirement with a
    decision table or scenario matrix
              ↓
11. Translate rules into financially
    meaningful Boolean expressions
              ↓
12. Implement control flow
              ↓
13. Test boundaries and intersections
              ↓
14. Verify the financial interpretation
              ↓
15. Document assumptions and rule sources
```

The central principle remains: **specification first; code second.**

## 2.4.31 Correctness and Production Perspective

Financial decision logic can be evaluated through several levels:

```text
Python-valid
     ↓
numerically valid
     ↓
mathematically valid
     ↓
boundary-correct
     ↓
branch-complete
     ↓
rule-priority correct
     ↓
model-valid
     ↓
financially meaningful
```

Consider:

```python
if return_rate > Decimal("0.05"):
    status = "Target Achieved"
```

The code may be syntactically, numerically, and mathematically valid. But if the requirement says **at least 5%**, the implementation is wrong at exactly 5%. Successful execution therefore does not prove financial correctness.

In production systems, decision rules may influence reconciliation exceptions, exposure monitoring, account classifications, transaction routing, operational alerts, eligibility checks, scenario classifications, settlement workflows, and risk-review queues.

Consequential rules should be explicit, traceable, testable, reviewable, and explainable as appropriate to the system. Useful questions include where a threshold came from, which rule version is active, what units and time basis apply, what happens at boundaries or when several conditions are true, which assumptions are required, which representation drives the decision, and whether the result and its reasoning can be reproduced.

This section does not build a production rules engine. It establishes the modeling discipline required before more complex financial decision systems can be designed safely.
