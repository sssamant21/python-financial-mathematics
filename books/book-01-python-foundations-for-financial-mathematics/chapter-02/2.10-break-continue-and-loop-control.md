## 2.10.1 Why Financial Loops Sometimes Need Early Control

A loop normally continues until its iterable is exhausted or, for a `while` loop, until its condition becomes false. Financial models often need explicit early control because a target has been reached, a loan is repaid, a constraint is breached, an observation should be skipped, a scenario is invalid, a search has found its result, or a simulation has reached a stopping condition.

Python provides two important statements:

```python
break
continue
```

`break` terminates the nearest enclosing loop. `continue` skips the remainder of the current iteration and proceeds with the next iteration of the nearest enclosing loop.

> **Loop control should reflect an explicit financial stopping, skipping, or completion rule.**

## 2.10.2 Normal Loop Completion

```python
from decimal import Decimal

balance = Decimal("10000.00")
annual_return = Decimal("0.06")

for year in range(1, 6):
    balance *= Decimal("1") + annual_return
    print(f"Year {year}: ${balance:,.2f}")
```

No special loop control is needed because every period is expected to be processed.

## 2.10.3 The `break` Statement

```python
for period in range(1, 101):
    if period == 10:
        break
    print(period)
```

The loop processes periods 1 through 9. When `period == 10`, `break` terminates the nearest enclosing loop and execution continues after that loop.

## 2.10.4 Stop When an Investment Target Is Reached

```python
from decimal import Decimal

balance = Decimal("50000.00")
annual_return = Decimal("0.08")
target_balance = Decimal("100000.00")
maximum_years = 50

for year in range(1, maximum_years + 1):
    balance *= Decimal("1") + annual_return

    if balance >= target_balance:
        print(f"Target reached in Year {year}: ${balance:,.2f}")
        break
```

The financial target can stop processing early, while `maximum_years` provides a finite model horizon.

## 2.10.5 The Position of the Stopping Condition Matters

In the preceding example, the return is applied before the target test. The model therefore asks whether the target has been reached after the current year's return. Checking before applying the return answers a different financial question and can create an off-by-one-period result.

> **A program being able to stop does not establish that it is stopping at the financially correct point.**

## 2.10.6 Financial Stopping Conditions Should Be Explicit

Prefer descriptive rules such as:

```python
if balance >= target_balance:
    break
```

A reviewer should be able to determine why processing stopped, when it stopped, and what financial state triggered termination.

## 2.10.7 Loan Amortization and Early Termination

```python
from decimal import Decimal

loan_balance = Decimal("10000.00")
monthly_payment = Decimal("900.00")
monthly_rate = Decimal("0.01")
maximum_months = 24

for month in range(1, maximum_months + 1):
    interest = loan_balance * monthly_rate
    amount_due = loan_balance + interest
    payment = min(monthly_payment, amount_due)
    loan_balance = amount_due - payment

    if loan_balance <= 0:
        loan_balance = Decimal("0.00")
        print(f"Loan repaid in Month {month}")
        break
```

This simplified example assumes monthly interest is applied to the opening balance before the payment for that period. Real loan calculations can involve contractual accrual timing, payment timing, day-count conventions, compounding, fees, irregular payments, rounding, grace periods, delinquency, and prepayment rules.

## 2.10.8 `break` in a `while` Loop

```python
from decimal import Decimal

balance = Decimal("50000.00")
target_balance = Decimal("100000.00")
annual_return = Decimal("0.08")
year = 0

while True:
    year += 1
    balance *= Decimal("1") + annual_return

    if balance >= target_balance:
        break
```

`while True` depends on another control path to terminate. It should be used carefully because an unreachable stopping condition can create an infinite loop.

## 2.10.9 Use Defensive Boundaries

A safer financial model often combines a completion condition with a finite horizon.

```python
from decimal import Decimal

balance = Decimal("50000.00")
annual_return = Decimal("0.00")
target_balance = Decimal("100000.00")
year = 0
maximum_years = 100

while balance < target_balance:
    if year >= maximum_years:
        print("Target not reached within model horizon.")
        break

    year += 1
    balance *= Decimal("1") + annual_return
```

> **Financial iteration should have either a mathematically defensible finite boundary or a clearly reachable stopping rule—and often both.**

## 2.10.10 The `continue` Statement

```python
for period in range(1, 6):
    if period == 3:
        continue
    print(period)
```

The output contains 1, 2, 4, and 5. Period 3 skips the remainder of its iteration, but the loop continues.

## 2.10.11 Missing Financial Observations

```python
returns = [0.02, None, -0.01, 0.03, None, 0.01]

for period_return in returns:
    if period_return is None:
        continue
    print(f"Observed return: {period_return:.2%}")
```

> **`continue` controls program flow; it does not determine whether excluding financial data is methodologically correct.**

Missing data may instead require rejection, imputation, warning, explicit exclusion, repair, termination, or investigation.

## 2.10.12 Do Not Hide Data Problems with `continue`

Silent exclusion can alter averages, return series, volatility, counts, cash-flow totals, risk metrics, and reconciliation results. Track exclusions when they are operationally significant.

```python
skipped_observations = 0

for value in financial_data:
    if value is None:
        skipped_observations += 1
        continue
    # process valid observation
```

## 2.10.13 Track Why Observations Are Skipped

```python
missing_count = 0
zero_count = 0
processed_count = 0

for amount in transactions:
    if amount is None:
        missing_count += 1
        continue

    if amount == 0:
        zero_count += 1
        continue

    processed_count += 1
```

A useful reconciliation principle is:

`input records = processed records + excluded records + rejected records`

## 2.10.14 Skipping Invalid Scenario Combinations

```python
from decimal import Decimal

growth_rates = [Decimal("0.02"), Decimal("0.04"), Decimal("0.08")]
discount_rates = [Decimal("0.06"), Decimal("0.08"), Decimal("0.10")]

for growth_rate in growth_rates:
    for discount_rate in discount_rates:
        if discount_rate <= growth_rate:
            continue

        print(f"Evaluate: g={growth_rate:.1%}, r={discount_rate:.1%}")
```

For the simplified constant-growth perpetuity formulation introduced earlier, `r > g` is necessary for the calculation shown, but does not by itself make a perpetual-growth assumption economically credible.

## 2.10.15 Guard-Style Loop Processing

```python
for transaction in transactions:
    if transaction is None:
        continue
    if transaction == 0:
        continue
    # main processing
```

Handling disqualifying conditions first can reduce nesting, but each skipped condition should have a defined financial or data-quality meaning.

## 2.10.16 `break` Versus `continue`

`break` stops the nearest enclosing loop. `continue` skips the remainder of the current iteration and continues that loop.

```python
for value in values:
    if stop_condition(value):
        break
    if skip_condition(value):
        continue
    process(value)
```

## 2.10.17 The Nearest Enclosing Loop

```python
for scenario in range(1, 4):
    for year in range(1, 6):
        if year == 3:
            break
        print(scenario, year)
```

The `break` terminates the inner `year` loop. The outer scenario loop continues.

## 2.10.18 `continue` and the Nearest Enclosing Loop

```python
for scenario in range(1, 4):
    for year in range(1, 6):
        if year == 3:
            continue
        print(scenario, year)
```

Year 3 is skipped for each scenario. The outer loop is not advanced by the inner `continue`.

## 2.10.19 Exiting Multiple Nested Loops

Ordinary `break` does not directly terminate several enclosing loops. One explicit technique is state propagation:

```python
target_found = False

for scenario in scenarios:
    for period in periods:
        if some_condition:
            target_found = True
            break

    if target_found:
        break
```

A flag is only one technique. Later, reorganizing the search or using a function and returning a result may provide a clearer design.

## 2.10.20 Loop `else`

Python `for` and `while` loops can have an `else` clause. The loop's `else` suite executes when the loop reaches its completion condition without executing `break`. For a `for` loop this normally means iterable exhaustion; for a `while` loop it normally means its condition becomes false. If `break` terminates the loop, the `else` suite is skipped. An unhandled exception or another control transfer that leaves the loop does not cause the loop's `else` suite to execute merely because `break` was absent.

## 2.10.21 Financial Search with `for` / `else`

```python
from decimal import Decimal

projected_balances = [
    Decimal("60000.00"),
    Decimal("72000.00"),
    Decimal("85000.00"),
    Decimal("97000.00"),
]
target_balance = Decimal("100000.00")

for period, balance in enumerate(projected_balances, start=1):
    if balance >= target_balance:
        print(f"Target reached in Period {period}")
        break
else:
    print("Target was not reached within the projection.")
```

Because the iterable is exhausted without `break`, the `else` suite executes.

## 2.10.22 Loop `else` Versus a Flag

```python
for balance in projected_balances:
    if balance >= target_balance:
        break
else:
    print("Target not found")
```

Loop `else` can directly express exhaustive search without finding a reason to break. Use it when that structure is clear to the intended reader.

## 2.10.23 `while` / `else`

```python
attempt = 0
maximum_attempts = 3
success = False

while attempt < maximum_attempts:
    attempt += 1
    if success:
        break
else:
    print("Maximum attempts completed without success.")
```

The `else` suite runs if the condition becomes false without `break`.

## 2.10.24 Loop Control and Financial State

A `break` may represent loan repaid, result found, target reached, or terminal boundary reached. A `continue` may represent an excluded observation, invalid scenario, out-of-scope transaction, or intentionally skipped period. The financial meaning should be visible in names and surrounding logic.

## 2.10.25 Avoid Unreachable Code

Statements after an unconditional `break` or `continue` on the same execution path are not reached. Required calculations, logging, or audit records must occur before the control-transfer statement when needed.

## 2.10.26 Avoid Overusing `break` and `continue`

Too many exit paths can make financial processing difficult to reason about. When loop control becomes complex, simplify business rules, separate validation from processing, use descriptive Boolean expressions, decompose logic into functions, or restructure the workflow.

## 2.10.27 Choosing Between a Loop Condition and `break`

`while balance < target_balance:` often communicates the continuation rule more directly than `while True` plus a later `break`. The latter may be useful when several stopping conditions exist or the condition is naturally evaluated after work in the iteration. Prefer the structure that makes the financial termination rule easiest to understand and test.

## 2.10.28 Multiple Stopping Conditions

```python
from decimal import Decimal

balance = Decimal("50000.00")
annual_return = Decimal("0.08")
target_balance = Decimal("100000.00")
minimum_balance = Decimal("10000.00")
maximum_years = 50

for year in range(1, maximum_years + 1):
    balance *= Decimal("1") + annual_return

    if balance >= target_balance:
        print("Target reached.")
        break

    if balance <= minimum_balance:
        print("Minimum balance breached.")
        break
else:
    print("Model horizon reached without another terminal state.")
```

A production model should normally record which terminal state occurred.

## 2.10.29 Practical Example — Investment Target Analyzer

```python
from decimal import Decimal

initial_investment = Decimal("50000.00")
annual_return = Decimal("0.07")
target_balance = Decimal("100000.00")
maximum_years = 30
balance = initial_investment

for year in range(1, maximum_years + 1):
    balance *= Decimal("1") + annual_return

    if balance >= target_balance:
        print(f"Target reached in Year {year}.")
        print(f"Balance: ${balance:,.2f}")
        break
else:
    print(f"Target not reached within {maximum_years} years.")
```

This combines bounded iteration, state evolution, period timing, target detection, `break`, and loop `else`.

## 2.10.30 Practical Example — Auditable Scenario Filtering

```python
from decimal import Decimal

growth_rates = [Decimal("0.02"), Decimal("0.04"), Decimal("0.06")]
discount_rates = [Decimal("0.05"), Decimal("0.07"), Decimal("0.09")]
evaluated = 0
skipped = 0

for growth_rate in growth_rates:
    for discount_rate in discount_rates:
        if discount_rate <= growth_rate:
            skipped += 1
            continue

        evaluated += 1
        print(f"Evaluate g={growth_rate:.1%}, r={discount_rate:.1%}")

total_combinations = len(growth_rates) * len(discount_rates)
assert evaluated + skipped == total_combinations
```

Counting both evaluated and skipped combinations preserves reconciliation.

## 2.10.31 Practical Example — First Threshold Crossing

```python
from decimal import Decimal

cash_balances = [
    Decimal("100000.00"),
    Decimal("85000.00"),
    Decimal("62000.00"),
    Decimal("48000.00"),
    Decimal("35000.00"),
]
minimum_cash = Decimal("50000.00")

for period, balance in enumerate(cash_balances, start=1):
    if balance < minimum_cash:
        print(f"Minimum cash breached in Period {period}: ${balance:,.2f}")
        break
else:
    print("Minimum cash was not breached.")
```

The loop stops at the first breach because the question asks for the first threshold crossing. If every breach were required, `break` would be inappropriate.

> **Loop control must match the exact financial question being asked.**

## 2.10.32 Common Failure Patterns

1. Using `break` when `continue` is intended.
2. Using `continue` when `break` is intended.
3. Forgetting the nearest-loop rule.
4. Infinite `while` loops.
5. Silent data exclusion.
6. Misunderstanding loop `else`.
7. Unreachable statements.
8. Too many exit paths.
9. No terminal-state reporting.
10. Stopping at the wrong financial time.
11. Confusing program validity with financial validity.
12. Assuming exclusion is harmless.

## 2.10.33 Testing Loop-Control Logic

Test `break` when its condition is true on the first, middle, and final iteration and when it is never true. Test `continue` with no, first, middle, last, and all observations skipped. Test loop `else` when `break` executes, when it does not, and with an empty iterable. For bounded financial loops, test targets reached before and exactly at the horizon, targets never reached, and targets unreachable under assumptions. For nested loops, test inner `break`, inner `continue`, continued outer iteration, and multi-level state propagation. Reconciliation tests should verify that input counts equal processed plus excluded plus rejected counts where those categories are exhaustive.

## 2.10.34 Production Loop-Control Checklist

Before using loop control, verify the financial event represented, whether processing should stop or skip one observation, which enclosing loop is affected, whether the stopping condition is reachable, whether a defensive boundary is required, whether the test occurs at the financially correct point in time, whether exclusions must be counted or logged, whether terminal state is recorded, whether loop `else` improves clarity, whether processing reconciles to inputs, and whether boundary and nested-loop behavior have been tested.

## 2.10.35 Key Takeaways

- `break` terminates the nearest enclosing loop.
- `continue` skips the remainder of the current iteration of the nearest enclosing loop.
- Financial stopping conditions should be explicit and meaningful.
- Skipping financial data is a modeling decision, not merely a programming decision.
- Excluded observations should be measurable when they affect auditability or reconciliation.
- Nested loops require careful attention to the nearest-loop rule.
- A loop's `else` suite is associated with reaching its completion condition without `break`.
- Potentially unbounded loops need reachable stopping conditions and appropriate defensive boundaries.
- Stopping-condition placement can change financial period timing.
- Programmatically valid scenarios are not automatically financially valid scenarios.
- Loop-control decisions should remain reconcilable with model inputs and outputs.

> **Loop control should reflect an explicit financial stopping, skipping, or completion rule.**

When `break`, `continue`, loop conditions, and loop `else` correspond directly to financial meaning, the model becomes easier to understand, validate, test, reconcile, audit, and maintain.
