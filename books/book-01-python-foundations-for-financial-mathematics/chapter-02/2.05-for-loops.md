## 2.5.1 From Decisions to Repeated Execution

Sections 2.1 through 2.4 developed Boolean conditions, conditional execution, and financial decision rules. Financial mathematics also requires the same calculation or decision to be applied repeatedly across transactions, scenarios, balances, or other collections.

Python provides loops for repeated execution. This section introduces the `for` loop.

```text
financial collection
        ↓
one supplied item
        ↓
calculation / decision
        ↓
update state or result
        ↓
next item
        ↓
final financial result
```

## 2.5.2 What Is a `for` Loop?

A Python `for` statement repeatedly executes a suite using items supplied through iteration.

```python
for item in iterable:
    statement
```

At a more precise level, Python evaluates the expression after `in`, obtains an iterable, obtains an iterator, requests successive items, assigns each item to the loop target, and executes the loop suite until the iterator is exhausted. After ordinary exhaustion, execution continues after the loop.

For the simple single-name loops used throughout this section, the loop target is also commonly described as the **loop variable**.

## 2.5.3 Iterable, Iterator, and Successive Items

An **iterable** is an object from which Python can obtain an iterator. An **iterator** supplies successive items during iteration.

```text
iterable
   ↓
iterator
   ↓
item
   ↓
item
   ↓
item
   ↓
exhaustion
```

For example:

```python
cash_flows = [
    Decimal("100.00"),
    Decimal("150.00"),
    Decimal("200.00"),
]
```

The list is iterable. When used in a `for` statement, Python obtains an iterator and consumes its items. For this list, values are supplied in list order. Different iterable types define their own iteration behavior, so an iterable should not automatically be interpreted as a financial time series.

## 2.5.4 First Financial `for` Loop

```python
cash_flows = [
    Decimal("100.00"),
    Decimal("150.00"),
    Decimal("200.00"),
]

for cash_flow in cash_flows:
    print(cash_flow)
```

The suite is reused once for each supplied value rather than being written separately for every item.

## 2.5.5 Loop Target and Loop Variable

In:

```python
for cash_flow in cash_flows:
    print(cash_flow)
```

`cash_flow` is the loop target. Because it is a single variable name, it is also natural to call it the loop variable. Successive iterations assign `100.00`, `150.00`, and `200.00` to that name.

Financial code benefits from meaningful names such as `cash_flow`, `amount`, or `return_rate` rather than generic names when the longer name improves clarity.

## 2.5.6 Iterations, Suites, and Indentation

One execution of the loop suite is an **iteration**. Indentation determines which statements belong to the suite and therefore repeat.

```python
for cash_flow in cash_flows:
    print("Cash flow:")
    print(cash_flow)

print("Processing complete.")
```

The two indented statements execute for each item. The unindented statement executes after ordinary loop completion.

## 2.5.7 Repeated Financial Calculations

Suppose:

```python
transaction_amounts = [
    Decimal("1000.00"),
    Decimal("2500.00"),
    Decimal("4000.00"),
]

fee_rate = Decimal("0.015")
```

The instructional calculation is:

\[
Fee = Amount \times FeeRate
\]

Apply it repeatedly:

```python
for amount in transaction_amounts:
    raw_fee = amount * fee_rate
    print(raw_fee)
```

The resulting `Decimal` values are represented as:

```text
15.00000
37.50000
60.00000
```

The financial formula defines what to calculate. The loop applies that calculation repeatedly to supplied items.

## 2.5.8 Repeated Decisions

```python
returns = [
    Decimal("0.03"),
    Decimal("0.07"),
    Decimal("0.12"),
]

target_return = Decimal("0.05")

for return_rate in returns:
    if return_rate >= target_return:
        print("Target achieved")
    else:
        print("Below target")
```

Result:

```text
Below target
Target achieved
Target achieved
```

The loop repeats across supplied values; the `if` statement chooses a path for the current value.

## 2.5.9 Iteration Versus Conditional Execution

A `for` statement asks which supplied items should be processed through repeated execution. An `if` statement asks which conditional path should execute for the current item.

```python
for return_rate in returns:
    if return_rate >= target_return:
        ...
```

Keeping these responsibilities distinct makes more complex financial control flow easier to reason about.

## 2.5.10 Accumulation and Initialization

A common loop pattern is **accumulation**.

```python
cash_flows = [
    Decimal("100.00"),
    Decimal("150.00"),
    Decimal("200.00"),
]

total_cash_flow = Decimal("0.00")

for cash_flow in cash_flows:
    total_cash_flow += cash_flow
```

The final value is `450.00`.

```text
initialize once
      ↓
update repeatedly
      ↓
use final result
```

Resetting the accumulator inside the loop discards previous accumulated state.

For this `Decimal` example, `total_cash_flow += cash_flow` expresses the same intended accumulator update pattern as `total_cash_flow = total_cash_flow + cash_flow`. Augmented assignment has its own Python semantics and should not be assumed to behave identically to ordinary assignment for every possible object.

## 2.5.11 Counting and State Representation

Loops can count values satisfying a rule.

```python
returns = [
    Decimal("0.03"),
    Decimal("0.07"),
    Decimal("0.12"),
    Decimal("0.02"),
]

target_return = Decimal("0.05")
meeting_target_count = 0

for return_rate in returns:
    if return_rate >= target_return:
        meeting_target_count += 1
```

The result is `2`.

A count can naturally begin with integer `0`, while a monetary accumulator may begin with `Decimal("0.00")`. Choose loop-state representation according to what the state means.

## 2.5.12 Conditional and Multiple Accumulation

```python
cash_flows = [
    Decimal("-1000.00"),
    Decimal("250.00"),
    Decimal("300.00"),
    Decimal("600.00"),
]

positive_total = Decimal("0.00")
negative_total = Decimal("0.00")

for cash_flow in cash_flows:
    if cash_flow > 0:
        positive_total += cash_flow
    elif cash_flow < 0:
        negative_total += cash_flow
```

Results:

```text
positive_total = 1150.00
negative_total = -1000.00
```

Zero contributes to neither category under this particular model. The model, not the loop, determines the financial meaning of positive, negative, and zero values.

## 2.5.13 Building Result Collections

A loop can produce one derived result for each supplied input.

```python
calculated_fees = []

for amount in transaction_amounts:
    raw_fee = amount * fee_rate
    calculated_fees.append(raw_fee)
```

This creates a separate output collection while preserving the input collection.

```text
input collection
      ↓
next item
      ↓
calculate result
      ↓
store result
      ↓
output collection
```

## 2.5.14 `append()` and Collection Mutation

`calculated_fees.append(raw_fee)` adds the value to the end of `calculated_fees` and mutates that result list.

This is clear here because the loop reads from `transaction_amounts` while modifying a different collection, `calculated_fees`. This differs from structurally modifying the same collection that currently supplies the loop's items.

## 2.5.15 Empty Iterables and Loop-Target Lifetime

```python
cash_flows = []
total_cash_flow = Decimal("0.00")

for cash_flow in cash_flows:
    total_cash_flow += cash_flow
```

The iterable supplies no items, so the loop performs zero iterations and `total_cash_flow` remains `0.00`.

Whether empty data means no activity, no observations, missing source data, or something else is a financial-model decision.

Because no iteration occurs, the loop performs no assignment to `cash_flow`. If a loop executes normally at least once, its target remains bound afterward to the final item assigned to it. Introductory financial code should generally use explicit result state rather than relying unnecessarily on the loop target after the loop.

## 2.5.16 Reassigning the Loop Target

```python
for amount in transaction_amounts:
    amount = amount * fee_rate
```

This does not automatically replace the corresponding value stored in `transaction_amounts`.

```text
item supplied by iterator
        ↓
amount bound to item
        ↓
amount rebound to result
        ↓
original list slot unchanged
        ↓
next item assigned to amount
```

If transformed results are required, make the destination explicit by building a result collection.

## 2.5.17 Modifying Collections During Iteration

Changing the same collection structurally while iterating over it can produce confusing or unintended behavior. A clearer transformation pattern is often to read from one collection and build another.

When modification of the source collection is genuinely required, the implementation should be designed deliberately—for example, by iterating over an appropriate copy where that behavior fits the model.

The introductory rule is: **do not casually modify the same collection that is controlling the iteration.**

## 2.5.18 Repeated Rules and Fixed Model Parameters

```python
fee_rate = Decimal("0.015")

for amount in transaction_amounts:
    raw_fee = amount * fee_rate
```

Here `amount` changes each iteration while `fee_rate` remains fixed across these iterations. The same model rule is applied repeatedly:

\[
Fee = Amount \times FeeRate
\]

Recognizing changing inputs and fixed model parameters makes repeated calculations easier to reason about. This is an introductory observation rather than a formal treatment of loop invariants.

## 2.5.19 `Decimal` Arithmetic in Repeated Calculations

Using `Decimal` is useful when a financial model requires decimal arithmetic.

```python
fee_rate = Decimal("0.015")
amount = Decimal("2500.00")
raw_fee = amount * fee_rate
```

The result is represented as `37.50000`. Do not automatically rewrite it as `37.50` unless the model introduces a posting, formatting, or quantization rule requiring that representation.

`Decimal` represents decimal inputs directly, but arithmetic still operates under the active decimal context. The context can govern precision, rounding, signals, and traps. `Decimal` should therefore not be interpreted as unlimited-precision arithmetic under every possible operation.

## 2.5.20 Iteration Policy Versus Numerical Policy

A loop answers which supplied items should be processed. It does not determine when values should be rounded.

```text
iteration policy
        ≠
numerical policy
```

A model might round each posted transaction before aggregation, or it might aggregate raw calculations before applying a final rounding rule. Those procedures can produce different results. The governing financial specification determines the appropriate numerical lifecycle.

## 2.5.21 Repeated Financial Classification

Section 2.4 introduced this instructional return classification:

```text
r < 5%          → Below Target
5% <= r < 10%  → Target
10% <= r < 15% → High
r >= 15%        → Exceptional
```

Apply it repeatedly:

```python
returns = [
    Decimal("0.03"),
    Decimal("0.05"),
    Decimal("0.08"),
    Decimal("0.12"),
    Decimal("0.16"),
]

for return_rate in returns:
    if return_rate >= Decimal("0.15"):
        classification = "Exceptional"
    elif return_rate >= Decimal("0.10"):
        classification = "High"
    elif return_rate >= Decimal("0.05"):
        classification = "Target"
    else:
        classification = "Below Target"

    print(return_rate, classification)
```

Expected classifications are `Below Target`, `Target`, `Target`, `High`, and `Exceptional`. The loop applies the existing rule repeatedly; it does not redefine thresholds or precedence.

## 2.5.22 Testing `for` Loops

Useful introductory tests include an empty collection, one item, multiple items, boundary values when decisions are involved, relevant positive/zero/negative states, and independently calculated accumulator totals.

For example:

```text
100 + 150 + 200 = 450
```

provides an expected accumulator result that can be checked manually without duplicating the implementation under test.

Whenever practical, derive expected test results independently from the code being tested.

## 2.5.23 Common `for` Loop Mistakes

Common mistakes include forgetting the colon, incorrect indentation, resetting an accumulator inside the loop, confusing iteration with conditional execution, assuming loop-target reassignment changes the source list, modifying the iterated collection without deliberate design, ignoring empty input, relying unnecessarily on the loop target afterward, aggregating incompatible financial quantities, applying rounding without a defined policy, and treating successful execution as proof of financial correctness.

## 2.5.24 Financial `for` Loop Design Pattern

A disciplined introductory workflow is:

```text
1. Identify the financial collection
              ↓
2. Determine what one supplied item means
              ↓
3. Identify fixed model parameters
              ↓
4. Determine whether state must be initialized
              ↓
5. Start the for loop
              ↓
6. Process one supplied item
              ↓
7. Apply any required decision rule
              ↓
8. Update accumulator or result collection
              ↓
9. Repeat for remaining items
              ↓
10. Use the final result
              ↓
11. Verify edge cases and financial interpretation
```

At the Python level:

```text
iterable → iterator → item → loop target → suite → state/result update → repeat
```

## 2.5.25 Production-Minded Perspective

Loops can appear in financial systems processing transactions, positions, balances, reconciliation items, scenarios, rates, fees, cash flows, and reporting records.

Larger systems may eventually require batching, streaming, vectorized or database-side computation, memory and performance analysis, partial-failure handling, retry behavior, idempotency, auditability, concurrency, and numerical-policy controls. Those topics are outside this introductory section.

A loop that executes successfully can still repeatedly apply the wrong formula, threshold, accumulator, rounding lifecycle, or unit interpretation. Automation multiplies both correct behavior and mistakes, so repeated execution increases rather than removes the importance of model verification.
