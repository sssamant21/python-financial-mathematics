## 2.9.1 From Simple Decisions to Multi-Level Financial Logic

Financial models rarely contain only one decision or one loop. A model may need to process multiple years, months or quarters within each year, classify cash flows, apply different assumptions under different conditions, evaluate multiple scenarios, calculate values for multiple instruments, or aggregate results across several levels.

These requirements often lead to **nested control flow**: one control-flow structure appearing inside another.

```python
for year in range(1, 4):
    for quarter in range(1, 5):
        print(year, quarter)
```

The outer loop processes years and the inner loop processes four quarters for each year.

> **Nested control flow should mirror the hierarchy of the financial model.**

## 2.9.2 What Does Nested Mean?

A conditional may contain another conditional:

```python
if condition_a:
    if condition_b:
        ...
```

A loop may contain another loop:

```python
for item_a in sequence_a:
    for item_b in sequence_b:
        ...
```

Different structures may also be combined. The important question is not merely whether Python permits nesting; the structure should communicate a meaningful relationship in the financial model.

## 2.9.3 Nested Conditional Statements

```python
expected_return = 0.10
risk_score = 3

if expected_return >= 0.08:
    if risk_score <= 4:
        print("Investment passes initial screening.")
```

The second condition is reached only after the first succeeds. Nested conditions can therefore represent dependent or sequential financial decision rules.

## 2.9.4 Nested Conditions Versus Combined Conditions

A combined condition is often appropriate when several conditions collectively form one rule:

```python
if (
    expected_return >= required_return
    and risk_score <= maximum_risk
):
    print("Approved")
```

Nesting may be more expressive when the second decision conceptually depends on the first. The code should reflect the financial reasoning as clearly as possible.

## 2.9.5 Nested `if` / `else` Logic

```python
expected_return = 0.09
required_return = 0.08
risk_score = 6
maximum_risk = 4

if expected_return >= required_return:
    if risk_score <= maximum_risk:
        print("Approve")
    else:
        print("Reject: risk too high")
else:
    print("Reject: return too low")
```

The nested structure makes the reason for each outcome visible, which can be valuable where decisions must later be explained, tested, or audited.

## 2.9.6 Nested Loops

```python
for year in range(1, 4):
    for quarter in range(1, 5):
        print(f"Year {year}, Quarter {quarter}")
```

If the outer loop completes `m` iterations and the inner loop completes all `n` iterations for each outer iteration, the innermost body executes `m × n` times. This assumes every inner loop runs completely; later loop-control mechanisms, exceptions, conditional paths, or variable-length sequences can change the actual count.

## 2.9.7 Annual and Monthly Financial Models

```python
forecast_years = 3
months_per_year = 12

for year in range(1, forecast_years + 1):
    for month in range(1, months_per_year + 1):
        print(f"Year {year}, Month {month}")
```

Assuming full execution, this produces `3 × 12 = 36` monthly observations. This hierarchy is useful when annual assumptions coexist with monthly calculations.

## 2.9.8 Applying Annual Assumptions to Monthly Calculations

```python
from decimal import Decimal

annual_revenue = Decimal("1200000.00")
annual_growth_rate = Decimal("0.05")
forecast_years = 3
months_per_year = 12

for year in range(1, forecast_years + 1):
    if year > 1:
        annual_revenue *= Decimal("1") + annual_growth_rate

    monthly_revenue = annual_revenue / Decimal(months_per_year)

    for month in range(1, months_per_year + 1):
        print(f"Year {year}, Month {month}: ${monthly_revenue:,.2f}")
```

The placement of the annual calculation is deliberate. Moving it unnecessarily inside the monthly loop could repeat it twelve times and change the financial meaning.

## 2.9.9 Converting Nested Periods to a Sequential Period

```python
months_per_year = 12

for year in range(1, 4):
    for month in range(1, months_per_year + 1):
        period = (year - 1) * months_per_year + month
        print(year, month, period)
```

In general, `t = (y - 1)m + p`, where `t` is the sequential period, `y` the year, `m` subperiods per year, and `p` the current subperiod.

## 2.9.10 Scenario Analysis with Nested Loops

```python
from decimal import Decimal

growth_rates = [Decimal("0.03"), Decimal("0.05"), Decimal("0.07")]
discount_rates = [Decimal("0.06"), Decimal("0.08"), Decimal("0.10")]

for growth_rate in growth_rates:
    for discount_rate in discount_rates:
        print(f"Growth: {growth_rate:.1%}, Discount: {discount_rate:.1%}")
```

If every combination is processed, the model evaluates nine scenario combinations. This is the basic control-flow structure behind a two-dimensional sensitivity grid.

## 2.9.11 Financial Validation Inside a Scenario Grid

For a constant-growth perpetuity:

`TV_n = CF_(n+1) / (r - g)`

where `CF_(n+1)` is expected cash flow in the following period, `r` is the required return or discount rate, and `g` is perpetual growth.

```python
from decimal import Decimal

terminal_year_cash_flow = Decimal("100000.00")
growth_rates = [Decimal("0.02"), Decimal("0.03"), Decimal("0.04")]
discount_rates = [Decimal("0.07"), Decimal("0.08"), Decimal("0.09")]

for growth_rate in growth_rates:
    for discount_rate in discount_rates:
        if discount_rate > growth_rate:
            next_period_cash_flow = (
                terminal_year_cash_flow
                * (Decimal("1") + growth_rate)
            )
            terminal_value = (
                next_period_cash_flow
                / (discount_rate - growth_rate)
            )
            print(
                f"g={growth_rate:.1%}, r={discount_rate:.1%}, "
                f"TV=${terminal_value:,.2f}"
            )
```

The condition `discount_rate > growth_rate` prevents a zero or negative denominator under this simplified stable-growth formulation. It is only one requirement: mathematically executable assumptions are not automatically economically credible.

## 2.9.12 Conditional Logic Inside a Loop

```python
from decimal import Decimal

cash_flows = [
    Decimal("-1000.00"),
    Decimal("300.00"),
    Decimal("-200.00"),
    Decimal("700.00"),
]

for cash_flow in cash_flows:
    if cash_flow >= 0:
        print("Inflow:", cash_flow)
    else:
        print("Outflow:", cash_flow)
```

The loop processes observations and the conditional classifies each observation.

## 2.9.13 Loop Inside a Conditional

```python
investment_active = True
cash_flows = [1000, 1200, 1400]

if investment_active:
    for cash_flow in cash_flows:
        print(cash_flow)
```

This pattern can prevent calculations from running when a model is in an inapplicable state.

## 2.9.14 Multi-Level Financial Classification

```python
from decimal import Decimal

transactions = [
    Decimal("500.00"),
    Decimal("-2000.00"),
    Decimal("15000.00"),
    Decimal("-400.00"),
]

large_inflow_threshold = Decimal("10000.00")
large_outflow_threshold = Decimal("1000.00")

for amount in transactions:
    if amount >= 0:
        if amount >= large_inflow_threshold:
            print("Large inflow")
        else:
            print("Standard inflow")
    else:
        if abs(amount) >= large_outflow_threshold:
            print("Large outflow")
        else:
            print("Standard outflow")
```

Nested conditions are appropriate because magnitude classification occurs within direction classification.

## 2.9.15 State Has a Logical Level

```python
portfolio_total = 0

for portfolio in portfolios:
    security_total = 0

    for security in portfolio:
        security_total += security.value

    portfolio_total += security_total
```

`security_total` belongs inside the portfolio loop because each portfolio requires a fresh subtotal. `portfolio_total` belongs outside because it accumulates across portfolios.

> **Initialize accumulated state at the level where that state logically belongs.**

## 2.9.16 Annual Totals and Grand Totals

```python
revenues = [
    [100, 110, 120],
    [130, 140, 150],
]

grand_total = 0

for year_revenues in revenues:
    annual_total = 0

    for revenue in year_revenues:
        annual_total += revenue

    grand_total += annual_total
    print("Annual total:", annual_total)

print("Grand total:", grand_total)
```

Correct initialization mirrors the hierarchy of the accumulated state.

## 2.9.17 Scenario State Must Be Reset

```python
from decimal import Decimal

initial_investment = Decimal("50000.00")
return_scenarios = [Decimal("0.04"), Decimal("0.07"), Decimal("0.10")]
investment_years = 5

for annual_return in return_scenarios:
    balance = initial_investment

    for year in range(1, investment_years + 1):
        balance *= Decimal("1") + annual_return
        print(f"Year {year}: ${balance:,.2f}")
```

`balance = initial_investment` must execute once for each scenario. Otherwise one scenario could begin with the ending state of the previous scenario, producing state contamination.

## 2.9.18 Nested Financial Data

```python
cash_flows = [
    [1000, 1200, 1300],
    [1500, 1600, 1700],
]

for scenario_cash_flows in cash_flows:
    for cash_flow in scenario_cash_flows:
        print(cash_flow)
```

When data hierarchy, control-flow hierarchy, and financial interpretation align, the program becomes easier to reason about.

## 2.9.19 Avoid Repeating Work at the Wrong Level

If an annual rate needs to be determined once per year, calculate it outside the monthly loop rather than twelve times inside it. Calculation placement can affect performance, numerical consistency, external data access, logging volume, reproducibility, and financial interpretation.

A calculation should normally be placed at the narrowest logical level at which it needs to change.

## 2.9.20 Computational Scale

```python
for scenario in range(10):
    for year in range(20):
        for month in range(12):
            ...
```

With full execution, the innermost body runs `10 × 20 × 12 = 2,400` times. A workload of 10,000 instruments × 100 scenarios × 360 periods contains 360,000,000 innermost iterations.

The lesson is not that nested loops are inherently inefficient, but that modest dimensions can create very large workloads when multiplied together.

## 2.9.21 Order of Nesting Matters

A model may iterate securities then scenarios, or scenarios then securities. If all combinations are processed, both can represent the same Cartesian set, but ordering can affect result organization, aggregation, shared calculations, state initialization, caching, logging, data access, and readability.

The outer loop should generally represent the higher-level unit of work for the model.

## 2.9.22 Avoid Excessive Nesting

Deep nesting creates substantial cognitive overhead. When nesting becomes difficult to follow, consider combining conditions that genuinely form one rule, separating validation from calculation, reorganizing data, extracting meaningful operations into functions, or redesigning the workflow.

Later sections introduce additional loop-control and function techniques that can simplify some nested structures.

## 2.9.23 Flatten Conditions When They Represent One Rule

```python
if (
    expected_return >= required_return
    and risk_score <= maximum_risk
):
    print("Approved")
```

If conditions form one approval rule, a combined Boolean expression may be clearer. If each stage has separate outcomes or downstream processing, nesting may better express the decision tree.

## 2.9.24 Practical Example — Multi-Year Monthly Cash Forecast

```python
from decimal import Decimal

starting_cash = Decimal("100000.00")
monthly_revenue = Decimal("30000.00")
monthly_expenses = Decimal("24000.00")
forecast_years = 3
months_per_year = 12
cash_balance = starting_cash

for year in range(1, forecast_years + 1):
    for month in range(1, months_per_year + 1):
        net_cash_flow = monthly_revenue - monthly_expenses
        cash_balance += net_cash_flow
        print(
            f"Year {year}, Month {month}, "
            f"Cash = ${cash_balance:,.2f}"
        )
```

`cash_balance` is intentionally initialized outside both loops because the balance carries forward across the entire forecast horizon.

## 2.9.25 Practical Example — Multi-Scenario Investment Projection

```python
from decimal import Decimal

initial_investment = Decimal("50000.00")
return_scenarios = [Decimal("0.04"), Decimal("0.07"), Decimal("0.10")]
investment_years = 5

for annual_return in return_scenarios:
    balance = initial_investment

    for year in range(1, investment_years + 1):
        balance *= Decimal("1") + annual_return
        print(
            f"Return {annual_return:.1%}, Year {year}, "
            f"Balance ${balance:,.2f}"
        )
```

The outer loop changes the scenario, the inner loop advances time, and scenario state resets before each new scenario.

## 2.9.26 Practical Example — Educational Eligibility Decision Tree

```python
credit_score = 740
debt_to_income = 0.32
minimum_credit_score = 680
maximum_debt_to_income = 0.40

if credit_score >= minimum_credit_score:
    if debt_to_income <= maximum_debt_to_income:
        if credit_score >= 760:
            rate_tier = "Tier 1"
        elif credit_score >= 720:
            rate_tier = "Tier 2"
        else:
            rate_tier = "Tier 3"
        print(f"Eligible — {rate_tier}")
    else:
        print("Not eligible — DTI above example threshold")
else:
    print("Not eligible — credit score below example threshold")
```

This is an instructional programming example only. Real lending eligibility, underwriting, pricing, and credit decisions involve substantially more complex legal, regulatory, contractual, governance, data-quality, model-risk, and fair-lending requirements. The thresholds shown should not be interpreted as real lending recommendations.

## 2.9.27 Testing Nested Financial Logic

Test important boundaries across decision hierarchies, nested loops, and stateful models: values just below and exactly at thresholds, first and final periods, zero and one period, one and multiple scenarios, empty data, each rejection path, scenario-start state, final state, and state reset before the next scenario.

A defect hidden inside one branch or one nested combination may remain invisible under ordinary happy-path testing.

## 2.9.28 Auditability and Explainability

Meaningful names expose the reasoning represented by control flow:

```python
if meets_return_requirement:
    if meets_risk_requirement:
        if has_sufficient_liquidity:
            decision = "Approve"
```

A reviewer should be able to determine what condition was evaluated, why it was evaluated, which branch executed, which assumption controlled it, what calculation followed, which state changed, and what result was produced.

## 2.9.29 Common Failure Patterns

1. Incorrect indentation.
2. Excessive nesting.
3. Failing to reset scenario state.
4. Initializing state at the wrong level.
5. Repeating work at the wrong level.
6. Incorrect period boundaries.
7. Assuming every scenario combination is valid.
8. Ignoring computational scale.
9. Mixing unrelated business rules.
10. Ambiguous state ownership.

## 2.9.30 Production Modeling Checklist

Before implementing nested control flow, verify the financial hierarchy represented by each nesting level, outer and inner dimensions, calculation frequency, state ownership and reset behavior, parameter validity, period boundaries, computational scale, test coverage, and whether the resulting decision or calculation can be explained to a reviewer.

## 2.9.31 Key Takeaways

- Nested conditionals can represent dependent financial decisions.
- Combined Boolean conditions are often clearer when tests form one rule.
- Nested loops naturally represent dimensions such as years and months.
- Nested loops can generate scenario and sensitivity combinations.
- Full nested-loop execution counts multiply across dimensions, but actual counts may differ when loops do not complete normally.
- Initialize financial state at the level where it logically belongs.
- Reset scenario-specific state before each scenario.
- Validate parameter combinations before financial calculations.
- Make timing assumptions explicit in valuation formulas.
- Avoid repeating calculations at unnecessarily deep levels.
- Estimate computational scale before implementing large scenario models.
- Test branch boundaries, period boundaries, and state-reset behavior.
- Use descriptive names so nested logic remains auditable.

> **Nested control flow should mirror the hierarchy of the financial model.**

When program structure matches financial structure—scenario, year, month, instrument, transaction, eligibility rule, or classification level—the code becomes easier to understand, validate, test, audit, and extend.
