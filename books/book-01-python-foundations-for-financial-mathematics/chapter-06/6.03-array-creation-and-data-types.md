## 6.3.1 Purpose

Creating an array makes decisions about representation, dimensions, initial state, and conversion. Those decisions can alter the meaning of financial inputs before any model runs.

This section builds synthetic scenario inputs with explicit dtypes and a validated text-to-float boundary. It also demonstrates conversion failures that a successful NumPy constructor alone cannot prevent.

## 6.3.2 Learning Objectives

1. Select a constructor by the intended initial state.
2. Specify integer, floating-point, and boolean representations explicitly.
3. Distinguish count-based grids from integer step sequences.
4. Validate wire values before conversion.
5. Identify truncation and precision loss during casting.
6. Preserve a distinction between uncomputed results and genuine zeros.

## 6.3.3 Start with Meaning

The lab needs three illustrative input rates, four period indices, five scenario shifts, and a five-by-three result workspace. These arrays deliberately have different roles. No valuation is performed and the period indices are not combined with the scenario grid.

| Array | Shape | Dtype | Meaning |
|---|---|---|---|
| rates | (3,) | float64 | Decimal-fraction scenario inputs |
| periods | (4,) | int64 | Abstract indices 1 through 4 |
| shifts | (5,) | float64 | Five additive decimal-fraction shifts |
| results | (5, 3) | float64 | Uncomputed scenario-by-input workspace |
| completed | (5, 3) | bool | Explicit calculation-status flags |
| factors | (3,) | float64 | Neutral multiplicative starting values |

An input rate 0.025 denotes 2.5 percent. A shift 0.01 denotes one percentage point, not one percent of the original rate. The example does not establish a compounding convention, annualization basis, forecast, or market quote. These require separate contracts before a valuation can use the inputs.

## 6.3.4 Choose a Constructor Deliberately

| Constructor | Basic role | Decision in this lab |
|---|---|---|
| np.array | Build from supplied values | Validated rates with explicit float64 |
| np.arange | Step sequence, normally excluding stop | Integer indices 1 to 4 |
| np.linspace | A specified number of spaced points | Five shifts, both endpoints included |
| np.zeros | Initialize zero entries | No completed calculations yet |
| np.ones | Initialize one entries | Neutral factors |
| np.full | Initialize one explicit fill value | NaN marks uncomputed numeric results |
| np.empty | Allocate without numeric initialization | Deliberately not used |

Never read a numeric np.empty workspace as if it held valid initialized results. Only choose it when every relevant entry is written before use and that behavior is verified. Here an explicit uncomputed state is easier to inspect.

A zero-filled results array would be ambiguous: zero might mean a real calculated outcome or work that never ran. The NaN workspace and separate boolean status distinguish those concepts. The lab tests their initial state; it does not implement the later calculation/status-update protocol.

## 6.3.5 Integer Sequences and Floating Grids

`np.arange(1, 5, dtype=np.int64)` expresses the integer sequence 1, 2, 3, 4. These indices are not calendar dates or a day-count convention.

`np.linspace(-0.01, 0.01, num=5, endpoint=True, dtype=np.float64)` expresses the requested point count and endpoint policy. Its intended shifts are -0.010, -0.005, 0.000, 0.005, and 0.010. Floating entries are binary approximations, so the tests use a small explicit tolerance.

When the requirement is a fixed number of floating points across an interval, state it directly with linspace. Floating-step arange can have endpoint and length surprises caused by finite representation. Neither constructor decides whether a scenario range is economically sensible.

## 6.3.6 Dtype Is Part of the Input Contract

Use an explicit dtype when a boundary requires a particular representation. In this lab float64 holds analytical inputs, int64 holds abstract counts, and bool holds status. Default inference is convenient for exploration, but the application should not depend on accidental input mixtures.

| Representation | Appropriate question | Limitation to review |
|---|---|---|
| float64 | Approximate analytical values? | Finite precision and range |
| float32 | Is reduced precision intentional? | Less precision than float64 |
| int64 | Bounded whole counts or deliberately scaled units? | Fixed-width bounds and arithmetic overflow |
| bool | A true/false condition? | Not a substitute for a numeric measurement |
| object | Python-object storage intentionally required? | Different arithmetic/storage behavior |

Explicit float64 does not make decimal fractions exact. Explicit int64 does not make arbitrary-size Python integers fit. Choosing a type is the beginning of a numerical policy, not a substitute for domain and range validation.

## 6.3.7 Validate Before Coercing

The rate_vector boundary accepts an exact tuple of 1–1,000 exact strings. Text uses an optional minus sign, an integer part 0 or 1, and at most six fractional digits. The numerical bound is [-1, 1]. Whitespace, exponent notation, percent signs, booleans, numeric wire values, and nonfinite tokens fail.

The grammar intentionally rejects alternative spellings such as .1, 00.1, and +0.1. That is this teaching API's choice, not a restriction imposed by NumPy or Decimal. Negative zero text is accepted as numerically zero; the interface does not define a sign-of-zero business meaning.

Decimal checks the bounded text value before conversion. Then conversion to Python float and an explicit float64 array introduces the intended binary approximation. It does not preserve exact decimal arithmetic. The finite small bounds make overflow impossible for these conversions; a general parser would need a broader range policy.

Validate the original wire types first. A constructor that accepts True as a number cannot recover the fact that the application wanted to reject booleans after they have already become 1.0.

## 6.3.8 Casting Is Not Financial Rounding

For the bounded demonstration values 1.9 and -1.9, casting a float array to int64 gives 1 and -1. That is truncation toward zero, not a declared monetary rounding policy. The test also requests casting='safe' and verifies that this float-to-integer conversion is rejected.

A casting rule describes allowed representation changes. It does not validate currency, scale, accounting policy, or financial materiality. If whole units are required, define how fractional inputs are treated before applying an integer conversion.

The precision-loss example starts with integer 16,777,217, converts through float32, then returns to int64 as 16,777,216. A later conversion cannot reconstruct information already lost. Keep identifiers in their intended text/integer representation rather than routing them through floating point for convenience.

## 6.3.10 File — creation_types.py

```python
"""Create explicit scenario inputs without silent wire-value coercion."""
from decimal import Decimal
import re
import numpy as np


def rate_vector(texts: tuple[str, ...]) -> np.ndarray:
    """Convert 1–1000 decimal-fraction rate texts in [-1, 1] to float64.

    At most six fractional digits; no whitespace, exponent, percent sign,
    boolean, or numeric wire values. Binary approximation is intentional.
    These are scenario inputs, not validated market quotes or forecasts.
    """
    if type(texts) is not tuple:
        raise TypeError('rates must be a tuple of decimal text')
    if not 1 <= len(texts) <= 1000:
        raise ValueError('expected 1 to 1000 rates')
    checked = []
    for text in texts:
        if type(text) is not str:
            raise TypeError('each rate must be exact text')
        if re.fullmatch(r'-?(0|1)(\.[0-9]{1,6})?', text) is None:
            raise ValueError('invalid rate text')
        value = Decimal(text)
        if not Decimal('-1') <= value <= Decimal('1'):
            raise ValueError('rate outside lab bounds')
        checked.append(float(value))
    return np.array(checked, dtype=np.float64)


def scenario_inputs() -> dict[str, np.ndarray]:
    """Create independent illustrative arrays; perform no valuation."""
    return {
        'rates': rate_vector(('0.01', '0.025', '0.04')),
        'periods': np.arange(1, 5, dtype=np.int64),
        'shifts': np.linspace(-0.01, 0.01, num=5, endpoint=True, dtype=np.float64),
        'results': np.full((5, 3), np.nan, dtype=np.float64),
        'completed': np.zeros((5, 3), dtype=np.bool_),
        'factors': np.ones(3, dtype=np.float64),
    }


def main() -> None:
    arrays = scenario_inputs()
    print('Rates:', arrays['rates'].tolist())
    print('Periods:', arrays['periods'].tolist())
    print('Shift grid:', [f'{value:.3f}' for value in arrays['shifts']])
    print('Result shape:', arrays['results'].shape)
    print('Uncomputed results:', int(np.isnan(arrays['results']).sum()))
    print('Completed entries:', int(arrays['completed'].sum()))
    print('Neutral factors:', arrays['factors'].tolist())


if __name__ == '__main__':
    main()
```

Each call constructs new arrays. Editing one returned scenario input does not change a later call's baseline. These writable arrays are deliberately independent; no persistent research bundle or immutable configuration object is claimed.

## 6.3.11 File — test_creation_types.py

```python
import unittest
import numpy as np
from creation_types import rate_vector, scenario_inputs


class CreationTests(unittest.TestCase):
    def test_valid_rate_conversion(self):
        result = rate_vector(('-1','0','0.025','1'))
        self.assertEqual(result.shape,(4,))
        self.assertEqual(result.dtype,np.dtype('float64'))
        np.testing.assert_allclose(result,[-1.,0.,.025,1.],rtol=0,atol=1e-15,equal_nan=False)

    def test_wire_types(self):
        with self.assertRaises(TypeError):
            rate_vector(['0.1'])
        for value in (True,1,0.1,None):
            with self.assertRaises(TypeError):
                rate_vector((value,))

    def test_wire_domain(self):
        for value in ('',' 0.1','0.1 ','1e-2','2%','NaN','Infinity','1.000001',
                      '-1.1','00.1','.1','0.1234567'):
            with self.subTest(value=value),self.assertRaises(ValueError):
                rate_vector((value,))
        for values in ((),('0',)*1001):
            with self.assertRaises(ValueError):
                rate_vector(values)

    def test_creation_shapes_and_initial_state(self):
        arrays = scenario_inputs()
        self.assertEqual(arrays['results'].shape,(5,3))
        self.assertTrue(np.isnan(arrays['results']).all())
        self.assertFalse(arrays['completed'].any())
        self.assertEqual(arrays['completed'].dtype,np.dtype('bool'))
        np.testing.assert_array_equal(arrays['factors'],[1.,1.,1.])

    def test_grid_and_integer_periods(self):
        arrays = scenario_inputs()
        self.assertEqual(arrays['periods'].dtype,np.dtype('int64'))
        np.testing.assert_array_equal(arrays['periods'],[1,2,3,4])
        np.testing.assert_allclose(arrays['shifts'],[-.01,-.005,0.,.005,.01],
                                   rtol=0,atol=1e-15,equal_nan=False)
        self.assertEqual(arrays['shifts'].size,5)

    def test_independent_calls(self):
        first,second = scenario_inputs(),scenario_inputs()
        for key in first:
            self.assertFalse(np.shares_memory(first[key],second[key]))
        first['rates'][0] = .5
        self.assertAlmostEqual(second['rates'][0],.01)

    def test_cast_is_not_rounding_policy(self):
        values = np.array([1.9,-1.9],dtype=np.float64)
        np.testing.assert_array_equal(values.astype(np.int64),[1,-1])
        with self.assertRaises(TypeError):
            values.astype(np.int64,casting='safe')

    def test_precision_loss_cannot_be_recovered(self):
        original = np.array([16777217],dtype=np.int64)
        recovered = original.astype(np.float32).astype(np.int64)
        self.assertEqual(int(recovered[0]),16777216)
        self.assertNotEqual(int(original[0]),int(recovered[0]))


if __name__ == '__main__':
    unittest.main(verbosity=2)
```

## 6.3.13 Creation Review Checklist

For each constructor, record the intended shape, dtype, units, initial state, and ownership. For each conversion, record which source types are allowed and whether approximation or information loss is acceptable.

Before increasing a scenario count, estimate the output shape and allocation budget. Before changing dtype, rerun numerical and boundary checks appropriate to the new representation. A smaller dtype can alter behavior even when a small demonstration still prints the same rounded value.

## 6.3.14 Troubleshooting

| Symptom | Inspect | Correction |
|---|---|---|
| Fractional values disappear | Integer cast or integer destination | Define conversion/rounding explicitly |
| Incorrect scenario count | Floating-step sequence | Use a count-based grid when count is required |
| Boolean silently becomes numeric | Validation order | Reject original wire type before coercion |
| Huge identifier changes | Floating conversion | Keep identifier representation explicit |
| Workspace appears complete but never ran | Zero-filled results | Use explicit status and uncomputed state |
| NaN leaks into final report | Completion/domain checks | Require validated completed results |
| New run uses edited baseline | Shared arrays | Create deliberate independent inputs |
| Unexpected dtype from mixed values | Inference and input schema | Validate and specify representation |

## 6.3.16 Key Takeaways

Create arrays from an explicit contract for shape, representation, and initial state. Validate source values before a conversion can hide their original types or notation.

A successful cast does not prove numerical preservation or financial correctness. Keep approximation, rounding, missingness, and status as deliberate application decisions.
