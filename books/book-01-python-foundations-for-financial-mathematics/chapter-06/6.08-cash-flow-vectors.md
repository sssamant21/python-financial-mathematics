## 6.8.1 Purpose

A cash-flow vector is useful only when its amounts remain aligned with timing and an explicit sign perspective. A list of numbers alone cannot distinguish an initial payment, a receipt, or a later obligation.

This section represents a synthetic event schedule with aligned period and amount vectors. It computes cumulative nominal cash movement and preserves timing for later valuation work. It deliberately performs no discounting, compounding, NPV, or IRR calculation.

## 6.8.2 Learning Objectives

1. Represent timing and signed amounts as aligned vectors.
2. State perspective, currency, and period-unit assumptions.
3. Distinguish sparse event schedules from dense period grids.
4. Reject duplicate and unsorted timing under an explicit policy.
5. Interpret cumulative nominal movement without overstating its financial meaning.
6. Preserve independent output storage and test known schedules.

## 6.8.3 The Schedule Contract

Use the investor's perspective: a positive amount is received and a negative amount is paid. All entries use USD in the demonstration. Time is an abstract integer period offset from an agreed origin, not a calendar date or a year fraction.

| Period offset | Amount | Meaning in the example | Cumulative nominal movement |
|---|---|---|---|
| 0 | -1000 | Initial payment | -1000 |
| 1 | 200 | Receipt | -800 |
| 3 | -50 | Further payment | -850 |
| 4 | 1000 | Receipt | 150 |

The initial event is explicitly present at period 0. The API also permits a schedule whose first event is later than 0; it does not invent an initial event. The caller is responsible for supplying all events required by the question.

The final value 150 is the sum of the supplied signed amounts. It is not an annualized return, present value, or sufficient evidence that an investment is attractive. Fees, taxes, terminal asset value, and other flows are included only if supplied explicitly under a consistent contract.

## 6.8.4 Two Aligned Vectors

| Vector | Dtype | Meaning | Required relationship |
|---|---|---|---|
| periods | int64 | Event timing offsets | Strictly increasing, nonnegative |
| amounts | float64 | Signed same-currency amounts | Same one-dimensional shape as periods |
| cumulative | float64 | Running nominal sum in event order | One output per supplied event |

The lab supports 1–10,000 events, period offsets up to 1,000,000, and finite amounts with absolute value at most 1e12. Those are deliberate teaching bounds. They constrain allocation and magnitude but do not turn float64 into exact decimal money.

A zero amount is valid and means a known zero event in the supplied schedule. Missing or nonfinite amounts fail rather than being interpreted as zero. Boolean or floating timing arrays are rejected by the exact int64 boundary.

## 6.8.5 Sparse Events and Dense Grids

Periods [0, 1, 3, 4] describe an event schedule with a gap between offsets 1 and 3. The cumulative calculation follows event order and makes no arithmetic use of the gap length.

A dense grid would have an entry for every selected period, including offset 2. If the source schedule is complete and there is known to be no flow at offset 2, a dense representation could use a zero there. A missing observation is a different state and must not be filled silently.

The event representation avoids allocating every possible intermediate period. It also requires the timing vector to travel with the amounts. Do not infer a regular interval from array position when actual offsets have been supplied.

A monthly offset is not a day-count year fraction, and an integer period does not establish business-day conventions. Real-date parsing and valuation conventions are separate boundaries developed later in the book.

## 6.8.6 Ordering and Duplicate Policy

The API requires strictly increasing offsets and rejects repeated periods. It does not sort input silently, since sorting timing without applying the same permutation to amounts would corrupt the schedule.

Two distinct events can legitimately occur at the same time. This API's duplicate rejection is a representation policy, not a claim that such events are financially invalid. Combine them upstream under a documented grouping policy or use a richer event-record representation that preserves individual identities.

When netting events, decide whether audit requirements also require gross receipts and payments, event IDs, and original ordering. A combined zero can conceal offsetting movements. Netting is not a substitute for preserving source evidence.

The order check compares adjacent period values directly. It does not rely on subtracting arbitrary unsigned or extreme integer values. Period bounds are checked before the schedule is accepted.

## 6.8.7 Cumulative Movement and Nominal Net

For ordered amounts c_0 through c_k, define cumulative nominal movement:

```math
C_k=\sum_{j=0}^{k}c_j.
```

The implementation uses np.cumsum with an explicit float64 accumulator. The final cumulative entry is returned as nominal_net, ensuring it refers to the same ordered accumulation shown in the output.

Cumulative cash movement is not necessarily an account balance. An account-balance model needs an opening balance and any other specified effects, such as interest or transfers. This lab starts the accumulation at zero before the first supplied event and includes nothing beyond those events.

A schedule with the same amounts at offsets [0, 10, 30, 40] has the same nominal net as the example. The timing change is preserved but does not affect addition. Valuation must incorporate timing and a stated rate/discount convention; this section establishes the data representation without introducing an implicit one.

## 6.8.8 Numerical and Ownership Policy

Float64 is an approximate analytical representation. Even with bounded inputs, cancellation and rounding can lose small amounts relative to large ones. A final cumulative value need not agree bit for bit with a separately computed reduction that uses another addition order.

The local floating-point policy raises on signaled overflow, underflow, invalid arithmetic, and division errors; the result is also checked for finiteness. The supported amount/event bounds keep ordinary cumulative magnitudes below approximately 1e16, but finiteness does not establish cent-level accuracy throughout that range.

For exact accounting behavior, define a decimal or scaled-integer design with explicit rounding and overflow rules. Do not silently claim that printing two decimal places makes the underlying array exact.

The returned period, amount, and cumulative arrays have independent storage. Mutating the returned amounts does not recompute cumulative values: this is a result record, not a reactive model. Recalculate after deliberate edits and retain the original schedule when needed for evidence.

## 6.8.10 File — cashflow_vectors.py

```python
"""Represent a signed, single-currency event schedule without discounting."""
import numpy as np


def cashflow_schedule(periods: np.ndarray, amounts: np.ndarray) -> dict[str, object]:
    """Return independent vectors and cumulative nominal cash movement.

    Periods are integer offsets in one caller-defined unit, strictly increasing,
    in [0, 1000000]. Amounts: finite signed float64, abs <= 1e12. 1–10000 events.
    Positive means received by the stated investor; negative means paid.
    Caller establishes currency, perspective, event completeness, and timing.
    """
    if type(periods) is not np.ndarray or periods.dtype != np.dtype('int64'):
        raise TypeError('periods must be an exact int64 ndarray')
    if type(amounts) is not np.ndarray or amounts.dtype != np.dtype('float64'):
        raise TypeError('amounts must be an exact float64 ndarray')
    if periods.ndim != 1 or amounts.ndim != 1 or periods.shape != amounts.shape:
        raise ValueError('periods and amounts must be equal-shape vectors')
    if not 1 <= periods.size <= 10000:
        raise ValueError('expected 1 to 10000 events')
    if (periods < 0).any() or (periods > 1000000).any():
        raise ValueError('period outside lab bounds')
    if (periods[1:] <= periods[:-1]).any():
        raise ValueError('periods must be strictly increasing; combine duplicates upstream')
    if not np.isfinite(amounts).all() or (np.abs(amounts) > 1e12).any():
        raise ValueError('amounts must be finite and within lab bounds')
    with np.errstate(over='raise',under='raise',invalid='raise',divide='raise'):
        cumulative = np.cumsum(amounts,dtype=np.float64)
    if not np.isfinite(cumulative).all():
        raise ValueError('nonfinite cumulative movement')
    return {'periods':periods.copy(),'amounts':amounts.copy(),
            'cumulative':cumulative,'nominal_net':float(cumulative[-1])}


def main() -> None:
    periods = np.array([0,1,3,4],dtype=np.int64)
    amounts = np.array([-1000.,200.,-50.,1000.],dtype=np.float64)
    result = cashflow_schedule(periods,amounts)
    print('Perspective: investor; unit: abstract period; currency: USD')
    print('Periods:',result['periods'].tolist())
    print('Amounts:',result['amounts'].tolist())
    print('Cumulative nominal movement:',result['cumulative'].tolist())
    print(f'Nominal net: {result["nominal_net"]:.2f}')
    print('Inflow periods:',periods[amounts > 0].tolist())
    print('Outflow periods:',periods[amounts < 0].tolist())


if __name__ == '__main__':
    main()
```

The example's currency, investor perspective, and abstract period unit are displayed explicitly. The kernel cannot establish those external assumptions from the vectors themselves.

## 6.8.11 File — test_cashflow_vectors.py

```python
import unittest
import numpy as np
from cashflow_vectors import cashflow_schedule


def inputs():
    return np.array([0,1,3,4],dtype=np.int64),np.array([-1000.,200.,-50.,1000.])

class CashflowTests(unittest.TestCase):
    def test_known_schedule(self):
        result = cashflow_schedule(*inputs())
        np.testing.assert_array_equal(result['cumulative'],[-1000.,-800.,-850.,150.])
        self.assertEqual(result['nominal_net'],150.)
        np.testing.assert_array_equal(result['periods'],[0,1,3,4])

    def test_scalar_reference(self):
        periods,amounts = inputs()
        expected,total = [],0.
        for amount in amounts.tolist():
            total += amount
            expected.append(total)
        np.testing.assert_allclose(cashflow_schedule(periods,amounts)['cumulative'],expected,
                                   rtol=1e-12,atol=1e-12,equal_nan=False)

    def test_timing_changes_not_nominal_net(self):
        periods,amounts = inputs()
        alternative = np.array([0,10,30,40],dtype=np.int64)
        first,second = cashflow_schedule(periods,amounts),cashflow_schedule(alternative,amounts)
        self.assertEqual(first['nominal_net'],second['nominal_net'])
        self.assertFalse(np.array_equal(first['periods'],second['periods']))

    def test_duplicate_unsorted_and_negative_periods(self):
        for periods in ([0,1,1,4],[0,3,1,4],[-1,1,3,4],[0,1,3,1000001]):
            with self.assertRaises(ValueError):
                cashflow_schedule(np.array(periods,dtype=np.int64),inputs()[1])

    def test_shape_and_dtype(self):
        for periods in (np.array([],dtype=np.int64),np.array([[0,1,3,4]],dtype=np.int64),
                        np.array([0,1],dtype=np.int64)):
            with self.assertRaises(ValueError):
                cashflow_schedule(periods,inputs()[1])
        with self.assertRaises(TypeError):
            cashflow_schedule(np.array([0.,1.,3.,4.]),inputs()[1])
        with self.assertRaises(TypeError):
            cashflow_schedule(inputs()[0],np.array([-1000,200,-50,1000]))

    def test_amount_domain(self):
        for value in (np.nan,np.inf,-np.inf,1e12+1):
            amounts = inputs()[1]
            amounts[0] = value
            with self.assertRaises(ValueError):
                cashflow_schedule(inputs()[0],amounts)

    def test_zero_single_event_and_boundaries(self):
        self.assertEqual(cashflow_schedule(np.array([5],dtype=np.int64),np.array([0.]))['nominal_net'],0.)
        periods = np.arange(10000,dtype=np.int64)
        self.assertEqual(cashflow_schedule(periods,np.full(10000,1e12))['nominal_net'],1e16)
        with self.assertRaises(ValueError):
            cashflow_schedule(np.arange(10001,dtype=np.int64),np.zeros(10001))

    def test_source_preservation_and_independence(self):
        periods,amounts = inputs()
        before = (periods.copy(),amounts.copy())
        result = cashflow_schedule(periods,amounts)
        for current,original in zip((periods,amounts),before):
            np.testing.assert_array_equal(current,original)
        for key in ('periods','amounts','cumulative'):
            self.assertFalse(np.shares_memory(result[key],periods))
            self.assertFalse(np.shares_memory(result[key],amounts))
        result['amounts'][0] = 0.
        self.assertEqual(amounts[0],-1000.)

if __name__ == '__main__':
    unittest.main(verbosity=2)
```

## 6.8.13 Review Before Valuation

Confirm perspective, currency, completeness, time origin, unit, order, and duplicate policy before using a cash-flow vector in a financial model. Then define how timing enters the calculation.

A period-zero flow and a later flow can have the same nominal amount but a different valuation role. A final receipt is not automatically a terminal market value, and an intermediate payment is not automatically a fee. Preserve event meaning outside the numerical kernel when those distinctions matter.

For multiple instruments or scenarios, choose axes deliberately and state which timing vector applies to each. Do not pad incomplete schedules with zeros merely to form a rectangular array. This section handles one schedule only.

## 6.8.14 Troubleshooting

| Symptom | Inspect | Correction |
|---|---|---|
| Receipts/payments reversed | Perspective and sign convention | Normalize signs explicitly with source meaning |
| Shape mismatch | Filter/sort applied to one vector only | Transform timing and amounts together |
| Duplicate period rejected | Event netting policy | Combine upstream or retain richer event records |
| Nominal net unchanged after timing change | Pure addition ignores elapsed time | Preserve timing for explicit valuation later |
| Gap interpreted as missing observation | Sparse versus dense representation | Establish completeness before filling zeros |
| Zero inserted for unknown payment | Missing-data policy | Reject or mark incomplete rather than inventing data |
| Displayed cents hide loss | Magnitude, cancellation, representation | Review numerical accuracy requirements |
| Cumulative values stale after edit | Stored result versus live model | Recompute from the edited schedule |

## 6.8.16 Key Takeaways

Cash-flow amounts require aligned timing, signs, units, and completeness. A sparse event schedule and a dense period grid communicate different assumptions.

Cumulative nominal addition describes supplied cash movement. Preserve timing and event meaning for later valuation, and keep numerical precision and output ownership explicit.
