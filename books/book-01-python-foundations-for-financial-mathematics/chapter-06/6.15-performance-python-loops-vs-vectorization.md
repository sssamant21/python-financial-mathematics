## 6.15.1 Purpose

Performance claims need an explicit workload, equivalent results, measured boundaries, and evidence from the environment that ran them. A concise array expression is not by itself proof of a faster application.

This section benchmarks the fixed-quantity price-only change q*(end-start) from Section 6.5. It separates a list-to-list application boundary from a kernel whose inputs already reside in NumPy arrays. Correctness gates run before timing.

## 6.15.2 Learning Objectives

1. Define what a benchmark includes and excludes.
2. Compare equivalent input/output boundaries.
3. Validate numerical agreement before measuring runtime.
4. Record repeated samples and environment context.
5. Distinguish array payload from peak process memory.
6. Interpret a local result without generalizing it into a universal speedup.

## 6.15.3 Financial Workload

For each aligned synthetic position, calculate signed fixed quantity multiplied by end-minus-start price. Inputs share currency, per-unit convention, and one interval. There are no trades, distributions, fees, FX effects, or aggregation.

The known fixture uses quantities [10,-5,0], start prices [100,80,50], and end prices [105,76,52], yielding [50,20,0]. Generated benchmark inputs use bounded deterministic values rather than random generation inside a timer.

These are prevalidated teaching kernels. They are not replacements for Section 6.5's validated public API. For example, python_lists uses zip and assumes equal input lengths; it does not detect a shorter list. Never remove validation from an application merely because the microbenchmark excludes it.

## 6.15.4 Three Explicit Boundaries

| Case | Timed inputs | Timed work | Timed output |
|---|---|---|---|
| python_lists | Existing Python float lists | List comprehension arithmetic and allocation | Python float list |
| numpy_lists | Same existing lists | Convert three lists, array arithmetic, convert result back | Python float list |
| numpy_resident | Existing float64 arrays | Array arithmetic and result allocation | float64 ndarray |

The first two cases have the same external representation. Their ratio is reported as python-list median divided by NumPy-list median. A ratio above one means the NumPy route took less median time for that measured list-boundary case; below one means the Python route did.

The resident-array case answers a different question. It excludes conversion and returns a different representation, so the report does not label its ratio against python_lists as a like-for-like application speedup.

Preparing data, checking correctness, importing libraries, parsing files, reporting, and domain validation are outside every timer. Neither setup nor a list's earlier creation is secretly charged to one case only. The list-conversion case does include each conversion it needs during the call.

## 6.15.5 Correctness Before Timing

verify computes the Python reference and checks both NumPy routes for equal shape and approximate numerical agreement. It uses rtol=1e-12 and atol=1e-12 with NaNs disallowed for these bounded fixtures.

Separate tests establish a known financial answer, output representation, input preservation, and independent array storage. Agreement between two implementations alone could reproduce a shared formula mistake, so the known-answer fixture matters.

A failed gate stops the benchmark. Timing a wrong formula, truncated zip, mismatched dtype, or different output cannot establish a useful optimization. Larger performance differences do not excuse a contract change.

## 6.15.6 Measurement Protocol

For each size 3, 1000, and 100000, the driver creates arrays and equivalent Python lists, checks correctness, and performs one untimed warm-up per implementation. It then uses timeit.repeat with five samples, each containing three calls.

Each sample total is divided by three to obtain seconds per call. The JSON report retains every sample plus its minimum and median. These are batch-average call times, not individual request-latency observations or a confidence interval.

The minimum can indicate a relatively low-interference observation. The median describes the center of these five local samples. Neither summarizes every source of variability. Fixed short batches, implementation order, shared-host scheduling, caches, and allocator behavior limit interpretation, especially for tiny cases.

The methods run in the same fixed order for each size. A more rigorous experiment can rotate order, use adaptive batch lengths, isolate processes, and repeat across sessions. Those extensions should preserve the same correctness and boundary definitions.

## 6.15.7 What timeit Changes

The timing mechanism uses a high-resolution elapsed-time timer and excludes setup. timeit normally disables cyclic garbage collection during the timed loop and restores its prior state afterward. That policy is part of this microbenchmark's scope, not an account of a complete application's memory lifecycle.

Callable invocation, output allocation, and release of the returned temporary participate in these measurements. All implementations compute eagerly. No file I/O, network activity, or lazy-result materialization is hidden after the timer.

Do not run a heavy benchmark inside a unit test and assert a speed threshold. The supplied tests check behavior, not timing ratios. Actual timings belong in a separate evidence report because shared resources and runtime conditions vary.

## 6.15.9 File — performance_lab.py

```python
"""Bounded microbenchmark of fixed-quantity price-only P&L kernels."""
import json
import platform
import statistics
import timeit
import numpy as np


def python_lists(q, start, end):
    """Prevalidated equal-length Python float lists -> Python float list."""
    return [a*(c-b) for a,b,c in zip(q,start,end)]


def numpy_resident(q, start, end):
    """Prevalidated equal-shape float64 arrays -> newly allocated array."""
    return q*(end-start)


def numpy_lists(q, start, end):
    """Same list boundary as python_lists; includes array conversion/output list."""
    return numpy_resident(np.asarray(q,dtype=np.float64),
                          np.asarray(start,dtype=np.float64),
                          np.asarray(end,dtype=np.float64)).tolist()


def prepare(size):
    if type(size) is not int or not 1 <= size <= 100000:
        raise ValueError('size must be an exact int in [1,100000]')
    q = np.linspace(-10.,10.,size,dtype=np.float64)
    start = np.linspace(50.,150.,size,dtype=np.float64)
    end = start + np.linspace(-2.,3.,size,dtype=np.float64)
    arrays = (q,start,end)
    lists = tuple(x.tolist() for x in arrays)
    return arrays,lists


def verify(arrays, lists):
    expected = python_lists(*lists)
    for actual in (numpy_resident(*arrays),numpy_lists(*lists)):
        if np.asarray(actual).shape != (len(expected),):
            raise AssertionError('output shape mismatch')
        np.testing.assert_allclose(actual,expected,rtol=1e-12,atol=1e-12,equal_nan=False)


def benchmark(size, *, repeat=5, number=3):
    if any(type(x) is not int or not 1 <= x <= 20 for x in (repeat,number)):
        raise ValueError('repeat and number must be exact ints in [1,20]')
    arrays,lists = prepare(size)
    verify(arrays,lists)  # Correctness gate precedes every timer.
    methods = {'python_lists':lambda:python_lists(*lists),
               'numpy_lists':lambda:numpy_lists(*lists),
               'numpy_resident':lambda:numpy_resident(*arrays)}
    results = {}
    for name,operation in methods.items():
        operation()  # One untimed warm-up; inputs remain unchanged.
        samples = [total/number for total in timeit.repeat(operation,repeat=repeat,number=number)]
        results[name] = {'seconds_per_call':samples,'minimum':min(samples),
                         'median':statistics.median(samples)}
    return {'size':size,'repeat':repeat,'number':number,'correctness':'passed',
            'input_array_element_bytes':sum(x.nbytes for x in arrays),
            'output_array_element_bytes':size*8,'timings':results,
            'list_boundary_median_ratio':results['python_lists']['median']/results['numpy_lists']['median']}


def main():
    report = {'python':platform.python_version(),'numpy':np.__version__,
              'system':platform.system(),'machine':platform.machine(),
              'processor':platform.processor(),
              'scope':'warm local kernels; list boundary includes conversion; no I/O or domain validation',
              'cases':[benchmark(size) for size in (3,1000,100000)]}
    print(json.dumps(report,indent=2,allow_nan=False))


if __name__ == '__main__':
    main()
```

The driver does not write files or modify source inputs. It prints JSON with measured samples and metadata; retain that output deliberately if a comparison must be reviewed later. The processor field can be sparse and does not replace a detailed hardware inventory.

## 6.15.10 File — test_performance_lab.py

```python
import unittest
import numpy as np
from performance_lab import python_lists,numpy_lists,numpy_resident,prepare,verify,benchmark

class PerformanceCorrectnessTests(unittest.TestCase):
    def test_known_long_short_flat(self):
        source = ([10.,-5.,0.],[100.,80.,50.],[105.,76.,52.])
        self.assertEqual(python_lists(*source),[50.,20.,0.])
        self.assertEqual(numpy_lists(*source),[50.,20.,0.])
        np.testing.assert_array_equal(numpy_resident(*(np.array(x) for x in source)),[50.,20.,0.])

    def test_all_benchmark_sizes_agree(self):
        for size in (3,1000,100000):
            verify(*prepare(size))

    def test_matching_list_boundary(self):
        _,lists = prepare(10)
        for operation in (python_lists,numpy_lists):
            result = operation(*lists)
            self.assertIs(type(result),list)
            self.assertTrue(all(type(x) is float for x in result))
            self.assertEqual(len(result),10)

    def test_array_boundary(self):
        arrays,_ = prepare(10)
        result = numpy_resident(*arrays)
        self.assertEqual(result.dtype,np.dtype('float64'))
        self.assertEqual(result.shape,(10,))
        for source in arrays:
            self.assertFalse(np.shares_memory(source,result))

    def test_source_preservation(self):
        arrays,lists = prepare(10)
        before = tuple(x.copy() for x in arrays),tuple(x.copy() for x in lists)
        python_lists(*lists); numpy_lists(*lists); numpy_resident(*arrays)
        for a,b in zip(arrays,before[0]):
            np.testing.assert_array_equal(a,b)
        self.assertEqual(lists,before[1])

    def test_size_policy(self):
        for size in (0,-1,True,3.,100001):
            with self.assertRaises(ValueError):
                prepare(size)

    def test_timer_count_policy(self):
        for count in (0,True,21,1.):
            with self.assertRaises(ValueError):
                benchmark(3,number=count)

    def test_single_entry_and_zero_change(self):
        verify(*prepare(1))
        source = ([2.,-3.],[5.,7.],[5.,7.])
        self.assertEqual(python_lists(*source),[0.,-0.])
        self.assertEqual(numpy_lists(*source),[0.,-0.])

if __name__ == '__main__':
    unittest.main(verbosity=2)
```

## 6.15.12 Memory Is a Separate Measurement

At 100000 positions, the three resident float64 input arrays contain 2,400,000 element bytes and one output contains 800,000. The expression also requires intermediate work, and the driver retains Python lists. These numbers are payload descriptions, not peak process memory.

Python lists contain references to objects, so multiplying list length by eight is not a full list-storage estimate. Conversion adds allocations; array temporaries and allocator reuse affect peaks. Broadcasting can also create unexpectedly large outputs, as Section 6.6 discussed.

This lab records input/output array payload only. It does not measure peak RSS, allocations, memory bandwidth, or garbage-collector pressure. A memory optimization claim would need separate instrumentation and a defined lifecycle.

## 6.15.13 Interpret Results for the Application

If data is already numerical and reused across many calculations, retaining arrays can avoid repeated conversions. If the application must accept and return lists for each small call, conversion costs may dominate. Measure the actual boundary instead of selecting the most favorable isolated kernel number.

Validation, parsing, database/network access, and report generation can dominate end-to-end runtime. Profile the application to identify what matters before replacing clear code. A faster kernel has limited value if it is a small fraction of total work.

np.vectorize is primarily a convenience wrapper around Python-callable evaluation; its name is not evidence of the performance of native numeric array operations. No np.vectorize timing is included in this run.

Consider out buffers, chunking, or alternative compiled implementations only after defining ownership and numerical contracts. Reusing an output buffer changes allocation and aliasing semantics and requires a separately labeled comparison.

## 6.15.14 Troubleshooting

| Symptom | Inspect | Correction |
|---|---|---|
| Huge speedup disappears in application | Conversion and I/O boundaries | Measure the actual workflow |
| Fast implementation fails agreement | Formula, dtype, shape | Fix correctness before timing |
| Small-case ranking varies | Timer overhead and scheduling | Increase controlled repetitions and report variability |
| Resident-array result compared with list output | Different representations | Separate the cases explicitly |
| Results change after optimization | In-place writes or precision changes | Preserve contract and source data |
| Memory claim based on nbytes alone | Other arrays, objects, intermediates | Measure peak memory separately |
| Test fails only under load | Timing threshold in tests | Test behavior; record performance evidence separately |
| np.vectorize assumed compiled | Callable-wrapper behavior | Measure an equivalent implementation |

## 6.15.16 Key Takeaways

Benchmark a defined workload and comparable boundaries after correctness passes. Separate conversion-inclusive application work from a resident-array kernel.

Retain raw samples, environment context, and limitations. Optimize the workflow that matters, preserving numerical meaning and ownership rather than assuming vectorization always wins.
