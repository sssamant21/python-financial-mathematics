## 6.11.1 Purpose

A matrix organizes related numerical observations along named axes. Matrix multiplication combines entries along a shared axis, making it useful for applying many allocations to many scenarios at once.

This section extends Section 6.10's one-portfolio weighted return to a scenario-by-portfolio result table. It emphasizes the model behind the multiplication: compatible returns, opening allocations, and identical instrument order. It performs no optimization or calibration.

## 6.11.2 Learning Objectives

1. State the meaning and labels of each matrix axis.
2. Derive dimensions for a matrix product.
3. Distinguish elementwise multiplication from contraction over instruments.
4. Use a transpose deliberately without assuming independent storage.
5. Validate weights and identity order before multiplication.
6. Check results with known answers, scalar arithmetic, and consistent permutations.

## 6.11.3 Two Input Tables

The return matrix R has one row per alternative scenario and one column per instrument. Each scenario describes the same one-interval price-return convention.

| Scenario | A | B | CASH |
|---|---|---|---|
| UP | 0.10 | -0.05 | 0.00 |
| DOWN | -0.20 | 0.10 | 0.00 |
| CASH-YIELD | 0.00 | 0.00 | 0.002 |

The allocation matrix W has one row per portfolio and the same instrument columns.

| Portfolio | A | B | CASH |
|---|---|---|---|
| P1 | 0.60 | 0.30 | 0.10 |
| P2 | 0.20 | 0.30 | 0.50 |

These are synthetic long-only opening allocations. Each row includes cash and sums to one within the declared tolerance. Different scenario rows are alternatives, not successive time observations. Both portfolios retain their stated opening allocation for every scenario comparison.

The example cash component has a supplied mark-growth convention, including 0.002 in the third scenario. Its label does not create an unstated interest-accrual engine. Every return component must be defined consistently by the caller; no additional cash distribution is added by the kernel.

## 6.11.4 Derive the Product

For scenario s and portfolio p, define:

```math
Y_{s,p}=\sum_{i=1}^{N}R_{s,i}W_{p,i}.
```

This carries forward the weighted one-interval arithmetic contract from Section 6.10. In matrix notation:

```math
Y=RW^\mathsf{T}.
```

| Quantity | Shape | Axis meanings |
|---|---|---|
| R | (S, N) | Scenario, instrument |
| W | (P, N) | Portfolio, instrument |
| W.T | (N, P) | Instrument, portfolio |
| Y | (S, P) | Scenario, portfolio |

The instrument dimension is summed over. The scenario and portfolio dimensions remain. For this fixture, (3,3) multiplied by (3,2) produces (3,2).

The kernel uses ordinary two-dimensional ndarrays and the @ operator. It does not require the separate np.matrix class. Restricting rank to two avoids silently introducing higher-dimensional batch semantics into this introductory model.

## 6.11.5 Work a Cell by Hand

For UP and P1, 0.10*0.60 + (-0.05)*0.30 + 0*0.10 = 0.045. For DOWN and P2, (-0.20)*0.20 + 0.10*0.30 + 0*0.50 = -0.01.

| Scenario | P1 result | P2 result |
|---|---|---|
| UP | 4.50% | 0.50% |
| DOWN | -9.00% | -1.00% |
| CASH-YIELD | 0.02% | 0.10% |

The third row makes cash inclusion visible: 0.002*0.10=0.0002 and 0.002*0.50=0.001. These are illustrative allocation comparisons, not forecasts or recommended portfolios. No scenario probabilities are supplied.

## 6.11.6 Multiplication Is Not Always the Same Operation

`R * W` attempts elementwise multiplication with broadcasting. It does not sum across instruments to produce every scenario/portfolio comparison. The nonsquare portfolio count in the fixture causes that expression to fail rather than accidentally appear correct.

`R @ W.T` implements the stated sum of products. Reversing operands, omitting the transpose, or transposing the result can change the output meaning even when dimensions happen to permit an operation.

A transpose swaps axis roles. It does not sort labels, repair identity mismatches, or necessarily allocate new storage. The test confirms that W.T shares storage with W for the supplied array. The kernel only reads that view and allocates the product separately.

## 6.11.7 Identity Is Part of Matrix Compatibility

Numerical dimensions only establish how many components are paired. The instrument tuples must match in both identity and order. The function rejects differing return/weight instrument labels even when the numerical dimensions match.

A consistent permutation of both input column sets should preserve Y within numerical tolerance. The test reorders instruments to CASH, A, B in both matrices and verifies this property. Reordering only one labeled input fails validation.

Labels can still be wrong at the source. Matching tuples cannot prove that a return was attached to the correct real instrument. Preserve ingestion and valuation evidence upstream. Scenario and portfolio labels are also required to be unique nonempty unpadded strings with lengths matching their axes.

## 6.11.8 Financial Scope and Assumptions

Each row of W represents beginning values normalized under a long-only positive-denominator convention. Supplied weight rows are checked without automatic renormalization. The absolute sum tolerance is 1e-12 with relative tolerance zero.

Each R entry is a finite simple price return of at least -1, sharing the stated interval and currency convention. The model excludes trades, external flows, distributions, fees, financing, FX, and leverage. It does not use closing weights or model their drift.

Using the same opening W for alternative scenarios is intentional. Using it for successive historical periods could imply repeated rebalancing instead of fixed holdings. A time-path model needs rebalancing, costs, cash, and timing rules before the same matrix expression can be interpreted economically.

The output is a table of portfolio return comparisons. It is not a contribution cube, covariance matrix, optimized allocation, stress probability distribution, or risk forecast. Later chapters develop those models separately.

## 6.11.9 Domain, Memory, and Numerical Policy

The API requires exact float64 ndarrays with two nonempty axes. All entries must be finite. Weights lie in [0,1]; returns are at least -1. Full-input validation applies even to instruments with zero allocation in a particular portfolio.

The teaching max_cells policy limits each individual input matrix and the output matrix to at most 1,000,000 cells by default. The budget is a positive exact Python int. It does not limit total process memory, internal workspace, or all temporary validation arrays. Input validation occurs before the budget check, so it is not a guard against reading already allocated large inputs.

A full output has S*P float64 entries. Computing the product directly avoids explicitly materializing an S-by-P-by-N contribution cube. This is a representation choice, not a measured performance claim or a guarantee about internal library workspace.

Local numerical handling raises on signaled errors and the product is checked for finite values. Exact floating-point signal behavior can depend on the underlying operation and numerical backend, so final result validation remains necessary. These checks do not detect every rounding or cancellation issue.

All numerical comparisons in the fixtures use rtol=1e-12 and atol=1e-12 with NaNs disallowed. These small-example tolerances are not general financial materiality thresholds or a promise of bitwise equality across platforms.

## 6.11.11 File — matrix_models.py

```python
"""Compare fixed opening allocations across common one-interval scenarios."""
import numpy as np


def label_axis(labels: tuple[str, ...], size: int) -> None:
    if type(labels) is not tuple or len(labels) != size:
        raise ValueError('axis labels must be a matching tuple')
    if any(type(x) is not str or not x or x.strip() != x for x in labels):
        raise ValueError('axis labels must be nonempty unpadded text')
    if len(set(labels)) != size:
        raise ValueError('axis labels must be unique')


def matrix(value: np.ndarray) -> None:
    if type(value) is not np.ndarray or value.dtype != np.dtype('float64'):
        raise TypeError('expected an exact float64 ndarray')
    if value.ndim != 2 or 0 in value.shape:
        raise ValueError('expected a nonempty two-dimensional matrix')
    if not np.isfinite(value).all():
        raise ValueError('matrix must be finite')


def allocation_scenarios(returns: np.ndarray, return_ids: tuple[str, ...],
                         scenarios: tuple[str, ...], weights: np.ndarray,
                         weight_ids: tuple[str, ...], portfolios: tuple[str, ...],
                         *, max_cells: int = 1000000) -> dict[str, object]:
    """Compute (scenario, instrument) @ (instrument, portfolio).

    Long-only weight rows sum to one within abs tolerance 1e-12; no correction.
    Returns are compatible one-interval simple price returns >= -1.
    Same currency convention, no trades/flows/distributions/fees/FX/financing.
    Each scenario uses the same opening weights; scenarios are alternatives.
    """
    matrix(returns)
    matrix(weights)
    label_axis(return_ids,returns.shape[1])
    label_axis(weight_ids,weights.shape[1])
    label_axis(scenarios,returns.shape[0])
    label_axis(portfolios,weights.shape[0])
    if return_ids != weight_ids:
        raise ValueError('instrument identity and order must match')
    if (returns < -1).any() or (weights < 0).any() or (weights > 1).any():
        raise ValueError('unsupported return or weight domain')
    if type(max_cells) is not int or max_cells < 1:
        raise ValueError('max_cells must be a positive exact int')
    if any(int(rows)*int(cols) > max_cells for rows,cols in
           (returns.shape,weights.shape,(returns.shape[0],weights.shape[0]))):
        raise ValueError('input or output matrix exceeds cell budget')
    with np.errstate(over='raise',under='raise',invalid='raise',divide='raise'):
        sums = np.sum(weights,axis=1,dtype=np.float64)
        if not np.isclose(sums,1.,rtol=0.,atol=1e-12).all():
            raise ValueError('each portfolio weight row must sum to one')
        result = returns @ weights.T
    if not np.isfinite(result).all():
        raise ValueError('nonfinite matrix result')
    return {'scenarios':scenarios,'portfolios':portfolios,'returns':result,
            'weight_sums':sums}


def inputs():
    returns = np.array([[.1,-.05,0.],[-.2,.1,0.],[0.,0.,.002]],dtype=np.float64)
    weights = np.array([[.6,.3,.1],[.2,.3,.5]],dtype=np.float64)
    return returns,('A','B','CASH'),('UP','DOWN','CASH-YIELD'),weights,('A','B','CASH'),('P1','P2')


def main() -> None:
    result = allocation_scenarios(*inputs())
    print('Axes: scenario, portfolio')
    print('Output shape:',result['returns'].shape)
    print('Portfolios:',result['portfolios'])
    for name,row in zip(result['scenarios'],result['returns']):
        print(name+': '+', '.join(f'{value:.2%}' for value in row))


if __name__ == '__main__':
    main()
```

The result includes both output label axes and the observed portfolio weight sums. The function does not mutate input matrices. Returned numerical result storage is independent of the source matrices.

## 6.11.12 File — test_matrix_models.py

```python
import unittest
import numpy as np
from matrix_models import allocation_scenarios,inputs

class MatrixTests(unittest.TestCase):
    def test_known_model(self):
        result = allocation_scenarios(*inputs())
        self.assertEqual(result['returns'].shape,(3,2))
        np.testing.assert_allclose(result['returns'],[[.045,.005],[-.09,-.01],[.0002,.001]],
                                   rtol=1e-12,atol=1e-12,equal_nan=False)
        self.assertEqual(result['portfolios'],('P1','P2'))

    def test_nested_reference(self):
        r,rids,scenarios,w,wids,portfolios = inputs()
        expected = [[sum(a*b for a,b in zip(scenario,portfolio)) for portfolio in w.tolist()]
                    for scenario in r.tolist()]
        np.testing.assert_allclose(allocation_scenarios(r,rids,scenarios,w,wids,portfolios)['returns'],
                                   expected,rtol=1e-12,atol=1e-12,equal_nan=False)

    def test_consistent_column_permutation(self):
        r,ids,s,w,_,p = inputs()
        order = [2,0,1]
        permuted = tuple(ids[i] for i in order)
        actual = allocation_scenarios(r[:,order],permuted,s,w[:,order],permuted,p)
        np.testing.assert_allclose(actual['returns'],allocation_scenarios(*inputs())['returns'],
                                   rtol=1e-12,atol=1e-12,equal_nan=False)
        with self.assertRaises(ValueError):
            allocation_scenarios(r,ids,s,w[:,order],permuted,p)

    def test_axes_and_product_not_elementwise(self):
        r,ids,s,w,_,p = inputs()
        self.assertEqual(w.T.shape,(3,2))
        with self.assertRaises(ValueError):
            _ = r*w
        result = allocation_scenarios(r[:1],ids,s[:1],w[:1],ids,p[:1])
        self.assertEqual(result['returns'].shape,(1,1))

    def test_invalid_labels_and_shapes(self):
        r,ids,s,w,_,p = inputs()
        for bad_s in (('X','X','Y'),('UP',),['UP','DOWN','CASH-YIELD']):
            with self.assertRaises(ValueError):
                allocation_scenarios(r,ids,bad_s,w,ids,p)
        with self.assertRaises(ValueError):
            allocation_scenarios(r[0],ids,s,w,ids,p)
        with self.assertRaises(TypeError):
            allocation_scenarios(r.astype(np.float32),ids,s,w,ids,p)

    def test_domain_and_weight_rows(self):
        r,ids,s,w,_,p = inputs()
        for value in (-1.01,np.nan,np.inf):
            bad = r.copy(); bad[0,0] = value
            with self.assertRaises(ValueError):
                allocation_scenarios(bad,ids,s,w,ids,p)
        bad_w = w.copy(); bad_w[1] = [0.,0.,0.]
        with self.assertRaises(ValueError):
            allocation_scenarios(r,ids,s,bad_w,ids,p)

    def test_budget(self):
        self.assertEqual(allocation_scenarios(*inputs(),max_cells=9)['returns'].shape,(3,2))
        for budget in (8,0,True):
            with self.assertRaises(ValueError):
                allocation_scenarios(*inputs(),max_cells=budget)

    def test_source_and_transpose_storage(self):
        r,ids,s,w,_,p = inputs()
        before_r,before_w = r.copy(),w.copy()
        result = allocation_scenarios(r,ids,s,w,ids,p)['returns']
        np.testing.assert_array_equal(r,before_r)
        np.testing.assert_array_equal(w,before_w)
        self.assertFalse(np.shares_memory(result,r))
        self.assertFalse(np.shares_memory(result,w))
        self.assertTrue(np.shares_memory(w.T,w))

if __name__ == '__main__':
    unittest.main(verbosity=2)
```

## 6.11.14 Review Before Extending the Model

Write the sum-of-products equation and name the axis being contracted before selecting an operator. Check dimensions, identity order, units, timing, and the interpretation of every surviving output axis.

For factor exposures, a superficially similar product needs factor units and sensitivity conventions. For cash-flow valuation, another product needs timing-aligned discount factors. Shared matrix syntax does not make those financial contracts interchangeable.

Section 6.12 introduces linear algebra operations. Solving an equation, estimating a model, and applying a known allocation are different tasks even when each uses matrices.

## 6.11.15 Troubleshooting

| Symptom | Inspect | Correction |
|---|---|---|
| Product dimension error | Inner instrument dimension and transpose | Derive the shapes from the equation |
| Elementwise array returned | * used instead of @ | Use the intended sum-of-products operation |
| Plausible but wrong numbers | Column identity/order | Align labels and values together |
| Output axes reversed | Operand order/result transpose | Preserve scenario-by-portfolio contract |
| Edits to transpose change weights | Shared view | Copy deliberately if an independent edit is needed |
| One row fails weight check | Per-portfolio normalization | Repair that allocation explicitly |
| Oversized product rejected | Matrix cell policy | Plan bounded chunks or reduce retained output |
| Historical result assumes constant weights | Time versus alternative scenarios | Define rebalancing and drift separately |

## 6.11.17 Key Takeaways

Matrices make repeated sum-of-products models compact, but the axes and contracted identities determine their meaning. Derive dimensions from the model before relying on compatible shapes.

Validate labels, units, timing, domains, and ownership. Known cells, nested references, and consistent-permutation checks provide complementary evidence for a matrix implementation.
