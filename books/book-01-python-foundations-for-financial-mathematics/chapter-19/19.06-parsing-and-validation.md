## Learning objectives

Separate decoding, syntax parsing, type conversion and financial validation; define a data contract; classify invalid records; distinguish missing, malformed and valid values; handle duplicates and revisions explicitly; and retain evidence for reproducible ingestion.

## 1. From bytes to financial records

Parsing transforms input into structured values. Validation checks whether those values satisfy a stated contract and are suitable for a particular use. A syntactically valid number may still have the wrong currency, unit, timestamp or financial meaning.

A typical pipeline is: raw bytes → decoding → syntax parsing → schema and type conversion → domain and cross-record checks → accepted records and documented failures. Each step should identify the source and transformation applied.

## 2. Define the contract

For the synthetic examples in this section:

| Field | Contract |
|---|---|
| instrument | Nonempty string |
| date | ISO calendar date in YYYY-MM-DD form |
| close | Positive finite decimal text |
| currency | USD |
| key | Instrument and observation date within the batch |

The key is deliberately narrow for teaching. A real dataset may require venue, price type, source, revision or publication time. A date does not establish when information became available.

## 3. Syntax, types and domain rules

- **Syntax:** Can the CSV or JSON be decoded and parsed according to its format?
- **Schema:** Are required fields present, with the expected structure and types?
- **Domain:** Is a price positive and finite under the specified price contract?
- **Cross-record:** Is a defined key duplicated or a required sequence out of order?
- **Business meaning:** Are currency, price type, instrument identity and time conventions appropriate?

Rules must fit the data. A positive close may be required for a particular equity series; a negative yield can be valid. Parsing alone cannot establish financial correctness.

## 4. Missing, null, empty and zero

A missing key, null, empty string and numeric zero are different conditions. The source contract must define their meanings. Do not silently replace an absent price with zero or infer an unknown currency.

Possible policies include rejecting the batch, quarantining individual rows with reasons, or applying an explicitly approved correction. Retain enough provenance to investigate, without exposing sensitive data unnecessarily.

## 5. Decimal and numeric domains

Parse decimal text with `Decimal` when the contract requires decimal arithmetic. Reject NaN and infinity when finite prices are required. State scale and rounding policy; converting a binary float to decimal does not recover an original exact decimal entry.

For closes 100.00 and 101.50, simple return is **101.50/100−1=.015**, or 1.5%, assuming the same instrument, currency and price definition.

## 6. Dates and availability

Validate date format and distinguish observation date from an event instant or publication time. A valid date may still fall on an unexpected market holiday or lack timezone context; such checks require the relevant calendar and source contract.

A corrected historical record may not have been known at an earlier decision time. Preserve publication or availability timestamps and revisions when the source supports them; otherwise point-in-time accuracy cannot be assumed.

## 7. Duplicates and revisions

Duplicate keys can result from retries, multiple venues or legitimate corrections. Do not automatically keep the first or last row without a documented precedence rule. Determine whether source version, timestamp or venue belongs in the key, and preserve revision lineage.

The reference code below quarantines later duplicates in a batch. That is a teaching policy, not a universal correction strategy.

## 8. Fail-fast and quarantine

A fail-fast policy rejects the whole batch on the first error. A quarantine policy separates invalid records for review while keeping valid records identifiable. Neither policy should silently label an incomplete batch as complete.

Set acceptance thresholds, report accepted and rejected counts, and decide whether downstream publication is allowed. Keep the raw input and error evidence according to security and retention policy. Avoid logging secrets or sensitive content.

## 9. Cross-field and cross-record checks

Examples include matching currency to the intended instrument contract, comparing event time with publication time where definitions permit, validating date ordering, and reconciling totals or counts. A large price movement may be an error, a corporate action or a genuine market event; investigate rather than automatically deleting it.

A checksum can identify source bytes but cannot establish authenticity, completeness or economic correctness.

## 10. Reference implementation

Save as `parsing_validation.py`. It validates already-decoded synthetic record dictionaries. It returns accepted records and error codes without logging raw data. It is not a CSV or JSON parser, a complete security boundary, or a production data pipeline.

~~~python
from datetime import date
from decimal import Decimal, InvalidOperation
import unittest

FIELDS={"instrument","date","close","currency"}

def parse_record(row):
    if not isinstance(row,dict) or set(row)!=FIELDS:
        raise ValueError("schema")
    if any(not isinstance(row[k],str) for k in FIELDS):
        raise ValueError("type")
    instrument=row["instrument"].strip()
    if not instrument:
        raise ValueError("instrument")
    if row["currency"]!="USD":
        raise ValueError("currency")
    try:
        day=date.fromisoformat(row["date"])
    except ValueError as exc:
        raise ValueError("date") from exc
    # Enforce the contract's exact YYYY-MM-DD representation.
    if day.isoformat()!=row["date"]:
        raise ValueError("date")
    try:
        close=Decimal(row["close"])
    except InvalidOperation as exc:
        raise ValueError("close") from exc
    if not close.is_finite() or close<=0:
        raise ValueError("close")
    return {"instrument":instrument,"date":day,"close":close,"currency":"USD"}

def validate_batch(rows):
    accepted,rejected=[],[]
    seen=set()
    for index,row in enumerate(rows,1):
        try:
            parsed=parse_record(row)
            key=(parsed["instrument"],parsed["date"])
            if key in seen:
                raise ValueError("duplicate")
            seen.add(key)
            accepted.append(parsed)
        except ValueError as exc:
            rejected.append({"record_number":index,"reason":str(exc)})
    return {"accepted":accepted,"rejected":rejected,
            "complete":len(rejected)==0}

def simple_return(start,end):
    if not isinstance(start,Decimal) or not isinstance(end,Decimal):
        raise ValueError("Decimal required")
    if not start.is_finite() or not end.is_finite() or start<=0 or end<0:
        raise ValueError("invalid prices")
    return end/start-Decimal("1")

class ValidationTests(unittest.TestCase):
    def setUp(self):
        self.row={"instrument":"EXAMPLE","date":"2026-01-05",
                  "close":"100.00","currency":"USD"}
    def test_valid(self):
        self.assertEqual(parse_record(self.row)["close"],Decimal("100.00"))
    def test_missing(self):
        with self.assertRaises(ValueError): parse_record({"instrument":"X"})
    def test_null(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":None})
    def test_empty(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":""})
    def test_nonfinite(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":"NaN"})
    def test_zero_price(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":"0"})
    def test_bad_currency(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"currency":"EUR"})
    def test_bad_date(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"date":"20260105"})
    def test_duplicate(self):
        result=validate_batch([self.row,self.row])
        self.assertEqual(result["rejected"][0]["reason"],"duplicate")
        self.assertFalse(result["complete"])
    def test_complete(self):
        self.assertTrue(validate_batch([self.row])["complete"])
    def test_return(self):
        self.assertEqual(simple_return(Decimal("100"),Decimal("101.50")),Decimal(".015"))
    def test_bad_start(self):
        with self.assertRaises(ValueError): simple_return(Decimal("0"),Decimal("1"))

if __name__ == "__main__":
    rows=[{"instrument":"EXAMPLE","date":"2026-01-05","close":"100.00","currency":"USD"},
          {"instrument":"EXAMPLE","date":"2026-01-06","close":"101.50","currency":"USD"}]
    result=validate_batch(rows)
    print("accepted:",len(result["accepted"]),"rejected:",len(result["rejected"]),
          "complete:",result["complete"])
    print("return:",simple_return(result["accepted"][0]["close"],
                                  result["accepted"][1]["close"]))
    unittest.main(verbosity=2)
~~~

The code accepts rows in input order, stores accepted rows and keys in memory, and does not enforce date ordering, price type, source identity, exchange calendar or availability time. A batch with no rows is considered complete by this example; a real contract should define whether empty input is allowed. The error reason is a small code, not a full data-quality report.

## 13. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Schema error | Missing or unexpected fields | Compare source and contract versions |
| Close rejected | Empty, nonfinite or nonpositive value | Inspect source and domain rule |
| Duplicate error | Retry, revision or insufficient key | Review identity and precedence policy |
| Valid date but missing observation | Calendar or source coverage issue | Check exchange calendar and completeness |
| Historical signal appears too early | Availability time omitted | Review publication and revision history |
| Accepted counts look correct but data are wrong | Units or price type differ | Reconcile source semantics |
