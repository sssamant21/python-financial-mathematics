## Learning objectives

Identify common financial data sources and formats; distinguish market, reference, corporate-action and transaction data; interpret timestamps, units and provenance; inspect CSV and JSON safely; recognize data quality and look-ahead risks; and design a small reproducible ingestion workflow.

## 1. Why financial data engineering matters

Financial calculations depend on the meaning and quality of their inputs. A correct return formula can produce a misleading result when prices are stale, timestamps are misaligned, corporate actions are omitted or currencies differ.

Data engineering turns source records into datasets with documented meaning, validation and lineage. The objective is not merely to read a file: it is to understand what each record represents, when it became available, and how it was transformed.

## 2. Common financial data categories

| Category | Examples | Questions to ask |
|---|---|---|
| Market data | Trades, quotes, closing prices, rates | Venue, timestamp, price type and currency? |
| Reference data | Instrument identifiers, issuer, currency | Which identifier and effective period? |
| Corporate actions | Splits, dividends, mergers | Effective date, adjustment method and revision? |
| Fundamentals | Financial statements, earnings | Reporting period and publication time? |
| Transaction data | Orders, fills, fees, settlements | Trade versus settlement date and sign conventions? |
| Derived data | Returns, volatility, indicators | Source, transformation, window and availability time? |

A price of 100 without an instrument, currency, timestamp and price definition is not a complete financial observation.

## 3. Sources

Data may come from exchange feeds, licensed vendors, broker statements, company filings, internal databases, APIs, spreadsheets or public datasets. Availability, licensing, update frequency, coverage and correction practices differ. Confirm whether your intended use, retention and redistribution are permitted by the source terms.

Source choice should match the question. A delayed daily close is different from a real-time executable quote, and a vendor-adjusted series is different from raw transaction prices.

## 4. Market data: trade, quote and close

A **trade** records an executed transaction. A **quote** generally contains bid and ask prices and possibly sizes, subject to its venue and timestamp. A **close** can mean an official exchange close, a vendor's end-of-day value or another convention.

Bid, ask and last trade are not interchangeable. A trade can be stale relative to a current quote; a quote can change or expire. Record the price type, venue and retrieval or event time.

## 5. Identifiers and reference data

Symbols can change, be reused or differ by venue. A robust dataset records an instrument identifier and its type, source, exchange or venue, and effective dates where needed. Do not assume a ticker uniquely identifies a security for all time.

Reference data can be revised. Distinguish the date a mapping is effective from the time the mapping became available to the system.

## 6. Corporate actions and adjusted prices

A stock split changes the number of shares and price per share; a dividend may affect total return. Vendor-adjusted prices use a documented adjustment methodology and can be revised after new actions or corrections.

Do not mix raw and adjusted prices without understanding the transformation. A split-adjusted price series is not necessarily a total-return series. Retain the original source, adjustment method and version.

## 7. Formats

| Format | Typical use | Considerations |
|---|---|---|
| CSV / TSV | Simple tabular exchange | Delimiter, quoting, encoding, missing values and types need explicit rules |
| JSON | APIs and nested records | Schema, nesting, numeric representation and nulls need validation |
| Excel | Human-maintained reports | Sheets, formulas, cached values and date formats may differ |
| Parquet | Columnar analytical datasets | Schema, partitioning, metadata and compatible readers matter |
| Database tables | Structured queried records | Keys, constraints, time semantics and transaction snapshots matter |
| API response | On-demand data transfer, often JSON | Pagination, rate limits, errors, revisions and availability time matter |

A file extension or format does not by itself guarantee data quality, schema consistency or accuracy.

## 8. CSV example

~~~csv
instrument,date,close,currency
EXAMPLE,2026-01-05,100.00,USD
EXAMPLE,2026-01-06,101.50,USD
~~~

This is synthetic data. Here `date` is an observation date, not automatically a timestamp or a publication time. The two closes produce a simple return of **101.50/100−1=.015**, or 1.5%, assuming the same instrument and comparable price definitions.

## 9. JSON example

~~~json
{
  "instrument": "EXAMPLE",
  "observation_date": "2026-01-06",
  "close": "101.50",
  "currency": "USD",
  "price_type": "unadjusted_close"
}
~~~

The price is a string here so its decimal text can be parsed deliberately. JSON can also contain numeric values, nulls or nested arrays. A missing key, a null and an invalid numeric string are distinct conditions; define how each is handled.

## 10. Numeric precision and units

Financial values may be expressed in dollars, cents, percentages, decimal rates or basis points. Five percent is .05 as a decimal; one basis point is .0001 in decimal-rate units. A price of 10,000 cents equals 100 dollars.

Python's `decimal.Decimal` can preserve decimal text for calculations requiring decimal arithmetic, provided values are constructed from strings. It does not automatically validate the financial model, currency, rounding policy or source accuracy.

## 11. Time and availability

Distinguish at least:

- **Event time:** when the market event occurred.
- **Observation or effective date:** the date the value describes.
- **Publication or availability time:** when the data became available.
- **Ingestion time:** when your system received or stored it.

Time zones, daylight saving changes, weekends, market calendars and late corrections matter. A date alone is not equivalent to an instant. For historical analysis, use the value and revision that would have been available at the decision time.

## 12. Look-ahead and revisions

Look-ahead bias occurs when a calculation uses information that was not available at the modeled decision time. For example, a statement covering a quarter may be published weeks after the quarter ends; using it on the quarter-end date leaks future information.

Record publication times, ingestion times and revisions when available. A current corrected historical dataset may not reconstruct what was known at the time. Avoid claiming point-in-time correctness unless the necessary historical versions and availability data exist.

## 13. Quality checks

Useful checks include:

- Required fields, schema and valid data types.
- Valid currency and instrument identifiers for the intended scope.
- Positive prices where required, finite numbers and explicit missing-value handling.
- Duplicate keys and ordering, using a defined key such as instrument/date/price type.
- Timestamp and timezone validity, expected coverage and stale observations.
- Unit consistency, corporate-action treatment and source reconciliation.
- Outlier investigation without automatically deleting genuine market moves.

A quality rule is conditional on the dataset. For example, negative yields can be valid; a blanket “all rates positive” rule would be inappropriate.

## 14. Provenance and reproducibility

Retain source identity, retrieval time, file or dataset version, schema version, transformation code revision, parameters, and an appropriate content checksum. A checksum identifies bytes; it does not prove that source data are accurate or authorized.

Keep raw inputs and transformed outputs distinguishable. Record corrections and processing failures, and avoid silently replacing missing values with zeros. Protect credentials and sensitive data according to the applicable access rules.

## 15. Reference implementation

Save as `financial_data_basics.py`. The standard-library example parses synthetic CSV, validates a small schema and calculates a simple return. Its scope is intentionally narrow: one instrument, one currency, strictly increasing dates and positive unadjusted closes.

~~~python
import csv
import hashlib
import io
from datetime import date
from decimal import Decimal, InvalidOperation
import unittest

REQUIRED = ("instrument", "date", "close", "currency")

def parse_prices(text):
    if not isinstance(text, str):
        raise ValueError("CSV text required")
    reader = csv.DictReader(io.StringIO(text, newline=""))
    if reader.fieldnames is None or len(reader.fieldnames) != len(set(reader.fieldnames)):
        raise ValueError("missing or duplicate headers")
    if not set(REQUIRED).issubset(reader.fieldnames):
        raise ValueError("missing required columns")
    records = []
    for row in reader:
        if None in row or any(row.get(key) is None for key in REQUIRED):
            raise ValueError("malformed row")
        instrument = row["instrument"].strip()
        currency = row["currency"].strip()
        if not instrument or currency != "USD":
            raise ValueError("instrument and USD currency required")
        try:
            day = date.fromisoformat(row["date"].strip())
            price = Decimal(row["close"].strip())
        except (ValueError, InvalidOperation) as exc:
            raise ValueError("invalid date or price") from exc
        if not price.is_finite() or price <= 0:
            raise ValueError("positive finite price required")
        if records and (instrument != records[0]["instrument"]
                        or day <= records[-1]["date"]):
            raise ValueError("one instrument and increasing dates required")
        records.append({"instrument":instrument, "date":day,
                        "close":price, "currency":currency})
    if len(records) < 2:
        raise ValueError("at least two records required")
    return records

def simple_return(start, end):
    if not isinstance(start, Decimal) or not isinstance(end, Decimal):
        raise ValueError("Decimal prices required")
    if not start.is_finite() or not end.is_finite() or start <= 0 or end < 0:
        raise ValueError("positive starting price and nonnegative ending price required")
    return end/start-Decimal("1")

def content_sha256(text):
    if not isinstance(text, str):
        raise ValueError("text required")
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

class DataTests(unittest.TestCase):
    def setUp(self):
        self.good = ("instrument,date,close,currency\n"
                     "EXAMPLE,2026-01-05,100.00,USD\n"
                     "EXAMPLE,2026-01-06,101.50,USD\n")
    def test_parse(self):
        self.assertEqual(len(parse_prices(self.good)),2)
    def test_decimal(self):
        self.assertEqual(parse_prices(self.good)[0]["close"],Decimal("100.00"))
    def test_return(self):
        self.assertEqual(simple_return(Decimal("100"),Decimal("101.50")),Decimal(".015"))
    def test_hash_replay(self):
        self.assertEqual(content_sha256(self.good),content_sha256(self.good))
    def test_missing_header(self):
        with self.assertRaises(ValueError): parse_prices("instrument,date\na,2026-01-01\n")
    def test_duplicate_date(self):
        with self.assertRaises(ValueError):
            parse_prices(self.good.replace("2026-01-06","2026-01-05"))
    def test_bad_currency(self):
        with self.assertRaises(ValueError): parse_prices(self.good.replace("USD","EUR"))
    def test_bad_price(self):
        with self.assertRaises(ValueError): parse_prices(self.good.replace("101.50","NaN"))
    def test_bad_date(self):
        with self.assertRaises(ValueError): parse_prices(self.good.replace("2026-01-06","bad"))
    def test_zero_start(self):
        with self.assertRaises(ValueError): simple_return(Decimal("0"),Decimal("1"))

if __name__ == "__main__":
    example = ("instrument,date,close,currency\n"
               "EXAMPLE,2026-01-05,100.00,USD\n"
               "EXAMPLE,2026-01-06,101.50,USD\n")
    rows = parse_prices(example)
    print("return:",simple_return(rows[0]["close"],rows[1]["close"]))
    print("sha256 of UTF-8 text:",content_sha256(example))
    unittest.main(verbosity=2)
~~~

The digest covers the UTF-8 encoding of the supplied text, which may differ from the original file's bytes if it was decoded or newline-normalized. The parser does not implement exchange calendars, point-in-time data, corporate actions or production schema governance.

## 18. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Return looks 100 times too large | Percent versus decimal confusion | Check units and conversions |
| Duplicate records | Retry, correction or incorrect key | Review source version and key semantics |
| Sudden price jump | Corporate action, error or genuine move | Investigate source and adjustment method |
| Data appears before publication | Look-ahead or timestamp mismatch | Inspect availability and timezone |
| Different results from same file | Changed parser, encoding or dependencies | Compare versions and raw-byte identity |
| Missing values become zeros | Implicit coercion | Define and enforce a missing-data policy |
