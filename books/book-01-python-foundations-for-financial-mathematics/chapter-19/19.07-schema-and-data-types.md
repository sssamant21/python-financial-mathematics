## Learning objectives

Design a financial data schema; distinguish physical types from business meaning; define keys, nullability, precision, scale and units; handle schema evolution; and validate synthetic records with explicit assumptions and provenance.

## 1. What is a schema?

A schema describes the structure and constraints of data. It can specify field names, types, allowed values, nullability and relationships. A financial data contract also needs meaning: currency, units, price type, time semantics, source, availability and revision rules.

A value can satisfy a type and still be wrong. For example, `100.00` is a valid decimal but cannot be interpreted as a financial price without knowing the instrument, currency and convention.

## 2. Logical and physical types

A logical concept can have different physical representations:

| Concept | Possible representation | Needed semantics |
|---|---|---|
| Price | Decimal or decimal text | Currency, scale, price type |
| Identifier | String | Identifier system, issuer or venue, effective dates |
| Observation date | Date or ISO text | Calendar date, not automatically an instant |
| Event time | Timezone-aware timestamp | Timezone and precision |
| Rate | Decimal | Decimal versus percent, compounding and period |
| Availability | Timestamp | When the record could be used |
| Missing value | Null or explicit status | Meaning and allowed handling |

CSV often transports everything as text; JSON and columnar formats can carry types but still need a documented contract. Schema inference is useful for exploration, not a substitute for validation.

## 3. Synthetic price schema

This section uses:

| Field | Type | Rule |
|---|---|---|
| instrument | Text | Nonempty |
| observation_date | ISO date text | Exact YYYY-MM-DD |
| close | Decimal text | Positive, at most two fractional digits and at most eight total decimal digits under the example rule |
| currency | Text | USD |
| price_type | Text | unadjusted_close |

The example's identifier and limits are instructional, not universal standards. Its key is (instrument, observation_date, price_type); a real key may require source, venue, currency and revision.

## 4. Precision and scale

A fixed decimal type is often described by precision p (total digits) and scale s (digits after the decimal point). The exact rules for storage and rounding depend on the system. A value that exceeds the contract should be rejected or transformed only under an explicit policy.

For this example, the reference code accepts plain nonnegative decimal strings with up to six integral digits and up to two fractional digits, counts leading zeros as supplied digits, and requires the numeric value to be positive. Thus `123456.78` is accepted, while `1234567.00` and `1.234` are rejected. The rule does not round values or accept scientific notation.

`Decimal` avoids some binary representation issues, but precision, rounding and calculation context still need a policy. Decimal storage alone does not determine economic meaning.

## 5. Rates and units

A rate may be represented in decimal units, percent or basis points. Five percent is .05 as a decimal, and 100 basis points is .01. Record the unit, horizon, compounding convention and day-count basis as applicable.

Do not apply a positive-only rule to every financial number: negative yields can be legitimate. A constraint belongs to a field's semantics and intended use, not merely its numeric type.

## 6. Nullability and missingness

A missing field, null, empty string and zero are different. Define whether each is allowed and why. A missing close should not automatically become 0; zero may represent a meaningful value in other contexts.

Record quality status and rejection reason where appropriate. A nullable field needs a documented interpretation so downstream users know whether null means unavailable, not applicable or another condition.

## 7. Keys and relationships

A key identifies a record under a stated scope. Tickers can change or be reused; identifier type, venue and effective dates can matter. Revisions may require version or publication time in the key rather than overwriting history.

Duplicates must be investigated against the contract. “Keep last” is not a universal rule and can introduce look-ahead bias if a later correction is used at an earlier decision time.

## 8. Dates and timestamps

A date is a calendar day, not a timezone-aware instant. Event, publication, ingestion and effective times have different meanings. Timestamp timezone, precision and daylight-saving rules must be explicit.

A schema containing only an observation date cannot prove point-in-time availability. Financial data engineering should preserve source revisions and availability times when supported.

## 9. Schema evolution

Schemas change: fields are added, renamed, widened or reinterpreted. Define a version and compatibility policy. Adding an optional field can still affect strict consumers; changing a unit from percent to decimal without changing the contract is a semantic breaking change even if the physical type stays numeric.

Test producers and consumers against the relevant versions, retain provenance and decide whether unknown fields are rejected, ignored or preserved. Never silently reinterpret a field.

## 10. Validation layers

Validate encoding and syntax, schema shape and types, domain constraints, cross-field consistency and cross-record relationships. Reconcile with source data and inspect outliers. A schema-valid record can still be stale, incorrect, unauthorized or based on future information.

A raw-byte hash helps identify an input; it does not certify its contents or authenticity.

## 11. Reference implementation

Save as `schema_data_types.py`. It validates already-decoded synthetic dictionaries under the exact schema above. It is an instructional contract, not a universal financial schema or a parser for CSV/JSON.

~~~python
import re
from datetime import date
from decimal import Decimal
import unittest

FIELDS={"instrument","observation_date","close","currency","price_type"}
PRICE_PATTERN=re.compile(r"^[0-9]{1,6}(?:\.[0-9]{1,2})?$")

def parse_record(row):
    if not isinstance(row,dict) or set(row)!=FIELDS:
        raise ValueError("schema")
    if any(not isinstance(row[k],str) for k in FIELDS):
        raise ValueError("type")
    instrument=row["instrument"].strip()
    if not instrument:
        raise ValueError("instrument")
    if row["currency"]!="USD" or row["price_type"]!="unadjusted_close":
        raise ValueError("semantics")
    text=row["close"]
    if not PRICE_PATTERN.fullmatch(text):
        raise ValueError("precision_or_scale")
    close=Decimal(text)
    if close<=0:
        raise ValueError("close")
    try:
        day=date.fromisoformat(row["observation_date"])
    except ValueError as exc:
        raise ValueError("date") from exc
    if day.isoformat()!=row["observation_date"]:
        raise ValueError("date")
    return {"instrument":instrument,"observation_date":day,"close":close,
            "currency":"USD","price_type":"unadjusted_close"}

def validate_unique(rows):
    records=[]
    seen=set()
    for row in rows:
        record=parse_record(row)
        key=(record["instrument"],record["observation_date"],record["price_type"])
        if key in seen:
            raise ValueError("duplicate")
        seen.add(key)
        records.append(record)
    return records

def simple_return(start,end):
    if not isinstance(start,Decimal) or not isinstance(end,Decimal):
        raise ValueError("Decimal required")
    if not start.is_finite() or not end.is_finite() or start<=0 or end<0:
        raise ValueError("invalid prices")
    return end/start-Decimal("1")

class SchemaTests(unittest.TestCase):
    def setUp(self):
        self.row={"instrument":"EXAMPLE","observation_date":"2026-01-05",
                  "close":"100.00","currency":"USD","price_type":"unadjusted_close"}
    def test_valid(self):
        self.assertEqual(parse_record(self.row)["close"],Decimal("100.00"))
    def test_return(self):
        self.assertEqual(simple_return(Decimal("100"),Decimal("101.50")),Decimal(".015"))
    def test_missing(self):
        with self.assertRaises(ValueError): parse_record({"instrument":"X"})
    def test_null(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":None})
    def test_scale(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":"1.234"})
    def test_integral_width(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":"1234567.00"})
    def test_zero(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":"0.00"})
    def test_notation(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"close":"1e2"})
    def test_date(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"observation_date":"20260105"})
    def test_currency(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"currency":"EUR"})
    def test_duplicate(self):
        with self.assertRaises(ValueError): validate_unique([self.row,self.row])
    def test_extra_field(self):
        with self.assertRaises(ValueError): parse_record({**self.row,"venue":"X"})

if __name__ == "__main__":
    rows=[{"instrument":"EXAMPLE","observation_date":"2026-01-05",
           "close":"100.00","currency":"USD","price_type":"unadjusted_close"},
          {"instrument":"EXAMPLE","observation_date":"2026-01-06",
           "close":"101.50","currency":"USD","price_type":"unadjusted_close"}]
    records=validate_unique(rows)
    print("records:",records)
    print("simple return:",simple_return(records[0]["close"],records[1]["close"]))
    unittest.main(verbosity=2)
~~~

The implementation rejects all unknown fields and uses a strict price-text rule. It does not validate source identity, instrument lifecycle, exchange calendar, publication time or corporate actions. It retains records and keys in memory and permits an empty list; a production contract must state whether empty batches are acceptable.

## 14. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Price rejected | Excess scale, width or notation | Compare input with contract |
| Duplicate error | Revision, venue or insufficient key | Review identity and source semantics |
| Extra field error | Producer schema changed | Apply a documented version policy |
| Valid record gives wrong return | Currency or price type differs | Check financial meaning and units |
| Historical data appears too early | Availability not represented | Review source publication and revisions |
| Memory grows with batch | Records and keys retained | Design bounded-memory validation |
