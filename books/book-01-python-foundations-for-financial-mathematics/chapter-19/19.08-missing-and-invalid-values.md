# 19.8 — Missing and Invalid Values

**Book:** Book 1 — Python Foundations for Financial Mathematics  
**Chapter:** 19 — Financial Data Engineering Foundations

## Learning objectives

Distinguish missing, null, empty, invalid and zero values; classify financial data failures; select an explicit rejection or quarantine policy; understand imputation and stale-data risks; and retain evidence for reproducible correction.

## 1. Why missing data matters

A missing price is not a zero price. Substituting zero can produce a false −100% return, distort risk statistics or trigger an incorrect decision. A syntactically valid number may also be invalid for the field, stale, associated with the wrong instrument or unavailable at the decision time.

Define the source, field meaning, units, key, availability and permitted handling before choosing a treatment. No single rule fits all financial data.

## 2. Distinct conditions

| Condition | Example | Interpretation |
|---|---|---|
| Missing key | No `close` field | Required field absent |
| Null | `"close": null` | Explicit lack of value |
| Empty string | `"close": ""` | Text field contains no characters |
| Source marker | `"N/A"` | Meaning depends on provider contract |
| Zero | `"close": "0"` | A supplied numeric zero |
| Malformed | `"close": "abc"` | Cannot parse under the numeric contract |
| Nonfinite | `"close": "NaN"` | Not a finite price |
| Domain invalid | Negative price under a positive-close contract | Parsed but fails the rule |

These states should not be collapsed silently. A zero can be meaningful in one field and invalid in another; negative yields may be valid even if a particular close price must be positive.

## 3. Where invalidity can occur

A record can fail decoding, syntax, schema, type conversion, domain constraints or cross-record checks. It can also be semantically wrong despite passing them: wrong currency, stale quote, incorrect venue, corporate-action mismatch or future information.

Use error categories and source identifiers to support investigation. Avoid exposing sensitive payloads in logs; retain raw inputs only where permitted.

## 4. Synthetic example

| Date | Close text | State under this section's contract |
|---|---|---|
| 2026-01-05 | 100.00 | Valid |
| 2026-01-06 | empty | Missing |
| 2026-01-07 | 102.00 | Valid |
| 2026-01-08 | NaN | Invalid nonfinite |

The record for January 6 does not imply a zero close. The return from the valid January 5 price to the valid January 7 price is 102/100−1=**2% over the observed interval**, not necessarily a one-day return. Exchange calendars and availability times are not supplied in this illustration.

## 5. Fail, quarantine or retain

A **fail-fast** policy rejects or stops processing when a violation occurs. A **quarantine** policy isolates invalid records with reasons for review. A nullable field can be retained when the contract explicitly permits null and downstream consumers understand its meaning.

Decide whether any rejected records make a batch incomplete and whether downstream publication is allowed. Report accepted, missing and invalid counts; do not silently discard records or present partial results as complete.

## 6. Imputation and forward fill

Imputation substitutes an estimate for a missing value; forward fill carries a previous observation forward. These change the data and can affect returns, volatility and risk. If used, document why, the permitted gap, source, time availability, whether the original value is retained, and a quality flag.

Do not fill through unknown closures, corporate actions or instrument changes without a justified policy. Never use a later value to fill an earlier decision point in a backtest unless it was actually available then; that can introduce look-ahead bias. A calendar-aware, point-in-time rule requires appropriate calendar and availability data.

## 7. Stale values and duplicates

A nonmissing quote can be stale. Compare its event time and availability with the intended decision time and freshness threshold. A date alone does not establish quote freshness.

Duplicates may represent retries, venues or corrections. The record key and revision policy determine whether they are invalid. Automatically keeping the latest correction can leak future information into historical analysis.

## 8. Domain checks and outliers

Domain checks depend on financial meaning. A positive-close rule can be appropriate for a particular equity price series, while negative interest rates may be valid. A large movement may reflect an error, corporate action or real market event. Flag and investigate it; do not silently remove it based solely on magnitude.

## 9. Numeric precision

Parse decimal text deliberately when the data contract requires it. `Decimal` can preserve decimal representation, but does not determine currency, unit, scale, rounding or correctness. Reject NaN and infinity where finite values are required.

For valid positive starting price P₀ and nonnegative ending price P₁, simple return is P₁/P₀−1. An unknown price cannot be used in the formula without an explicit and defensible treatment.

## 10. Provenance and evidence

Record source, retrieval time, input identity, schema version, record key, rejection reason, code version and any correction or imputation. A raw-byte hash helps identify the input; it does not prove data accuracy or authenticity.

Data quality metrics need denominators and scope: “one missing close out of four submitted records” is clearer than an unqualified “25% missing,” especially when some rows were not parsed.

## 11. Reference implementation

Save as `missing_values.py`. It classifies the close field in already-decoded synthetic dictionaries. This is a small instructional example, not a complete ingestion system.

~~~python
from decimal import Decimal, InvalidOperation
import unittest

def classify_close(row):
    if not isinstance(row,dict):
        return "invalid_row",None
    if "close" not in row:
        return "missing_key",None
    value=row["close"]
    if value is None:
        return "null",None
    if not isinstance(value,str):
        return "invalid_type",None
    if value == "":
        return "empty",None
    if value == "N/A":
        return "source_missing",None
    try:
        close=Decimal(value)
    except InvalidOperation:
        return "malformed",None
    if not close.is_finite():
        return "nonfinite",None
    if close <= 0:
        return "nonpositive",None
    return "valid",close

def classify_batch(rows):
    accepted,rejected=[],[]
    for index,row in enumerate(rows,1):
        status,value=classify_close(row)
        if status=="valid":
            accepted.append({"record_number":index,"close":value})
        else:
            rejected.append({"record_number":index,"reason":status})
    return {"accepted":accepted,"rejected":rejected,
            "submitted":len(accepted)+len(rejected),
            "complete":len(rejected)==0}

def simple_return(start,end):
    if not isinstance(start,Decimal) or not isinstance(end,Decimal):
        raise ValueError("Decimal values required")
    if not start.is_finite() or not end.is_finite() or start<=0 or end<0:
        raise ValueError("invalid prices")
    return end/start-Decimal("1")

class MissingValueTests(unittest.TestCase):
    def test_valid(self):
        self.assertEqual(classify_close({"close":"100.00"}),("valid",Decimal("100.00")))
    def test_missing_key(self):
        self.assertEqual(classify_close({})[0],"missing_key")
    def test_null(self):
        self.assertEqual(classify_close({"close":None})[0],"null")
    def test_empty(self):
        self.assertEqual(classify_close({"close":""})[0],"empty")
    def test_source_marker(self):
        self.assertEqual(classify_close({"close":"N/A"})[0],"source_missing")
    def test_malformed(self):
        self.assertEqual(classify_close({"close":"abc"})[0],"malformed")
    def test_nonfinite(self):
        self.assertEqual(classify_close({"close":"NaN"})[0],"nonfinite")
    def test_zero(self):
        self.assertEqual(classify_close({"close":"0"})[0],"nonpositive")
    def test_invalid_type(self):
        self.assertEqual(classify_close({"close":True})[0],"invalid_type")
    def test_batch_incomplete(self):
        result=classify_batch([{"close":"100"},{"close":""}])
        self.assertEqual(result["submitted"],2)
        self.assertFalse(result["complete"])
    def test_return(self):
        self.assertEqual(simple_return(Decimal("100"),Decimal("102")),Decimal(".02"))
    def test_bad_start(self):
        with self.assertRaises(ValueError): simple_return(Decimal("0"),Decimal("102"))

if __name__ == "__main__":
    rows=[{"close":"100.00"},{"close":""},{"close":"102.00"},{"close":"NaN"}]
    print(classify_batch(rows))
    print("observed-interval return:",simple_return(Decimal("100"),Decimal("102")))
    unittest.main(verbosity=2)
~~~

The code treats exactly `"N/A"` as a source missing marker and an empty string as missing; whitespace-only text is malformed under this specific policy. It validates only the close field, stores results in memory, and treats an empty batch as complete. It does not check dates, keys, currency, stale values, revisions or point-in-time availability. A real contract should explicitly decide those cases.

## 14. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Apparent −100% return | Missing price converted to zero | Trace source and missing-value policy |
| Missing rate differs from expectation | Different denominator or markers | Compare scope and classifications |
| Valid-looking value is stale | Event or availability time omitted | Check source timestamp and freshness |
| Unexpected spike | Corporate action, genuine move or error | Investigate rather than auto-delete |
| Historical result changes after refresh | Later correction overwrote earlier data | Review version and point-in-time policy |
| Rejected rows disappear | Quarantine or reporting gap | Preserve counts and reasons under policy |
