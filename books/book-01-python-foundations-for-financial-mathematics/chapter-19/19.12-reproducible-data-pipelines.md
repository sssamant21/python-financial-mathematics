## Learning objectives

Describe a reproducible financial data pipeline; distinguish replay from idempotence; retain input identity, configuration and lineage; implement deterministic validation and transformation; compare outputs; and identify point-in-time, security and operational limits.

## 1. What is a reproducible pipeline?

A reproducible pipeline allows an authorized reviewer to trace a result to its inputs, schema, code, configuration and execution environment. Given the same controlled inputs and rules, a deterministic transformation should produce the same logical output. Exact byte-for-byte replay may additionally require a fixed serialization format, ordering and compatible runtime.

Reproducibility does not prove that source data, financial conventions or model assumptions are correct. A repeatable error is still an error.

## 2. Pipeline stages

A simple financial pipeline may:

1. Acquire an authorized source snapshot.
2. Preserve or identify the raw input.
3. Decode and parse according to a versioned contract.
4. Validate types, units, keys and domain constraints.
5. Transform accepted records using explicit rules.
6. Publish only under a defined completeness policy.
7. Record output identity, counts, errors and lineage.

The source might revise history or publish late. Capture availability and revision information where available; an observation date alone cannot establish what was known at a decision time.

## 3. Replay, determinism and idempotence

**Determinism:** the same inputs and configuration produce the same logical result in a compatible environment.

**Replay:** run the pipeline again from identified input and rules.

**Idempotence:** repeating an operation has the same intended effect as performing it once. A deterministic transform does not make an append-only database write idempotent; a retry can insert duplicate records unless the sink has an appropriate key and write policy.

For external writes, define transaction boundaries, retry behavior, conflict policy and recovery. This section's code performs no external write.

## 4. Data identity and lineage

Record source, retrieval time, raw-byte checksum, schema version, code revision, parameters, dependency versions and output identity. A hash identifies the hashed bytes; it does not prove source authenticity, completeness or accuracy.

A JSON or CSV file's whitespace, encoding and line endings affect raw hashes. Logical equivalence requires a separately documented canonicalization policy. Never use a hash as a substitute for retaining authorized source and version information.

## 5. Synthetic example

Two comparable closes are 100.00 and 101.50 USD. Their simple return is **101.50/100−1=.015**, or 1.5%. The example assumes one instrument, strictly increasing observation dates, positive closes and a consistent price definition.

Dates alone do not identify publication or ingestion times. This example cannot certify point-in-time correctness, exchange-calendar coverage or corporate-action treatment.

## 6. Failure handling

Choose a policy before running: fail the batch, quarantine invalid records with reasons, or allow a documented partial result. Do not silently replace missing values with zero or present an incomplete batch as complete.

Record counts and denominators, error categories and source identity. Avoid logging secrets and sensitive raw payloads. A checksum does not make data safe to disclose.

## 7. Serialization and ordering

A stable logical result needs a defined ordering and representation. For example, canonical JSON can sort keys and use fixed separators; decimal values can be serialized as strings under a documented schema. Timestamps and random run IDs may be retained as metadata but will differ between executions and should not be confused with deterministic output fields.

Floating-point results can vary across platforms and reduction orders. Use appropriate tolerance-based comparisons when bitwise equality is not required or feasible.

## 8. Incremental processing and corrections

An incremental pipeline needs a documented watermark, source identity, key and late-arrival policy. A maximum event timestamp alone may miss late records or corrections. Reprocessing a window can be useful only with a sink strategy that handles duplicates and revisions correctly.

Distinguish event time, effective date, publication time and ingestion time. Preserve historical versions when point-in-time analysis requires them and the source supports them.

## 9. Security and operations

Use approved access controls, secret storage and retention policies. Record operational metadata without embedding credentials in manifests or logs. Apply resource limits, monitor failures, and provide a recovery procedure for partial processing.

The following example is in-memory and synthetic; it does not connect to external services or claim production operational guarantees.

## 10. Reference implementation

Save as `reproducible_pipeline.py`. It transforms a narrow JSON input into a canonical JSON result and a manifest of input/output hashes. It rejects a batch on any invalid record and does not write to a database or filesystem.

~~~python
import hashlib
import json
import platform
from datetime import date
from decimal import Decimal, InvalidOperation
import unittest

FIELDS={"instrument","date","close","currency"}

def digest(raw):
    if not isinstance(raw,bytes):
        raise ValueError("bytes required")
    return hashlib.sha256(raw).hexdigest()

def reject_duplicate_keys(pairs):
    result={}
    for key,value in pairs:
        if key in result:
            raise ValueError("duplicate JSON key")
        result[key]=value
    return result

def reject_constant(value):
    raise ValueError("nonstandard numeric constant: "+value)

def transform(raw):
    if not isinstance(raw,bytes):
        raise ValueError("bytes required")
    try:
        data=json.loads(raw.decode("utf-8"),
                        object_pairs_hook=reject_duplicate_keys,
                        parse_constant=reject_constant)
    except (UnicodeDecodeError,json.JSONDecodeError) as exc:
        raise ValueError("invalid UTF-8 or JSON") from exc
    if not isinstance(data,list) or len(data)!=2:
        raise ValueError("exactly two records required")
    parsed=[]
    for row in data:
        if not isinstance(row,dict) or set(row)!=FIELDS:
            raise ValueError("schema")
        if any(not isinstance(row[k],str) for k in FIELDS):
            raise ValueError("type")
        if not row["instrument"].strip() or row["currency"]!="USD":
            raise ValueError("instrument or currency")
        try:
            day=date.fromisoformat(row["date"])
            close=Decimal(row["close"])
        except (ValueError,InvalidOperation) as exc:
            raise ValueError("date or close") from exc
        if day.isoformat()!=row["date"] or not close.is_finite() or close<=0:
            raise ValueError("date or close")
        parsed.append((row["instrument"].strip(),day,close))
    if parsed[0][0]!=parsed[1][0] or parsed[0][1]>=parsed[1][1]:
        raise ValueError("one instrument and increasing dates required")
    result=parsed[1][2]/parsed[0][2]-Decimal("1")
    # Decimal arithmetic follows the active context; record or control it in production.
    output={"instrument":parsed[0][0],"start_date":parsed[0][1].isoformat(),
            "end_date":parsed[1][1].isoformat(),"simple_return":str(result),
            "currency":"USD"}
    output_bytes=json.dumps(output,sort_keys=True,separators=(",",":"),
                            allow_nan=False).encode("utf-8")
    manifest={"schema_version":1,"input_sha256":digest(raw),
              "output_sha256":digest(output_bytes),
              "python_version":platform.python_version(),
              "record_count":2}
    return output_bytes,manifest

class PipelineTests(unittest.TestCase):
    def setUp(self):
        self.raw=(b'[{"instrument":"EXAMPLE","date":"2026-01-05","close":"100.00","currency":"USD"},'
                  b'{"instrument":"EXAMPLE","date":"2026-01-06","close":"101.50","currency":"USD"}]')
    def test_return(self):
        output,_=transform(self.raw)
        self.assertEqual(json.loads(output)["simple_return"],"0.015")
    def test_replay(self):
        self.assertEqual(transform(self.raw),transform(self.raw))
    def test_input_hash_changes(self):
        self.assertNotEqual(digest(self.raw),digest(self.raw+b" "))
    def test_output_hash(self):
        output,manifest=transform(self.raw)
        self.assertEqual(manifest["output_sha256"],digest(output))
    def test_duplicate_key(self):
        bad=self.raw.replace(b'"close":"100.00"',b'"close":"100.00","close":"99"')
        with self.assertRaises(ValueError): transform(bad)
    def test_missing(self):
        with self.assertRaises(ValueError): transform(b'[{}]')
    def test_nonfinite(self):
        with self.assertRaises(ValueError): transform(self.raw.replace(b'"101.50"',b'"NaN"'))
    def test_nonstandard_json(self):
        with self.assertRaises(ValueError): transform(self.raw.replace(b'"101.50"',b'NaN'))
    def test_bad_order(self):
        with self.assertRaises(ValueError):
            transform(self.raw.replace(b"2026-01-06",b"2026-01-05"))
    def test_bad_currency(self):
        with self.assertRaises(ValueError): transform(self.raw.replace(b"USD",b"EUR"))
    def test_bad_encoding(self):
        with self.assertRaises(ValueError): transform(b"\xff")
    def test_wrong_type(self):
        with self.assertRaises(ValueError): transform("text")

if __name__ == "__main__":
    raw=(b'[{"instrument":"EXAMPLE","date":"2026-01-05","close":"100.00","currency":"USD"},'
         b'{"instrument":"EXAMPLE","date":"2026-01-06","close":"101.50","currency":"USD"}]')
    output,manifest=transform(raw)
    print(output.decode("utf-8"))
    print(json.dumps(manifest,sort_keys=True))
    unittest.main(verbosity=2)
~~~

The example's arithmetic uses the active Decimal context. For reliable replay, a production contract should set and record precision and rounding explicitly. The manifest lacks source, retrieval time, code revision, dependency identity and availability information; add these in a real pipeline. The function assumes inputs already represent compatible unadjusted closes but does not validate that assumption.

## 13. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Input hash changes | Bytes, encoding or whitespace changed | Compare raw source versions |
| Output differs on replay | Code, context, input or ordering changed | Compare manifest and environment |
| Duplicate records after retry | Sink write is not idempotent | Review key, transaction and retry policy |
| Historical output changes | Source correction or revision | Inspect point-in-time lineage |
| Batch fails on valid-looking price | Type or domain contract mismatch | Inspect schema and source representation |
| Same output but questionable result | Wrong model or source assumption | Independently validate semantics |
