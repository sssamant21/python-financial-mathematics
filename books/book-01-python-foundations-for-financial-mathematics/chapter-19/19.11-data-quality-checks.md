## Learning objectives

Define measurable data quality rules; check schema, completeness, uniqueness, validity and freshness; reconcile financial data; distinguish alerts from automatic corrections; and produce evidence with explicit scope, denominators and limitations.

## 1. Quality is purpose-specific

A dataset is fit for use only if it satisfies requirements for its intended purpose. A daily research dataset and a real-time trading feed have different freshness, precision and availability requirements. A valid-looking price may still be stale, in the wrong currency or unavailable at the modeled decision time.

Define the data contract, owner, source, scope, measurement window and response before implementing checks. Quality checks provide evidence; they do not guarantee source accuracy or model suitability.

## 2. Common dimensions

| Dimension | Example question |
|---|---|
| Completeness | Are required fields and expected observations present? |
| Validity | Do values meet schema and domain rules? |
| Uniqueness | Does the defined record key repeat? |
| Timeliness | Is data available within the agreed freshness threshold? |
| Consistency | Do currency, units and price type agree with the contract? |
| Accuracy | Does the value reconcile to an appropriate independent source? |
| Lineage | Can the input and transformations be traced? |

Dimensions overlap. Record the exact rule and denominator rather than relying only on a label such as “quality score.”

## 3. A synthetic contract

This section uses records with `instrument`, `date`, `close` and `currency`. The example contract requires nonempty instrument text, exact ISO date, positive finite decimal-text close and USD currency. The batch key is instrument/date.

This is intentionally narrow. A real key may include venue, price type, source and revision. A valid date does not prove a trading day, and an observation date does not establish publication or availability time.

## 4. Completeness and denominators

For a submitted batch, a missing-close rate might be **number of rows with a missing or empty close / number of submitted rows**. Specify whether null, source markers or malformed values are included. A field-completeness check cannot establish that every expected trading date is present without an expected calendar and coverage definition.

Example: one missing close among four submitted records gives 1/4=**25%**. An empty batch has no meaningful percentage under this definition; report it explicitly rather than dividing by zero.

## 5. Validity and domain rules

Check structure, types, allowed values and financial domains. A positive close may be required for an equity series; negative yields can be valid. Reject or quarantine nonfinite values when finite values are required.

Large changes may be genuine, erroneous or caused by corporate actions. Flag for review under a documented threshold; do not automatically delete or replace them.

## 6. Uniqueness and revisions

Define the key before measuring duplicates. Two observations on the same instrument/date may be valid if they differ by venue, price type or revision. In the example, a later row repeating an already accepted instrument/date is flagged.

A correction may have an older effective date but later availability time. Blindly keeping the latest record can introduce look-ahead bias. Retain source version and revision history as required.

## 7. Freshness and availability

Freshness requires a defined reference time, source event or publication time, threshold and timezone. A date-only record is insufficient to measure intraday staleness. Distinguish event, publication, retrieval and ingestion times.

For a backtest, information must be available at the decision time under the applicable revision policy. This section's reference code does **not** perform freshness or point-in-time checks because its synthetic schema lacks those timestamps.

## 8. Reconciliation

Compare values or totals with an appropriate independent source under matching dates, currencies, units, price types and rounding. A difference is an investigation item, not automatically proof that either source is wrong.

Document source hierarchy, tolerance, timing and correction process. A checksum identifies the exact bytes hashed but does not prove the content is correct or authentic.

## 9. Failure handling and observability

Decide which violations reject a batch, quarantine records or produce a review alert. Set thresholds and ownership before processing, record counts and reasons, and avoid labeling a partial batch complete.

Metrics should identify source, window, rule version and denominator. Protect sensitive information and avoid logging credentials or raw confidential data.

## 10. Reference implementation

Save as `data_quality_checks.py`. It assesses already-decoded synthetic dictionaries, reports one primary reason per rejected row and flags repeated accepted keys. It is an instructional batch checker, not a production pipeline.

~~~python
from datetime import date
from decimal import Decimal, InvalidOperation
import unittest

FIELDS={"instrument","date","close","currency"}

def assess_record(row):
    if not isinstance(row,dict):
        return None,"schema"
    if "close" not in row or row["close"] is None or row["close"]=="":
        return None,"missing_close"
    if set(row)!=FIELDS:
        return None,"schema"
    if any(not isinstance(row[k],str) for k in FIELDS):
        return None,"type"
    instrument=row["instrument"].strip()
    if not instrument:
        return None,"instrument"
    if row["currency"]!="USD":
        return None,"currency"
    try:
        day=date.fromisoformat(row["date"])
    except ValueError:
        return None,"date"
    if day.isoformat()!=row["date"]:
        return None,"date"
    try:
        close=Decimal(row["close"])
    except InvalidOperation:
        return None,"close"
    if not close.is_finite() or close<=0:
        return None,"close"
    return {"instrument":instrument,"date":day,"close":close,"currency":"USD"},None

def check_batch(rows):
    accepted=[]
    reasons={}
    seen=set()
    total=0
    for row in rows:
        total+=1
        record,reason=assess_record(row)
        if reason is None:
            key=(record["instrument"],record["date"])
            if key in seen:
                reason="duplicate"
            else:
                seen.add(key)
                accepted.append(record)
        if reason is not None:
            reasons[reason]=reasons.get(reason,0)+1
    rejected=total-len(accepted)
    return {"submitted":total,"accepted":accepted,"rejected":rejected,
            "reasons":reasons,
            "missing_close_rate":reasons.get("missing_close",0)/total if total else None,
            "complete":total>0 and rejected==0}

class QualityTests(unittest.TestCase):
    def setUp(self):
        self.row={"instrument":"EXAMPLE","date":"2026-01-05",
                  "close":"100.00","currency":"USD"}
    def test_valid(self):
        self.assertIsNone(assess_record(self.row)[1])
    def test_missing(self):
        self.assertEqual(assess_record({**self.row,"close":""})[1],"missing_close")
    def test_null(self):
        self.assertEqual(assess_record({**self.row,"close":None})[1],"missing_close")
    def test_nonfinite(self):
        self.assertEqual(assess_record({**self.row,"close":"NaN"})[1],"close")
    def test_zero(self):
        self.assertEqual(assess_record({**self.row,"close":"0"})[1],"close")
    def test_currency(self):
        self.assertEqual(assess_record({**self.row,"currency":"EUR"})[1],"currency")
    def test_date(self):
        self.assertEqual(assess_record({**self.row,"date":"20260105"})[1],"date")
    def test_duplicate(self):
        result=check_batch([self.row,self.row])
        self.assertEqual(result["reasons"]["duplicate"],1)
    def test_rate(self):
        result=check_batch([self.row,{**self.row,"close":""}])
        self.assertEqual(result["missing_close_rate"],.5)
    def test_empty(self):
        result=check_batch([])
        self.assertIsNone(result["missing_close_rate"])
        self.assertFalse(result["complete"])
    def test_complete(self):
        self.assertTrue(check_batch([self.row])["complete"])
    def test_invalid_row(self):
        self.assertEqual(assess_record(None)[1],"schema")

if __name__ == "__main__":
    rows=[{"instrument":"EXAMPLE","date":"2026-01-05","close":"100.00","currency":"USD"},
          {"instrument":"EXAMPLE","date":"2026-01-06","close":"","currency":"USD"}]
    print(check_batch(rows))
    unittest.main(verbosity=2)
~~~

The missing-close rule is evaluated before other rules, so each row receives one primary reason; totals are not counts of every possible defect. A duplicate is detected only against earlier **accepted** records. The code retains accepted rows and keys in memory, does not check expected coverage, freshness, revisions or independent-source accuracy, and rejects empty batches as incomplete.

## 13. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| High missing rate | Source outage or mapping change | Verify denominator, source and schema |
| Duplicate count rises | Retry, revision or insufficient key | Review identity and source version |
| Reconciliation differs | Time, unit or price-type mismatch | Align conventions and investigate |
| Valid date but missing market data | Calendar or coverage gap | Compare expected sessions and source |
| Metrics show no failures for empty batch | Denominator or empty-batch policy | Report empty status explicitly |
| Historical values change | Later correction overwrote history | Review point-in-time lineage |
