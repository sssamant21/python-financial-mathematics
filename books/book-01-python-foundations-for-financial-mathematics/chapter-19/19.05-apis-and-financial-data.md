## Learning objectives

Explain financial API requests and responses; interpret status codes and pagination; protect credentials; distinguish observation, publication and retrieval times; validate response contracts; implement bounded retry policies; and preserve provenance for reproducible analysis.

## 1. What is a financial data API?

An application programming interface (API) exposes a defined way to request or receive data. A financial API might provide prices, quotes, reference data, corporate actions or account transactions. A request specifies an endpoint and parameters; a response contains status, headers and a body under the provider's contract.

A successful request does not prove the data are complete, current or appropriate. Confirm coverage, delay, source, currency, price type, revisions, licensing and permitted usage.

## 2. Request components

A typical HTTPS request includes:

- Method, such as GET for retrieving a resource.
- Endpoint and query parameters, such as instrument and date range.
- Authentication, often an API token or another provider-specific mechanism.
- Headers describing accepted format or client identity.
- Timeout and retry policy appropriate to the operation.

Follow the provider's documentation. Do not place secrets in source code, repository files or URLs that may be logged. Use an approved secret store or environment configuration, and avoid printing authorization headers.

## 3. Synthetic response contract

The following is a fictional JSON response, not a live provider endpoint:

~~~json
{
  "records": [
    {"instrument": "EXAMPLE", "date": "2026-01-05", "close": "100.00", "currency": "USD"},
    {"instrument": "EXAMPLE", "date": "2026-01-06", "close": "101.50", "currency": "USD"}
  ],
  "next_cursor": null
}
~~~

Under this illustrative contract, close is decimal text, dates are observation dates and `next_cursor` indicates another page or null when complete. The return from 100.00 to 101.50 is **1.5%**, assuming comparable records. A production provider may use different types and pagination rules.

## 4. Status codes and errors

Responses can report successful retrieval, invalid requests, authentication or authorization failures, rate limits, or server errors. Interpret status codes according to the HTTP and provider contract; an error response may have a different body schema than a successful response.

A successful status can still contain an empty dataset, a partial page or stale data. Validate the response body and completeness separately.

## 5. Timeouts and retries

Set explicit connection and response timeouts in a real client. Retry only operations and error conditions for which retry is safe and permitted. A bounded exponential-backoff policy with jitter can reduce synchronized retries; honor a valid provider `Retry-After` instruction where applicable. Define a maximum attempt count and total deadline.

GET is generally intended to be safe, but provider behavior and billing can still matter. Never blindly retry a write: idempotency, side effects and provider-specific idempotency keys must be assessed. Authentication failures and invalid input normally require correction rather than repeated retries.

## 6. Rate limits

Providers may limit requests per second, minute, account or endpoint. A limit response can include retry guidance. Handle it according to the contract, use bounded backoff and avoid overwhelming the service. Rate limits and billing policies can change; check the current provider documentation before configuring a live client.

Batch requests and caching can reduce traffic where supported, but cached market data may be stale. Record cache age and source time.

## 7. Pagination and completeness

Large result sets may be split across pages using cursors, offsets or links. Continue until the documented completion condition is met; handle repeated cursors, missing cursors, duplicate records and page failures explicitly.

A cursor is an opaque provider value unless the contract says otherwise. A successful first page is not evidence of a complete dataset. If a page fails, report incomplete status rather than silently returning a partial dataset as complete.

## 8. Time semantics and revisions

Distinguish event or observation time, publication time, retrieval time and ingestion time. A daily date is not an instant and does not necessarily indicate when information became available. Timezones, market calendars and provider corrections matter.

For historical analysis, current revised data may contain information unavailable at the decision time. Preserve point-in-time versions and availability timestamps when the source provides them; do not claim point-in-time correctness without sufficient evidence.

## 9. Schema and decimal values

Validate top-level structure, required fields, numeric representation, instrument, date and currency before calculating. A missing key, null and zero are different. JSON floating-point numbers can introduce binary representation effects; a documented decimal-string contract can be parsed with `Decimal`.

Do not silently coerce malformed prices or substitute zero. Define how schema changes and unexpected fields are handled.

## 10. Security and licensing

Use approved credential storage, least privilege and TLS according to organizational policy. Keep tokens out of logs and example files; redact request metadata where needed. Review provider terms for retention, redistribution and permissible use.

This section uses only synthetic responses and does not call a live financial service.

## 11. Provenance and reproducibility

Record provider, endpoint identifier without secrets, request parameters, retrieval time, page identifiers, response status, schema and code versions, and appropriate raw-byte hashes. Preserve raw responses where permitted. A checksum identifies the bytes hashed; it does not prove the response is complete, authentic or financially correct.

## 12. Reference implementation

Save as `financial_api_basics.py`. The example uses an injected mock fetch function. It validates synthetic pages, detects repeated cursors and duplicate records, and enforces a maximum page count. It performs no network access, authentication or retries.

~~~python
from datetime import date
from decimal import Decimal, InvalidOperation
import unittest

FIELDS={"instrument","date","close","currency"}

def parse_page(payload):
    if not isinstance(payload,dict) or set(payload)!={"records","next_cursor"}:
        raise ValueError("invalid page object")
    records=payload["records"]
    cursor=payload["next_cursor"]
    if not isinstance(records,list):
        raise ValueError("records must be a list")
    if cursor is not None and (not isinstance(cursor,str) or not cursor):
        raise ValueError("cursor must be nonempty text or null")
    parsed=[]
    for row in records:
        if not isinstance(row,dict) or set(row)!=FIELDS:
            raise ValueError("invalid record fields")
        if any(not isinstance(row[k],str) for k in FIELDS):
            raise ValueError("all record fields must be strings")
        if not row["instrument"].strip() or row["currency"]!="USD":
            raise ValueError("instrument and USD currency required")
        try:
            day=date.fromisoformat(row["date"])
            close=Decimal(row["close"])
        except (ValueError,InvalidOperation) as exc:
            raise ValueError("invalid date or close") from exc
        if not close.is_finite() or close<=0:
            raise ValueError("positive finite close required")
        parsed.append({"instrument":row["instrument"].strip(),"date":day,
                       "close":close,"currency":row["currency"]})
    return parsed,cursor

def collect_pages(fetch,max_pages=10):
    if type(max_pages) is not int or max_pages<1:
        raise ValueError("positive integer page limit required")
    cursor=None
    seen_cursors=set()
    seen_records=set()
    output=[]
    for _ in range(max_pages):
        payload=fetch(cursor)
        records,next_cursor=parse_page(payload)
        for row in records:
            key=(row["instrument"],row["date"])
            if key in seen_records:
                raise ValueError("duplicate instrument/date")
            seen_records.add(key)
            output.append(row)
        if next_cursor is None:
            return output
        if next_cursor in seen_cursors:
            raise ValueError("repeated cursor")
        seen_cursors.add(next_cursor)
        cursor=next_cursor
    raise RuntimeError("page limit reached; result incomplete")

def simple_return(start,end):
    if not isinstance(start,Decimal) or not isinstance(end,Decimal):
        raise ValueError("Decimal prices required")
    if not start.is_finite() or not end.is_finite() or start<=0 or end<0:
        raise ValueError("positive start and nonnegative end required")
    return end/start-Decimal("1")

def mock_fetch(cursor):
    pages={
        None:{"records":[{"instrument":"EXAMPLE","date":"2026-01-05",
                          "close":"100.00","currency":"USD"}],"next_cursor":"p2"},
        "p2":{"records":[{"instrument":"EXAMPLE","date":"2026-01-06",
                          "close":"101.50","currency":"USD"}],"next_cursor":None},
    }
    return pages[cursor]

class ApiTests(unittest.TestCase):
    def test_two_pages(self):
        self.assertEqual(len(collect_pages(mock_fetch)),2)
    def test_return(self):
        rows=collect_pages(mock_fetch)
        self.assertEqual(simple_return(rows[0]["close"],rows[1]["close"]),Decimal(".015"))
    def test_empty_complete(self):
        self.assertEqual(collect_pages(lambda _:{"records":[],"next_cursor":None}),[])
    def test_repeated_cursor(self):
        with self.assertRaises(ValueError):
            collect_pages(lambda _:{"records":[],"next_cursor":"again"})
    def test_page_limit(self):
        with self.assertRaises(RuntimeError):
            collect_pages(mock_fetch,max_pages=1)
    def test_missing_field(self):
        with self.assertRaises(ValueError):
            parse_page({"records":[{"instrument":"X"}],"next_cursor":None})
    def test_null_price(self):
        bad={"records":[{"instrument":"X","date":"2026-01-01",
                         "close":None,"currency":"USD"}],"next_cursor":None}
        with self.assertRaises(ValueError): parse_page(bad)
    def test_bad_cursor(self):
        with self.assertRaises(ValueError):
            parse_page({"records":[],"next_cursor":""})
    def test_nonfinite_price(self):
        bad={"records":[{"instrument":"X","date":"2026-01-01",
                         "close":"NaN","currency":"USD"}],"next_cursor":None}
        with self.assertRaises(ValueError): parse_page(bad)
    def test_duplicate_records(self):
        row={"instrument":"X","date":"2026-01-01","close":"1","currency":"USD"}
        with self.assertRaises(ValueError):
            collect_pages(lambda _:{"records":[row,row],"next_cursor":None})

if __name__ == "__main__":
    rows=collect_pages(mock_fetch)
    print("records:",rows)
    print("simple return:",simple_return(rows[0]["close"],rows[1]["close"]))
    unittest.main(verbosity=2)
~~~

The collector assumes unique instrument/date records, preserves provider order and stores all rows in memory. It does not check price type, venue, response timestamps, HTTP status, authentication, network timeouts, retries or provider-specific completeness. A live implementation needs a provider-specific contract and appropriate security and resource controls.

## 15. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Authentication failure | Missing, expired or unauthorized credentials | Check approved access without exposing secrets |
| Repeated rate-limit responses | Request rate exceeds provider policy | Honor retry guidance and bounded backoff |
| Missing records | Pagination stopped early | Check completion marker and page evidence |
| Duplicate record error | Revision, retry or incomplete key | Review provider identity and version semantics |
| Stale price | Delayed feed or cache | Inspect observation and retrieval times |
| Historical analysis uses future data | Availability time absent | Review publication and revision history |
