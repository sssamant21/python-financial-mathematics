# 21.16 — Documentation and Reproducibility

**Book:** Book 1 — Python Foundations for Financial Mathematics  
**Chapter:** 21 — Integrated Capstone: Financial Mathematics Toolkit

## Learning objectives

Document financial assumptions and public interfaces, identify the information needed to reproduce a calculation, distinguish source, artifact and data identities, record actual test outcomes, and explain why a repeatable result is not necessarily correct or suitable.

## 1. Documentation is part of the financial contract

A reader must be able to determine what a result means, how it was produced and what it excludes. For each calculation document its purpose, inputs, units, rate and time conventions, output, accepted domain, errors, numerical behavior, examples and model limitations. Documentation describes the implementation actually supplied; planned modules or controls must be labeled as planned.

For example, the Section 21.5 time-value function discounts one amount using an effective rate per period. The Section 21.6 cash-flow function treats its first entry as time zero. Section 21.8's bond model values a simplified fixed-coupon bond on a specified coupon date; it does not compute accrued interest. These distinctions are necessary to interpret results and compare benchmarks.

A reproducible result is not automatically correct, authorized, safe or financially suitable. Independent financial, numerical, data, software and editorial review remains necessary for the intended use. The capstone code in these sections is educational draft material; the complete package and its acceptance evidence are not published as a certified artifact.

## 2. Documentation inventory

| Document | Questions it should answer |
|---|---|
| README and setup | What is implemented, how is it installed, what dependencies and platforms are supported, and what is still planned? |
| API reference and docstrings | What are the inputs, units, conventions, return values, types, errors and numerical limits? |
| Requirements and assumptions | What use is supported, who owns it, which assumptions and exclusions apply, and what constitutes acceptance? |
| Data dictionary and lineage | What are identifiers, timestamps, currencies, sources, revisions, adjustments and missing-data policies? |
| Numerical policy | Which representations, precision, rounding stages, tolerances and supported ranges apply? |
| Model and validation records | What benchmarks, independent challenge, findings, limitations and decisions apply? |
| Operations and change history | How are versions, dependencies, releases, ownership, monitoring and rollback managed? |
| Test evidence | What was actually run, where, against which revision or artifact, and with what results? |

A requirement, a test definition, an execution result and an approval are different records. A test that has not run must not be reported as passing. Store sensitive information, evidence and credentials under appropriate access and retention controls; examples should use synthetic values.

## 3. What to capture for a repeatable run

Capture an exact source revision and any local changes; identify the built artifact and its cryptographic hash if an artifact is used. Record Python implementation and version, operating system, relevant dependency versions and build tools, commands, configuration, locale or timezone when material, and input dataset identity and version. For time-sensitive data, preserve observation, availability and revision information. For a simulation, record the algorithm, generator, seed, parameters and scenario count as well as the environment.

Record actual outputs, exit status, test counts, skipped or blocked checks and numerical tolerances in their units. Capture the reviewer, timestamp, unresolved findings and decisions as required by the workflow. A seed alone does not guarantee the same sequence across every Python version, implementation or random library. Pinning dependencies supports reproducibility but does not establish correctness or security; a lockfile and a clean environment need review and actual verification.

Reproducibility can mean bitwise identical output or agreement within a stated tolerance. The required level depends on the algorithm, environment and use. Floating-point summation order, hardware, libraries and parallel execution may change results. State the criterion before interpreting a rerun.

## 4. Identity, integrity and privacy

A SHA-256 digest identifies a particular byte sequence for comparison. A matching digest can support integrity checking when the expected digest is obtained from a trusted channel; it does not prove authorship, provenance, confidentiality, authorization or financial validity. A digest of a low-entropy secret or sensitive value can be guessable. Do not use hashes as a substitute for access control, encryption, retention policy or a trusted signature.

The reference example below hashes a deliberately restricted, synthetic metadata record encoded as deterministic UTF-8 JSON. It makes **no claim of a general canonical JSON standard**, artifact verification or secure evidence storage. Exact whitespace, serialization rules and included fields affect the digest. Never place credentials, personal information, proprietary prices or sensitive identifiers in this demonstration record.

## 5. Reference metadata fingerprint

Save as `run_metadata.py` in an isolated teaching directory. This is a standalone documentation example; it does not collect environment information, run tests, create a manifest on disk or integrate with the capstone package. Python 3.10 or newer is assumed.

```python
"""Educational fingerprint for a restricted synthetic metadata record."""
import hashlib
import json

FIELDS = frozenset({"revision", "python", "command", "status"})
STATUSES = frozenset({"not_run", "passed", "failed", "blocked"})


def metadata_bytes(record: dict) -> bytes:
    """Return deterministic UTF-8 JSON bytes for this narrow schema.

    All fields must be nonblank, trimmed built-in strings; status must be one
    of the documented values. This function does not verify that claims are
    true, authenticate the record, or protect sensitive information.
    """
    if type(record) is not dict or record.keys() != FIELDS:
        raise ValueError("record must contain exactly the required fields")
    for value in record.values():
        if type(value) is not str or not value or value != value.strip():
            raise ValueError("fields must be nonblank trimmed strings")
    if record["status"] not in STATUSES:
        raise ValueError("invalid status")
    encoded = json.dumps(record, sort_keys=True, separators=(",", ":"),
                         ensure_ascii=True, allow_nan=False)
    return encoded.encode("utf-8")


def metadata_sha256(record: dict) -> str:
    """Return the hexadecimal SHA-256 digest of metadata_bytes(record)."""
    return hashlib.sha256(metadata_bytes(record)).hexdigest()


if __name__ == "__main__":
    example = {"revision": "synthetic-revision", "python": "record actual version",
               "command": "not executed", "status": "not_run"}
    print(metadata_sha256(example))
```

The output is a fingerprint of the supplied metadata bytes, not a fingerprint of the source tree, input data, command output or installed wheel. A `passed` string is accepted syntactically but is not evidence that a test passed. A genuine test record must refer to actual output, environment, artifact and review; the function neither checks nor stores these. The example's placeholder fields do not claim execution.

## 6. Twelve Python reference tests

Save as `test_run_metadata.py` beside the reference file. These test definitions have **not** been executed for publication. They check serialization and input behavior, not the truth of metadata or the security of an evidence system.

```python
import hashlib
import unittest
from run_metadata import metadata_bytes, metadata_sha256


def record(**changes):
    value = {"revision": "abc123", "python": "3.x", "command": "python -m unittest",
             "status": "not_run"}
    value.update(changes)
    return value


class MetadataTests(unittest.TestCase):
    def test_same_record_same_bytes(self):
        self.assertEqual(metadata_bytes(record()), metadata_bytes(record()))
    def test_key_order_independent(self):
        original = record()
        reversed_record = dict(reversed(list(original.items())))
        self.assertEqual(metadata_bytes(original), metadata_bytes(reversed_record))
    def test_digest_matches_hashlib(self):
        item = record()
        self.assertEqual(metadata_sha256(item), hashlib.sha256(metadata_bytes(item)).hexdigest())
    def test_digest_shape(self):
        digest = metadata_sha256(record())
        self.assertEqual(len(digest), 64)
        self.assertTrue(all(ch in "0123456789abcdef" for ch in digest))
    def test_changed_record_changes_digest(self):
        self.assertNotEqual(metadata_sha256(record()), metadata_sha256(record(revision="def456")))
    def test_input_not_mutated(self):
        item = record()
        before = item.copy()
        metadata_bytes(item)
        self.assertEqual(item, before)
    def test_missing_field(self):
        item = record()
        del item["python"]
        with self.assertRaises(ValueError):
            metadata_bytes(item)
    def test_extra_field(self):
        with self.assertRaises(ValueError):
            metadata_bytes(record(extra="x"))
    def test_blank_field(self):
        with self.assertRaises(ValueError):
            metadata_bytes(record(command="  "))
    def test_wrong_type(self):
        with self.assertRaises(ValueError):
            metadata_bytes(record(revision=123))
    def test_invalid_status(self):
        with self.assertRaises(ValueError):
            metadata_bytes(record(status="approved"))
    def test_not_run_status_preserved(self):
        self.assertIn(b'"status":"not_run"', metadata_bytes(record()))


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

During deferred QA, run from the directory containing both files:

```bash
python run_metadata.py
python -m unittest -v test_run_metadata
python -m compileall -q run_metadata.py test_run_metadata.py
```

Capture actual commands, outputs, exit status, revision, interpreter version and platform. The test comparing a digest to `hashlib` checks consistent use of the same library; it is not an independent cryptographic implementation review. The digest-change example is a regression check on those two inputs, not a proof that collisions are impossible.

## 7. Example calculation record

For a synthetic one-period payment of 110 at an effective rate of 10%, the exact present value under the specified model is 100. A useful calculation record would identify the inputs and units, formula and timing, source revision or artifact hash, Python and dependencies, actual unrounded output, output tolerance and independent benchmark, execution command and results, model exclusions, reviewer and open findings. At publication these are **requirements for a future record**, not a claim that a run or review occurred.

If the result comes from the Section 21.12 simulation, additionally capture the pseudorandom generator, algorithm, seed, scenario count, parameter values and environment. If it comes from Section 21.13's validated prices, capture the decision cutoff and the actual source revision or controlled data snapshot; event and availability timestamps alone do not establish historical revision correctness. For Section 21.14 charts, record the Matplotlib version, backend, figure settings and actual visual-review findings.

## 10. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Metadata raises `ValueError` | Missing, extra, blank or invalid field | Compare with the exact teaching schema |
| Digest changes | Bytes, field values or encoding rules differ | Compare serialized bytes and the trusted expected record |
| Same seed gives different output elsewhere | Generator, version, inputs or environment differ | Compare the full reproducibility record |
| Results are reproducible but financially wrong | Model, inputs, timing or conventions are unsuitable | Perform independent financial and data review |
| Sensitive information appears in evidence | Raw data or credentials were included | Apply the organization's incident and data-handling process |
