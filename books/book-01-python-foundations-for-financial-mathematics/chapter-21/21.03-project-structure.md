## 1. Why structure matters

A predictable layout helps contributors find the implementation, requirements, tests and documentation. It also makes boundaries visible: input validation and financial calculations belong in the package, while examples and presentation call the package through documented interfaces. Structure alone does not establish financial accuracy, secure operation or model suitability.

The full capstone is developed over later sections. This section provides a small runnable scaffold for one-period present value. Names for other modules below are **planned**, not implemented or tested here. The example is educational; actual deployment requires appropriate packaging, numerical, security, model and operational review.

A `src` layout reduces accidental imports directly from the repository root; it does not by itself prove an installed package is correct.

| Location | Responsibility | Design rule |
|---|---|---|
| `src/financial_toolkit/` | Importable library and public interfaces | Calculation code does not depend on a user interface or presentation layer |
| `tests/` | Unit and integration checks | Keep expected results and execution evidence distinct |
| `examples/` | Small synthetic demonstrations | Use documented public interfaces; do not embed credentials |
| `docs/` | Requirements, assumptions and review records | Track version and status; protect sensitive inputs and evidence |
| `pyproject.toml` | Build-system and project metadata | State actual requirements; validate installation in a clean environment |
| `README.md` | Setup, scope and entry points | Distinguish implemented features from planned work |

A future bond module may reuse a stable cash-flow interface. Avoid circular imports: for example, visualization can depend on calculations or results, but calculations should not import visualization. A validator should define data and unit contracts without silently changing financial meaning.

## 3. Minimal installable scaffold

Use Python 3.10 or newer. The package has no third-party **runtime** dependencies. Building and installing it requires compatible versions of the declared build backend and its prerequisites; those are build-time dependencies, not part of Python's standard library. The example does not pin them, so record and control build tools for reproducible work. It is not a production release.

Create a directory named `financial-toolkit` and save the files below with the indicated paths.

### `pyproject.toml`

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "financial-toolkit-educational"
version = "0.1.0"
description = "Educational one-period financial valuation scaffold"
readme = "README.md"
requires-python = ">=3.10"

[tool.setuptools.packages.find]
where = ["src"]
```

The distribution name `financial-toolkit-educational` and the import name `financial_toolkit` are different names for different purposes. The version is an example identifier, not a claim of maturity. Build isolation may download build dependencies; offline use requires an approved, locally available build environment or wheelhouse. Pin and review dependencies according to the actual release policy.

### `src/financial_toolkit/time_value.py`

```python
"""Small deterministic time-value-of-money example."""
import math


def present_value_one_period(payment: float, rate: float) -> float:
    """Discount a payment at the end of one effective period.

    Accept finite built-in floats; the rate must be greater than -1. Return an
    unrounded float in payment units. Invalid inputs or a nonfinite result
    raise ValueError. Rounding and underflow remain possible.
    """
    if type(payment) is not float or not math.isfinite(payment):
        raise ValueError("payment must be a finite float")
    if type(rate) is not float or not math.isfinite(rate) or rate <= -1.0:
        raise ValueError("rate must be a finite float greater than -1")
    value = payment / (1.0 + rate)
    if not math.isfinite(value):
        raise ValueError("nonfinite present value")
    return value
```

For payment \(C\) and effective rate \(r>-1\), this implements \(PV=C/(1+r)\). For `110.0` at `0.10`, PV is 100 in exact arithmetic. The function accepts negative payments and rates above −1, but a valid input is not necessarily appropriate for a real instrument. It has no currency label or FX conversion; the caller must maintain unit consistency. The public contract is intentionally consistent with the calculation in Section 21.1, while the request/result objects in that section are not included in this minimal package.

### `examples/one_period.py`

```python
from financial_toolkit import present_value_one_period

value = present_value_one_period(110.0, 0.10)
print(f"PV: {value:.2f} payment units")
```

Formatting to two decimal places is for display. It is not a specified accounting or currency rounding policy.

## 4. Twelve reference tests

Save as `tests/test_time_value.py`. These are definitions and were not executed for this draft. Tolerances are illustrative in amount units, not universal financial acceptance thresholds.

```python
import math
import unittest
from financial_toolkit import present_value_one_period


class TimeValueTests(unittest.TestCase):
    def test_known_value(self):
        self.assertTrue(math.isclose(present_value_one_period(110.0, 0.1), 100.0,
                                     rel_tol=0.0, abs_tol=1e-10))
    def test_zero_rate(self):
        self.assertEqual(present_value_one_period(110.0, 0.0), 110.0)
    def test_negative_rate(self):
        self.assertTrue(math.isclose(present_value_one_period(95.0, -0.05), 100.0,
                                     rel_tol=0.0, abs_tol=1e-10))
    def test_zero_payment(self):
        self.assertEqual(present_value_one_period(0.0, 0.1), 0.0)
    def test_negative_payment(self):
        self.assertTrue(math.isclose(present_value_one_period(-110.0, 0.1), -100.0,
                                     rel_tol=0.0, abs_tol=1e-10))
    def test_positive_payment_rate_monotonicity(self):
        self.assertGreater(present_value_one_period(100.0, 0.05),
                           present_value_one_period(100.0, 0.10))
    def test_rate_boundary(self):
        with self.assertRaises(ValueError):
            present_value_one_period(100.0, -1.0)
    def test_nonfinite_payment(self):
        with self.assertRaises(ValueError):
            present_value_one_period(float("nan"), 0.1)
    def test_nonfinite_rate(self):
        with self.assertRaises(ValueError):
            present_value_one_period(100.0, float("inf"))
    def test_integer_rejected(self):
        with self.assertRaises(ValueError):
            present_value_one_period(100, 0.1)
    def test_boolean_rejected(self):
        with self.assertRaises(ValueError):
            present_value_one_period(100.0, True)
    def test_nonfinite_result_rejected(self):
        with self.assertRaises(ValueError):
            present_value_one_period(1e308, -0.5)


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

## 5. Environment, installation and deferred verification

Use a disposable virtual environment and the same interpreter for installation and execution. From the project root, during deferred QA:

```bash
python -m venv .venv
```

Activate it with `. .venv/bin/activate` on macOS/Linux or `.venv\Scripts\Activate.ps1` in Windows PowerShell. Confirm `python --version` and `python -m pip --version`. Install the local project in editable mode, then run the example and tests:

```bash
python -m pip install -e .
python examples/one_period.py
python -m unittest discover -s tests -v
python -m compileall -q src tests examples
```

Editable installation is useful for development; it reads the source tree, so a passing editable test is not an independent check of a distributable artifact. Installation can require network access to obtain build dependencies, depending on the environment. Use an approved dependency source and record resolved versions.

For release verification, build a wheel using an approved build environment, install the resulting wheel into a **separate clean environment**, and execute acceptance checks from outside the source checkout with no `PYTHONPATH` pointing to it. Record the artifact name and cryptographic hash, interpreter and dependency versions, exact commands, environment and actual results. The build tooling, wheel, clean environment and acceptance evidence are not supplied here. A successful install or test does not establish model suitability.

On Windows, PowerShell execution policy can prevent activation; use the virtual environment's Python directly (for example `.\.venv\Scripts\python.exe -m pip install -e .`) under the applicable local policy. Do not modify system execution policy merely to run this lab.

## 6. Interfaces, configuration and evidence

The package's public import is `from financial_toolkit import present_value_one_period`. `__all__` documents intended wildcard exports; it does not make other Python objects inaccessible. Define compatibility and deprecation policies before a stable release, and avoid depending on private implementation details.

Keep financial assumptions and runtime configuration explicit. Do not commit passwords, tokens, confidential input data, virtual environments or generated build artifacts. Use synthetic examples and an appropriate ignore policy. If an application later reads environment variables or configuration files, validate them at the application boundary and record non-sensitive settings needed to reproduce an analysis. Do not silently replace missing rates or failed valuations with zero.

Separate tests from evidence. A test file defines a check; a timestamped run record contains what actually happened. Evidence should identify the source revision, artifact hash when relevant, commands, environment, result, reviewer and unresolved findings, subject to data-protection and retention rules. A source repository can hold non-sensitive documentation; sensitive evidence may require a controlled store.

## 9. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| `ModuleNotFoundError` | Project not installed in the interpreter being used | Check interpreter, environment and installation command |
| Build dependency unavailable | Offline environment or unapproved source | Use an approved pre-provisioned build environment or wheelhouse |
| Import works locally but not after installation | Source checkout or `PYTHONPATH` masked a packaging issue | Test a built artifact in a clean environment outside the checkout |
| `ValueError` | Wrong input type, nonfinite input, invalid rate or overflow | Check the documented contract and sanitized input |
| Result differs slightly | Binary float rounding or mismatched convention | Reconcile timing, rate and units; use a justified tolerance |
