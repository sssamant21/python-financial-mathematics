## Learning objectives

Plan traceable financial and software checks, derive independent benchmarks, select numerical tolerances, test module boundaries and invalid inputs, preserve actual execution evidence, and distinguish code verification from financial model validation and release approval.

## 1. Verification plan, not a certification

This section defines checks for the teaching toolkit developed in Sections 21.3–21.14. The reader must first assemble those reference files into a local project. The tests shown in this manuscript are definitions; they have not been executed during publication. Complete the Book 1 manuscript before undertaking the agreed comprehensive runtime, mathematical and editorial validation. A passing test samples specified behavior; it does not prove all inputs, data, financial assumptions or model uses are correct.

Software verification asks whether the implementation meets its specified behavior. Model validation examines conceptual soundness, implementation and outcomes for a specific intended use. These activities overlap but neither can be inferred from the mere existence of tests. Review, ownership and release decisions must follow the applicable context and policy.

## 2. Traceability matrix for deferred QA

| Area | Example requirement or property | Planned evidence |
|---|---|---|
| Time value | 100 at 10% for two periods has FV 121 in exact arithmetic | Independently derived benchmark and actual test result |
| Cash flows | `[-100, 110]` at 10% has NPV zero with time-zero treatment | Benchmark, timing convention and run output |
| Loan | 1,000 at 10% for one period has payment 1,100 | Formula review, boundary cases and results |
| Bond | A two-period 5% coupon bond at 5% yield prices at par in the simplified model | Independent cash-flow derivation and calculation results |
| Returns and portfolio | 10% then −10% links to −1%; 60% at 10% plus 40% at −5% gives 4% | Independent calculations and alignment checks |
| Statistics and simulation | Sample variance uses `n-1`; a zero-probability two-outcome run selects the down outcome | Known values, reproducibility record and model review |
| Validation and visualization | Unavailable data is rejected; axes reflect the supplied units and times | Timestamp tests, source review, plot checks and visual inspection |
| Packaging and operations | Built artifact behaves in a clean environment and evidence is retained | Artifact hash, commands, environment, results and review record |

This matrix is a plan, not a report of passing checks. Each actual check should identify its requirement, inputs, expected result, tolerance and units, result, environment, revision or artifact, reviewer and disposition. A nonblank evidence reference does not authenticate its contents.

## 3. Layers of checks

1. **Unit checks:** isolate a function's valid inputs, known values, boundaries and failure behavior.
2. **Financial invariants:** test properties with stated assumptions, such as linear scaling or positive-payment present value decreasing with a rising rate.
3. **Integration checks:** exercise contracts between modules, including time-zero conventions, signs, units and compatible limits.
4. **Numerical checks:** compare against independently derived or higher-precision references over a defined range; examine cancellation, overflow, underflow and tolerances.
5. **Data and model review:** assess provenance, availability, assumptions, exclusions, benchmark quality and intended use.
6. **Installed-artifact and operational checks:** test a built wheel in a clean environment, document dependencies and platforms, and review security, privacy and operational controls appropriate to the use.
7. **Presentation and editorial checks:** inspect figures at intended size, check links and source attribution, reconcile examples and review manuscript clarity.

Coverage indicates which code ran, not whether assertions are meaningful, all inputs are covered, or the financial model is suitable. Property and round-trip tests can share implementation errors; independently derived expected values remain important.

## 4. Benchmarks, tolerance and failure evidence

For an effective per-period rate \(r\), one certain payment \(C\) at the end of a period has \(PV=C/(1+r)\). For 110 at 10%, PV is 100 in exact arithmetic. For a time-zero outflow of 100 followed by 110, NPV is zero. For two periods, 100 at 10% compounds to 121 in exact arithmetic. These values assume matching rate and period conventions.

Binary float results can differ slightly from exact arithmetic. Choose absolute tolerance in output units for comparisons near zero; relative tolerance alone cannot allow a nonzero difference from zero. A tolerance that is reasonable for a synthetic amount near 100 is not necessarily appropriate for a large trade, a rate, an account balance or an operational acceptance threshold. Investigate discrepancies and conventions before changing a threshold.

Record failures and errors, including the command, inputs or controlled references, expected and actual values, source revision, environment, owner and follow-up. Do not silently replace a failure with zero. Do not include credentials or sensitive input values in publicly accessible logs or reports. Keep test source, test execution results and independent model-review decisions distinct.

## 5. Twelve cross-module Python reference checks

After completing the Section 21.3 scaffold and applying package updates through Section 21.14, save the following as `tests/test_capstone_verification.py`. This suite tests representative integration and boundary cases; it does not implement the full toolkit or replace the individual section tests. Plotting requires separate Matplotlib tests and visual inspection as described in Section 21.14.

```python
from datetime import datetime, timezone
import math
import unittest

from financial_toolkit import (
    fixed_coupon_bond_price, future_value, level_payment, linked_return,
    net_present_value, portfolio_return, present_value, simple_price_return,
    simulate_two_outcome, summarize_sample, validated_price_return,
)


class CapstoneVerificationTests(unittest.TestCase):
    def test_future_value_known(self):
        self.assertTrue(math.isclose(future_value(100.0, 0.1, 2), 121.0,
                                     rel_tol=0.0, abs_tol=1e-10))
    def test_present_value_known(self):
        self.assertTrue(math.isclose(present_value(110.0, 0.1, 1), 100.0,
                                     rel_tol=0.0, abs_tol=1e-10))
    def test_npv_time_zero(self):
        self.assertTrue(math.isclose(net_present_value([-100.0, 110.0], 0.1),
                                     0.0, rel_tol=0.0, abs_tol=1e-10))
    def test_loan_one_period(self):
        self.assertTrue(math.isclose(level_payment(1000.0, 0.1, 1), 1100.0,
                                     rel_tol=0.0, abs_tol=1e-9))
    def test_bond_par(self):
        price = fixed_coupon_bond_price(100.0, 0.05, 0.05, 2)
        self.assertTrue(math.isclose(price, 100.0, rel_tol=0.0, abs_tol=1e-10))
    def test_linked_returns_known(self):
        self.assertTrue(math.isclose(linked_return([0.1, -0.1]), -0.01,
                                     rel_tol=0.0, abs_tol=1e-12))
    def test_portfolio_known(self):
        result = portfolio_return([0.6, 0.4], [0.1, -0.05])
        self.assertTrue(math.isclose(result, 0.04, rel_tol=0.0, abs_tol=1e-12))
    def test_sample_variance_known(self):
        summary = summarize_sample([1.0, 2.0, 3.0])
        self.assertEqual((summary.mean, summary.sample_variance), (2.0, 1.0))
    def test_simulation_endpoint(self):
        run = simulate_two_outcome(100.0, 0.1, 0.0, 0.0, 3, 42)
        self.assertEqual(run.terminal_values, (100.0, 100.0, 100.0))
    def test_price_return_integration(self):
        utc = timezone.utc
        first_time = datetime(2025, 1, 2, 16, tzinfo=utc)
        second_time = datetime(2025, 1, 3, 16, tzinfo=utc)
        cutoff = datetime(2025, 1, 3, 18, tzinfo=utc)
        first = dict(instrument="X", currency="USD", price=100.0,
                     observed_at=first_time, available_at=first_time, source="synthetic")
        second = dict(instrument="X", currency="USD", price=110.0,
                      observed_at=second_time, available_at=second_time, source="synthetic")
        result = validated_price_return(first, second, cutoff)
        self.assertTrue(math.isclose(result, 0.1, rel_tol=0.0, abs_tol=1e-12))
        self.assertEqual(result, simple_price_return(100.0, 110.0))
    def test_invalid_rate(self):
        with self.assertRaises(ValueError):
            present_value(100.0, -1.0, 1)
    def test_invalid_weights(self):
        with self.assertRaises(ValueError):
            portfolio_return([0.4, 0.4], [0.1, 0.2])


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

The integration check compares a validated calculation with the same lower-level return function; it is not an independent implementation. The independently derived 10% expected value is a separate check. The seed-based simulation test uses probability zero, so it does not test distributional quality or cross-version random-sequence identity. The suite is intentionally incomplete and should be expanded against the agreed requirements and supported domains.

## 6. Deferred execution and evidence

After Book 1 manuscript completion, assemble the teaching package and run its section and cross-module checks in an isolated environment. With an approved Matplotlib dependency installed, set the headless backend before the test process, as shown in Section 21.14. From the teaching project root, an illustrative command is:

```bash
# macOS/Linux; PowerShell: $env:MPLBACKEND = 'Agg' before the Python commands
MPLBACKEND=Agg python -m unittest discover -s tests -v
python -m compileall -q src tests
```

PowerShell does not support the shell-style prefix shown above; use `$env:MPLBACKEND = 'Agg'` followed by `python -m unittest discover -s tests -v` and `python -m compileall -q src tests`. A missing plotting dependency can cause discovery to fail; report that failure, not a pass. Discovery runs all tests in the directory, not only the 12 checks above.

For artifact acceptance, build a wheel in an approved, controlled environment, record its cryptographic hash, install it into a separate clean environment, and run appropriate checks from outside the source checkout without pointing `PYTHONPATH` at the source. Editable installs are useful for development but do not independently verify the wheel. Inspect chart outputs separately and retain source and model-review evidence.

A minimal evidence record should contain: requirement and test identifiers; source revision or artifact hash; exact command and actual output/exit status; interpreter, dependency versions, platform and backend where relevant; timestamp and reviewer; assumptions and tolerances; and unresolved findings. Secure input references and results according to their sensitivity and retention policy. A test that was not run, skipped or blocked must be labeled accordingly.

## 8. Forty worked exercises

1. **Verification:** What does software verification assess? **Answer:** Whether the implementation meets specified behavior.
2. **Validation:** What does model validation assess? **Answer:** Suitability of conceptual design, implementation and outcomes for intended use.
3. **Status:** Have the reference checks in this section run? **Answer:** No.
4. **Known PV:** PV of 110 at 10% for one period? **Answer:** 100 in exact arithmetic.
5. **Known FV:** FV of 100 at 10% for two periods? **Answer:** 121 in exact arithmetic.
6. **NPV:** NPV of `[-100, 110]` at 10%? **Answer:** Zero in exact arithmetic.
7. **Loan:** One-period payment on 1,000 at 10%? **Answer:** 1,100 in exact arithmetic.
8. **Bond:** Two-period bond with 5% coupon and yield on face 100? **Answer:** 100 under the stated model.
9. **Returns:** Link 10% and −10%. **Answer:** −1% in exact arithmetic.
10. **Portfolio:** 60% at 10% and 40% at −5%? **Answer:** 4% in exact arithmetic.
11. **Statistics:** Sample variance of 1, 2 and 3? **Answer:** 1.
12. **Simulation:** At zero up probability, which outcome is selected? **Answer:** The down outcome.
13. **Timing:** Is the first cash flow discounted? **Answer:** No; it is at time zero in the specified module.
14. **Sign:** How are borrower payments represented in an NPV schedule? **Answer:** As negative outflows, with proceeds positive.
15. **Period:** Must rate frequency match payment frequency? **Answer:** Yes.
16. **Tolerance:** What units does a price absolute tolerance use? **Answer:** Price or amount units.
17. **Near zero:** Why specify absolute tolerance? **Answer:** Relative tolerance alone cannot allow nonzero error against zero.
18. **Round trip:** Does it establish independent correctness? **Answer:** No; shared errors may cancel.
19. **Integration:** Does a bond-to-cash-flow comparison use independent implementations here? **Answer:** No; the bond function calls the cash-flow module.
20. **Benchmark:** Why derive expected values separately? **Answer:** To reduce the chance of repeating an implementation error.
21. **Boundary:** Why test −1 as a periodic discount rate? **Answer:** It creates a zero denominator and is outside the contract.
22. **NaN:** Why test it? **Answer:** Nonfinite inputs must be explicitly rejected where specified.
23. **Boolean:** Why test it separately from integers? **Answer:** Python Boolean values are integer subtypes, while the contracts reject them.
24. **Overflow:** Can finite inputs overflow? **Answer:** Yes.
25. **Underflow:** Can a nonzero exact value become zero? **Answer:** Yes.
26. **Coverage:** Does 100% line coverage prove model suitability? **Answer:** No.

28. **Data:** Does a valid schema prove source accuracy? **Answer:** No.
29. **Time:** Why record data availability time? **Answer:** To assess whether information was available at the decision cutoff.
30. **Revision:** Does one timestamp prove the correct historical revision was used? **Answer:** No.
31. **Simulation:** Does a seed alone guarantee cross-version reproducibility? **Answer:** No.
32. **Plot:** Do structural tests prove readability? **Answer:** No; visual inspection is needed.

## 9. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Import error | Package or optional dependency not installed in the selected interpreter | Check environment, exports and dependency status |
| Benchmark mismatch | Timeline, units, rate convention, signs or rounding differ | Reconcile assumptions and independently recalculate |
| Tests pass but intended use is unsuitable | Model or data assumptions are inappropriate | Perform independent model and data review |
| Editable tests pass but installed artifact fails | Packaging or dependency differences | Inspect wheel contents and repeat clean-environment checks |
| A plot check passes but labels overlap | Structural assertions do not measure readability | Inspect the actual figure at its intended size |
