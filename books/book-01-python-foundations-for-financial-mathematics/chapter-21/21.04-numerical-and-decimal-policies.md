## Learning objectives

Choose numerical representations for a stated financial use; distinguish precision, scale, rounding and tolerance; document conversion and error policies; design comparisons and independent benchmarks; and recognize when numerical behavior and model assumptions require separate review.

## 1. A numerical policy is part of the contract

A financial calculation needs more than a formula. Its specification should define input representation, units, allowed ranges, arithmetic precision, rounding mode and stage, output scale, error handling, comparison tolerances and evidence. The correct choices depend on the instrument, currency, jurisdiction, product terms and intended use. The policies below are educational examples, not universal accounting rules.

Section 21.3's one-period calculation uses built-in `float` inputs and returns an unrounded float. This section proposes a separate Decimal example; it does not silently change that public API. Any future conversion between numeric types must be explicit and reviewed, since it can change values and behavior. The complete toolkit and its module-specific policies are not yet implemented.

## 2. Float and Decimal

A Python `float` normally uses binary floating-point arithmetic. Many decimal fractions, including 0.1, have no exact finite binary representation. A float can be suitable for numerical methods, statistics and simulation when its precision and error behavior are acceptable for the stated use. Formatting a float to two decimal places changes its display, not the stored value.

`decimal.Decimal` represents decimal coefficients and exponents. Constructing `Decimal("0.1")` represents the specified decimal value exactly, while `Decimal(0.1)` converts the already approximated binary float. Decimal arithmetic is still subject to context precision, rounding, exponent limits, flags and traps. Decimal representation does not automatically make a model accurate or determine the correct business rounding policy.

| Decision | Specify explicitly |
|---|---|
| Input | Representation, source, units, permitted scale and whether conversions are allowed |
| Arithmetic | Numeric type, working precision, context, permitted range and exceptional conditions |
| Rounding | Mode, target quantum, stage and treatment of negative values |
| Output | Units, scale, display formatting and whether the returned value has already been rounded |
| Comparisons | Absolute and relative tolerance in relevant units; independent expected value |
| Review | Benchmarks, error analysis, actual test evidence, model scope and limitations |

## 3. Precision, scale and rounding

Decimal **precision** limits significant digits used by context-controlled arithmetic. **Scale** concerns the decimal places of a representation; quantizing to `Decimal("0.01")` specifies an exponent of −2. These are different controls. `quantize` rounds to the exponent of its second operand: `Decimal("0.05")` still has exponent −2 and does **not** by itself round to the nearest five cents. Cash increments require a separately specified algorithm, especially for negative ties.

Rounding mode and stage matter. With `ROUND_HALF_UP`, `Decimal("0.005")` rounds to `0.01` at cents, and `Decimal("-0.005")` rounds to `-0.01`. Under `ROUND_HALF_EVEN`, `0.005` rounds to `0.00` and `0.015` to `0.02`. For two amounts of `0.005`, rounding each to cents using half-up and then adding yields `0.02`; adding first and rounding once yields `0.01`. Choose the mode and stage from the applicable contract, not convenience.

Currencies do not all use two decimal places, and some settlement rules use increments different from the display scale. The example's cents policy is explicitly illustrative and does not validate currency or implement settlement rules.

## 4. Context and exceptional values

A Decimal context controls arithmetic precision, rounding, exponent limits, flags and traps. A flag records a condition; a trap causes the corresponding signal to raise an exception. `localcontext` limits changes to a local block, but copying the ambient context can still inherit settings. The reference example constructs a fresh context with explicit precision, rounding, exponent bounds and trap settings to avoid depending on the caller's context. It does not change the caller's active context.

The example rejects non-Decimal and nonfinite input with `ValueError`, and lets documented Decimal arithmetic exceptions propagate when its context traps them. It accepts finite Decimal amounts, including negative amounts, and uses `ROUND_HALF_EVEN` to quantize to cents with 28 significant digits. If a large coefficient cannot be quantized within that precision, `InvalidOperation` is raised. The function does not promise that all finite Decimal inputs can be quantized. These choices require review for a real application.

## 5. Comparisons and financial benchmarks

For finite floats, `math.isclose(a, b, rel_tol=..., abs_tol=...)` compares the difference with the larger of the relative and absolute thresholds. Tolerances are dimensioned: an amount tolerance is in amount units, while a rate tolerance is in rate units. Near zero, a meaningful absolute tolerance is usually needed. Never enlarge a tolerance merely to hide a discrepancy; first reconcile timing, units, model convention and calculation.

For a certain payment of 110 one period ahead at a 10% effective rate, the exact expression \(110/1.1\) equals 100. For `[-100, 110]` with time-zero treatment, NPV is zero in exact arithmetic. A benchmark must be independently derived and compared under consistent assumptions. A test can establish agreement for a case; it cannot establish that a certain-payment model fits a risky instrument.

## 6. Numerical risks and controls

| Risk | Example | Possible control |
|---|---|---|
| Representation | Decimal input first converted through a float | Parse a decimal string directly when the source contract specifies a decimal |
| Cancellation | Subtract nearly equal large numbers | Reformulate or increase precision where appropriate; compare with an independent reference |
| Overflow or underflow | Extreme magnitudes or rates | Define supported ranges, detect failures and test extremes |
| Intermediate rounding | Rounding each component before summation | State and test the contractually required stage |
| Mixed units or types | Combining USD and EUR or float and Decimal without a policy | Validate units and make conversions explicit |
| Incorrect tolerance | A threshold masks a material discrepancy | Tie thresholds to units, numerical analysis and business acceptance |
| Context leakage | A function changes a caller's Decimal context | Use a defined local context and test restoration |
| Invalid special values | NaN or infinity propagates | Validate finiteness and define failure behavior |

`math.fsum` can improve accuracy for many float summations, but it does not make all computations exact or replace numerical analysis. Decimal also has finite context precision for operations such as division. Record assumptions, algorithm, input provenance, environment and observed results, and obtain independent review appropriate to the use.

## 7. Reference policy implementation

Save as `numerical_policy.py`. This standalone teaching example does not integrate with Section 21.3's package and does not implement a currency or accounting system. Python 3.10 or newer is assumed.

```python
from decimal import (
    Clamped, Context, Decimal, DivisionByZero, FloatOperation, Inexact,
    InvalidOperation, Overflow, ROUND_HALF_EVEN, Rounded, Subnormal,
    Underflow, localcontext,
)


CENT = Decimal("0.01")


def example_context() -> Context:
    """Return the explicitly configured teaching context.

    Inexact/Rounded and other nontrapped conditions are permitted here;
    callers requiring their flags must inspect them inside their own context.
    """
    ctx = Context(prec=28, rounding=ROUND_HALF_EVEN, Emin=-999999,
                  Emax=999999, capitals=1, clamp=0)
    for signal in (Clamped, DivisionByZero, FloatOperation, Inexact,
                   InvalidOperation, Overflow, Rounded, Subnormal, Underflow):
        ctx.traps[signal] = signal in (DivisionByZero, InvalidOperation, Overflow)
    ctx.clear_flags()
    return ctx


def round_to_example_cents(amount: Decimal) -> Decimal:
    """Quantize a finite Decimal to 0.01 using half-even, precision 28.

    This is a teaching rule, not a currency-specific settlement policy.
    Non-Decimal or nonfinite input raises ValueError. Decimal exceptions,
    including InvalidOperation when quantization exceeds context precision,
    propagate. The caller's active Decimal context is not modified.
    """
    if not isinstance(amount, Decimal) or not amount.is_finite():
        raise ValueError("amount must be a finite Decimal")
    with localcontext(example_context()):
        return amount.quantize(CENT)
```

Construct monetary inputs from validated source strings when the source contract calls for decimal values. This function rejects `float` and `int` arguments rather than converting them. It neither records currency nor protects against incorrect source data. The local context prevents its flags and settings from becoming the caller's active context; it does not preserve an audit trail of inexact operations.

## 8. Twelve reference tests

Save as `test_numerical_policy.py` beside the implementation. These tests have not been run for this publication and are not a production certification.

```python
import math
import unittest
from decimal import Decimal, InvalidOperation, ROUND_UP, getcontext, localcontext
from numerical_policy import round_to_example_cents


class NumericalPolicyTests(unittest.TestCase):
    def test_half_even_low_tie(self):
        self.assertEqual(round_to_example_cents(Decimal("0.005")), Decimal("0.00"))
    def test_half_even_high_tie(self):
        self.assertEqual(round_to_example_cents(Decimal("0.015")), Decimal("0.02"))
    def test_negative_tie(self):
        self.assertEqual(round_to_example_cents(Decimal("-0.015")), Decimal("-0.02"))
    def test_exact_cents(self):
        self.assertEqual(round_to_example_cents(Decimal("12.34")), Decimal("12.34"))
    def test_output_exponent(self):
        self.assertEqual(round_to_example_cents(Decimal("1")).as_tuple().exponent, -2)
    def test_float_rejected(self):
        with self.assertRaises(ValueError):
            round_to_example_cents(1.25)
    def test_integer_rejected(self):
        with self.assertRaises(ValueError):
            round_to_example_cents(1)
    def test_nan_rejected(self):
        with self.assertRaises(ValueError):
            round_to_example_cents(Decimal("NaN"))
    def test_infinity_rejected(self):
        with self.assertRaises(ValueError):
            round_to_example_cents(Decimal("Infinity"))
    def test_large_quantize_raises(self):
        with self.assertRaises(InvalidOperation):
            round_to_example_cents(Decimal("1e30"))
    def test_caller_context_unchanged(self):
        with localcontext() as ctx:
            ctx.prec = 6
            ctx.rounding = ROUND_UP
            before = (getcontext().prec, getcontext().rounding)
            value = round_to_example_cents(Decimal("0.005"))
            self.assertEqual(value, Decimal("0.00"))
            self.assertEqual((getcontext().prec, getcontext().rounding), before)
    def test_float_zero_benchmark_with_absolute_tolerance(self):
        value = -100.0 + 110.0 / 1.1
        self.assertTrue(math.isclose(value, 0.0, rel_tol=0.0, abs_tol=1e-10))


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

## 10. Forty worked exercises

2. **Float:** Is decimal 0.1 exactly representable in ordinary binary float? **Answer:** No.
3. **Decimal:** Is `Decimal("0.1")` exactly one tenth? **Answer:** Yes as a decimal value.
4. **Conversion:** Is `Decimal(0.1)` the same intended decimal input? **Answer:** It captures the float approximation rather than the exact string value.
5. **Precision:** What does context precision control? **Answer:** Significant digits in context-controlled arithmetic.
6. **Scale:** What exponent does quantizing to `0.01` specify? **Answer:** −2.
7. **Quantum:** Does `quantize(Decimal("0.05"))` round to five-cent increments? **Answer:** No; it sets the exponent to −2.
8. **Half-even:** Round 0.005 to cents. **Answer:** 0.00.

10. **Half-up:** Round 0.005 to cents. **Answer:** 0.01.
11. **Negative half-up:** Round −0.005 to cents. **Answer:** −0.01.
12. **Stage:** Round two 0.005 amounts individually using half-up, then add. **Answer:** 0.02.
13. **Stage:** Add those amounts then round using half-up. **Answer:** 0.01.
14. **Currency:** Do all currencies use two decimal places? **Answer:** No; currency and contract rules differ.
15. **Display:** Does `f"{x:.2f}"` change the stored float? **Answer:** No.
16. **Context:** What can a trap do? **Answer:** Cause an arithmetic signal to raise an exception.
17. **Flag:** What does a Decimal flag indicate? **Answer:** A corresponding condition occurred in that context.

## 11. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| `ValueError` | Non-Decimal or nonfinite amount | Inspect the source contract and validate the input |
| `InvalidOperation` | Quantized result exceeds context precision or another invalid operation | Review magnitude, required precision and documented limits |
| Two results differ by a cent | Different mode or rounding stage | Reconcile the contract, inputs and intermediate operations |
| Float comparison fails | Rounding, unsuitable tolerance or convention mismatch | Investigate units and independently derive the benchmark |
| Repeated results are consistent but unsuitable | Model or data assumptions do not match intended use | Seek independent model and data review |
