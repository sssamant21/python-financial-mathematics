## Learning objectives

Write testable functional and nonfunctional requirements, separate requirements from assumptions and limitations, define financial input and output contracts, build a requirements-to-evidence matrix, and make acceptance decisions based on recorded results. Apply these ideas to the one-period valuation slice introduced in Section 21.1.

## 1. From architecture to a specification

Architecture identifies boundaries; requirements specify the behavior and constraints those boundaries must satisfy. Assumptions state conditions taken as given for a model or use. Limitations describe what the model, data or implementation does not address. An acceptance criterion describes an observable condition for a particular requirement. Evidence is the recorded result of a review or check, not the check's definition.

For example, “calculate one-period present value” is broad. A more useful requirement specifies the payment timing, effective-rate convention, accepted input types and range, output units, failure behavior and a benchmark. Each requirement needs an identifier, owner, priority, verification method and status appropriate to the project.

This chapter designs an educational toolkit. The requirements below are a proposed baseline; later sections must refine each module's contract. The only implemented calculation described here is the Section 21.1 one-period slice. There is no production approval, live data service or claim that the planned modules already exist.

## 2. Scope and stakeholders

**Intended educational use:** demonstrate reproducible financial calculations on synthetic inputs, using documented conventions and explicit errors. Learners and reviewers can explore results and compare them with independently derived examples.

**Out of scope for the reference slice:** live pricing, personalized advice, regulatory reporting, execution, custody, credit/default, taxes, fees, liquidity, actual dates and day counts, inflation, FX conversion, market data ingestion and production deployment. These exclusions are not assertions that later modules can never address them; changes require an explicit specification and review.

A project owner defines intended use and acceptance, financial reviewers challenge assumptions and benchmarks, developers implement and test, and an independent reviewer assesses risks and findings as appropriate. In a small educational exercise one person may perform multiple roles; that is not independent validation. A real organization must apply its own governance and applicable obligations.

## 3. Requirements and assumptions register

| ID | Kind | Proposed statement | Verification method |
|---|---|---|---|
| R-01 | Functional | Accept a request containing a payment, effective one-period rate and nonblank currency label. | Contract and invalid-input checks |
| R-02 | Functional | Return one-period PV $`C/(1+r)`$, in the payment's units, for the supported domain. | Independently derived benchmarks and formula review |
| R-03 | Functional | Include input payment, rate, currency label, convention and model identifier with the result. | Result-field checks |
| R-04 | Input | Accept finite built-in floats for payment and rate, with $`r>-1`$; reject booleans, integers and nonfinite values. | Boundary and type checks |
| R-05 | Input | Reject a blank or non-string currency label. | Invalid-input checks |
| R-06 | Error | Raise `ValueError` for invalid input or a nonfinite computed result. | Exception checks |
| R-07 | Numerical | Return an unrounded binary float; document rounding, underflow and overflow limitations. | Code and documentation review; range tests |
| R-08 | Operational | Record revision, inputs or controlled references, configuration, environment and actual results for an executed review. | Inspect evidence record |
| R-09 | Model | Document intended use, assumptions, exclusions, owner, independent review and findings before any approved use. | Model documentation and governance review |
| R-10 | Integration | Future modules shall specify compatible units, timelines, error behavior and data contracts before integration. | Interface and integration review |

A-01: the payment is a certain amount at the end of one period. A-02: the supplied rate is an effective rate for that same period. A-03: input and output are in the same currency and amount units. A-04: the simplified model holds the supplied rate constant for the period. These are model assumptions, not guarantees about real instruments. The code accepts negative payments and rates greater than −1, but an accepted value may be inappropriate for an intended use.

The currency string is a caller-provided label: it is neither ISO-code validation nor currency conversion. R-08 through R-10 describe future project controls; the Section 21.1 in-memory example alone does not implement an evidence store, governance workflow or integrated toolkit.

## 4. Financial contract and benchmark

For a payment $`C`$ at the end of one period and effective period rate $`r>-1`$:

```math
PV=\frac{C}{1+r}.
```

For `payment=110.0`, `rate=0.10` and `currency="USD"`, the exact mathematical PV is 100 USD. The input rate is a decimal, not a percentage number: 10% is `0.10`. If a rate is annual while the payment period is monthly, conversion must be specified before using the function. For an effective annual rate of 12%, the equivalent effective monthly rate is $`(1.12)^{1/12}-1`$, approximately 0.00948879.

At zero rate PV equals the payment. A payment of 95 at −5% has PV 100 in exact arithmetic. For a positive payment, PV decreases as the rate rises, holding all other inputs fixed. With a negative payment the direction reverses. These properties test parts of behavior; they do not establish that the model is economically suitable.

## 5. Measurable acceptance and traceability

| Requirement | Example acceptance criterion | Evidence to collect during deferred QA | Status now |
|---|---|---|---|
| R-02 | For 110 and 0.10, computed PV differs from independently derived 100 by at most `1e-10` amount units in the specified environment. | Revision, command, environment and actual result; benchmark derivation and review. | Not executed |
| R-03 | Result retains the exact supplied label and input values, plus the specified convention and model identifier. | Actual field-check output and source revision. | Not executed |
| R-04/R-06 | Reject −1, nonfinite rates and payments, integer and Boolean inputs with `ValueError`. | Boundary-test results and input cases. | Not executed |
| R-05 | Reject empty or whitespace-only and non-string labels. | Invalid-input test results. | Not executed |
| R-07 | Return unrounded float and reject nonfinite result; document numerical limitations. | Source review, overflow and representative range checks. | Not executed |
| R-08/R-09 | Records and reviews exist, are attributable and cover the intended use and unresolved findings. | Actual evidence package and review decisions. | Not implemented or reviewed |

The illustrative `1e-10` amount-unit threshold is for a small example, not a universal financial materiality threshold. Acceptance criteria should also specify supported ranges, platforms and uncertainty. For results near zero, an absolute tolerance matters; relative tolerance alone does not accept a nonzero difference against zero. Passing an acceptance test does not establish suitability of the model.

## 6. Nonfunctional requirements and open decisions

| Area | Decision to specify | Example acceptance or evidence |
|---|---|---|
| Accuracy | Supported range, numerical error budget, input uncertainty and business materiality | Benchmark and stress results with tolerances in units |
| Reliability | Failure modes, explicit exceptions and recovery at the caller boundary | Invalid-input and failure-path checks |
| Reproducibility | Revision, environment, dependency versions and configuration | A second run with retained evidence; simulation additionally records RNG details |
| Security and privacy | Data classification, access, retention, dependency controls and log redaction | Applicable security review and control evidence |
| Performance | Workload, hardware, concurrency, measurement method and target | Representative benchmark against a stated target |
| Usability | Error messages, examples, documentation and supported interfaces | Review with representative users |
| Compatibility | Supported Python versions, platforms, package and API versions | Installed-artifact checks on the defined support matrix |
| Operations | Owner, monitoring, incident response, deployment and rollback for a real service | Operational review and exercised procedures |

Do not invent a performance target before defining the workload. Immutable in-memory data structures reduce accidental reassignment but are not a durable audit trail. Do not log sensitive inputs by default. Reproducibility is compatible with an incorrect model; independent challenge is still needed.

## 7. Reference requirements checker

The following small self-contained example checks whether a requirements record contains specific fields and whether acceptance evidence is represented honestly. It is separate from the Section 21.1 valuation code and does not run a financial calculation or validate a model. The checker is deliberately simple: it cannot determine the quality of a criterion, assess evidence authenticity, confirm ownership or prove compliance.

Save as `requirements_check.py` (Python 3.10 or newer):

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Requirement:
    identifier: str
    statement: str
    criterion: str
    method: str
    status: str = "not_run"
    evidence: str = ""


def validate_requirement(requirement: Requirement) -> None:
    """Validate the record's narrow structural and status contract.

    A passed or failed check requires a nonblank evidence reference. A
    not-run or blocked item may include a note but does not claim success.
    This does not authenticate evidence or determine criterion quality.
    """
    if not isinstance(requirement, Requirement):
        raise ValueError("requirement must be a Requirement")
    for name in ("identifier", "statement", "criterion", "method"):
        value = getattr(requirement, name)
        if type(value) is not str or not value.strip():
            raise ValueError(f"{name} must be a nonblank string")
    if type(requirement.status) is not str or requirement.status not in (
            "not_run", "blocked", "passed", "failed"):
        raise ValueError("invalid status")
    if type(requirement.evidence) is not str:
        raise ValueError("evidence must be a string")
    if requirement.status in ("passed", "failed") and not requirement.evidence.strip():
        raise ValueError("completed status requires an evidence reference")


def ready_for_review(requirements: list[Requirement]) -> bool:
    """Return whether a nonempty list has structurally valid passed records.

    This is a bookkeeping gate, not model approval or evidence verification.
    Invalid records raise ValueError; non-passed records return False.
    """
    if type(requirements) is not list or not requirements:
        raise ValueError("requirements must be a nonempty list")
    for requirement in requirements:
        validate_requirement(requirement)
    return all(requirement.status == "passed" for requirement in requirements)


if __name__ == "__main__":
    r = Requirement("R-02", "Calculate one-period PV", "110 at 10% is 100",
                    "independent benchmark")
    print(f"Ready for review: {ready_for_review([r])}")  # False: not run
```

A `passed` record without evidence is rejected, but the presence of a string cannot prove that evidence is real, complete or independently reviewed. The gate checks every record before reporting readiness; an invalid record raises even if another record is not run. `ready_for_review` does not confer approval.

## 8. Twelve reference tests

Save as `test_requirements_check.py` beside the checker. These definitions have not been executed for this publication. They test the checker contract, not the toolkit's financial implementation.

```python
import unittest
from requirements_check import Requirement, ready_for_review, validate_requirement


def record(**changes):
    fields = dict(identifier="R-02", statement="Calculate PV",
                  criterion="110 at 10% is 100", method="benchmark")
    fields.update(changes)
    return Requirement(**fields)


class RequirementsTests(unittest.TestCase):
    def test_valid_not_run(self):
        self.assertIsNone(validate_requirement(record()))
    def test_not_run_not_ready(self):
        self.assertFalse(ready_for_review([record()]))
    def test_passed_with_evidence(self):
        self.assertTrue(ready_for_review([record(status="passed", evidence="run-1")]))
    def test_failed_not_ready(self):
        self.assertFalse(ready_for_review([record(status="failed", evidence="run-2")]))
    def test_blocked_not_ready(self):
        self.assertFalse(ready_for_review([record(status="blocked", evidence="waiting")]))
    def test_empty_list_rejected(self):
        with self.assertRaises(ValueError):
            ready_for_review([])
    def test_wrong_container_rejected(self):
        with self.assertRaises(ValueError):
            ready_for_review((record(),))
    def test_blank_identifier_rejected(self):
        with self.assertRaises(ValueError):
            validate_requirement(record(identifier="  "))
    def test_blank_criterion_rejected(self):
        with self.assertRaises(ValueError):
            validate_requirement(record(criterion=""))
    def test_invalid_status_rejected(self):
        with self.assertRaises(ValueError):
            validate_requirement(record(status="approved"))
    def test_pass_without_evidence_rejected(self):
        with self.assertRaises(ValueError):
            validate_requirement(record(status="passed", evidence="  "))
    def test_invalid_later_record_still_rejected(self):
        with self.assertRaises(ValueError):
            ready_for_review([record(), record(status="failed", evidence="")])


if __name__ == "__main__":
    unittest.main(verbosity=2)
```

During deferred QA, in the directory containing both files:

```bash
python requirements_check.py
python -m unittest -v test_requirements_check
python -m compileall -q requirements_check.py test_requirements_check.py
```

Record actual results, source revision, Python version and platform. The example intentionally reports `False` for the unexecuted requirement. A test definition or an evidence reference alone is not a passed test.

## 10. Forty worked exercises

1. **Requirement:** What is a requirement? **Answer:** A specified behavior or constraint the system must satisfy.
2. **Assumption:** What is an assumption? **Answer:** A condition taken as given for a model or use.
3. **Limitation:** What is a limitation? **Answer:** A boundary or shortcoming that constrains use or interpretation.
4. **Criterion:** What makes acceptance measurable? **Answer:** An observable result, conditions and a defined threshold or rule.
5. **Evidence:** Are test definitions evidence that tests passed? **Answer:** No; retain actual execution results.
6. **Scope:** Is this slice a production trading system? **Answer:** No; it is an educational example.
7. **Owner:** Why identify one? **Answer:** To establish accountability for requirements, findings and decisions.
8. **Independence:** Is the developer automatically an independent validator? **Answer:** No; independence depends on roles and context.
9. **Benchmark:** PV of 110 in one period at 10%? **Answer:** 100 in exact arithmetic.
10. **Zero rate:** PV of 110 at 0%? **Answer:** 110.
11. **Negative rate:** PV of 95 at −5%? **Answer:** 100 in exact arithmetic.
12. **Boundary:** Why reject −1? **Answer:** The denominator becomes zero.
13. **Unit:** What units does PV use? **Answer:** The same amount and currency units as the payment.
14. **Rate:** How is 10% represented? **Answer:** `0.10`.
15. **Frequency:** Does an annual rate directly match a monthly period? **Answer:** No; specify an appropriate conversion.
16. **Effective conversion:** Convert 12% effective annually to monthly. **Answer:** $`(1.12)^{1/12}-1`$, about 0.948879%.
17. **Sign:** Is a negative payment permitted? **Answer:** Yes, under the stated contract.
18. **Monotonicity:** What happens to positive-payment PV as rate rises? **Answer:** It falls, all else equal.
19. **Negative payment:** What happens to its PV as rate rises? **Answer:** It rises toward zero, all else equal.
20. **Label:** Does `USD` perform FX conversion? **Answer:** No; it is metadata.
21. **Type:** Is integer `110` accepted by Section 21.1? **Answer:** No; it requires a built-in float.
22. **Boolean:** Is `True` a valid rate? **Answer:** No.
23. **Nonfinite:** Is NaN permitted? **Answer:** No; inputs must be finite.
24. **Output:** Is the float rounded to cents? **Answer:** No; displayed rounding is separate.
25. **Tolerance:** Does `1e-10` suit every use? **Answer:** No; justify it for units, scale and purpose.
26. **Zero:** Why specify absolute tolerance near zero? **Answer:** Relative tolerance alone does not accommodate a nonzero difference from zero.
27. **Overflow:** Can finite inputs produce infinity? **Answer:** Yes; R-06 requires rejection of a nonfinite result.
28. **Underflow:** Does a finite result prove accuracy? **Answer:** No; rounding and underflow remain possible.
29. **Model:** Does the formula include default? **Answer:** No.
30. **Software:** Does a correct implementation prove model suitability? **Answer:** No.
31. **Traceability:** What connects an acceptance result to a requirement? **Answer:** Its identifier, criterion, method and recorded evidence.
32. **Status:** Can a blocked check be recorded as passed? **Answer:** No.
33. **Checker:** What does `ready_for_review` mean? **Answer:** All supplied records are structurally valid and marked passed with evidence strings; it is not approval.
34. **Evidence string:** Does a nonblank reference prove evidence authenticity? **Answer:** No.
35. **Empty set:** Is an empty requirements list accepted by the checker? **Answer:** No; it raises `ValueError`.
36. **Failure:** Does a failed item need an evidence reference in the checker? **Answer:** Yes.
37. **Performance:** What precedes a meaningful latency target? **Answer:** A defined workload, environment and measurement method.
38. **Privacy:** Should raw sensitive data appear in logs by default? **Answer:** No; minimize and protect it.
39. **Change:** What happens when a material assumption changes? **Answer:** Reassess requirements, tests, impact and review under the applicable process.
40. **Next:** What is the next locked section? **Answer:** 21.3 — Project Structure.

## 11. Troubleshooting

| Symptom | Likely issue | Next step |
|---|---|---|
| Requirement cannot be tested | Criterion lacks units, conditions or a threshold | Rewrite it in observable terms and specify scope |
| Checker raises `ValueError` | Missing field, invalid status, missing evidence reference or wrong container | Inspect the structural contract; do not invent evidence |
| A benchmark differs | Timing, rate convention, signs or units differ | Reconcile assumptions and independent derivation |
| All records say passed but approval is absent | Bookkeeping does not verify model suitability or authenticate evidence | Obtain the required independent review and decision |
| Results cannot be reproduced | Revision, environment, inputs or configuration are missing | Capture actual run metadata under the evidence policy |
