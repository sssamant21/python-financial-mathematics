## Learning objectives

Reproduce a simulation within a documented environment; explain why a seed alone is insufficient; record inputs, generator, code and software versions; distinguish exact replay from tolerance-based comparison; manage parallel streams; and retain evidence for review.

## 1. What does reproducibility mean?

A reproducible simulation allows another run to be traced to its model, input data, code, random generator and environment. Define the expected level of agreement before comparing results:

- **Exact replay:** the same random sequence and outputs under a controlled implementation, inputs, state and operation order.
- **Numerical agreement:** results differ only within an agreed tolerance, appropriate when platform or numerical-library differences affect rounding.
- **Statistical agreement:** independent runs are consistent within an appropriate uncertainty assessment; their individual draws are not expected to match.

These are different goals. A reproducible wrong model remains wrong, and a repeated seed does not validate market assumptions or establish independence.

## 2. Simulation contract

Write down the purpose, horizon, currency, input source and timestamp, payoff, probability model, sample count and output measures. State whether returns are simple or logarithmic and whether the run represents a real-world or risk-neutral model.

For illustration, an asset starts at 100 and ends at 110 with probability .6 or 90 otherwise. Its model expectation is .6×110+.4×90=**102**. A simulation estimates 102; it does not forecast an individual outcome.

## 3. The seed and generator

A pseudorandom generator is deterministic given its state and operation sequence. Record the seed **and** generator family, implementation and software versions. Equal integer seeds across different libraries or algorithms need not yield the same sequence.

A local generator limits interference from other functions:

~~~python
import random

rng = random.Random(42)
print([rng.random() for _ in range(5)])
~~~

Creating a new generator with the same seed for every path can repeat the same first draw. Initialize once per intended stream, then advance it normally.

## 4. Draw order and state

A new draw consumes generator state. Adding a random operation before an existing one changes subsequent draws even if the seed stays the same. Changes to batching, loop order and parallel scheduling can also alter which path receives which draw.

Within a compatible implementation, save and restore state when exact continuation is required:

~~~python
import random

rng = random.Random(42)
checkpoint = rng.getstate()
first = rng.random()
rng.setstate(checkpoint)
assert rng.random() == first
~~~

Store state only in a trusted and compatible form. Record what point in the simulation it represents; the state alone does not capture the model, data or program.

## 5. Environment and inputs

Record at least:

- Code revision or source checksum, configuration and command.
- Python, numerical libraries, generator family and relevant platform details.
- Seed, state or stream construction, sample count and draw order.
- Input dataset version, source, timestamp, units and content checksum where appropriate.
- Model parameters, time horizon, conventions, payoff, tolerances and output summaries.

A hash can identify bytes and detect accidental changes; it does not prove the input data are correct or trustworthy. Protect sensitive data and evidence according to organizational policy.

## 6. Floating-point and platform effects

Even with identical draws, floating-point results can vary due to hardware, library versions, parallel reduction order or compiler choices. Addition is not associative. For numerical comparison specify an absolute and relative tolerance and the reference scale:

**|actual−reference| ≤ atol + rtol |reference|.**

Tolerance-based comparisons should reflect units and intended use; they do not excuse a changed model or data. Bitwise equality requires a sufficiently controlled environment and algorithm.

## 7. Parallel streams

Starting every worker with the same seed can duplicate draws. Use a generator's documented stream-spawning method. Different manually chosen seeds alone do not prove independence or non-overlap.

For example, NumPy's `SeedSequence.spawn` derives child streams. Record parent seed, NumPy version, child identifiers, mapping to tasks, partition sizes and reduction order. Child streams are designed to be very probably independent, not guaranteed non-overlapping for every possible use.

~~~python
import numpy as np

parent = np.random.SeedSequence(42)
children = parent.spawn(2)
streams = [np.random.default_rng(child) for child in children]
print([stream.random() for stream in streams])
~~~

Changing the worker count or path-to-worker assignment can change outputs even with the same parent seed. Define a stable partition if exact replay matters.

## 8. Common random numbers

To compare two model configurations, one can intentionally feed the same underlying draws to both. This paired design can reduce the variance of the estimated difference when outputs respond similarly to the shared randomness; it is not guaranteed to improve every comparison.

Use standard errors for the **paired differences**, not a formula that assumes the two estimates are independent. Preserve the draw mapping and clearly distinguish deliberate coupling from accidental duplicate worker streams.

## 9. Repeated seeds and independent replications

A fixed seed supports debugging and regression testing. Multiple properly constructed independent replications help assess sampling variability. They do not remove model bias, coding errors or time-discretization bias. A confidence interval has assumptions and does not automatically quantify the uncertainty in the financial model.

## 10. Run manifest

A manifest can contain a schema version, run ID, model name, parameters, seed, generator, sample count, code revision, runtime versions, input identity and summary. Avoid relying on a human-readable label as a data identity; where appropriate, use a content hash.

The following reference implementation stores a simple JSON manifest and an SHA-256 digest of its canonical JSON representation. The digest identifies the encoded manifest, not an external dataset or the correctness of the run. It intentionally excludes timestamps so identical inputs in the same environment can produce identical manifests. A real system may include timestamps as metadata outside a comparison of deterministic fields.

## 11. Reference implementation

Save as `reproducible_simulation.py`. It models the two-outcome example and uses the standard-library generator. This is a teaching example rather than a production audit framework.

~~~python
import hashlib
import json
import math
import platform
import random
import unittest

def run(seed, count, up_probability):
    if type(seed) is not int or type(count) is not int or count < 2:
        raise ValueError("integer seed and count >= 2 required")
    if (type(up_probability) not in (int, float)
            or not math.isfinite(up_probability)
            or not 0 <= up_probability <= 1):
        raise ValueError("probability must be finite and in [0,1]")
    rng = random.Random(seed)
    up_count = sum(rng.random() < up_probability for _ in range(count))
    # Integer-valued outcomes keep this example's summary simple.
    mean = (110 * up_count + 90 * (count-up_count)) / count
    return {
        "schema_version": 1,
        "model": "two-outcome-terminal-value",
        "initial_value": 100,
        "up_value": 110,
        "down_value": 90,
        "up_probability": up_probability,
        "seed": seed,
        "count": count,
        "generator": "random.Random / Mersenne Twister",
        "python_implementation": platform.python_implementation(),
        "python_version": platform.python_version(),
        "up_count": up_count,
        "mean": mean,
    }

def canonical_json(manifest):
    return json.dumps(manifest, sort_keys=True, separators=(",", ":"),
                      allow_nan=False)

def manifest_digest(manifest):
    return hashlib.sha256(canonical_json(manifest).encode("utf-8")).hexdigest()

def within_tolerance(actual, reference, atol, rtol):
    if any(type(x) not in (int, float) or not math.isfinite(x)
           for x in (actual, reference, atol, rtol)):
        raise ValueError("finite numbers required")
    if atol < 0 or rtol < 0:
        raise ValueError("nonnegative tolerances required")
    return abs(actual-reference) <= atol + rtol*abs(reference)

class ReproducibilityTests(unittest.TestCase):
    def test_replay(self):
        self.assertEqual(run(42,100,.6),run(42,100,.6))
    def test_digest_replay(self):
        self.assertEqual(manifest_digest(run(42,100,.6)),
                         manifest_digest(run(42,100,.6)))
    def test_all_up(self):
        self.assertEqual(run(1,10,1)["mean"],110)
    def test_all_down(self):
        self.assertEqual(run(1,10,0)["mean"],90)
    def test_canonical_key_order(self):
        self.assertEqual(manifest_digest({"a":1,"b":2}),
                         manifest_digest({"b":2,"a":1}))
    def test_digest_changes(self):
        self.assertNotEqual(manifest_digest({"seed":1}),
                            manifest_digest({"seed":2}))
    def test_tolerance_pass(self):
        self.assertTrue(within_tolerance(100.01,100,.02,0))
    def test_tolerance_fail(self):
        self.assertFalse(within_tolerance(100.02,100,.01,0))
    def test_invalid_probability(self):
        with self.assertRaises(ValueError): run(1,10,1.1)
    def test_invalid_count(self):
        with self.assertRaises(ValueError): run(1,1,.5)

if __name__ == "__main__":
    manifest = run(42,10000,.6)
    print(canonical_json(manifest))
    print("manifest_sha256:", manifest_digest(manifest))
    unittest.main(verbosity=2)
~~~

For deferred QA, run:

~~~bash

python -m compileall -q reproducible_simulation.py
~~~

The ten reference tests have not been executed during publication. They check selected behavior; they do not certify the model, generator quality, environment portability or production readiness.

## 12. Twelve-step lab

1. Record Python implementation and version.
2. Save the reference implementation and define its two-outcome assumptions.
3. Calculate the analytical expected terminal value, 102.
4. Run with seed 42, 10,000 samples and p=.6; retain the manifest and digest.
5. Repeat with the same inputs and environment; compare deterministic fields and digest.
6. Change the seed and compare the sample mean; do not expect exact agreement.
7. Change p to .5 and calculate the new analytical expectation.
8. Change the sample count and record the new manifest.
9. Demonstrate saving and restoring generator state.
10. Add one extra draw before the sample and observe the effect on draw order.
11. Run the reference tests and retain actual output.
12. Document what is needed to replay the run and what model risks remain for the planned QA phase.

## 13. Forty worked exercises

1. **Exact replay:** What must match? **Answer:** State, algorithm, operations, inputs and a compatible environment.
2. **Seed:** Is it sufficient by itself? **Answer:** No.
3. **Different generator:** Same seed guarantees same sequence? **Answer:** No.
4. **Extra draw:** Effect? **Answer:** It advances state and changes later draws.
5. **Local generator:** Benefit? **Answer:** It reduces interference from shared state.
6. **Generator state:** What does restoring it allow? **Answer:** Replay from that point in a compatible implementation.
7. **Model:** Values 110 and 90, p=.6. Expected value? **Answer:** 102.
8. **Model:** Same values, p=.5. **Answer:** 100.
9. **Sample mean:** Must a 10,000-draw estimate equal 102 exactly? **Answer:** No.
10. **Seed reuse:** Reinitialize with the same seed on every path. Risk? **Answer:** Repeated draws.
11. **Parallel workers:** Same seed for each. Risk? **Answer:** Duplicate streams.
12. **Different seeds:** Do they prove independence? **Answer:** No.
13. **Spawning:** What should be recorded? **Answer:** Parent seed, child mapping, generator and configuration.
14. **Worker count:** Can changing it affect replay? **Answer:** Yes.
15. **Checksum:** What does it identify? **Answer:** The bytes hashed.
16. **Checksum:** Does it prove data correctness? **Answer:** No.
17. **Canonical JSON:** Why sort keys? **Answer:** To make equivalent key order serialize consistently under the chosen encoding.
18. **Timestamp:** Why exclude it from exact deterministic comparisons? **Answer:** It changes between runs.
19. **Tolerance:** Actual 100.01, reference 100, atol .02, rtol 0. **Answer:** Pass.
20. **Tolerance:** Actual 100.02, reference 100, atol .01, rtol 0. **Answer:** Fail.
21. **Near zero:** Why use absolute tolerance? **Answer:** Relative error can be undefined or unhelpful.
22. **Floating point:** Why can reduction order matter? **Answer:** Addition is not associative.
23. **Numerical agreement:** Does it require identical bytes? **Answer:** No.
24. **Statistical agreement:** Must independent draws match? **Answer:** No.
25. **Fixed seed:** What does it help with? **Answer:** Debugging and regression replay.
26. **Multiple replications:** What do they assess? **Answer:** Sampling variability under the specified setup.
27. **Bias:** Does more sampling remove wrong assumptions? **Answer:** No.
28. **Model validation:** Does replay prove correctness? **Answer:** No.
29. **Common random numbers:** Purpose? **Answer:** Pair model comparisons using shared draws.
30. **Paired SE:** Which observations matter? **Answer:** The paired outcome differences.
31. **Variance reduction:** Is it guaranteed by pairing? **Answer:** No.
32. **Dataset:** What should be recorded? **Answer:** Source, version, timestamp, units and suitable identity or hash.
33. **Sensitivity:** Why vary parameters? **Answer:** To assess dependence on assumptions.
34. **Python version:** Why record it? **Answer:** It helps establish a compatible runtime.
35. **Code revision:** Why record it? **Answer:** It identifies implementation used.
36. **Manifest hash:** Does it hash external data automatically? **Answer:** No.
37. **Security:** Is a simulation PRNG suitable for secret tokens? **Answer:** Not generally; use a cryptographic source.
38. **Failure:** A changed digest appears. Next step? **Answer:** Compare manifest fields and inputs before drawing conclusions.
39. **Evidence:** Are illustrative results execution evidence? **Answer:** No.
40. **Scope:** Is reproducibility a replacement for model validation? **Answer:** No.

## 14. Troubleshooting

| Symptom | Possible cause | Next check |
|---|---|---|
| Same seed, different results | Generator, version or draw order changed | Compare manifest and code |
| Identical workers | Seed or state duplicated | Inspect child stream assignment |
| Digest differs | Manifest fields or encoding differ | Compare canonical representations |
| Same draws, small numerical differences | Platform or reduction order | Use justified tolerances and investigate |
| Repeatable but implausible result | Wrong inputs or model | Compare independent benchmarks |
| Different runs disagree beyond expected sampling error | Dependence, defect or assumptions | Inspect streams, uncertainty and model |
