## Learning objectives

Measure simulation performance; estimate time and memory needs; compare scalar, vectorized and batched approaches; use streaming statistics; understand parallel random streams; and balance computational cost with statistical accuracy and reproducibility.

## 1. Performance begins with the question

A simulation must be correct enough for its intended purpose and complete within available time and memory. Define the output and precision requirement before optimizing. Generating more paths reduces ordinary independent-sample standard error at approximately 1/√N, but does not remove model bias, incorrect assumptions or discretization error.

Measure a baseline with representative inputs. Profile the actual workload and optimize the limiting part. A speedup claim requires recorded hardware, software, input sizes, method and measurements; it should not be inferred from code style alone.

## 2. Work and memory

For N paths and T time steps, generating all steps generally requires work proportional to N×T. Storing a dense array of all prices also requires O(NT) elements. If only terminal prices or summary statistics are needed, storing all intermediate prices can be unnecessary.

A dense binary64 array with N=100,000 and T=253 stored values per path requires 100,000×253×8=**202,400,000 bytes**, about **193.0 MiB**, for element data alone. This excludes array metadata, temporary arrays, random draws, the initial time point if stored separately, and application overhead. Python lists of float objects can use substantially more memory.

## 3. Scalar and vectorized computation

A Python loop is straightforward but may incur per-element interpreter overhead. NumPy can perform operations over arrays in compiled code; vectorization may improve throughput for suitable workloads. It can also allocate large temporary arrays. Benchmark both approaches with the same mathematical problem and precision requirements.

Do not assume matching seeds across Python and NumPy produce matching draws. Compare implementations against analytical benchmarks and equivalent distributions rather than requiring identical random sequences unless the random inputs are explicitly shared.

## 4. Batching

Batching processes a subset of paths at a time, updates the desired summary and releases temporary arrays. If batch size is B and each path has T stored values, peak working storage can be reduced toward O(BT), plus summary and implementation overhead.

For 100,000 paths in batches of 10,000, there are ten batches; a final partial batch is needed when N is not divisible by B. Batched computation can change draw ordering or floating-point reduction order, so reproducibility and tolerances must be defined.

## 5. Streaming mean and variance

When only mean and variance are required, Welford's online algorithm updates a count, mean and sum of squared deviations M₂ without keeping every observation:

1. n←n+1; δ=x−mean.
2. mean←mean+δ/n.
3. M₂←M₂+δ(x−mean).

For n≥2, sample variance is M₂/(n−1). This is often numerically preferable to subtracting two large nearly equal sums, but floating-point error and overflow are still possible. The sample standard error s/√n assumes independent observations or appropriate independent units.

A streaming mean and variance do not retain the full distribution. Exact empirical quantiles generally require retaining or otherwise selecting from the observations; approximate sketches introduce their own accuracy and validation considerations.

## 6. Precision and memory tradeoffs

A binary32 array uses four bytes per element and binary64 uses eight. Reduced precision can save memory and improve throughput on some hardware, but may amplify rounding, overflow, underflow or accumulation error. Validate the chosen precision against financial tolerances and independent benchmarks; do not assume the final two-decimal display makes intermediate precision unimportant.

Use appropriate reduction methods and avoid unnecessary repeated rounding. Different reduction orders can yield slightly different floating-point results.

## 7. Benchmarking responsibly

Use a monotonic high-resolution clock such as `time.perf_counter`. Separate setup from the timed operation where relevant, warm up when appropriate, repeat measurements and report a robust summary such as median and range.

Record CPU, memory, operating system, Python and library versions, thread settings, path count, time steps, batch size, generator, precision, model and whether setup is included. Compare equivalent outputs and correctness criteria. Timing in a shared environment is noisy and may not generalize.

## 8. Profiling and bottlenecks

A profiler can identify time spent in random generation, payoff evaluation, allocations or serialization. Memory pressure and copying can dominate even when arithmetic is fast. Profile representative cases before changing code.

For reproducible benchmarks, record thread counts and library configuration. Excessive nested parallelism can oversubscribe CPUs and hurt performance. A GPU or distributed system adds transfer, scheduling and operational costs; it is not automatically faster.

## 9. Parallel random streams

Parallel workers should use documented generator stream-spawning or partitioning mechanisms. Initializing every worker with the same seed can duplicate paths and understate uncertainty. Different arbitrary seeds alone do not prove independence or non-overlap.

Retain generator type, parent seed, child assignments, worker count, path partition and reduction order. If scheduling or partition changes, exact output may change even though the statistical model is unchanged. Estimate uncertainty using the correct independent units.

## 10. Accuracy per unit cost

For an IID sample mean with finite variance, SE≈s/√N. Four times as many paths roughly halves SE at approximately four times the sampling work if per-path cost is constant. The required path count for a desired fixed-sample normal-approximation half-width h is approximately (zσ/h)², subject to the assumptions and uncertainty in σ.

Variance-reduction methods may improve accuracy per unit of computation, but they change how uncertainty is calculated. Benchmark estimator accuracy and cost together. Repeatedly stopping an ordinary fixed-N confidence interval as soon as it narrows can change coverage.

## 11. Path-dependent payoffs

A terminal payoff may need only the current price, while an average payoff needs a running sum and a discrete barrier payoff needs a running flag. Some payoffs require more history; determine this from the payoff definition.

A discrete barrier check can miss crossings between grid points. Avoid claiming continuous-monitoring accuracy solely because a simulation is fast or because GBM grid-time updates are exact.

## 12. Reference implementation

Save as `simulation_performance.py`. The standard-library example computes streaming mean and variance of a three-state payoff and times a run. It keeps no payoff list; its model and benchmark are deliberately simple.

~~~python
import math
import random
import time
import unittest
from dataclasses import dataclass

def finite(x):
    return type(x) in (int,float) and math.isfinite(x)

@dataclass
class RunningStats:
    count: int = 0
    mean: float = 0.0
    m2: float = 0.0

    def update(self, x):
        if not finite(x):
            raise ValueError("finite observation required")
        self.count += 1
        delta = x-self.mean
        self.mean += delta/self.count
        self.m2 += delta*(x-self.mean)
        if not math.isfinite(self.mean) or not math.isfinite(self.m2):
            raise ValueError("nonfinite running statistics")

    def sample_variance(self):
        if self.count < 2:
            raise ValueError("at least two observations required")
        return self.m2/(self.count-1)

    def standard_error(self):
        return math.sqrt(self.sample_variance()/self.count)

def streaming_run(count, seed):
    if type(count) is not int or count < 2 or type(seed) is not int:
        raise ValueError("count >= 2 and integer seed required")
    rng=random.Random(seed)
    stats=RunningStats()
    for _ in range(count):
        u=rng.random()
        stats.update(80.0 if u < .25 else (100.0 if u < .75 else 120.0))
    return stats

def run_batches(count, batch_size, seed):
    if type(count) is not int or count < 2 or type(batch_size) is not int or batch_size < 1:
        raise ValueError("count >= 2 and positive integer batch size required")
    if type(seed) is not int:
        raise ValueError("integer seed required")
    rng=random.Random(seed)
    stats=RunningStats()
    remaining=count
    while remaining:
        size=min(batch_size,remaining)
        for _ in range(size):
            u=rng.random()
            stats.update(80.0 if u < .25 else (100.0 if u < .75 else 120.0))
        remaining -= size
    return stats

def array_bytes(paths, observations_per_path, bytes_per_element):
    if any(type(x) is not int or x < 1
           for x in (paths,observations_per_path,bytes_per_element)):
        raise ValueError("positive integers required")
    return paths*observations_per_path*bytes_per_element

class PerformanceTests(unittest.TestCase):
    def test_mean(self):
        stats=RunningStats()
        for x in [80,100,120]: stats.update(x)
        self.assertAlmostEqual(stats.mean,100)
    def test_variance(self):
        stats=RunningStats()
        for x in [80,100,120]: stats.update(x)
        self.assertAlmostEqual(stats.sample_variance(),400)
    def test_standard_error(self):
        stats=RunningStats()
        for x in [80,100,120]: stats.update(x)
        self.assertAlmostEqual(stats.standard_error(),20/math.sqrt(3))
    def test_constant(self):
        stats=RunningStats()
        for x in [100,100]: stats.update(x)
        self.assertEqual(stats.sample_variance(),0)
    def test_replay(self):
        self.assertEqual(streaming_run(100,42),streaming_run(100,42))
    def test_batches_match_stream_order(self):
        self.assertEqual(streaming_run(101,42),run_batches(101,10,42))
    def test_array_size(self):
        self.assertEqual(array_bytes(100000,253,8),202400000)
    def test_short_sample(self):
        with self.assertRaises(ValueError): RunningStats().sample_variance()
    def test_nonfinite(self):
        with self.assertRaises(ValueError): RunningStats().update(float("nan"))
    def test_bad_count(self):
        with self.assertRaises(ValueError): streaming_run(1,42)
    def test_bad_batch(self):
        with self.assertRaises(ValueError): run_batches(10,0,42)
    def test_bad_dimensions(self):
        with self.assertRaises(ValueError): array_bytes(0,10,8)

if __name__ == "__main__":
    started=time.perf_counter()
    result=streaming_run(10000,42)
    elapsed=time.perf_counter()-started
    print("count:",result.count,"mean:",result.mean,
          "standard error:",result.standard_error(),"seconds:",elapsed)
    unittest.main(verbosity=2)
~~~

The two functions intentionally use the same generator and draw order, so they can be compared exactly in a compatible environment. This property should not be assumed for a vectorized or parallel rewrite. The timing is a single illustrative measurement, not a benchmark result.

## 13. Optional NumPy batching pattern

~~~python
import numpy as np

rng = np.random.default_rng(42)
remaining = 100_000
batch_size = 10_000
total = 0.0
while remaining:
    size = min(batch_size, remaining)
    u = rng.random(size)
    payoff = np.where(u < .25, 80.0, np.where(u < .75, 100.0, 120.0))
    total += payoff.sum(dtype=np.float64)
    remaining -= size
print("mean:", total / 100_000)
~~~

This estimates the same model mean, but it does not compute a standard error and is not expected to reproduce the standard-library sequence. `np.where` and intermediate arrays allocate memory; measure actual peak usage. Record NumPy version and configuration.

## 16. Troubleshooting

| Symptom | Possible cause | Next step |
|---|---|---|
| Out-of-memory error | Full paths and temporary arrays too large | Estimate peak memory and batch |
| Vectorized code is slower | Small workload or allocation overhead | Profile and benchmark equivalent operations |
| Batched results differ slightly | Draw or reduction order changed | Compare generator, ordering and tolerances |
| Identical worker outputs | Duplicate seed or state | Inspect documented stream spawning |
| Small SE but wrong result | Model or implementation bias | Compare independent benchmark |
| Timing varies widely | Shared resources or initialization | Repeat, report range and environment |
