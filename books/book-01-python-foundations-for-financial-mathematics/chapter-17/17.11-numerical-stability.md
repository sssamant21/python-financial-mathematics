## Learning objectives

Explain floating-point limitations; distinguish rounding error, truncation error, conditioning, and algorithmic stability; identify catastrophic cancellation, overflow, and underflow; use stable numerical primitives; evaluate root-finding, optimization, integration, and yield-curve calculations; and establish validation tolerances and audit controls.

## 1. Why numerical stability matters in finance

A formula can be mathematically correct and still produce a misleading result on a computer. Financial calculations frequently combine large and small amounts, discount distant cash flows, solve sensitive roots, optimize nearly singular covariance matrices, and estimate tiny probabilities.

Numerical stability is not merely a coding concern: an inaccurate price, yield, risk estimate, or hedge sensitivity can affect a real decision.

## 2. Floating-point representation

Most Python `float` values use IEEE-754 binary64 representation. Many decimal fractions, including 0.1, cannot be represented exactly in binary.

Near 1, the spacing between adjacent binary64 values is approximately:

**ε=2⁻⁵²≈2.220446049250313×10⁻¹⁶**.

Machine epsilon is a scale indicator, not a universal upper bound on the error of a full numerical calculation.

```python
import sys
print(sys.float_info.epsilon)
print(0.1 + 0.2 == 0.3)
```

## 3. Rounding error and accumulation

Each floating-point operation can introduce rounding. Repeated operations can accumulate error, especially when magnitudes differ greatly.

Floating-point addition is not associative:

**(a+b)+c** need not equal **a+(b+c)** numerically.

For example, adding 1 to 10¹⁶ can lose the unit increment in binary64. Summing many cash flows in an unfortunate order can amplify such effects.

## 4. Stable summation

Python's `math.fsum` uses an accurate summation strategy and often reduces error when summing numbers with widely varying magnitudes.

```python
import math
values = [1e16, 1.0, -1e16]
print(sum(values))
print(math.fsum(values))
```

For a discounted cash-flow model, prefer accurate summation when cash flows are numerous or cancellation is likely.

## 5. Catastrophic cancellation

Cancellation occurs when subtracting nearly equal numbers, causing leading significant digits to disappear.

For tiny x, directly evaluating:

**(1+x)−1**

can return zero even when x is nonzero.

This is particularly dangerous when a formula subtracts two values close to 1, such as discount factors for very short periods.

## 6. Stable logarithms: log1p

For small x, use:

**log1p(x)=ln(1+x)**,

which is designed to retain accuracy near zero.

For a small simple return r, the corresponding log return is:

**ln(1+r)=log1p(r)**.

When prices P₀ and P₁ are close, one implementation is:

```python
import math
log_return = math.log1p((P1 - P0) / P0)
```

This requires positive prices and a valid return greater than −1.

## 7. Stable exponentials: expm1

For small x, use:

**expm1(x)=exp(x)−1**.

The expression **1−exp(−x)** can be evaluated as:

**−expm1(−x)**.

This matters in discounting and annuity calculations where x=rT is very small.

## 8. Worked example — continuous annuity

A constant continuous cash-flow intensity C over [0,T], discounted at continuously compounded rate r, has present value:

**PV=C(1−e^(−rT))/r**, for r≠0.

A numerically stable implementation uses:

**PV=C[−expm1(−rT)]/r**.

At r=0, the continuous limit is:

**PV=CT**.

For C=100, T=2, and r=.05:

**PV=100[−expm1(−.1)]/.05≈190.325**.

For extremely small r, the stable expression avoids subtracting nearly equal floating-point values.

## 9. Stable compounding and discounting

A compound-growth factor for n periods at rate r is:

**(1+r)ⁿ=exp[n log1p(r)]**, provided r>−1.

Similarly:

**(1+r)⁻ⁿ=exp[−n log1p(r)]**.

These forms can improve accuracy for small rates and large period counts. They do not eliminate overflow, underflow, or invalid-input risks.

## 10. Overflow and underflow

**Overflow** occurs when a computed magnitude exceeds the representable range.

**Underflow** occurs when a nonzero value becomes too small to represent at normal precision or rounds to zero.

For example, exp(1000) cannot be represented as a finite binary64 float, while exp(−1000) may underflow to zero.

A zero discount factor produced by underflow is not necessarily evidence of a genuinely zero economic value; it may indicate the computation needs a log-domain representation.

## 11. Log-domain computation

When summing exponentials of large values, compute:

**log(Σᵢexp(aᵢ))=m+log(Σᵢexp(aᵢ−m))**,

where **m=max(aᵢ)**.

This is the log-sum-exp transformation.

For aᵢ=1000 and 1000, the result is:

**1000+ln 2**,

without evaluating exp(1000) directly.

Log-domain methods also appear in likelihood estimation, probability tails, and certain pricing calculations.

## 12. Stable quadratic formula

The usual quadratic formula:

**x=[−b±√(b²−4ac)]/(2a)**

can lose accuracy when **−b** and **√Δ** nearly cancel.

A more stable real-root construction is:

**q=−(b+sign(b)√Δ)/2**,

then:

**x₁=q/a**, **x₂=c/q**,

with separate handling for repeated or degenerate roots.

This demonstrates a general lesson: algebraically equivalent formulas may have very different numerical behavior.

## 13. Conditioning versus stability

**Conditioning** describes sensitivity of the mathematical problem to small input changes.

**Stability** describes whether an algorithm amplifies errors unnecessarily relative to that problem.

A well-implemented stable algorithm cannot make an intrinsically ill-conditioned problem well-conditioned.

For example, if a yield-to-maturity root lies where the price derivative with respect to yield is very small, a tiny price perturbation may imply a large yield change.

## 14. Root-finding stability

For a root f(x*)=0, a first-order sensitivity approximation is:

**δx≈−δf/f′(x*)**, when f′(x*)≠0.

If |f′(x*)| is small, the root can be sensitive.

Use brackets when possible, check function signs, inspect residuals, and distinguish a small function residual from an accurate root estimate.

For nonconventional cash flows, multiple IRRs may exist; a single root result is not proof of uniqueness.

## 15. Numerical differentiation

A forward finite difference is:

**f′(x)≈[f(x+h)−f(x)]/h**.

Large h creates truncation error; very small h amplifies cancellation and roundoff.

A central difference often reduces truncation error:

**f′(x)≈[f(x+h)−f(x−h)]/(2h)**.

Derivative validation should use several step sizes and, when appropriate, analytic or automatic differentiation benchmarks.

## 16. Numerical integration stability

Increasing the number of quadrature panels reduces discretization error only up to a point.

Eventually floating-point error and cancellation can limit further improvement.

Compare successive refinements and known analytic integrals. For difficult functions, adaptive quadrature or variable transformations may outperform a brute-force fixed grid.

## 17. Portfolio covariance and conditioning

A covariance matrix with eigenvalues close to zero may be nearly singular.

Small changes to estimated correlations can produce large changes in unconstrained optimized weights.

Prefer numerically stable linear solvers rather than explicitly computing matrix inverses. Consider regularization, shrinkage, bounds, and sensitivity testing, while clearly documenting how these choices change the model.

## 18. Yield curves and discount factors

For continuously compounded zero rate z(t):

**D(t)=exp(−z(t)t)**.

Log discount factors are:

**ln D(t)=−z(t)t**.

Working in log-discount space can improve stability and makes interval forward rates straightforward:

**f(t₁,t₂)=[ln D(t₁)−ln D(t₂)]/(t₂−t₁)**.

Very short tenor intervals can still be ill-conditioned because the denominator is small.

## 19. Probability tails

For large positive z, computing a standard-normal upper-tail probability as:

**1−Φ(z)**

can lose accuracy when Φ(z) rounds to 1.

Use a specialized survival function where available, such as `scipy.stats.norm.sf(z)`.

This is particularly important in rare-event risk, tail probabilities, and stress calculations.

## 20. Scaling optimization problems

An optimizer may struggle when one objective term is around 10⁻⁶ and another is around 10⁹, or when constraint residuals use incompatible units.

Scale variables, objective terms, and constraints consistently.

For example, use portfolio returns as decimals rather than mixing percent and basis points, and ensure transaction-cost coefficients use matching units.

Scaling changes numerical behavior; it should not silently change economic priorities.

## 21. Absolute, relative, and mixed tolerances

An absolute error test is:

**|x−x_ref|≤atol**.

A relative error test compares error with a meaningful scale. A combined criterion is:

**|x−x_ref|≤atol+rtol|x_ref|**.

Near zero, relative error alone is unreliable.

A tolerance must reflect the financial quantity: a one-cent pricing threshold differs from a 1-basis-point yield threshold or a unitless optimization feasibility threshold.

## 22. Decimal arithmetic and financial reporting

Python's `decimal.Decimal` can represent specified decimal fractions exactly and is useful for certain accounting and settlement requirements.

It does not automatically solve every numerical analysis problem. Transcendental functions, matrix operations, numerical solvers, and financial model assumptions still require appropriate precision and validation.

Avoid rounding every intermediate result merely because the final amount is displayed to two decimal places.

## 23. Reproducibility and platform effects

Numerical outputs may vary slightly across hardware, library versions, BLAS implementations, compiler optimizations, and solver tolerances.

A production numerical run should record software versions, inputs, algorithm parameters, units, stopping criteria, residuals, and a deterministic reference benchmark where possible.

Do not require bit-for-bit equality across platforms unless the computational environment is controlled accordingly.

## 24. SciPy and NumPy stability illustration

```python
import numpy as np
from scipy.special import logsumexp
from scipy.stats import norm

values = np.array([1000.0, 1000.0])
assert np.isfinite(logsumexp(values))
assert abs(logsumexp(values) - (1000.0 + np.log(2.0))) < 1e-10

tail = norm.sf(8.0)
assert tail > 0.0

A = np.array([[4.0, 1.0], [1.0, 3.0]])
b = np.array([1.0, 2.0])
x = np.linalg.solve(A, b)
assert np.linalg.norm(A @ x - b) < 1e-12
```

This snippet requires NumPy and SciPy. A small linear-system residual is useful, but interpreting solution accuracy also requires attention to matrix conditioning.

## 25. Complete standard-library reference implementation

Save as `numerical_stability.py`. The reference includes stable discounting, continuous annuities, log returns, compounding, summation, quadratic roots, log-sum-exp, NPV, residual checks, and **12 reference unit tests**.

```python
"""17.11 Numerical stability: reference functions and tests."""
import math
import sys
import unittest

def finite(x):
    return type(x) in (int, float) and math.isfinite(x)

def stable_discount(rate, tenor):
    if not finite(rate) or not finite(tenor) or tenor<0:
        raise ValueError("finite rate and nonnegative tenor required")
    return math.exp(-rate*tenor)

def continuous_annuity(rate, tenor, intensity):
    if not all(finite(x) for x in (rate,tenor,intensity)) or tenor<0:
        raise ValueError("invalid annuity inputs")
    if rate==0:return intensity*tenor
    return intensity*(-math.expm1(-rate*tenor))/rate

def stable_log_return(start,end):
    if not all(finite(x) for x in (start,end)) or min(start,end)<=0:
        raise ValueError("positive finite prices required")
    return math.log1p((end-start)/start)

def stable_compound(small_rate, periods):
    if not finite(small_rate) or small_rate<=-1 or type(periods) is not int or periods<0:
        raise ValueError("invalid compound inputs")
    return math.exp(periods*math.log1p(small_rate))

def stable_sum(values):
    vals=list(values)
    if any(not finite(v) for v in vals):raise ValueError("nonfinite sum term")
    return math.fsum(vals)

def quadratic_real_roots(a,b,c):
    if not all(finite(x) for x in (a,b,c)) or a==0:
        raise ValueError("finite nonzero quadratic coefficient required")
    discriminant=b*b-4*a*c
    if not math.isfinite(discriminant) or discriminant<0:
        raise ValueError("no finite real roots")
    root=math.sqrt(discriminant)
    if root==0:return (-b/(2*a),-b/(2*a))
    q=-.5*(b+math.copysign(root,b))
    if q==0:raise ValueError("degenerate root computation")
    return (q/a,c/q)

def log_sum_exp(log_values):
    vals=list(log_values)
    if not vals or any(not finite(v) for v in vals):
        raise ValueError("finite nonempty log values required")
    m=max(vals)
    return m+math.log(math.fsum(math.exp(v-m) for v in vals))

def npv(cashflows,rate):
    vals=list(cashflows)
    if not finite(rate) or rate<=-1 or any(not finite(c) for c in vals):
        raise ValueError("invalid NPV inputs")
    return math.fsum(c*math.exp(-t*math.log1p(rate)) for t,c in enumerate(vals))

def residual(f,x):
    y=f(x)
    if not finite(y):raise ValueError("nonfinite residual")
    return abs(y)

class StabilityTests(unittest.TestCase):
    def test_01_zero_annuity(self):self.assertEqual(continuous_annuity(0,2,100),200)
    def test_02_small_annuity(self):self.assertAlmostEqual(continuous_annuity(1e-12,2,100),200,places=8)
    def test_03_discount(self):self.assertAlmostEqual(stable_discount(.05,2),math.exp(-.1))
    def test_04_log_return(self):self.assertAlmostEqual(stable_log_return(100,101),math.log(1.01))
    def test_05_compound(self):self.assertAlmostEqual(stable_compound(.01,12),1.01**12)
    def test_06_fsum(self):self.assertEqual(stable_sum([1e16,1,-1e16]),1)
    def test_07_roots(self):
        roots=quadratic_real_roots(1,-1e8,1)
        self.assertAlmostEqual(min(roots),1e-8,places=15)
    def test_08_logsumexp(self):self.assertAlmostEqual(log_sum_exp([1000,1000]),1000+math.log(2))
    def test_09_npv(self):self.assertAlmostEqual(npv([-100,110],.1),0,places=12)
    def test_10_residual(self):self.assertEqual(residual(lambda x:x*x-4,2),0)
    def test_11_bad_rate(self):
        with self.assertRaises(ValueError):npv([1],-1)
    def test_12_bad_input(self):
        with self.assertRaises(ValueError):stable_sum([float("nan")])

if __name__=="__main__":
    print("epsilon:",sys.float_info.epsilon)
    print("annuity:",continuous_annuity(1e-12,2,100))
    print("compensated sum:",stable_sum([1e16,1,-1e16]))
    unittest.main(verbosity=2)
```


The tests are provided as reference material but have not been independently executed during this publication step.

## 28. Troubleshooting

| Symptom | Likely cause | Corrective action |
|---|---|---|
| Small cash-flow difference disappears | Catastrophic cancellation | Reformulate with stable primitives |
| Discount factor rounds to zero | Underflow | Work in log domain |
| Exponential calculation overflows | Large positive exponent | Use log-sum-exp or scaled representation |
| Portfolio weights change dramatically | Ill-conditioned covariance | Review eigenvalues, estimation, regularization |
| Solver success but inaccurate result | Poor scaling or misleading residual | Independently assess conditioning and feasibility |
| Normal tail probability is zero | Subtraction from near-one CDF | Use survival function |
| Numerical derivative unstable | Step size too small or too large | Compare multiple steps and analytic benchmark |
| Different machines yield last-digit changes | Floating-point/platform differences | Use tolerance-based comparisons |
| Runtime evidence absent | Comprehensive QA deferred | Execute tests and retain artifacts during QA |
