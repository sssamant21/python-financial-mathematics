Exact source helpers/probes, supplemental file-bound caller/orchestration and design-only update/platform/analysis claims are distinguished per prompt.

## 5.8-E1 — SOURCE_HELPERS+SUPPLEMENT

**Prompt:** Remove the unit fixture's requirement line and observe hash-mode dependency rejection in a fresh environment.

Keep report1.0.0 exact pin/hash but omit unit line. In a fresh runtime, original hash-mode install_arguments rejects missing transitive unit hash; raw diagnostic and absent-import probe retained. Retry complete direct/transitive pin+hash closure with original approved wheel bytes; install, pip check and original known/invalid behavior pass. No --no-deps bypass.

## 5.8-E2 — SOURCE_HELPERS+SUPPLEMENT

**Prompt:** Replace the approved report hash with an incorrect digest. Verify rejection without relabeling the artifact as approved.

Second fresh runtime uses deliberately incorrect all-zero report digest in a separate wrong-report-hash file; pip rejects against actual bytes. Original approved wheel and complete specification unchanged. Retry original complete spec succeeds. Store wrong spec/error as negative evidence rather than relabeling its hash as approval.

## 5.8-E3 — SUPPLEMENTAL_EVIDENCE

**Prompt:** Add an application-source digest and input-file digest to a durable evidence design.

Retain concrete evidence-bundle with approved original wheels/spec, consumed input.txt12.50, application_probe.py and manifest SHA256 links. New file-bound caller uses original installed fixture API and original behavior assertions, reads input bytes once then decodes, and reports consumed input/application digests. Unchanged original BEHAVIOR separately executed. Manifest records manuscript/code/orchestration hashes, runtime/platform and selected results; this is scoped provenance, not authorship or model attestation.

## 5.8-E4 — DESIGN

**Prompt:** Explain why pinning versions does not establish rounding, currency units, or observation dates.

Package pins constrain version labels, not economic units, signed cash-flow perspective, precision/rounding stage, quote units, valuation time, calendars or data vintage. Exact code/input/policy snapshots and reviewed financial expectations are separate requirements. This fixture only returns validated instrument units, with no rounding/valuation calculation.

## 5.8-E5 — SOURCE+COMPARISON_POLICY

**Prompt:** Define which evidence fields should match across two recreations and which may legitimately differ.

Same approved wheel/spec/source/input hashes, installed fixture versions, independent expected instrument_units12.50 and selected source/input digest results must match. Runtime prefix/executable/tool-location strings legitimately differ and are checked as different. Full evidence JSON need not be byte-equal; base runtime/platform must be recorded and compared against supported target policy. Two independently checked known outputs are required, not only pairwise agreement.

## 5.8-E6 — DESIGN

**Prompt:** Describe how platform-specific compiled wheels would change the approved artifact set.

Compiled-wheel approval needs target Python implementation/version/ABI, OS/architecture and compatible wheel tags plus each platform-specific artifact/digest and relevant native/toolchain/runtime-library records. A pure-Python py3-none-any fixture does not establish compiled-library portability. Retain target-appropriate artifact sets; source-build fallback requires separately approved build inputs/checks. No compiled/platform matrix run.

## 5.8-E7 — DESIGN+BASELINE

**Prompt:** Design a dependency-update regression using known-value and invalid-input checks.

Dependency-update plan: preserve old closure/artifacts, create candidate environment with reviewed new versions/digests, run pip check plus installed-origin/API/known-zero/fraction/invalid-type/nonfinite/negative checks, compare selected numeric/semantic invariants and explain changes before replacing old baseline. Original regression code runs against both current1.0.0 recreations here; no candidate external version or promotion was tested. Version/hash equality alone does not approve a changed financial result.

## 5.8-E8 — DESIGN

**Prompt:** Explain the difference between reproducing an installation, reproducing a build, and reproducing a financial analysis.

Installation repetition uses already-selected artifact bytes in fresh runtimes; build reproduction regenerates artifacts from declared sources/toolchain and must specify byte/semantic criteria; financial-analysis reproduction additionally binds consumed data, source, parameters, assumptions, units/numeric policy and interpretation. This run supports same-runtime installation/selected behavior only. Fixture regeneration may change ZIP timestamps; no bit-reproducible build or independent financial acceptance claimed.
